# The Same Spec, Ten Runs: What Justifies Making an Instruction a Team Default?

> **TL;DR** — A team adds a pre-submission self-check to an agent's brief, and the next patch passes acceptance. Does that self-check deserve a place in the default template for every job of the same kind? This piece first separates three questions: has what should happen already been decided, does this particular program do it, and would the added self-check make later deliveries better? Each needs different evidence. If a requirement is undecided, find whoever has the authority to decide; if the way we check is wrong, fix the basis for judging first. Neither of those jobs has to wait for a comparison of methods. What genuinely needs a comparison is whether, with the requirements held fixed, an extra self-check improves delivery, and whether the improvement is enough to offset the added cost and human effort. The series uses an event-processing tool from my own repo as its study: four briefs each generated ten programs, and all forty passed 103 checks; that result is still not enough to say which brief is better. The piece first explains why the study was worth doing, then uses a CSV export example to walk you through deciding whether the work in front of you needs a requirement filled in, an acceptance check repaired, or a separate comparison. Finally it turns one self-check into a proposal that can be reviewed, spelling out when it can only be tried on a small scale, when there is reason to adopt it as a default, and who is responsible for maintaining and re-examining it.

> Series: **Overview (this piece)** → Part 1, Specification (coming soon) → Part 2, Contract (coming soon) → Part 3, Variance (coming soon). Chinese edition: [同一份規格，跑十次：我們憑什麼把一種交代變成團隊預設？](https://medium.com/p/6986ee29219e).

## 1. After the workshop gap, the question turned to the brief

At the pattern-language-driven development workshop in August 2026, I recorded an observation that I have returned to many times since. Method A produced 25 files, and all 5 tests passed; yet when I checked it item by item against the sixteen-item compliance checklist, only ten items passed and the other six had not been done. Among the missing pieces was `EventSourcedAggregate`, the core object the requirements called for, and the path that rebuilds state from events was never executed.

"Rebuilding state from events" sounds abstract, so take a bank account as an illustration: after storing a record of depositing 100 and another of withdrawing 30, the system should be able to recompute a balance of 70. That is only an example to explain the concept, not the workshop's actual exercise; the workshop's gap was that the rebuild the requirements demanded was simply never performed. That observation is a single case (N=1), and it is not part of this series' formal study. What it reminded me of, in the Green Is Not Done series, is that between "all tests green" and "meets the requirements" there can be a gap of six whole requirements.

Green Is Not Done began by asking how to accept an artifact, then followed that question into who is accountable for review and the reliability evidence a class of tasks has to accumulate before authorization can be widened. After an agent hands in a patch, the team has to confirm that the tests have not weakened a requirement they were supposed to enforce, that the approval record can be traced to a responsible person, and that recurring problems get carried back into the rules and the acceptance checks. All of that work eventually leads back to the same starting point: the next time we hand out a task, how do we intend to brief it?

Starting from that gap, a natural next step is to go back and change the brief: write the missing core object into the spec, list the rebuild path as a mandatory item, and add a pre-submission self-check. If the next artifact really does pass, the change looks like a success; and then someone may well propose that, since it worked, the paragraph should go into the default template for every task of the same kind.

This series follows the previous one's question and looks closely at that one step, changing the brief. Which choices did that paragraph record? Did it really improve delivery, or did it only fill in a requirement that had never been stated clearly? Once it enters the default template, it travels with every assignment, and it becomes text that someone has to maintain for a long time. That is where this piece's title comes from: after one instruction change succeeds, what justifies making it the team's default?

To answer that, this piece first separates three things: making a requirements decision, accepting this particular program, and comparing ways of briefing. It then uses the formal study and the CSV example to test whether that separation is useful. Only at the end does it turn to the proposal and the conditions for adoption: what we need to know is not only what numbers the study produced, but whether those numbers can support the team's next choice.

## 2. After one success, who bears the cost of a default?

What follows is a hypothetical scenario set up for explanation, not a real meeting. A team asks an agent to fix the input handling of a small Python tool, and the person reviewing it finds that when the program receives a certain kind of badly formed input, it treats it as normal data. The team adds a pre-submission self-check to the task description, listing several input cases the agent must check one by one before submitting. After the second delivery passes acceptance, someone proposes putting that self-check into the default brief for every Python tool patch.

From here on, each program awaiting acceptance is called a candidate: a solution that might be adopted, not one that has already qualified. The person who reviews a candidate is the reviewer; the person with the authority to decide the requirements, and the responsibility for that decision, is the requirements owner. The two are sometimes the same person, but "did the program do it" and "what should it have done in the first place" remain different questions.

The proposal is reasonable, because it preserves a lesson learned once. The trouble is that "default" changes what the paragraph is for. Originally it belonged to a single task and could be set aside once the task ended; as a default it becomes standing guidance in the repo or the template, goes out with every assignment, and every reviewer has to judge whether the candidate followed it.

When Birgitta Böckeler analyzed several tools that let a spec guide development, she distinguished two arrangements: some specs are written only before a piece of work begins, while others keep being maintained as later changes arrive; she also separated a spec for a single task from a background document used across many pieces of work ([Böckeler, 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). Applied to this piece's scenario, my worry is this: if a standing document does not say what it applies to and who maintains it, a choice made for one patch can become a constraint on all the work that follows. Moving a self-check into the default template therefore means answering those two questions afresh.

Once the paragraph changes status, the cost lands in three places. The first is attention. Anthropic's official best-practice guidance for Claude Code warns that an overlong CLAUDE.md can let important instructions drown in noise, and recommends observing whether a change actually altered behavior ([Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)). That is vendor practice advice, not an effect study, but it points at one thing: the more default text there is, the more each paragraph needs to be able to state its own purpose. The second is review. The reviewer has one more set of items to check; and if the self-check conflicts with a particular task's requirements, someone has to rule on which side wins. The third is maintenance. When the requirements change, the paragraph will not necessarily be updated with them, and stale guidance keeps shaping every output.

The more fundamental problem is that the second delivery passing has at least three explanations, and they point to different next steps.

The first explanation is that the paragraph actually made a decision for the team that nobody had made before. If the self-check says "this kind of input must be rejected" and the original requirements said nothing about it, then the thing that did the work was that decision. It belongs back in the requirements, confirmed by whoever has the authority to decide, and it does not have to exist in the form of a self-check at all. Once confirmed, the required behavior and the compatibility rules can be written straight into the team's briefs and acceptance checks; the reason for adopting them is an obligation the team already carries, and these obligations apply without waiting for a comparison of effects.

The second explanation is that this particular candidate happened to get it right, or that acceptance happened not to see its other problems. From a single delivery you cannot tell whether the method improved or this one run simply succeeded; and if acceptance can only see a few ways of being wrong, passing only means those particular faults did not show up.

Only the third is the effect the self-check proposal wants to claim: with the requirements unchanged, changing only how the task is briefed makes later deliveries reliably better. If the team wants to make an optional self-check a default on that ground, it needs to design the comparison in advance and then see whether the result supports the investment. The effect threshold discussed later applies only to this kind of claim; it is not used to decide whether a required rule that already stands should still be followed.

In "[Agentic Engineering, Part 2 — The Harness Blueprint: Making Your System Legible to Agents](https://medium.com/p/3facc281f633)" I made two recommendations: before changing the background information and instructions an agent receives, name the concrete outcome you want to improve; after changing them, re-run a representative set of tasks. That piece called the latter golden tasks, a set of work the team can check against again and again. This piece adds one step before that: before re-running anything, work out which of the explanations the success in front of you belongs to.

If the team worries that answering "is it worth making a default" means an expensive study first, it can start by checking the first two situations. Sometimes finding the right owner, or fixing how right and wrong are judged, is all the task in front of you needs. The next section starts from the spec itself: which decisions can a document make on the team's behalf, and which things still have to be verified separately?

## 3. Book anchor: Lamport's blueprints preserve the choices already made

To explain what a spec actually does, I want to borrow a short essay. Leslie Lamport is a distributed-systems researcher and the designer of the specification language TLA+. In 2013 he wrote "Why We Should Build Software Like We Build Houses," arguing that we should draw a blueprint before we write code. The version read here is the three-page one preserved on the author's website, dated 24 January 2013. The version and the scope of what was consulted are listed in the References at the end.

The essay makes three points that bear directly on this piece's problem. First, writing a spec forces the author to say what the program is supposed to do before modifying the code. Many of the places we have not thought through only surface when we try to write them down. Second, a spec pulls the knowledge needed to use an interface out of the implementation and into a description that can be maintained, so that a caller does not have to read the code to call it correctly. Third, how precise the description needs to be depends on the problem: simple behavior can be stated in ordinary prose, and only the subtle or critical parts justify more precise methods and tools.

He also states his own limit: writing specs cannot guarantee that programs will never crash, and eliminating coding bugs still requires other methods. The essay expresses his engineering position and experience; it is not a comparative trial, and the time it reports him spending on modifying code cannot be converted into a return on investment for writing specs.

I map those three points and that limit onto this piece's three layers of questions. The most direct job of a spec is to preserve the choices the team has already made and to bring the choices not yet made to the surface; that corresponds to the first layer, "have the requirements been decided?" Lamport says plainly that a spec cannot guarantee the program is free of errors and that other methods are still needed, so the second layer, "did this particular candidate do it?", needs its own acceptance. Whether one way of writing specs deserves to become a team default is something his essay does not address and never set out to answer; that is the third layer, and it needs a comparison.

From the second point I have distilled a question that can be used directly. It is my inference, not a template from Lamport's text: **without looking at the implementation, relying on this description alone, can a program that calls this tool know how to use it, and know when not to trust its output?** Wherever the answer is missing, record it as an open question and hand it to someone who can decide; there is no need to rush to make the document longer.

Take "make the input parser more robust" as an example. A parser turns the text it receives into data the program can work with, for example by reading one line of a message and extracting its contents. "More robust" could mean skipping damaged lines, failing explicitly on an error, or treating an abnormal value as no message at all. Those three choices give the tool's users different results. The behaviors a spec selects and requires the implementation to honor are what this piece calls the contract; it is an engineering agreement about behavior. A later maintainer who sees only the words "type fix" still has no way of knowing which of the three the team chose.

## 4. Three layers of questions: first establish which kind of evidence is missing

Return to the self-check from section 2. To judge whether it should become a default, I would ask three questions in order.

The first layer is the requirements decision: for a given input, has anyone ever decided what behavior counts as correct? The second is acceptance of a specific candidate: did this artifact implement the behavior that was decided, and can our yardstick see where it went wrong? The third is the comparison of delivery methods: when this way of briefing is used repeatedly across a representative batch of work, are the effect, the cost and the human effort all worth it?

The second layer needs a basis for judgment. If the requirements have decided that a `null` date produces an empty field, the checking tool can compare results against that; if the requirements have not decided, the checking tool has no authority to pick an answer itself. This basis for judging a result right or wrong is called the **oracle**. It might be an expected value derived from the spec, a reference program, the output of an older version, or human judgment, and each has blind spots.

Separating the oracle from the automated acceptance program also makes what follows easier to read. The oracle says what counts as correct; the program that runs the checks and issues the verdict is what this piece calls the grader. The oracle and the grader together are the yardstick this piece keeps referring to. Think of an answer key and the marking procedure: the key can be right and the marking still wrong, and faithful marking can still grade against a wrong key. The table below sets the three layers side by side; read across each row, comparing the basis for judgment with the common mix-up, to establish which step needs more evidence. The positive and negative controls mentioned in the table are a verified legitimate version that should pass and a known faulty version that should fail.

The most important use of this table is to see that the evidence for one layer cannot answer for another. A neatly formatted spec does not by itself decide whether an empty date should produce an empty field or be rejected; a candidate that passed acceptance does not prove that the brief that produced it is better; and even a rigorously designed method comparison cannot supply a requirement nobody ever decided. Worse is getting the order backwards: the first layer still has a hole, and the team starts comparing documents. What the comparison then reflects is only which document happened to guess the preference the owner never said out loud.

The second layer has another aspect that is easy to overlook: a contract often deliberately leaves implementation freedom. To reject a wrong type, for instance, one program might concentrate the check in a small shared function (a helper), while another writes it directly into the branches that handle each kind of input. As long as the external behavior meets the requirements, both can qualify. Demanding that every generated program look the same is not the same as raising quality.

If the team genuinely needs an architectural constraint, the team has to record where that constraint comes from and provide a matching acceptance check; "it does not look like last time" cannot be used after the fact as a reason to send work back. So a good yardstick has to do two things at once: reject known faults, and accept different implementations that meet the contract. The positive and negative controls, prepared in advance and verified, are used from here on to confirm that the check does not get the two categories backwards.

The requirements owner confirms the null-value policy; the QA owner fixes the yardstick and then re-scores the artifacts that already exist with the new version. After that, the candidate goes through the team's usual review and approval as before, and the approval responsibility does not shift because a gap was filled along the way. ## 5. Example Mapping: a model cannot fill in a policy nobody has decided

The first layer's gap is the easiest to skip past, because a line like "handle the formatting properly" can sound like a complete brief while leaving the handling of empty values undecided. Example Mapping, which Matt Wynne introduced in 2015, exists precisely to find this kind of gap through concrete examples. Wynne was leading the Cucumber project at the time; the method splits a discussion into four kinds of card: the work to be done, the known rules, concrete examples, and questions nobody in the room can answer on the spot.

For instance, "export the date" is the work; "when a date is present, output it in the specified format" is a rule; one record that carries a date is an example; and "what if there is no date?" may still be a question. The examples let everyone check that they understand the rules the same way, and the question cards record the knowledge or decisions still missing. Wynne also explains that the discussion is for a shared understanding of what done means, and need not be written up on the spot as complete Gherkin, the Given/When/Then format for describing scenarios ([Wynne, 2015](https://cucumber.io/blog/bdd/example-mapping-introduction/)).

What I value most is the question card. It marks "not yet decided," so the team knows whom to ask, instead of someone quietly filling it in.

Now apply the method to this series' parser. The tool reads events an agent emits; each event is one JSON record, one per line, a format called JSONL. Think of it as a work log arriving piece by piece: this line says "what the agent said," the next says "this turn is complete." The tool has to process each line as it arrives, which is what streaming means here.

Within it, a message event's `text` field holds the words the agent said. If the requirement says only "fix the type handling of text," then a missing field, `null`, an empty string, a whitespace-only `" "`, `false`, `0`, an array, an object and the number `123` all need an answer: does each count as no message, as a format error, or get printed as it is? And if it is printed, does that count as the agent having spoken?

The contract this series' study fixed in advance, R05, already answers these questions. R05 is the number of the fifth requirement, so that the spec, the examples and the checks can all point at the same rule. It specifies that a missing `text`, `null` and the empty string produce no output and do not count as a message; that a nonempty string is printed unchanged and the buffered content is sent to the output immediately (flushed), rather than letting the next program read it only after the whole batch of work ends; that whitespace-only strings are still valid; and that every other non-string value, including `false`, `0`, arrays and objects, is a format error, which the spec calls malformed and the rest of this piece calls malformed too.

Every one of those answers is a choice. Counting a whitespace-only string as an agent message is a decision; treating `false` as malformed rather than as no message is another. A different tool could choose a different contract; but in this repo, the behavior existing callers depend on already constitutes a compatibility obligation, and it cannot be changed at will just because the maintainer changed.

One limit needs stating here: all four documents in the formal study had these answers written in advance, so the study did not measure any benefit from requirements exploration. This piece's discussion of Example Mapping is an extension into engineering practice, not something the study observed.

Why can't an undecided policy be left for the model to fill in? It is easier to see in a table-export job. CSV is a text format with comma-separated fields; one record might hold a name, a date and a note in that order. Suppose a CSV export tool is to gain date-column formatting, the caller has already required that input row order and duplicate rows be preserved, but nobody has decided whether an empty date should produce an empty field or be rejected. Laid out as cards, it looks roughly like this. Read the third column first for the answers still missing, then the fourth for who answers. In the table, a record is one complete entry; LF and CRLF are two character sequences used to mark the end of a line, and the details come up in the actual output in section 8.

📌【在此插入表 table-02.png】

Even with the first row's question card unanswered, an agent may still deliver a program, because both policies fit the text known so far; it may also stop and ask. It might choose the empty field, or it might choose to reject. The trouble starts here: if the test author takes this run's output as the expected value, a guess gets written down as the baseline. The regression tests that recheck old behavior on every later change will then faithfully protect that guess; and when the owner finally decides the opposite, correcting it will look like a regression. The decision belongs to whoever has to answer for the result, and however well the model writes, it cannot make that decision for the team.

Question cards have limits too. Rules everyone already understands do not need examples manufactured for them. If the owner cannot decide for the moment, my recommendation is to confine the provisional assumption to a clearly scoped exploration or prototype, write down who is responsible for answering and when it will be revisited, and mark which tests depend on the assumption. Behavior that has not been decided cannot be entered into the formal contract and declared accepted. The point is to keep a provisional assumption provisional, and not to let a neatly formatted SPEC.md look as though it has made the decision on someone's behalf.

## 6. A narrow case: four briefs, forty candidates, all 103 checks passed

So far we have separated "the requirements are decided" from "the program did it." The series name, The Same Spec, Ten Runs, comes from a study that fixed those two layers first and then observed different briefs. The study was designed and executed in collaboration with AI agents; I set the direction and read the study design and the reports. The question it wanted to answer: when the same set of requirements is briefed to the model in different ways, do the resulting patches differ?

The task comes from my `medium-articles` repo. `research/scripts/codex_jsonl.py` is a single-file Python streaming tool that reads the JSONL events just introduced. It reports to the outside through three channels: stdout carries the normal content meant for the next program, stderr carries errors and diagnostics, and the exit code is a single number handed back at the end so the caller can decide what to do next. Exit 0 is usually taken as success, but it is only the program's own report; whether the content is actually correct still has to be checked.

The study fixed a starting version, the seed commit; every run began repairing the same old program. Two problems can be reproduced on that version. First, given the valid JSON `[]` or `null`, the program treats it as an object and calls `.get()` on it, and crashes. Second, if a message's `text` is the number `123` and a valid completion event follows, the program prints `123` as review content and exits 0. The tool has a real calling interface and real compatibility obligations, but the study does not claim it corresponds to any production incident.

The study prepared four briefs sharing the same seed and the same thirteen requirements, R01–R13. A0 has 936 English words; it is compact, but it already contains the full set of goals R01–R13, not just a one-line user story sketching the work. A has 1,655 words and expands each requirement in turn, with fixed outputs and tables, and some clauses also explain their reasons. B has 1,923 words: the full text of A plus a concentrated statement of rationale and six pre-submission self-check questions. C has 2,223 words: the full text of B plus an optional suggested implementation arrangement, which it calls a pattern. Word counts split on whitespace and include headings and code blocks but not the starting code. They are not token counts either; a token is the unit a model splits text into when it processes it, and that is a different count from English words split on whitespace.

The full text of the four English specs actually used can be read directly: [A0, compact](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/A0.md), [A, expanded](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/A.md), [B, A plus rationale and self-check](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/B.md), [C, B plus the optional implementation suggestion](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/C.md). The [reading guide to the full texts and line-by-line diffs](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/experiments/same-spec-ten-runs/SPECS.md) lays out a reading order and also points out one further difference in scope between A0 and A concerning command-line (CLI) options; beyond length, the wording still has to be checked for whether it changed a requirement.

The study calls the task description and starting code sent to the model together a packet, the bundled task input (the same archived system prompt accompanied every packet). Each of the four specs went into its own group's packet as the specification part. Each group has ten candidates; within a group, all ten runs received exactly the same packet text, while the four groups differ from one another. So the study did not run one prompt forty times. The forty generation slots, one per candidate, were scheduled in advance, with no retries, repairs, substitutions or samples added afterwards; only after all generation finished did the candidates enter the shared external acceptance.

Generation used `claude-opus-5-5` with the reasoning-effort setting at high. The model had no tools; it could only deliver a single file in one shot, and could not inspect the repo, ask questions or run tests. Acceptance comprised 102 batch cases, in which the whole input is sent and the result compared afterwards, plus 1 streaming probe, which checks, before the input has ended, whether the earlier message is already readable. The signal that input has ended is called EOF, so the probe is also called the pre-EOF check. Together the two kinds make 103 checks.

Beyond program behavior, the study separately verified the CLI version, the execution record, whether the model matched the configured one, and whether any tools were used. Only when both the behavioral acceptance and these operating conditions held was a slot recorded as accepted, meaning it met the acceptance conditions the study had set in advance.

The result: all forty were accepted.

Before interpreting that result, look at what the 103 checks actually verify. The table below assumes an input of only two lines: the first an agent message, the second a valid completion event. Only the value of `text` on the first line changes. Besides R05, read earlier, two more rules are needed. R11 chooses the exit code at EOF in order: 3 if there was any explicit failure, else 6 if any malformed event, else 4 if no valid completed turn, else 5 if the turn completed but there was no actual message, and 0 only when none of those applies. R12 appends the legacy end-of-stream summary only for exits 3, 4 and 5.

Start with `null`. It does not count as an agent message, the completion event that follows is valid, and the input contains no failure and nothing malformed, so when the turn comes to "completed but no message," the condition holds: exit 5, with the summary. With that derivation in hand, you can compare at which step `false` and the whitespace string head toward different results.

📌【在此插入表 table-03.png】

The `false` row is also a case of "completed but no message," yet it satisfies the malformed condition first, so the result is 6, with no legacy summary. What governs this is the order of precedence, not the numeric size of the exit codes, and not which event arrived first. The whitespace string is a valid agent message; after completion no other failure condition applies, so the result is 0.

The last row deserves a second look. The seed version printed `123` as review content and returned exit 0; the contract demands a diagnostic plus exit 6. The words "fix the type handling" alone do not tell you that `false` must count as malformed while `null` must not, nor that the malformed verdict takes precedence over "no message." These behaviors are first decided by the requirements at the first layer, then verified item by item by the checks at the second.

A full pass is reassuring, but ten runs may still be too few. Imagine a purely hypothetical case: if a brief succeeds with probability 70% on each run, and the runs do not influence one another, the chance that ten in a row all pass is still about 2.8%. So seeing ten out of ten does not let you conclude that the method almost never fails.

A statistical interval exists to express this kind of estimation uncertainty. The study uses the two-sided 95% Clopper–Pearson interval: assuming the observations are independent, identically distributed and share one success probability, each group's 10/10 corresponds to an interval of roughly 69.15% to 100%. The lower bound can be checked by hand: it is the success probability at which "ten out of ten" has a probability of exactly 2.5%, that is, the solution of p¹⁰ = 0.025, which gives p ≈ 0.6915. That is not a guarantee that the next run succeeds, nor a statement that the true success rate definitely lies inside; it describes how wide a range of estimates the data still allows under this statistical procedure and its assumptions.

Four groups all passing cannot, on its own, rank the documents. "Equivalent" is a further claim that has to be defined in advance: how small would the difference have to be before the team treated two methods as practically the same? This round did not complete that kind of comparison, and a full pass cannot be read as showing that the longer text is useless, that high reliability has been reached, or that anything can be adopted across the board.

The cost has the same limits. By the CLI's list-price estimate, the ten generations in each of A0, A, B and C cost about USD 1.25, 1.38, 1.51 and 1.55 respectively, about 5.69 in all. That is not a bill, and it excludes the research and review work outside those forty generations, the pilots, the writing and the human cost. In these four groups, cost rises as the document gets longer, but this ordering cannot separate the effects of the rationale, the self-check and the pattern. The part of the cost an EM really needs to know, the human effort of reading the code, correcting it, approving it and maintaining the document, was not measured in this round, so no return on investment (ROI) can be computed here: we know the estimated cost of model generation, and we do not yet know what the team pays in total to get a deliverable result.

Another study offers a counterpoint, a reminder not to equate "less information" with "cheaper." On 5 program-repair tasks from SWE-bench Verified, the researchers used a single model, Kimi K3, with mini-swe-agent, combined 12 ways of writing the spec with 3 effort levels, and repeated each combination 15 times, producing 2,700 final execution records. After excluding the prompt that hands over the solution directly (the paper calls it the oracle prompt), the bare user story, which gives only a rough task description, cost about 29.7% more than the full specification. It is called an oracle prompt because that condition supplies the answer directly; it is not the oracle this piece uses to judge output right or wrong.

That cost difference is an estimate from a hierarchical model, with a 90% Bayesian credible interval of +5.1% to +58.7%; the wider 95% interval runs from −0.3% to +66.8% and includes zero. It is an interval expressing parameter uncertainty under that study's model and prior assumptions, not the Clopper–Pearson interval used for the binomial proportion above ([Can your AI agent be cheaper?, arXiv 2608.25399v1](https://arxiv.org/html/2608.25399v1), §4.1, Appendix C).

The study also records that with the original limit of 60 turns, the sparse specs were more often cut off at the limit; after raising it to 120 turns, 112 records were rerun. That shows that when work is stopped affects the comparison by itself. The reminder I keep from this study is that it compares the results of removing concrete information; it cannot be used directly to rank documents by thickness. In this round, A0 already contains the full set of goals and is not a bare user story; whether adding a self-check on top of a full specification is worth it still has to be answered separately.

This study ran into a first-layer problem of its own: one requirement was not stated identically across the four briefs. There is one known semantic difference between A0 and A: on new command-line options, A0 says in R01 that "No new CLI arguments or external dependencies are required," while A's R13 goes further and lists "adding CLI options" as "outside this task"; B and C inherit A's wording. The formal acceptance program did not fully check extra CLI options or the `main` interface, so what effect this difference has is still unknown. I therefore cannot claim that the four documents are semantically identical; nor can the frozen packets be edited after the fact. If the next round wants to remove this difference, it has to align the requirements first and then regenerate.

Some conditions could not be fully pinned down. The context the provider adds to the model internally, the temperature and random seed that govern output sampling, and the full operating-system state were all outside what this study could lock. The plan was archived locally before execution, but not pre-registered with a third party; a local record cannot be treated as third-party pre-registration.

The isolation mechanism was also tested with three boundary probes, confirming that attempts to read the oracle files, write files and bind the local network address localhost were refused; that still does not prove every route is sealed. The two pilot runs used to walk the process before the formal run, and the probes that checked the stop paths, are not counted in the formal data either. The details can be checked in the [formal study results](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/experiments/same-spec-ten-runs/RESULTS.md). Together these limits mark out the scope of the conclusion: this round provides the result that the candidates produced from these four briefs satisfy the fixed 103 checks; it does not answer "which brief deserves to become a default." What comes next is what else this batch of programs can tell us after a full pass.

## 7. After everything passes: legitimate variation, the ceiling, and regression assets

All forty candidates passed, but their programs are not the same. To describe the difference, the study uses two structural measures. The first reads the program into an abstract syntax tree (AST): the functions, conditions and calls in the text become linked syntax nodes. Think of it as parsing a sentence's grammar before comparing how it is put together. The study normalizes some of the identifiers, then computes a digest (hash) of the resulting representation; all forty digests are different.

That difference still needs careful reading. The study normalizes only some identifiers; it keeps attributes, import paths, constants and program order, and it does not resolve which scope a variable belongs to or how it is bound. So a different hash only means that this representation did not treat two programs as the same; it does not directly imply different control flow or lower quality.

The second measure only counts how many nodes of each syntax type there are, then compares the count distributions with cosine similarity. If two programs have similar numbers of conditions and calls, the score can be high even when operations occur in a different order within the two programs. This is not behavioral acceptance, and still less a quality score. The ten candidates in each group pair up into 45 pairs, but the same program appears in many pairs; 180 pairs across the four groups are still not 180 independent data points.

External research has seen something similar. A descriptive study obtained 90 agent runs from one frozen web-app spec; under the baseline condition of Opus 4.7 xHigh, all 6 repetitions scored the full 42 points, yet the source files ranged from 15 to 22 and the CSS from 174 to 468 lines ([arXiv 2607.02436v2](https://arxiv.org/pdf/2607.02436v2), Table 9). Those 90 runs span several models, execution frameworks, reasoning efforts and tool conditions; they are not one configuration repeated 90 times, and the conditions were not randomly assigned. File and line counts are only indirect indicators of program size, not a measurement of maintainability. In at least these two cases, full functional passes and structural differences appeared together.

Does looking different create a maintenance burden? That remains an unmeasured hypothesis. To see where the differences fall, after the study was complete, A0's two earliest candidates in the frozen execution order, `formal-01-A0` and `formal-02-A0`, were selected first, and then their code was read. The pair was not chosen by score, but it was not an analysis planned before the study either, still less a representative sample. Both programs passed the 103 checks. `formal-01-A0` keeps the malformed state in a dictionary (dict) inside one function and uses a few local variables to record whether a turn completed, whether the agent spoke and whether anything failed; `formal-02-A0` puts the state in a `_State` class and lets individual event-handling functions (handlers) deal with the different events.

Rather than rushing to judge which is better, trace three questions: where `text` is validated, when a valid event changes the state, and where the EOF precedence is decided. In the first program, the answers have to be found among local variables and branches; in the second, inside the class and the handlers.

This pair's cosine is about 0.994, which likewise carries no meaning about quality. This was a static reading, not a measurement of maintenance work.

The reading brings out one criterion for the second layer: acceptance has to accept the implementation freedom the contract allows. C's pattern even spells out two legitimate approaches: "an event handler can return a small result", or, "alternatively, retaining the existing branch structure with local validation is equally acceptable." The text helper it suggests also cannot be applied to the root-level error event, because R09 requires the error message to keep its legacy `str` conversion; in C's words, "top-level error must retain its separate str conversion rather than sharing that stricter helper." If a team genuinely cares about program structure, it has to write the structure down as an architectural requirement with a provenance and an acceptance check; until then, requiring every generated program to look the same cannot serve as a quality goal.

Next is the problem of a comparison hitting its ceiling. With all four groups at 10/10, the comparison has no discriminating power. Anthropic puts it bluntly in an engineering article on agent evals: "An eval at 100% tracks regressions but provides no signal for improvement." ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), Step 7: Monitor for capability eval saturation.) That is vendor engineering advice, not a controlled experiment, but it points to a useful purpose for 40/40: this set of checks cannot rank the documents, yet it can be kept as a regression asset.

A regression asset here does not mean running the study again; it means leaving behind material that can be rechecked later. For instance, keep one known faulty version, and whenever the acceptance program is changed later, you can confirm that it still rejects that faulty program. Fixed test material of this kind, prepared in advance with its behavior verified, is called a fixture.

But the same material cannot answer every regression question. The table below separates three uses; the third row mentions the harness, the execution framework that arranges how the model works, including the available tools, the prompts, how it stops and how it is recorded. When the framework or the model changes, the old program files do not produce a delivery for the new method, so that row needs new generation results.

Re-scoring the old forty candidates only confirms how those old artifacts fare under the specified grader. They were all passers to begin with, so on their own they cannot replace the positive and negative controls the grader check needs. A new candidate still has to actually face the contract checks; a model's or harness's delivery method needs new generation, and replaying old files cannot stand in for it. Another limit is easy to miss: this set of tasks, answers and scoring data has been disclosed in the course of the study and the writing. They can go on serving as regression assets, but saving another copy will not turn them back into unseen holdout tasks, tasks that were never used to tune the method and were kept for the final evaluation. Comparing documents or evaluating a new capability needs a separate set of formal tasks and scoring assets, and that data must not be used beforehand to tune the documents.

## 8. Triaging the CSV case: fix the oracle, and the existing acceptance is restored

The parser case showed how far the study can answer. Next, I use a different task to work through the triage diagram from section 4. This is a teaching hypothetical, not a second formal study task from my repo; it sent no model requests, and it has no model success rate or human time data.

The scenario continues from section 5: the CSV export tool gains date-column formatting, the caller requires row order and duplicate rows to be preserved, and the empty-date policy is undecided. The first diamond's answer here is "No," so the first step is to ask the requirements owner to decide the policy. Suppose the owner decides that a null date produces an empty field, and confirms three format conditions with the QA owner: the column headers (the header) are fixed in name and order as `name,date,note`; each complete entry (a record) may end with either of the two line-ending representations, LF or CRLF; and commas and line breaks inside a field's contents are preserved. These conditions are assumptions set up to check the oracle; they do not mean every CSV tool should handle things this way.

Only once the policy is decided can the expected values be derived. Here are three input records:

```json
[
  {"name":"王,小明","date":null,"note":"第一行\n第二行"},
  {"name":"李","date":"2026-09-28","note":""},
  {"name":"李","date":"2026-09-28","note":""}
]
```

By the contract, the output keeps all three records in their original order. The first record's name still contains its comma, its date is an empty field, and its note keeps the line break inside the field; the two identical records that follow are both kept. Under the default quoting rules of Python's `csv.writer`, one legitimate output looks like this. It is shown with LF endings; the CRLF version differs only at the end of each record.

```text
name,date,note
"王,小明",,"第一行
第二行"
李,2026-09-28,
李,2026-09-28,
```

This text has five physical lines but only three data records (plus the header), because the first record's note spans two lines. That difference matters for the comparisons that follow.

The teaching replay builds six outputs with Python's standard library. Two are legitimate representations, ending each record with CRLF and with LF respectively; the other four are deliberately wrong: duplicate rows removed, header column names swapped, data rows reordered, and one date value altered. These faults are prearranged test data, not mistakes an agent ever made. Each output is judged by three acceptance methods. The table records the actual replay results; read down each column and compare which outputs each yardstick accepted and which it rejected.

📌【在此插入表 table-05.png】

The first two yardsticks each have a defect. Byte-for-byte comparison demands that every byte of the file be identical; LF uses one newline character and CRLF a two-character sequence, so this comparison rejected the legitimate LF version. The problem is that the template preserves only one of the representations the contract allows.

Accepting anything that parses is too loose: all four faulty outputs are still syntactically valid CSV, so all were waved through, even though they had already violated the requirements on column order, row order, field values or preserved duplicates. The third yardstick first reads the CSV back into data, then checks the header and the complete, ordered records against the contract. It does not deduplicate or re-sort first, so it can still notice that a record was deleted. On these six fixed outputs, only the third made the expected judgment. That is the difference between comparing by the meaning of the data and comparing the file's representation byte by byte.

Three different decisions follow directly from this table.

First, if the team's current acceptance compares the whole output string byte for byte against a CRLF template, then when the LF candidate is rejected, the fault is in the yardstick, not the agent. The oracle should be fixed first: keep the old template and the original scoring records, give the new oracle a version, and re-score the same batch of existing outputs consistently with it. This step needs no new model generation, and there is no reason to lengthen the spec first. After the fix, confirm once more with the four contrasting outputs, duplicates removed, header wrong, row order wrong and date value wrong, so that accepting a legitimate line ending does not loosen the content requirements along with it.

Second, if a candidate really did remove duplicate rows, reject that candidate and go back to the requirement to preserve duplicates. From the output difference alone you cannot tell whether the model skipped the requirement, misunderstood it, or picked the wrong helper; still less does it prove that adding a self-check would improve things. The parser case works the same way. R13 requires repeated messages and repeated completions to be accepted, with repeated identical agent messages "printed/count separately" in the spec's words. That does not permit deduplication, and it does not mean that replaying the same batch of events adds nothing beyond the effect of processing it once; that latter guarantee is what idempotent handling would mean here. The order and duplicate preservation the CSV caller requires, and the parser's handling of repeated events, each have their own contractual basis; data cannot be cleaned up on the side just because it looks duplicated. Conversely, using a different helper, class or inline style is legitimate implementation freedom as long as the behavior meets the contract.

Third, this tool is only required to deliver a complete CSV file, not to emit each record in real time, so the parser's pre-EOF streaming probe should not be copied over; batch output can qualify just as well. If a streaming requirement is to be added, that goes back to the caller's needs and observable conditions, and the owner decides.

This is not a problem only CSV runs into. EvalPlus expanded the tests on 164 HumanEval Python function tasks across 26 models, found errors the original tests had not identified, and even changed the ranking between models. The same programs, placed under acceptance checks with different ability to detect faults, received different verdicts. The study also used precondition assertions to define which inputs fall within what a task promises to handle, because test inputs must obey the contract too: an input the contract never defined cannot be used to punish a different but reasonable implementation ([EvalPlus, arXiv 2305.01210v3](https://arxiv.org/html/2305.01210v3), §2.3, §3). HumanEval's small functions are not agent work in a repo, and adding tests cannot prove a program completely correct. What the study reminds us of is the order: before comparing any way of briefing, first confirm that the yardstick rejects known faults and does not wrongly reject legitimate variation.

You can check the replay yourself. [csv_transfer.py](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/workbench/csv_transfer.py) generates the six outputs and runs the three judgments; the [results file](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/workbench/csv-transfer-results.json) keeps each output's bytes and SHA-256; the [self-tests](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/workbench/test_csv_transfer.py), 11 in all, pass on CPython 3.14.5. The replay did not verify date-format conversion, other CSV dialects or a complete export tool; and those 11 tests are not part of the formal study's 40 slots or 103 checks.

Having walked through it, the CSV case has filled the first two layers' gaps: the owner decided the policy, QA fixed the oracle, and the work returned to the candidate's acceptance and the original approval flow. As long as the team only has to handle this patch to the export tool, and is not pushing the extra self-check into a default, it need not move on to a method comparison. The diagram's final "No" thus gives the team a reasoned closure.

## 9. A one-page proposal: turning "write it more clearly" into a claim that can be reviewed

If the first two layers are sound and the team genuinely has to decide whether to make a passage of a brief a default, I would ask the proposer to write a one-page proposal first. The proposal lets the team review the claim, and reject it. The proposer has to say which observable error they want to reduce, which work it applies to, how far the existing evidence supports it, and what result would make the team change its decision. A goal like "raise quality" is not enough to fill any field; "reduce the cases where `text: false` is treated as no message" is a goal that can be checked. After filling it in, ask once more: does this problem lie in a spec not yet decided, a candidate that did not do it, or an acceptance check that did not see it?

Below is a demonstration with the parser as the example. In plain words first: group P works from the full specification; group Q receives the same specification plus a self-check approved in advance. We want to know whether that extra self-check increases the share of original candidates that pass acceptance, and how much more human work it adds.

Here the historical fact and the next round's design have to be kept apart: the original forty runs were tool-free, single-shot generations; the next round is planned to let the agent use tools, check and correct itself within a fixed budget. The whole stretch of work from receiving the task to the end of this delivery is called a session; however many times the program changes along the way, it is still one piece of work. This comparison **has not been executed**. The YAML below only writes the proposal out as a record of fields; it is not a configuration file that starts an experiment when pasted in. Read why the comparison exists and what changed first, then how it is recorded and decided. The full version and a fill-in template are in the [document-change evaluation proposal](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/document-change-proposal.md).

```yaml
# Document-change evaluation proposal (design example, not executed; fields excerpted, full text in the attachment)
decision: Within a limited set of Python tool behavior patches, whether a self-check, rewritten under a fixed policy, becomes part of the default brief
why_now: The self-check needs someone to maintain it; we want to know whether it reduces non-qualifying deliveries, and how much writing, acceptance and review effort it adds
target_work: All eligible patch work arriving in a fixed period; keep the reasons for work that is unfinished, cannot yet be evaluated for acceptance, or is excluded
existing_evidence: The original four tool-free groups each passed the 103 checks at 10/10, which cannot rank them; B added rationale and self-check together, so their effects cannot be separated
intervention: Per task, P = the expanded spec; Q = P plus the approved self-check; for the same task, all other requirements, starting code, tools, budget and acceptance are identical
policy: Each scheduled slot starts from a fresh repo/session, may run the public checks and self-correct; the external hidden acceptance runs only after the session ends, and no replacement session is opened
prerequisites: Policies that would change expected values have been decided by the owner; the oracle has passed its positive and negative controls; each task's self-check mapping and P/Q have been approved and frozen
primary_outcome: The candidate each scheduled slot submits at the end of its session, before any human repair, passes external acceptance and the operating conditions hold; human rescue is recorded separately and never backfilled
human_effort: Record the actual human time spent taking over every piece of work; set the stratified deep-reading rule in advance; record reviewer assignment, reading order and familiarity with the same task
decision_rule: Support a default only if the lower bound of the Q−P effect interval exceeds +5 percentage points and the upper bound of added human time per qualifying delivery does not exceed 2 minutes
owners: The spec owner decides behavior; QA maintains the oracle; the platform owner preserves the execution environment; reviewers record takeover work; the EM/Staff and the people who will actually bear the work decide together
next_decision: Review by the pre-set rule when the planned slots or the cost/date boundary is reached; re-evaluate the affected layer when the requirements, grader or model/harness change
```

The 5 percentage points and 2 minutes are thresholds I assumed for the demonstration, not industry standards. Several fields still need their derivation explained.

The intervention keeps only one added ingredient. B in the original study added the concentrated rationale and the six self-check questions at the same time; even if B had done better, there would be no way to tell which passage did the work. So Q adds only the six self-check questions to P, without B's concentrated rationale and without C's pattern.

But the parser's six questions involve rules about EOF, token-count fields and error events, and cannot be pasted into other tools as they are. Before comparing across tasks, the [self-check transfer policy](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/self-check-transfer-policy.md) has to be fixed as well: each self-check question maps only to a requirement that task's P has already disclosed; where there is no match, it is marked not applicable by a rule set in advance, rather than letting Q quietly add an obligation. For every task, the P/Q difference is checked and frozen first, and repeats of the same task under the same conditions use the same text. What is then compared is the overall effect of the rewriting policy, and the manual work of mapping each self-check question onto each task's requirements, plus the maintenance afterwards, has to be counted as cost too. The mapping and input documents for the full set of tasks are not finished, so the proposal still cannot be handed to a runner as it stands.

Changing the delivery policy to a session with tools is meant to come closer to the workflow the team intends to adopt; the original study measured only tool-free single-shot generation and cannot vouch for that workflow. "The same tools" here means the same available tools, permissions and budget, not a requirement that P and Q make exactly the same sequence of tool calls. If the self-check leads the agent to run the public checks a few more times, that may well be the very route by which it works; it should be recorded, not excluded in advance. But even with the tool calls and the execution record (the trace) preserved, they do not establish the model's internal reasons for doing what it did.

The primary outcome has to say what is being counted. Take one patch task given to P and to Q three times each: there is one task and six scheduled slots, three under P and three under Q. `task_id` identifies the original requirement and the starting repo; `work_id` gives each of the six slots its own number. Each work_id corresponds to one session and to the hash of the program file at delivery, so that it is clear which version a verdict is about.

If a session changes the program three times along the way, it still counts as one slot; failing external acceptance counts as a failure, and no replacement session is opened. Human review and limited repair may let the work finally ship, but the new hash after repair is recorded separately, and a person's rescue cannot be backfilled as the agent having succeeded on its own.

Where the tasks come from also determines how far the conclusion applies. The proposal keeps the full inventory of eligible work that arrived in the fixed period, and records the reasons for anything unfinished, not yet evaluable for acceptance, or excluded. If all that is available is historical patches already merged, treat them as a backtest: hand known historical problems to the method to redo, starting from the pre-patch version, with the conclusion applying only to that backtest set. A rewrite of a task whose answer has already been seen cannot count as a new holdout task.

Human effort needs its own observation; it cannot be inferred from generation cost. METR's randomized controlled study published in July 2025 had 16 developers familiar with their own repos work on 246 real issues, and defined "done" as the developer believing the work would pass review, including style, tests and documentation ([METR, 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Those results belong to the tooling of early 2025, and the page is now marked as outdated; this piece borrows how it defined the completion point and does not use the study's effect figures.

The February 2026 update expanded to 57 developers, 143 repos and more than 800 tasks, but the authors themselves explain that the selection of developers and tasks, changes in compensation, and the attribution of working time when agents run in parallel prevented them from reliably estimating the current effect ([METR, 2026](https://metr.org/blog/2026-02-24-uplift-update/)). Both studies measure productivity, not long-term maintainability.

That brings us back to our proposal: it too has to define its completion point, but it does not adopt METR's endpoint. When a session closes, the original candidate is preserved first; once a person takes over, the review, limited repair, approval and final delivery keep being recorded. The clock cannot stop at "ready for review" and leave out the work that follows; and each stage records separately how many minutes of active effort went in and how much time elapsed in total.

So the proposal records the human time actually spent taking over every piece of work; if reviewers are additionally assigned to read deeply, the sampling rule is set first, for example drawing some of the passing and some of the failing work, rather than picking the pretty cases after the results are in. That is stratified sampling: group by predefined categories first, then sample in a predefined way. Who reads which piece, the reading order, whether the P/Q label can be hidden, and whether the same task is read twice are all recorded. The same person getting faster the second time through the same task says nothing about whether the document improved anything.

The numerator and denominator of the cost have to cover the same work. Suppose two scheduled pieces of work end up delivering only one qualifying result: the effort already spent on both is counted, then divided by one result; the failed run's effort cannot be dropped. If there is no qualifying delivery, no per-delivery ratio is computed, and the total effort is listed instead. This is an example of how to keep the accounts, not a value measured in this round. Without human observation arranged, the effort threshold can only stay in the plan; it cannot be treated as already met.

Only once the records are clear can anyone judge whether the improvement is worth it. The numbers in the table below are all hypothetical: the owner decides in advance that Q's primary outcome has to exceed P's by at least 5 percentage points before the self-check is worth maintaining. A percentage point is the direct difference between two proportions; going from 80% to 85%, say, is an increase of 5 percentage points.

A comparison does not yield a single, fully certain difference; it also yields an interval that expresses the uncertainty. Write the interval for Q−P as [L, U], with L the lower bound and U the upper. Then ask: does the whole interval lie above the threshold, entirely below it, or straddle it? Those three positions decide how far anything can currently be said.

📌【在此插入表 table-06.png】

The table is an example composed to demonstrate interpretation, not an estimate from any study. It guards against two common over-readings. The first reads "the direction is right" as "worth adopting": the lower bound of [+2, +8] is above 0, which supports a positive improvement, but it does not yet establish that the improvement is large enough to justify maintaining one more paragraph. The second reads "an improvement reaching the threshold is ruled out" as "no effect": [+1, +4] rules out an improvement of at least 5 percentage points, yet still supports a smaller positive effect.

Human effort is a separate condition that has to hold on its own. Suppose the proposal requires that the upper bound of the interval for added human time per final qualifying delivery not exceed 2 minutes. If the effect interval is [+6, +9], the upper bound on human time is 1.8 minutes, and the other pre-set cost conditions also hold, only then is adoption supported. If the upper bound on human time is 2.4 minutes, it cannot yet be confirmed that effort is within the limit. If the lower bound on human time already exceeds 2 minutes, the effort burden is over the limit and the self-check is not adopted for now; but that cannot be used to say the document has no improving effect. These human-time figures are likewise only illustrations.

One more line has to be drawn. If a single candidate violates an agreed requirement such as preserving order or preserving duplicates, that candidate is rejected, and scores on other items cannot offset it. A method comparison, on the other hand, preserves each trial's pass or fail as it happened, and cannot add an "observations must have zero failures" bar after the fact. Method-level necessary conditions and pause rules, such as acting beyond granted authority, changes to the acceptance checks, or a remediation burden beyond what the team can bear, are something the owner sets separately before seeing the results, and they cannot be offset by an average improvement. Assignment details, stopping rules and a blank template are in the [comparison plan example](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/comparison-plan-example.md).

## 10. Three exits: dry-run the process first, run a small trial, or adopt as a default

By this point some readers may feel that the bar for a self-check to become a default is simply too high. That feeling is right; I also think the bar should be high, because a default affects all the work that follows. What is discussed here is an optional self-check whose reason for adoption is improved delivery; required behavior still rests on the requirements decision and acceptance, and is not governed by this bar. And for an optional self-check, the team does not have to choose between "run the full comparison" and "do nothing." I would split the first steps into three arrangements with different purposes. They need different evidence, and what they can support once complete differs too.

**Dry-run the process first (the diagnostic pilot).** This is for checking whether the requirements, the positive and negative controls, the grader and the recording flow actually work. A single real task can expose a yardstick defect, like the byte-identical comparison in the CSV case. The pilot can also plant faults deliberately to check whether the yardstick catches them. It does not estimate the benefit across the batch of work; how often the planted faults appear says nothing about how often real work goes wrong; and it changes no authorization.

**Run a small-scale trial (the limited-deployment trial).** This keeps the original human approval, sets the scope of work, the responsible person, the stop conditions and the rollback path in advance, and observes the work a person actually has to do when taking over. For example, attach the self-check only to Python tool patches in one repo, with the approval rules completely unchanged; at the same time record what the reviewer actually did in addition, and whether the self-check conflicted with the task's requirements. As soon as a stop condition the owner set in advance appears, remove the text and record the version at removal. This is a reversible learning arrangement; it needs basic acceptance and a risk boundary, but it cannot be used to claim that the document's effect has been established.

**Adoption as a default, or widening the scope,** is the only one that uses the previous section's pre-set effect, cost and effort conditions to decide whether to extend the practice to the whole target set of work. The dry run answers "do the checks and the records work"; the small-scale trial answers "what does taking over actually involve"; adoption as a default has to answer "is the overall improvement worth it." Each has its own question, and finishing one step does not decide the next.

A team without the budget for a comparison still has plenty it can do; every item keeps the original human approval, and every one is scoped and reversible. A policy still unanswered on a question card can be handed to the owner to decide, with the decision recorded. A yardstick that wrongly rejects legitimate variation or lets a known fault through can be fixed with positive and negative controls, and the existing artifacts re-scored consistently. The passage of brief the team wants to try can first be attached to a few pieces of work as a limited-deployment trial, with the owner, stop conditions and review date written down. None of these improvements proves the self-check works, but each shores up one layer, and they let the team ask a sharper question if it does decide to compare later. This is my practical recommendation, not a verified benefit.

Different roles start in different places. The EM's most direct move is to require every "write the spec in more detail" proposal to state first the decision to be made, the target work, and what result would change the decision. A proposal that cannot say what it wants to improve can be sent back first, without rushing to assess its cost.

A Staff engineer is well placed to own the first layer and the architecture: confirming whether added text records a decision already made or quietly makes one on the owner's behalf, and recording the provenance and acceptance method for every architectural constraint.

The QA lead owns the second layer: building positive and negative controls that reject known faults and accept legitimate variation, versioning the oracle, and deciding which kind of change requires which layer of regression to be rerun.

None of the three roles has to wait for a comparison study to finish; each can start from the layer it owns.

When the data is incomplete, state the result honestly. If the effect meets its bar but human effort exceeds its limit, the conclusion is "not adopted for now." If the effect cannot yet be determined, say which kind of evidence is missing: task representativeness, repeats under the same conditions, the yardstick's ability to detect faults, or human effort. Keeping things as they are is also a reasoned decision, provided the reason can be written down.

## 11. Closing: who maintains that paragraph, and when it is withdrawn

Back to that workshop note: 25 files, all 5 tests passing, and only ten of the sixteen compliance items met. That gap made me ask, in Green Is Not Done, what else has to be looked at beyond a green light before an artifact can be taken over. This series asks the next question: having seen the gap, we go back and change the brief; and the one success after the change says less than it appears to.

Answering this piece's title means handling three questions in order. First, does the added text record a decision the owner has made, or does it decide a policy nobody has decided? Second, can the yardstick that accepts it reject known faults while accepting different implementations that meet the contract? Third, if the claim is that an optional self-check improves delivery, has a comparison result been obtained according to a plan set in advance, meeting the effect, cost and effort conditions at the same time? Writing the proposal only makes the claim checkable; until there are results, stop at a plan awaiting execution or a limited trial under the original approval, and do not declare that the reason for adoption has been established. Answering in order, if either of the first two layers still has a gap, deal with the requirements and the acceptance in front of you first. As in the CSV case, fixing the yardstick restores the power to judge, without comparing any document.

Once a paragraph really does become a default, the maintenance work begins. I would require it to have an owner who can say which requirement it serves and which observable error it is meant to reduce. It also needs a version, a review date and withdrawal conditions. Filling in a missing requirement, or extending acceptance to cover a certain fault, can each trigger a review, but neither automatically constitutes a reason to withdraw: acceptance can catch the error, yet a person may still have to redo the work, and the self-check may reduce that effort. The owner has to confirm whether the information is merely duplicated, whether it still has an effect, and whether the failures and the takeover burden after removal would be acceptable. Only if it conflicts with a task's requirements, a comparison result has ruled out an improvement worth the investment, or human effort exceeds the pre-set limit is it withdrawn or narrowed, for the corresponding reason.

Maintenance also has to tell apart which component changed. When the requirements are revised, re-derive the expected values and the positive and negative controls; when the grader is revised, check the yardstick with the verified fixed fixtures; a new candidate faces the contract checks; when the model or harness is replaced, obtain new generation results and check whether the delivery method has regressed. Re-scoring old candidates only updates the verdict on that batch of artifacts; it cannot substitute for the latter two kinds of work.

The formal study in this series remains narrow: one parser, four briefs, and forty tool-free single-shot generations, all passing 103 checks. The case can demonstrate how to read a brief and derive expected values, and it shows a comparison that has already hit its ceiling; but it cannot rank any document, and it cannot vouch for a workflow that uses tools. The P/Q comparison has not been executed, and the CSV case is a teaching replay.

Each of the next three parts adds one kind of judgment. Part 1, Specification, asks first "which kind of brief did we actually change this time," and organizes a document change into a reviewable spec change card. Part 2, Contract, then asks "how do we know this program got it right," deriving expected results from the requirements and checking whether the yardstick is too loose or too strict. Part 3, Variance, finally asks "which piece of evidence is still missing before this method can be adopted," putting the tasks, each piece of work and the human effort back into one comparison plan.

> **If a self-check is to become a team default on the ground that it improves delivery, the comparison result has to support that investment. The question, the yardstick and the maintainer make a comparison possible; they cannot stand in for its result. While the evidence is still insufficient, the team can first fill in the requirements, fix the acceptance, or run a limited trial under the original approval.**
