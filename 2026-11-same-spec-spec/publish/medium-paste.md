# 同一份規格，跑十次（一）：規格篇—先決定要什麼，再決定怎麼交代

> **TL;DR** — 「把輸入處理改得更穩健」指出了方向，卻還沒回答：沒有訊息、空白文字和錯誤型別，應不應該得到不同結果？本篇寫給文件作者與 Tech Lead，處理多寫一段文字之前的選擇。先找回既有要求；真正沒決定的事，交給有權決定的人；再區分必須遵守的規範、解釋規則的理由與例子、交稿前自查，以及可選的實作建議。文中會拆開正式研究的四份交代：A0 已包含完整目標，A 展開說明，B 增加理由與自查，C 再給一條可選寫法。它們有些差別只影響說明方式，有些卻改變了允許的範圍。四十份程式都通過檢查，仍不能因此替文件排名。讀完之後，你可以用具體輸入檢查一次改寫是否改了要求，將想增加的自查寫成可審查的修改卡，再決定哪些文字只服務這次工作、哪些需要長期維護。下一輪比較尚未執行，修改卡是提案，不是效果已成立的證明。

## 一、「把輸入處理改得更穩健」，還沒回答哪些事

本系列的研究任務來自我的 `medium-articles` repo。`research/scripts/codex_jsonl.py` 負責讀取 Codex 送來的工作紀錄。這些紀錄使用 JSONL：每一行是一筆 JSON 資料，有的行帶著審查文字，有的行表示工作完成。工具收到一行就辨認、處理一行，因此稱為串流解析工具（parser）。

它把結果分成三個部分交給下一個程式，也就是呼叫端：stdout 傳出正常的審查內容，stderr 傳出診斷訊息，最後的 exit code 則用一個數字回報結果。exit 0 表示工具認為這次產生了有效審查；其他數字會讓呼叫端走向不同的失敗處理。

研究從固定的起始版本（seed commit）重現了兩個問題。第一，收到合法 JSON `[]` 或 `null` 時，程式卻把它當成物件呼叫 `.get()`，因此崩潰。第二，訊息的 `text` 若是數字 `123`，後面又接著有效的完成事件，程式會把 `123` 印成審查內容，並以 exit 0 結束。修掉這兩個問題之前，得先說清楚：哪些輸入原本就該被接受，哪些才是錯誤？

假設任務說明只寫了一句：「修掉型別崩潰，把 parser 改得更穩健。」這句話聽起來很清楚。沒有人反對修掉崩潰，也沒有人希望一個數字被當成審查結果。可是實作者一打開程式，就會碰到這句話沒有替任何人作出的選擇。光是 agent 訊息的 `text` 欄位，就至少有四種值需要先有答案。

先把比較情境固定：收到一則帶有 `text` 的訊息後，只再收到一個有效完成事件，沒有其他發言、明確失敗或格式錯誤。後文把格式錯誤稱為 malformed，把一份已選定、要求程式遵守的行為約定稱為契約。表中 R05 代表契約第 5 條要求，方便對照規格與檢查。

exit 取決於整份輸入，不能只看單一欄位，所以後面那個完成事件也是必要前提。請橫向讀下表：先看實作者必須回答什麼，再看另一種答案會讓呼叫端看到什麼。最後一列提到 strip，也就是刪掉字串前後空白；在這個案例中，那不是無關緊要的整理。

這四列都是選擇，沒有一列能從「更穩健」推導出來。契約把 `false` 當成格式錯誤，是為了讓上游送錯型別時能被看見；只有空白的字串仍然有效，契約則寫明是「for legacy compatibility」，也就是為了相容既有用法。另一個產品也許會作出不同的選擇。不過在這個 repo 裡，既有呼叫端已經依賴的行為屬於相容責任，不能因為換了維護者就任意改寫。

除了 `text`，還有其他選擇。遇到 malformed 的行，要停下來還是繼續讀？契約 R03 選擇繼續讀。若同一份輸入既出現錯誤資料，又出現明確的失敗事件，最後該回報哪一件事？R11 規定，等到輸入結束的訊號 EOF 出現時，依序檢查：明確失敗就回報 3，其次是格式錯誤的 6，再來是沒有有效完成的 4，以及完成但沒有發言的 5；全都不符合才是 0。

這是一組優先序，和數值大小無關。它像一張按順序查的判斷清單，前面條件成立，就不以後面的條件作最後結論。重複訊息要不要刪掉？R13 規定照樣印出，分別當成有效事件處理。舊的結尾摘要能不能順手改得更好讀？R12 則要求逐字保留。這些都是對外行為的選擇，不只是程式裡的寫法。

這些決定對呼叫端的影響，比程式碼是否好看更直接。展開版規格在 R11 說明，非零的 exit 會讓既有呼叫端知道，這次沒有產生有效的完整審查。所以，只要修補時把空白字串 strip 掉，或把 malformed 的判定排到「沒有發言」之後，呼叫端得到的結論就會改變，即使程式因此變得更整齊。

Kiro 的修補規格（bugfix spec）文件把一次修補分成三部分：目前行為、預期行為，以及不變的行為（[Kiro Bugfix Specs](https://kiro.dev/docs/specs/bugfix-specs/)）。對這支 parser 來說，第三部分特別重要：既有診斷、exit 優先序與重複事件的處理，都是修補時必須保住的行為。範本本身不保證相容，仍要靠驗收確認。

Leslie Lamport 在 2013 年的短文〈Why We Should Build Software Like We Build Houses〉主張，寫程式也應該先畫藍圖。他指出，寫下規格會迫使人在修改程式之前，先說清楚程式應該做什麼；規格也讓介面的使用者不必讀懂實作，就知道該怎麼使用它（[Lamport, 2013](https://lamport.azurewebsites.net/pubs/wired.pdf)，pp. 1–3）。這是他的工程立場，不是比較試驗；他也說明，寫規格不能保證程式沒有錯。

從這兩點，我整理出一個文件作者可以直接使用的問題（這是我的推論，不是他的原文）：只看這份說明、不讀實作，呼叫端知不知道 `text: false` 最後會得到哪個 exit？如果答不出來，先查既有規範與相容責任。答案可能早已決定，只是這份說明漏寫了，這時應補回可追溯的要求；若答案真的尚未決定，才交給有權決定並承擔後果的需求 owner。兩種缺口不能都靠實作者猜測，也不能一概診斷成需求未決。

在前一系列[《綠燈不是驗收》](../2026-10-green-overview/article.md)裡，我一直把產物和支持驗收的依據分開看。回到這支 parser，驗收之前還有一個要釐清的地方：哪些行為已經承諾，哪些仍只是實作者面對的選擇？本系列[總論](../2026-11-same-spec-overview/article.md)把判斷分成三層：需求是否已經決定、這份程式是否做到、這種交代方式是否值得反覆使用。本文把待驗收的程式稱為候選；後面討論文件修改時，也會反覆問「原本合格的候選，修改後還合格嗎？」

本篇沿著一次文件修改往下走：先分清每句話的作用，再比較四份真實文件，接著把發現的問題寫成修改卡，最後決定保存與維護方式。正式研究的四份文件都已事先寫出行為目標，所以研究沒有量測需求探索的收益。它能幫我們看見的，是每份交代多了什麼，以及改寫是否夾帶了原本沒打算改的範圍。

## 二、同一份文件裡的五種句子：規範、理由、例子、自查與可選寫法

一段規格文字可能同時承擔好幾種工作，文件作者自己也未必察覺。先拿剛才的 `text: false` 排成五種句子：「false 必須回報格式錯誤」是在訂要求；「這樣才能看見上游送錯型別」是在解釋理由；列出 false 的輸入和應有輸出，是例子；「交稿前再確認 false 沒被略過」是自查；「可以抽出一個共用小函式處理 text」則是可選寫法。這種共用小函式，後文稱為 helper。

五句話都可能有用，卻不一定都能拿來退件。我建議審查時先判斷句子在做哪件事；如果它其實是在替尚未作出的決定尋找答案，就另外標成未決需求。分類是為了知道改掉這句話會影響誰、由誰確認。

有一個檢查方法，可以讓這個差別更具體：暫時刪掉一句話，看看哪些程式會從合格變成不合格，或反過來。後文把「所有允許被接受的實作」簡稱為合法集合。假如某句話是唯一要求保留重複訊息的依據，刪掉後，會刪除重複訊息的程式就可能不再被排除；這句話承擔了規範作用。

這只是一個方向的線索。刪掉後沒變，不代表那句話沒有規範作用，同一項要求可能在別處重複出現；仍要核對來源與文件給它的地位。例子也一樣：若文件指定某個例子為唯一驗收答案，它就同時承擔規範作用，不能因為標題叫「例子」就忽略。下表的理由、例子、自查與可選寫法，只指解釋或重述既有要求、沒有另增義務的情況。

這張表也可以反過來用。假設修改一段「理由」之後，原本合法的實作變成不合法，那段文字其實已經是規範，應該當成需求變更處理：找受影響的呼叫端確認，並更新驗收。可選寫法也是一樣。只要驗收開始拒絕沒有採用某個 helper 的實作，這個 helper 就被悄悄升格成要求了。

分類的單位是句子，不是整份文件。正式研究中最精簡的 A0，也在 R05 裡保留了一句理由。A 在 R02 說明，無法解碼的文字仍然靜默略過，這是「刻意保留的舊有容忍」；在 R07 則說明，單一項目的錯誤（item error）不直接標成整次工作失敗，是為了保留它與整輪失敗（failed turn）的舊區分。B 與 C 追加的段落，開頭就標明了自己的身分：B 說明這一節不新增要求，也不規定類別配置或 helper 名稱；C 說明任何符合同一契約的實作都可以接受。

分類之外，還要看一句話有多強的約束。以「使用共用 helper」為例，「必須使用」會排除不用 helper 的實作；「可以使用」則保留選擇；「應該使用，例外須有理由」又是另一種要求。這三句不該只靠讀者猜。

RFC 2119 為這類差別定義了 MUST、SHOULD、MAY：MUST 表示必須，MAY 表示可選；SHOULD 允許特定情況下依正當理由不採用，但要先理解並權衡完整後果。§6 也提醒，不要用這些命令式關鍵詞強加與互通無關的做法（[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119.html)）。RFC 8174 補充，依這項慣例以大寫出現的關鍵詞才帶有這些定義；沒用這些詞的句子，仍可能是規範（[RFC 8174](https://www.rfc-editor.org/rfc/rfc8174.html)，§2）。

這些文件有自己的 IETF 網際網路標準語境，不代表每份 repo 文件都必須照用。我借用的是把強度寫清楚的習慣：沒有寫 MUST，不代表可以不做；「建議」和「可以」也不能隨意互換。

最後要決定文字需要多精確。Lamport 認為描述可以有不同的精密程度：大多數簡單的東西，用一般文字就能說清楚；只有微妙或關鍵的部分，才值得使用更精密的方法（[Lamport, 2013](https://lamport.azurewebsites.net/pubs/wired.pdf)）。放到這支 parser 上，R05 就需要仔細區分型別與空值，值得逐值列舉，甚至整理成表格。「保留既有命令列啟動介面（CLI entrypoint）」這類要求，可以用簡短文字指向既有介面，不必因此採用形式化描述。不過，增加精確程度也可能增加維護工作：規範改了，對應的理由、例子、自查與可選寫法，都可能需要一起檢查。這就是分類的用途：改動時，知道還要一起檢查哪些句子。接下來把這個方法用在四份真正交給模型的文件上，看看「多寫一些」實際增加了哪些東西。

## 三、四份凍結交代：A0 不是空白對照，C 也不是 Skill

正式研究準備了四份交代，共用同一份起始程式碼與十三條要求 R01–R13，並在生成之前固定版本；這就是本篇所說的「凍結」。以後引用結果時，必須能找到當時那份文字，不能改了文件，卻當成原來受測的版本。

A0 最容易被誤解。它只有 936 個英文詞，但不是只概述想完成什麼工作的 user story，也不是沒有具體要求的空白對照。開場說明任務是修掉合法 JSON 的錯型崩潰，並避免非文字值被當成成功的審查；接著寫明以下要求就是完整契約，也說明這是維護工作，必須保留既有的寬鬆串流行為。R01–R13 都在，固定輸出字串也都寫了，只是每條要求都壓縮成一段。

A 在開頭加入一段背景：repo 會用這支 parser 把 Codex 的 JSONL 輸出轉成審查，同時把診斷分開。它也說明目前會造成問題的兩種輸入，並補充「驗收不會額外增加要求」。之後，A 逐項展開要求：R04、R10、R11 改用表格，R03 與 R12 的固定字串放進 code block，不少條文也多了一兩句理由。所以 A 並非沒有理由，只是理由分散在條文裡。A 還在 R13 多寫了一句範圍說明；因為這一句，A0 與 A 不能視為語義完全相同，第五節會推導這一點。

B 的開頭與 A 全文逐 byte 相同，也就是每個位元組都保留，後面才增加一節「Non-normative rationale and checklist」：不新增要求的理由與自查。集中理由有兩段。第一段指出，JSON 解碼成功只代表拿到合法 JSON 值，還不保證這個值是需要的物件，或裡面的欄位型別正確。

它也提醒一個 Python 陷阱：`if text:` 檢查的是值會被判成真還是假，不是它是否符合契約。這種真假值判斷稱為 truthiness；`0`、`false`、空陣列與空物件都可能落到「假」的分支，卻不能因此一律當成沒有訊息。第二段理由則提醒，逐筆事件和整次工作的狀態要分開：一個壞事件，不應抹掉先前輸出，也不該讓後面的明確失敗被忽略。

接著是六題自查，B 明言它們只引用既定契約。閱讀下列節譯時，只要先看出各題請實作者回頭核對什麼。第 3 題的 bool 是布林值，float 是浮點數，token 值則是完成事件回報的用量；即使數字看似合理，型別也得符合要求。第 4 題的 `str` 指轉成字串，`turn.failed` 則是明確宣告這次工作失敗的事件。括號內是對應要求的編號：

1. （R01–R03）輸出是否在 EOF 前送達？malformed 診斷是否使用實體行號，而被忽略的文字是否保持安靜？
2. （R04–R08）是否依各欄位自己的規則，區分缺值、null、空值與錯誤型別？
3. （R08）bool、float 與負數的 token 值，是否在用量註記出現之前就被拒絕？
4. （R09–R10）根層 error 是否保留舊的 str 轉換？malformed 的 turn.failed 是否仍能得到 exit 3？
5. （R11–R12）最終優先序是否仍是 3、6、4、5、0？舊摘要是否保持不變？
6. （R13）重複的訊息與完成事件、未知的字串型別是否仍被接受，而且沒有新增順序規則？

這六題都指回原本的條文，沒有任何一題新增行為。第六題值得多看一眼：它提醒實作者不要自行加入順序檢查或去重，等於預先防止修補越改越嚴。

所以 B 的改動，是把既有要求集中起來，方便交稿前逐一核對。下一份 C 才跨到另一件事：除了提醒要查什麼，還建議程式可以怎麼安排。

C 的開頭與 B 全文同樣逐 byte 相同，後面再加入「Non-normative implementation pattern」，也就是不新增要求的實作安排建議。它寫在輸入文字裡，不會替模型安裝功能，也不會自動執行任何工作；因此這裡的 pattern 不等於可供 agent 載入、使用的原生 Skill、plugin 或 hook。正式研究也沒有量測那些執行機制的效果。

C 保留 R01–R13，明言任何符合契約的實作都可接受。下面的虛擬流程是我的節譯；它像寫給實作者的路線草圖，用來說明處理順序，不是必須照抄的程式：

```text
# C 的可選 pattern（節譯；原文為英文純文字，不是可執行程式）
對每一個實體行號與原始行：
    strip 後嘗試 JSON 解碼
    驗證根層與已辨識事件的相關欄位
    必要時輸出一則 malformed 診斷
    否則輸出該事件的舊有 stdout／stderr
    即使 turn.failed 的診斷欄位 malformed，也保留明確失敗
EOF 時：
    依 3 > 6 > 4 > 5 > 0 選擇結果，並附對應的舊摘要
```

流程之後，C 建議用 helper 處理可選文字，區分缺值、null、空字串與錯誤型別；它也特別提醒，根層 error 必須保留自己的 str 轉換，不能共用這個較嚴格的 helper。C 還列出兩種同樣可接受的安排：由事件處理函式（handler）回傳一份描述輸出與狀態的小結果，或保留原本的 if 分支，在各分支中就地驗證。

四份文件各生成十份候選。同組十次收到的整包輸入（packet）完全相同，使用 `claude-opus-5-5`、high effort，也就是固定的推理投入設定；模型沒有工具，只能一次交付單一檔案。生成結束後，另一個驗收程式（grader）才檢查候選。102 個案例把完整輸入送完後比對結果，另 1 個 streaming probe 則在 EOF 前觀察訊息是否已送出，合計 103 項。四十份全部通過，操作條件也都成立。

這個結果仍有很大的不確定性。假設各次彼此獨立、分布相同，並共享同一個成功機率，每組 10/10 的雙側 95% Clopper–Pearson 區間約為 69.15% 到 100%；它是按指定統計方法表示估計範圍，不是下一次一定成功的保證。十次全過，仍不足以替四份文件排序（正式結果見 [RESULTS.md](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/experiments/same-spec-ten-runs/RESULTS.md)，推導與限制見本系列[總論](../2026-11-same-spec-overview/article.md)第六節）。

設計本身也限制了能回答的問題。A 相對於 A0，同時增加展開說明、表格、理由與一處範圍說明；B 相對於 A，同時增加理由與自查。就像一次改了食譜中的兩項材料，成品不同時，不能只歸功於其中一項。B／C 原則上可以比較整段 pattern 的增量，仍不能拆出其中哪條建議有效，更不能從結果推測模型的內部想法。本輪四組全過，也沒有提供足以證明這些增量有效的結果。

因此，接下來的逐句閱讀只回答「每份文件改了什麼」，不替它們評名次。可以保留本節開頭的全文連結，先挑 R05 這一條要求，看看同一件事在四份文件裡怎麼交代。

## 四、用 R05 逐句對照：合法行為沒變，多出來的是提醒與路徑

先完整說明 R05 的規則，後面幾節都會回到這裡。對 agent message 的 `text` 來說，缺值、`null` 與空字串都表示沒有訊息：不輸出，也不算發言。非空字串要原樣印出、加上一個換行並立即把暫存內容送到輸出端（flush），讓下一個程式現在就讀得到，而且算一次發言；不能刪去前後空白（strip），只有空白的字串也有效。其他非字串值都算 malformed，包括 `0`、`false`、空陣列與空物件。

依 R03，每個 malformed 的行都要輸出一則 `[codex malformed event] line N: REASON` 診斷，其中 N 是實體行號，REASON 可以是任何非空的單行說明，之後繼續讀取下一行。這一行不產生 stdout，也不算發言或完成。

用一個輸入示範這些規則如何串起來。第一行是 `text` 為 `false` 的 agent message，第二行是一個有效的完成事件。第一行屬於 malformed，所以輸出一則診斷，不算發言；第二行有效，因此印出用量註記，並記為一次完成。到了 EOF，沒有明確失敗，但有 malformed，所以依 R11 得到 exit 6；R12 規定 exit 6 不附結尾摘要。

四份文件對這個輸入的要求相同：B、C 在 R05 逐字保留 A；我逐句對照 A0 與 A 的 R05，也沒有找到任何差異會讓某份候選在其中一份文件下合法、在另一份文件下不合法（[A 原文](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/A.md)）。

## 五、看似同義的一句話：A0 與 A 對新 CLI 選項的範圍差異

R05 的對照說明，文字可以變長，而合法集合保持不變。另一種情況也存在，而且更難察覺：兩句話看起來在說同一件事，允許的做法卻不同。A0 與 A 之間就有這樣一處。

先看一個熟悉的命令列選項：執行工具時加上 `--debug`，就可能要求額外診斷輸出。CLI 選項就是這種從命令列傳進去的開關；shell wrapper 則是外面負責啟動工具、讀取結果的 shell 程式。知道它們各做什麼，再看兩份文件如何限定修改範圍。

A0 的 R01 說：「不需要新的 CLI 參數或外部相依」（No new CLI arguments or external dependencies are required）。A0 的 R13 則說，本次任務不加入 strict mode、不拒絕重複的終止事件，也不修改 shell wrapper。A 的 R01 與 A0 幾乎相同：不需要新的參數或相依，shell wrapper 也不在這次改動範圍內。差別出現在 A 的 R13 最後一句：拒絕重複的終止事件、壓掉重複文字、強制終止順序、修改 shell wrapper，**或新增 CLI 選項**，都不在本任務範圍內。

接著用一份假設的候選推導這個差異。候選 X 只是推導用的例子，不是正式研究中的任何一份候選。它完全符合 R01–R13 的其他要求，另外新增一個預設關閉的 `--debug` 選項；沒有指定這個選項時，所有輸出與 exit 都和契約一致。我刻意不用 `--strict` 當例子，因為兩份文件都已排除 strict mode，拿它來比較，看不出兩者的差異。

- 依 A0：R01 只說新參數「不需要」，對是否新增保持中立；R13 列出的範圍外事項也沒有包含 CLI 選項。A0 沒有任何一句話直接排除 X。reviewer 若要拒絕，只能從「這是維護工作」推論，文字依據明顯較弱。
- 依 A：R13 明確把新增 CLI 選項列為範圍外。X 做了本任務排除的事，所以 reviewer 有明確的文字依據退回它。

同一份 X，在 A0 下難以找到拒絕的條文依據，在 A 下卻有理由拒絕。因此，在「能不能新增 CLI 選項」這個維度上，A 允許的集合比 A0 窄；這句話承擔了一項範圍決定。這兩句也都沒有使用前面 RFC 慣例中的大寫關鍵詞。RFC 8174 說明，規範文字不一定要使用這些詞；所以，reviewer 仍可依 A 這句範圍說明退回候選，不會因為沒有 MUST NOT 而失去作用。

這處差異造成了什麼影響，目前仍不知道。正式 grader 沒有全面檢查額外的 CLI 選項與 `main` 介面，也就是啟動程式的介面，所以既有通過結果不能回答是否有候選新增了選項。本輪也尚未針對這一點全面檢查保存的候選；即使補做檢查，仍不能單憑某份候選新增了什麼，就把原因歸給這一句話。

目前能確定的有三件事。第一，不能宣稱 A0 與 A 的全文語義相同；從 A0 到 A，除了展開說明與加入理由，也改變了一項範圍決定。第二，已凍結的 packet 不能修改，這處差異必須原樣保留在紀錄裡。第三，下一輪若要消除這個差異，得先請 owner 決定：可不可以新增預設關閉的選項？決定之後，再同時修改兩份文字，讓驗收也檢查這項決定，最後重新生成。

我會用相同方法檢查其他規格改寫：針對每一組看似同義的句子，試著找出一份「在其中一邊合法、在另一邊不合法」的候選。找得到，兩句就不等價，必須由 owner 決定採用哪一邊；找不到，只代表這次沒有找到，不能證明兩句等價。語義對齊能找出差異，卻不能替 owner 決定該採用哪一邊。對齊之後的決定也要有驗收檢查，否則文字雖然一致了，行為仍然沒有人檢查。

## 六、先確認前提再診斷：錯誤的 exit code 讀不出模型在想什麼

前面用一份假設候選，看見兩份規格允許的範圍不同。現在換一個問題：規格的答案已經一致，但程式沒有做到，能不能直接說是文件寫得不夠清楚？正式四十份都通過，所以接下來仍使用假設錯法，不是新發現的正式失敗。我用它來說明，從輸出能定位到哪一步，又該在哪裡停止推測。

假設某份候選只有 `text` 分流寫錯，其餘有效完成事件與 EOF 的處理都遵守契約。下方分流與 B 理由段描述的舊程式 truthiness 判斷屬於同一類：

```python

    print(text, flush=True)
    spoke = True
# false、0、[]、{} 都會和 null、"" 一樣被靜默略過
```

接下來是最容易踩錯的一步：看到 exit 5，就推測模型「漏讀了 R05」。這個推論缺乏依據，至少還有三種可能：候選沿用了舊程式的 truthiness 結構；候選寫了一個把假值都當成缺值的 helper；或者候選理解了 R05，卻在其他地方寫錯。閱讀程式碼可以定位出錯的路徑，但在沒有工具、一次生成的條件下，沒有任何紀錄能說明模型為什麼這樣寫。即使換成可使用工具的一次完整工作（session），執行紀錄（trace）也只能顯示 agent 做了哪些動作，仍然無法顯示它如何理解需求。

所以，若要因此修改文件，這項修改只能先寫成假說：「這段提醒可能減少這類交付。」

至於逾時、trace 缺失或違反工具限制等操作問題，這些訊號本身不足以判斷候選是否符合行為契約。若已有可檢查的候選，可以另作契約驗收，操作狀態仍分欄保存；不能用其中一欄洗掉另一欄，也不要另開名額替補。

## 七、探索、文字、可執行回饋：三種介入接到三種動作

診斷表的價值，在於讓下一個動作有理由。還不知道空值該怎麼辦，就找人決定；已經有答案卻容易誤讀，可以改善說明；程式能自己執行檢查，則可以讓它在交付前看見錯誤。研究裡把刻意改變某個條件、觀察結果是否改變，稱為「介入」。在這裡，先用這三個具體動作理解它，再看它們各自能處理哪種缺口。

規格探索已有成熟的方法。Matt Wynne 介紹 Example Mapping 時，把討論拆成四類：想完成的工作（story）、規則、具體例子，以及沒有人能當場回答的問題。例子用來找出規則實際代表什麼；問題則顯示團隊還缺少誰的知識或決定（[Wynne, 2015](https://cucumber.io/blog/bdd/example-mapping-introduction/)）。第一節那張值表，其實就是一疊問題卡：false 算沒有訊息還是錯誤？空白要不要保留？這些問題有了答案，才有接下來的規範。

Anthropic 的 Claude Code 官方實務建議也提到，開發較大的功能時，可以讓 Claude 訪談使用者，找出邊界與取捨，再把 spec 留成獨立的產物（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)，Let Claude interview you）。這兩種做法都能幫團隊把「還沒決定」的事攤開來，但決定本身仍屬於 owner。

文字介入是否有用，先要問它改的是什麼。一項外部研究在 SWE-bench Verified 的 5 個程式修補任務上，使用單一模型 Kimi K3 搭配 mini-swe-agent，固定抽樣設定 temperature 1，組合 12 種規格寫法與 3 種 effort，每種組合各重複 15 次，最終資料表共 2,700 筆紀錄。分析排除直接提供解答的提示（論文稱為 oracle prompt），保留 11 種規格。這個 oracle prompt 是一種提供答案的提示條件，和前節作判斷依據的 oracle 不同。

只給概略任務描述的 bare user story，成本比完整規格高約 29.7%。這是分層模型在單一費率下的估計：90% 貝氏可信區間（credible interval）為 +5.1% 到 +58.7%，95% 區間為 −0.3% 到 +66.8%，包含零。區間表示該模型與先驗假設下的參數不確定性；不能只取 29.7% 當成每個團隊都能得到的固定差距（[arXiv 2608.25399v1](https://arxiv.org/html/2608.25399v1)，§4.1、Appendix C）。

研究也記錄，簡略規格較常碰到原本 60 回合的上限；改成 120 回合後，重新執行了 112 筆，其中 108 筆成功完成（Appendix A）。因此 2,700 是最終紀錄數，不能省略重執行後，把它當成總請求數；「成功完成」也不宜擴寫成全部通過 issue 解決驗收。

這項研究改變的是具體資訊是否提供，不是單純讓文件變長或變短。本輪 A0 已包含完整目標，不能套用 bare user story 的結果；而讓 agent 多工作幾回合，也已改變交付條件。這兩個限制都要求我們在修改卡裡先寫清楚，究竟打算改哪一件事。

相同文字還可能因使用環境不同而產生不同作用。這裡的 harness，指包住模型的工作框架：能用哪些工具、何時停止、哪些結果會回給它。想像一份自查寫著「交稿前執行測試」；如果模型沒有工具，它只能閱讀這句提醒；如果有工具，它才可能真的執行並依結果修正。這是說明作用途徑的例子，不是本輪量到的效果。

〈Prompt-Induced Waste in Coding Agents〉提供了相關研究。它使用 24 個有確定驗收條件的 coding 任務、18 種提示變體；其中 9 種主要變體保留目標、驗收條件與測試指令。核心分析有 4,644 個有效執行，其中七個模型能取得供應商提供的推理文字，共 2,801 份紀錄接受遮蔽條件標籤的標註，也就是標註者不知道紀錄屬於哪個提示條件。後者是前者的子集合，不是額外執行，也不包含另行安排的較難任務研究。

研究者觀察到，要求特定推理或驗證的內容，會改變實際投入的推理與驗證工作；只逐字重述原文，沒有重現全部效應（§3）。調整 effort 的效果也會隨 harness 政策改變（§6.1）。不過，這些任務偏小、成功率上限很高，幾乎沒有涵蓋依賴架構的任務，不能直接推到大型修改（[arXiv 2608.01347v6](https://arxiv.org/html/2608.01347v6)，§11–12）。我據此提出的假說仍是有限的：要求具體驗證動作的自查，可能改變工作方式；要觀察這條途徑，得讓文字與可用工具一起進入設計。

文字也有代價。Claude Code 的官方建議提醒，CLAUDE.md 太長時，重要指令可能被雜訊淹沒，因此應觀察改動是否真的改變了行為。同一份文件也提醒，被要求找缺口的 reviewer 往往會提出缺口；如果每一條意見都照改，很容易過度工程化。我的做法是只把違反正確性或既定要求的發現列為必修。如果自查清單寫成開放式的「找出問題」，也可能產生類似傾向（這是推論）；B 的第六題正好從相反方向提醒：不要新增順序規則。上述都是廠商的實務建議，沒有對照實驗的效果量。

Birgitta Böckeler 在 2025 年 9 月試用幾種 spec-driven development 工具時，記錄到小修補卻產生大量文件、讀者要審閱更多 Markdown，以及 agent 沒有完全照規格做的情況（[Böckeler, 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)）。這些是作者少量的試用經驗，不是平均因果效果。

本輪也記錄了生成費用：依 CLI 牌價估計，A0、A、B、C 每組十次的合計費用約為 USD 1.25、1.38、1.51、1.55。這不是實際帳單，也不含人工成本；真正需要衡量的閱讀、審查與維護時間，本輪沒有量測。

可執行回饋走的是另一條路。Claude Code 官方建議中有一節叫 Give Claude a way to verify its work：有了可執行的檢查，agent 就能看到結果並自行修正。正式研究的模型沒有工具，只能一次交付；自查只能在生成時被閱讀，模型無法實際執行任何測試。換到可使用工具的 session，同一段自查可能促使 agent 多執行幾次公開檢查。如果出現這條途徑，就應該記錄下來。原本只能閱讀文字，現在還能執行並取得回饋，作用途徑已經不同。因此，無工具研究不能直接替有工具流程背書。

工具也提供了不同入口，讓團隊不必把每個缺口都當成完整功能開發。依 2026-09-28 存取的 GitHub Spec Kit README，由規格引導開發（SDD）會先處理要做什麼、為什麼做，再進入如何實作；修補 bug 與評估想法則有選用的擴充入口（[Spec Kit README](https://github.com/github/spec-kit)，未鎖定版本）。同次研究查閱的 Kiro 文件，也區分從需求開始、從設計開始、修補與快速規格等路徑（[Kiro Specs](https://kiro.dev/docs/specs/)）。

對文件作者的意義是：如果只缺一個空值政策，先把這個問題交給 owner，不必為了流程完整就先生成整套文件。Böckeler 的少量試用早於上述文件版本，不能直接拿來評斷那些版本的工具；工具提供路徑，也不代表模型一定照做，或替團隊完成了產品決定。應從缺口選入口，不能從入口名稱倒推工作已經做完。

綜合來看，我的判斷是：多寫一段文字之前，先用診斷表確認缺口屬於哪一種。行為還沒有決定，就進行探索並找 owner。要求可以機械判定時，先考慮把它寫成檢查；這可能比多寫一段文字更直接，但這只是推論，本輪沒有比較兩者。若想以「改善交付」為理由新增可選文字，就在要求已定後，提出它可能影響哪個可觀察動作的假說，並用下一節的修改卡接受審查。記錄必要的行為與相容要求，本來就是文件的責任，不必等待這項效益比較。相關方法來源與限制，整理在[規格與契約基礎研究](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/spec-foundations-research.md)。

## 八、規格修改卡：把「只加六點自查」寫成可以被審的改動

規格修改卡是寫給 Tech Lead 審查的。它把「多加一段文字」寫成一項改動，並交代範圍、預期作用、反例與撤回條件。下面以 parser 為背景填一張卡。先說清楚這張卡的性質：R05 是已封存的真實要求；卡中的錯法來自第六節那份假設候選，正式 40 份裡沒有出現；卡中提出的比較也尚未執行。卡片全文與空白範本見附件的[規格修改卡](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/spec-change-card.md)。

先用一句話讀這張卡：P 是原本的展開規格，Q 是同一份規格加上六題自查；想知道這個新增部分是否值得。下面用 YAML 排列，是為了讓 reviewer 逐欄核對原因、改動、驗收和責任，不是可直接執行的設定檔。

```yaml
# 規格修改卡（設計範例，尚未執行比較；錯法為假設，不是正式 40 份的結果）
decision: 先以這個 parser 示範，是否在展開規格後附上六題自查；跨任務版本另依固定改寫政策建立
existing_requirements: R05（錯型假值為 malformed）、R03（一行一則診斷並繼續）、R11（EOF 優先序）
symptom: 假設某份候選以 `if text:` 作為唯一分流，靜默略過 text=false
diagnosis: 重現吻合時，已定要求未被實作；無法得知模型為何這樣寫
change:
  P: 展開規格
  Q: P 加上 B 的六題自查原文；不含 B 的兩段集中理由，也不含 C 的 pattern
held_constant: 既有要求、理由、例子、可選寫法、seed、工具權限、預算、停止條件與驗收版本
expected_effect: 減少不符合共同契約的交付；以六題整體作為比較單位，不歸因於單一題
acceptance_signals:
  malformed_case: false 接有效完成 → 無訊息輸出、一則 malformed 診斷、exit 6、無結尾摘要
  legal_cases: null 與 "" 不輸出；" " 原樣印出並算發言
compat_risk: 清單若被縮寫成「text 一律嚴格」，可能誤改 R09 根層 error 的 str 轉換
free_choices: 函式名稱、dict 或類別狀態、是否抽出 helper
owners: 規格 owner（確認清單不新增要求）、QA owner（正反對照）、接手 reviewer（記錄投入）；尚未指派真人
adoption_evidence: 事前範圍內的合格交付差距、各 requirement 的失敗、全部嘗試的費用與人工投入
disposition: 保留／撤回／修改／仍未定，附證據版本、理由、負責人與重新檢視條件
```

第一個審查重點，是「症狀」與「診斷」有沒有分開。症狀是可以重現的觀察，包括一個最小輸入、一份候選版本，以及實際的 stdout、stderr 與 exit。診斷則只寫到「已定要求沒有被實作」。卡片刻意不寫「模型漏讀 R05」，理由已在第六節說明。這兩欄分開寫，後續改動才會針對可見行為提出假說，不假裝能修正模型的想法。

第二個審查重點，是這次只改一件事。原研究的 B 同時加入集中理由與自查，所以就算 B 表現較好，也無法知道是哪一部分發揮了作用。這張卡只在 P 上加入六題自查的英文原文，不帶 B 的兩段理由，也不帶 C 的 pattern；R01–R13 仍然是完整契約。除了這六題，P 與 Q 的其他條件都要相同，包括既有的理由、例子與可選寫法，以及 seed、工具權限、預算與停止條件。兩份完整 packet 仍待建立與封存。如果有人想知道「只加一段解釋 truthiness 的理由」有沒有用，就要另寫一張卡，另外建立一組 P 與 Q。兩種介入都可能有幫助，也都需要閱讀與維護成本，應各自用對應的證據判斷。

跨到其他任務時，還要先固定[自查改寫政策](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/self-check-transfer-policy.md)。Parser 的六題包含 EOF、token 與錯誤事件要求，不能照貼到 CSV 或其他工具。例如，CSV 只要求交出完整檔案時，就不能沿用「EOF 前必須讀到訊息」這道 parser 問題。每道自查只能指回該任務 P 已有的要求；六個位置依事前規則改寫，無對應義務的位置標成不適用，不另加問題湊滿六題。未決政策先交 owner，補進共同 P 後才建立 Q。改寫者只能用 P 與兩條件共同可見的起始 repo 資訊，不能取用隱藏 grader、參考修補，或依正式題的結果調整 Q；否則即使沒有新增要求，也可能只讓 Q 得到答案線索。

各任務的 P、Q 要核對差異並封存，同題同條件的重複使用相同文字。這樣比較的是改寫政策的整體效果，把自查對應到各題要求的整理工作、審查與維護，都要計入成本。目前全體任務映射與輸入文件尚未完成，所以不能把這張卡直接當成可執行的跨任務方案。

第三個審查重點，是預期作用能不能觀察。這張卡希望六點自查能減少不符合共同契約的交付，比較單位是整份清單。`false` 被略過只是用來說明判斷過程的例子，不是清單唯一要觀察的目標。下面以第二題為例，看自查如何連回條文。

第二題問的是：是否依照各欄位自己的規則，區分缺值、null、空值與錯誤型別？實作者讀到這一題時，應先回到 R05，把容易混在一起的值分開：`null` 與空字串表示沒有訊息；`false` 雖然也是假值，卻屬於 malformed；只有空白的字串則是有效訊息。這一步只是在重新核對已決定的行為，並沒有新增規則。

接著檢查程式：如果 `if text:` 是唯一的分流，`false` 就會和 `null` 一起被略過，這一題就找到需要修正的地方。然後用 `acceptance_signals` 的輸入確認三個結果：stdout 沒有任何代表 `false` 的輸出，stderr 有一則指向第 1 行的 malformed 診斷，exit 是 6。修正時也可能改過頭，所以要同時檢查正例：若修正後連 `null` 也被拒絕，或把只有空白的字串 strip 掉，同樣違反第二題指向的要求。

這段檢查有一條界線：模型在自查後回答「已符合」，不能當成已符合的證據。自查只是提醒，證據要來自外部驗收。清單涵蓋的範圍也比 R05 廣；即使 `false` 這類錯誤減少，也不能因此斷定是第二題改變了模型的注意力。比較時要記錄整體的合格交付，也要分別記錄每條 requirement 的失敗，確認其他要求沒有因此變差。

第四個審查重點，是相容風險。清單的第四題明文要求保留 R09 根層 error 的 str 轉換；這是契約刻意保留的例外。根層 error 的 message 無論是數字、bool 還是容器，都照舊轉成字串，不算 malformed。風險出現在轉述清單的時候：如果有人把清單縮寫成「所有 text 一律嚴格檢查」，實作者可能把嚴格的 helper 套到 R09 上。這是假設的措辭風險，本輪沒有觀察到這項失敗；但它說明自查清單不能被隨手摘要，例外必須跟著清單一起保留。

第五個審查重點，是合法的實作自由。函式名稱、狀態要放在 dict 還是類別、是否抽出 helper，都不會因為加入自查而變成要求。外部驗收必須接受契約允許的不同安排；否則，P／Q 結果就可能只反映哪組比較像某份範本，而不是哪一組更符合契約。

第六個審查重點，是負責人與採用證據。規格 owner 要確認清單沒有暗中新增要求；QA owner 要確認驗收能分辨已知錯法，也會放行合法的例外；接手 reviewer 要記錄理解、修補與審閱各花了多少時間。這張範例卡還沒有指派真人負責。採用所需的證據，是在事前選定的目標任務範圍內比較合格交付，另外列出各 requirement 的失敗，並把所有嘗試的模型費用、人工處理與文件維護成本一起記錄。實務門檻、樣本規模與停止條件，應由實際負責人在看到結果之前決定。

卡片填完後，還不能直接開始比較。建立 P 與 Q 之前，要先確認驗收能抓到想研究的錯法，同時接受合法寫法；再核對這個 parser 的兩份 packet 只差原六題自查；其他任務則依核定政策檢查其自查區段，並保存完整輸入，並計算版本指紋（hash），避免把後來改過的文字和原結果混在一起。先用少數任務試走流程的 pilot 若發現要求或預期值本身有問題，應先修正，再另立版本。正式比較開始後，要依預定規則保存每個名額；不能在看到不理想的結果後修改清單、補跑或挑選樣本。

下一輪的設計也和正式研究不同：它規劃的是可以使用工具的有限 session。agent 可以在 session 內執行公開檢查並自行修正，session 結束後才進行外部驗收，也不另開 session 替補。一道題目、每次排定工作與 session 該怎麼計數，以及人工觀測如何安排，交由〈變異篇〉處理；完整提案與比較計畫，請見附件的[文件改動評估提案](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/document-change-proposal.md)與[比較計畫範例](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/comparison-plan-example.md)。

修改卡先把比較的承諾寫清楚；真正結果出來之後，才輪到最後的處置欄。即使 Q 的合格率較高，也要看差距的不確定性，是否足以支持它超過事前訂下的實務門檻，以及新增的人工與費用能否接受。如果兩組仍然全部通過，Anthropic 的 eval 實務文章有一句話可以參考：「An eval at 100% tracks regressions but provides no signal for improvement.」（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，Step 7）。

全部通過的結果可以留作回歸資產，日後有改動時拿來重查，卻無法說明六點自查有效或無效；這時要回頭判斷，缺的是量尺的辨別力、任務的代表性，還是樣本的精度。所以，卡片的處置（disposition）有四種：保留、撤回、修改，或仍未定。每一種都要寫下證據版本、理由、負責人，以及在什麼情況下需要重新檢視。

如果團隊目前還沒有能力做比較，也可以依改寫政策，在少數工作中附上與各任務要求相符的自查，作為維持原有人類核准的小範圍試行（有限部署 trial），並寫明範圍、owner、停止條件與檢視日期。這樣可以取得真實工作的觀察，但不能據此宣稱效果已經成立。

## 九、換到 CSV 匯出：同一張卡怎麼用

修改卡已經說清楚「為什麼改、只改哪裡、拿什麼判斷」，接下來要確認它能否離開 parser 仍然有用。以下換成 CSV，也就是以逗號分隔欄位的文字表格；例如一筆資料依序放姓名、日期與備註。這是假設需求，不是 repo 原有功能，也沒有新的模型生成。系列已用固定資料實際重播三種判斷方式，但沒有驗證完整的日期轉換功能；此節先看文件作者如何處理未決政策。教學程式與結果見 [CSV 重播紀錄](https://github.com/fantasybz/medium-articles/blob/774759192ab0e0b2da3d8b163eb3f07f3d12f4c3/research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/workbench/csv-transfer.md)。

假設某個 CSV 匯出工具要新增日期欄格式化，呼叫端已要求保留輸入列序與重複列。三筆資料中，第一筆姓名是 `王,小明`，日期為 null，備註含換行；後面兩筆都是「李」、日期為 2026-09-28、備註為空，內容完全相同。依既有要求，`王,小明` 必須排第一，兩筆「李」都要保留。團隊還沒決定的是空日期政策，也要確認 null、空字串與欄位缺少是否應區分。

文件作者接手時，先把已定要求與未決問題分開。以下只展開這個判斷需要的部分，不是完整日期轉換規格：

```markdown
<!-- 假設任務的單次規格草稿；未交給模型，並非完整功能實作規格 -->
## 要求
- 匯出時保留輸入列的相對次序與重複列；不排序，也不去重。

## 例子
- 王,小明在前，兩筆內容相同的李在後 → 仍輸出三筆，保持原次序。

## 未決問題
- null 日期要輸出空欄或拒絕？空字串與欄位缺少是否也適用相同政策？
  - 負責回答：匯出功能的需求 owner
  - 影響：依賴此政策的驗收預期值暫不定案
  - 若需暫行假設，只限原型探索，另作紀錄，不寫進正式驗收

## 理由
- 待補。若下游確實依原順序對照來源、把重複列當不同紀錄，就記下來。
- 尚未確認的用途，不自行補寫成事實。

## 可選寫法
- 可以抽出處理日期表示的 helper；不得排序、去重或自行決定未決政策。
```

這份草稿最重要的是「未決問題」這一段。它把不知道答案的狀態交給能回答的人；agent 也可以據此提出問題。如果沒有這段記錄，某次實作可能自行選定一種表示，測試再把它固定成唯一答案。理由段刻意留白，也是同樣的考量：虛構用途會讓後來的人誤以為已經查證過。

先補一個格式前提，才好讀第三種狀況。CSV 的一筆完整資料稱為 record，欄位標題稱為 header；record 結尾可以用不同字元表示換行，常見的兩種叫 LF 和 CRLF。若需求允許兩者，只因檔案的字元不同就退件，便可能是檢查太嚴。現在用第六節的診斷表，分開處理三種情況：

- **候選把資料列排序了。** 規格已有明文答案，應退回這份候選。排序結果說明它違約，不能說明模型為什麼這樣做。若想用自查減少此類交付，可以提出「輸出是否保留每一列的相對次序與重複次數？」這項介入；它的效益仍要另行衡量。
- **候選把 null 日期填成固定字樣，或拒絕輸入。** 先查既有介面與相容要求。若確實沒有答案，這是未決需求，交回 owner；不能只因不符合 reviewer 的偏好就判違約，也不能直接把候選的選擇寫成唯一預期值。
- **驗收誤拒 LF 輸出。** 若 owner 已確認每筆 record 可用 LF 或 CRLF 結束，QA 應修正只接受 CRLF 範本的 oracle，保存版本並一致重評相關候選。這時已定要求不必跟著改，也不需要先比較文件的長短。

沿用總論的後續假設，owner 決定 null 日期輸出空欄，並確認固定 header 為 `name,date,note`、列順序及重複次數不變、欄位內逗號與換行保持原樣。文件作者便把 null 的答案移到要求，再由它推導第一筆資料的例子。空字串與缺欄位若尚未決定，仍要分開保留問題，不能從這一個 null 例子自動推廣。若另有原型假設或測試依賴舊選擇，就核對影響並更新；owner 提供的下游理由，也要與這項決定一起記錄。

走到這裡，文件已能支持下一步：QA 依核定的輸出義務修正 oracle，再重評候選；尚未決定的日期範圍由 owner 補齊。CSV 固定資料重播示範的是前一項工作，不是完整日期功能已經驗收，也不是自查已經有效。

最後，parser 的 R01 要求 stdin 結束前就能讀到輸出，這是該 parser 的串流義務。CSV 工具若只承諾交出完整檔案，便不能照搬這條要求。在跨任務的自查範本裡，對應位置應依事前規則標成不適用。沿用的是核對要求的方法，具體義務仍須回到各自的呼叫端。

## 十、文件作者與 Tech Lead 的分工：常駐指引、單次規格與持續維護的 spec

上一節把 null 的問題交給 owner，答案確定後再寫回規範。下一個問題是：這份決定要留多久，之後改動時誰還會看見？只服務這次修補的提醒，和每次呼叫都必須成立的行為，不能靠同一種維護安排。

Böckeler 用三個名稱區分規格的生命週期。**spec-first** 是這次工作先寫規格再做程式；例如先列出這次 CSV 修補要改的行為。**spec-anchored** 是以後改動時，規格也跟著維護；例如日期空值政策跨版本仍有一份現行說明。**spec-as-source** 則進一步把規格當成主要編輯來源，程式由它衍生；不能只因先寫過一份 spec，就說自己採用了這種方式。她另把單次任務規格與跨次工作的背景文件分開（[Böckeler, 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)）。

工具文件也能看見相似的範圍區分。Claude Code 文件分別說明幾件事：以 CLAUDE.md 保存常駐指引，另寫 spec 記下訪談決定，並搭配可執行檢查和對抗式 review（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）。Spec Kit 則把專案通則 constitution，和單一功能的需求、計畫與任務步驟分開（[Spec Kit README](https://github.com/github/spec-kit)）。我據此把下列三類文字分開維護；這是我的整理，不是這些來源共同規定的分類。

下表整理三種文件主要保存什麼、應避免哪些混用，以及由誰負責檢視。第三欄列出容易讓適用範圍與責任混淆的放法，並非禁止所有跨類別引用。這是維護上的分工建議，不是只准某種內容存在於某個檔案的規則。

以 parser 為例：「只有空白的字串照舊有效」應放在持續維護的 spec，因為它是呼叫端依賴的相容行為，下一次修補也必須成立。「這次不新增 CLI 選項」屬於單次規格，只描述這次改動的範圍。至於跨任務的自查，如果比較結果支持採用，可以把改寫政策放進常駐指引或任務範本，再依各任務 P 建立自查；這正是第八節那張卡要回答的問題。若把某次修補的選擇直接寫進常駐指引，它就會悄悄限制之後的每一項工作，這是我最想避免的情況（這是我的推論，不是 Böckeler 的主張）。spec-as-source 是否適合既有 repo，則是另一個問題；spec-first 在單次任務上有用，不代表整個 repo 都該改成由規格衍生程式。

文件交接時，未決問題與例外也要一起保留。以下是我建議的處理方式，尚未在團隊實測：

- **未決問題與已核准契約分開標示。** 單次規格可以保留問題，持續維護的 spec 也可以另設待決區或連到 issue。每一題記下影響、owner、暫行假設與檢視日期；探索用假設及其測試另外標記，不冒充已驗收的承諾。分界取決於核准狀態與適用範圍，不取決於檔名。
- **規範的例外寫在該條規範旁邊。** R03 說明 malformed 事件不產生其他語義效果後，緊接著寫出 `turn.failed` 仍要記錄明確失敗；R05 也在同一段交代，只有空白的字串仍然有效。例外一旦和規則分開，轉述時就容易遺漏。容易漏掉的例外，可以再放進自查，B 的第四題就是這樣做。
- **可選寫法的例外要跟著 pattern 一起寫。** C 建議使用 text helper 時，在同一段就提醒根層 error 不能共用它。把 pattern 複製到別處時，例外也要一起帶過去。
- **團隊層級的例外要留下理由與核准者。** 依照 RFC 2119 對 SHOULD 的定義，有正當理由時可以不採用建議，但必須先理解並權衡後果。我會要求記下理由、核准者與適用範圍，並設定重新檢視的時間。
- **常駐指引與單次規格衝突時，先停下來請 owner 確認。** 例如，常駐指引寫著「所有文字欄位都要嚴格檢查型別」，單次規格卻要求 R09 保留 str 轉換。這時，在已決定的相容要求所涵蓋的範圍內，應以相容要求為準。這個衝突也表示常駐指引需要縮小適用範圍，應由它的 owner 修改，不能讓實作者自行選擇其中一邊。

到期責任，要在文字放進常駐指引時就寫清楚。我在 Agentic Engineering 技術篇〈[Harness 藍圖—把系統變成 agent 讀得懂的地方](https://fantasybz.medium.com/f2a139f5b561)〉提過兩項建議：修改 agent 的背景資訊與指令前，先指出想改善的具體結果；修改後，重新執行具代表性的固定任務（golden tasks）。

套用到這裡，每一段常駐文字都該記下四件事：它服務哪條要求、想減少哪種可觀察的錯誤、owner 是誰，以及下一次檢視的日期。需求改版、驗收開始涵蓋某種錯法、model 或 harness 更換，或它與任務要求衝突，都會觸發檢視。

不過，觸發檢視不等於撤回。驗收能攔下錯誤，但候選仍可能需要重做；自查也可能正好減少這類重做。owner 要確認這段文字是否只是重複、是否仍有作用，以及移除後，失敗與接手負擔是否可以接受。只有在它與要求衝突、比較結果已排除值得投入的改善，或人力超出事前上限時，才依相應理由撤回或縮小範圍。

這樣一來，分工也就清楚了。文件作者負責替句子分類、替未決問題找到 owner，並讓例外留在對應的規則旁邊。Tech Lead 審查修改卡，決定一段文字該放在哪一種文件裡，以及要附上什麼到期條件。需求 owner 負責作決定；QA owner 讓驗收跟上決定；repo 或平台 owner 則管理常駐指引的總量與衝突。沒有哪個角色需要一次做完所有工作，但每一段文字都要找得到負責的人。

## 十一、結語：留下可以保留、也可以撤回的理由

回到開頭那句「把 parser 改得更穩健」。這句話指出了方向，卻還不足以作為完整的行為答案；有些答案要從既有契約補回，有些才需要 owner 新作決定。`text` 是 null、false 還是只有空白？遇到 malformed 之後，要不要繼續讀？exit 要依什麼順序判定？這些問題最後總會有人回答。差別在於，是由需求與介面的 owner 回答並記錄下來，還是由某次實作在程式裡默默作出選擇，再被測試固定成基準。

讀到這裡，面對「要不要多寫一段」這個問題，我的建議是先確認那段文字的作用。它如果是在補一項決定，就交給 owner；如果是在說明已經作出的決定，就要確認它沒有暗中改變合法集合；如果是自查或可選寫法，就用一張修改卡寫清楚它想減少哪一種錯誤、比較單位是什麼、由誰負責，以及在什麼情況下撤回。

凍結文件讓我們逐句看見，交代如何圍繞共同目標累加；A0 與 A 那一句 CLI 範圍說明也提醒我們，看似只是潤飾的改寫，也可能改變範圍。正式研究的 40 份候選全部通過，但這個結果無法替文件排序；P 與 Q 的比較還沒有執行；CSV 是假設需求搭配固定資料重播，沒有新的模型比較，也沒有完整日期功能驗收。這些限制決定了下一步：先修正明確的缺口，再替可選的文字介入設計比較，不從目前全部通過的結果推論效果。

我最希望文件作者留下的，是讓每一段文字都帶著一個可以檢查的理由。R05 裡那句「只有空白的字串照舊有效，是為了 legacy 相容」就是一個好例子：它說明了保留這條規則的原因，也隱含了撤回的條件。哪一天，依賴空白訊息的呼叫端退場了，介面 owner 就知道該回頭檢視這條要求，並把修改當成需求變更，連同驗收一起處理，不會在某次重構時被順手刪掉。六點自查也應該帶著同樣清楚的理由：它是為了減少不符合共同契約的交付。事前規劃的比較結果若支持它，而且需要的人力可以接受，就保留；它若和要求衝突、比較結果已排除值得投入的改善，或人工成本超出上限，就撤回。

到這裡，文件作者已能交出兩樣東西：一份說清楚必要行為與合法自由的規格，以及一張說明新增文字用途的修改卡。下一位接手者仍要回答：「拿到一份程式，怎麼知道它做到了？」〈契約篇〉便從這裡開始，把要求轉成可觀察的結果，再檢查判斷依據會不會放過錯法或誤拒合法寫法。

> **多寫一段之前，先確認它要替誰解決哪個選擇；寫下它的同時，也寫下它何時應該撤回。**
