## 2. First-hand material for the planned themes

### 2026-10 綠燈不是驗收 (testing / review / reliability)

**`Asking Testing Seriously` (2cfe948f-e0ca-809d-b0ca-f08636010e5f, 2025-12-20 → 2026-03-03) — the planned book anchor.** Status check: the page holds the 節錄 stage only (the book's definitions chapter plus the *Taking Testing Seriously with James Bach* interview); the template sections 自由回想 / 一問一答 / 這本書最重要的三件事 are empty. The author must finish the read before a book-anchored 總論 is honest. What is already there is exactly the thesis material:

- 「Testing is the opposite of faith in the product. Testing begins with faith in the existence of trouble.」 — the natural opening line for 綠燈不是驗收.
- The testing / checking split: 「Checking is the mechanistic process of verifying propositions… testing cannot be automated, but checking can.」 and 「Quality is an opinion, not a fact, so quality cannot be verified.」 This sharpens the selection's thesis: a CI green light is *checking*, an agent's self-report is *checking of its own propositions*, and acceptance is *testing* — a human learning-and-evaluating act. Mutation score, constraint tests and pass^k are all better *checks*; the 總論 should say so plainly rather than calling them "testing", or Bach's readers will object.
- 「Testing is a responsible social process that allows our clients to make timely, informed business decisions.」 — the bridge to Review 篇 (review as the organisation's control point, not a reading-speed problem).
- The "walk toward the scary technology you are not prepared to understand… rapid learning, rapid analysis" passage — usable for the tester's new job when the agent says 沒問題.

**`極限編程系列（The XP Series）書籍整理` (1f0e948f-e0ca-8076-b9a8-dfdc9bd0efe7, 2025-05 → 2025-07-24).** Eleven-book summary; three chapters already published on Medium (XP Explained ch.1 and ch.3, Planning XP ch.1 「計畫不是預言書，是應變指南」), so the reader base knows this voice. For October: *Testing Extreme Programming* (Crispin & House) — 「人人都是測試者」, test cards next to story cards, the "Testing Pitfalls" anti-pattern column (「開發人員認為測試是測試人員的事」); *Extreme Programming Installed* — 「XP是第一個將焦點放在驗證上的流行開發流程，但肯定不會是最後一個」 (a ready-made epigraph); *Questioning XP* (McBreen) — 「XP 的做法能否確保充分的測試？」 as the sceptical lens on TDD-as-ritual. **`LeSS in Action: Developer Practices` (330386ad-6045-4e89-aab2-b37269adef55, Terry Yin / 91 / Joey Chen, 2022-04).** The author's A-TDD / SBE training. Directly reusable: the failing-test discipline 「Failing Test — 關注錯誤訊息，而且錯誤訊息要符合預期」 (a test must fail for the right reason — the human check against assertion loosening); 「設計 example 的重要性 — 避免負面導向的 assertion」; 「only use mocks if you have to, use the real thing if you can」; 「儘量操作數據、不操作代碼」; the observation that after an E2E goes green, refactoring produces classes that are already covered, so unit tests are fewer — a lens for judging what an agent *leaves behind*; "Testing and Checking" (satisfice link) was already on the course slides in 2022. Also 「CI ≠ GitLab ≠ Jenkins ⇒ Development Practice 反思」 for the Review 篇.

**CCA-F notes → Review 篇 and 可靠度篇.** Straight from the author's own study guide: 「不能用 assistant 回答文字去猜測 loop 是否結束，正確做法是看 stop_reason」 (self-report is not evidence); 「prompt instruction 有非零失敗率… deterministic compliance 場景要用 programmatic enforcement」 (hooks: PostToolUse, block dangerous action); 「independent review instance 比 self-review 更可靠」 and 「CI review 最好與 code generation session 分離」 (the condition under which AI-reviews-AI is acceptable — different instance, different session — and by implication when it must be banned); multi-pass review 「per-file local pass → cross-file integration pass」; escalation 「不應依賴 self-reported confidence 當唯一標準」; human review 「aggregate accuracy 可能掩蓋某些 document types 的低表現，需要 stratified random sampling」 (oversight-budget sampling design).

**Workshop A/B result → 可靠度篇 opener.** In Teddy's exercise the author ran the same requirement (Product Aggregate + CreateProduct use case) with and without the `execute-uc` skill, in two git worktrees, Opus 4.7. Compliance 「方法 A = 10/16, 方法 B = 16/16」, but the useful part is the diagnosis: A 「看起來非常專業——分層乾淨、Javadoc 完整… 25 個檔案編譯零 warning、5 個測試全綠。如果只看『能不能跑』，A 完全合格」, yet 「A 的 Product 完全不是 Event Sourcing… A 的測試不會抓到，因為它從記憶體裡的 aggregate 直接讀 getDomainEvents()，永遠不經過重播路徑」 and 「@DirtiesContext 缺了… 間歇性失敗——A 現在測試全綠，不代表 CI 上不會紅」. ### 2026-11 同一份規格，跑十次 (variance as harness metric)

**The workshop page is the core asset.** What the notes record, in order:

- *Day 1 opener: 去技能化 Deskilling.* Definition (「勞動者與專業人士失去核心知識、思考能力或實作手藝，從自主創造者退化成機械執行者或校對者」), three causes (AI 與高科技代勞 / 工作標準化與科層化 / 行政庶務過載), three effects (知識主權流失 / 勞動價值貶值 / 應變能力下降), and a podcast reference 「S1 EP09｜去技能化 2.0：當 AI 代替思考，專業人士如何失去知識主權？」. Teddy frames the whole method as an answer to deskilling — patterns keep the *human* holding the design knowledge while the agent executes. Then "Test Harness".
- *Exercise 裸 Prompt vs execute-uc* — see the A/B above. Note it is **one run per arm and measures compliance against a 16-item checklist, not variance**. It cannot be cited as variance evidence; it is the pilot that shows which *dimensions* a run-to-run comparison should score (the six items 「無法從通用訓練資料推導出來」: event-sourcing replay, framework contracts `mapper()` / `setVersion()` / `clearDomainEvents()`, `@DirtiesContext`).
- *SDD 三個 level:* 「Spec-first → 絕大部份目前主流方法能達到的程度；Spec-anchored；Spec-as-source」, citing the paper "Spec-Driven Development: From Code to Contract in the Age of AI". Old SDD vs new: 「RUP → CASE Tool；AI → LLM」.
- *Context vs Form:* 「Focus on Form: Code-First → 要自建 LLM Model；Focus on Context（窮舉 Context）: TDD (Test-First) → 絕大部份的人只能走這條路」; enumerate context along the SDLC (Requirement → Analysis → Design → Implement → Test). This is the theoretical backing for the selection's corrected thesis 「變異數在 loop 裡，不在 spec 裡」: you cannot change Form (the model), so all leverage is in the enumerated context — spec, conventions, patterns.
- *需求 vs 規格:* 「需求 (Requirement) — What to do (Problem Domain on Real World)；規格 (Specification) — How to do (Solution Domain on Machine Runtime)」, with Michael Jackson's Problem Frames and Daniel Jackson's "Three Directions in Design".
- *Day 2:* Lab 1 (91 Apps, Create ToDoItem) — 「從一張 Event Storming 便利貼，到 11 個 Java 類別」; "AI 產生程式碼檢查規則在那裡"; **Four-Form Patterns (Pattern, Rules and Gates) and when each is produced**; the author's own diagram prompt 「輸入 spec, pattern language(法律) → (LLM <-> Code) → 檢查腳本 → violation list」; 「如果公司有自己的規範、Pattern 以及 Rule，如何新增到目前的 repo、workflow 之中」; the **雙迴圈實作地圖** — 「把 Human → Context → LLM → Validation → Machine 這條鏈上的每一段，對應到這個 repo 裡真正存在的檔案、腳本與 hook」; 「formal picture of mental picture → 就是 Four-Form Patterns」.

**Flags for November.**
1. *Terminology collision.* Teddy defines 規格 as *How* (solution domain) and 需求 as *What*. The selection's 契約篇 says 「只做 what」. Define the words in the 總論 or the workshop alumni (the most engaged audience for this theme) will read the series as confused.
2. *Position on Teddy's ladder.* The title "spec is the new source" was dropped, yet Teddy's third rung is literally "Spec-as-source". State where the series sits (spec-anchored, with variance as the acceptance metric) and why it does not claim rung three.
3. *The third experimental arm is ready-made but not the author's.* `execute-uc`, the check scripts and hooks live in Teddy's course repo. Re-implement in the author's own repo before publishing details, or ask permission; cite the workshop, not the code.
4. *Reuse the checklist as the violation metric.* The selection's 變異篇 wants 「review 約束違規數」; the 16-item compliance list is a prototype of exactly that, and it separates "looks professional" items (1–4, always pass) from "only a skill can supply" items.
5. *A second anchor candidate.* The 2022 讀書筆記 (f7b7a7a8-c8b6-435f-8c18-38f24be5e326) holds Kahneman's 《雜訊》 with the quote 「人類只要做出判斷，就會有雜訊。這些雜訊比我們以為的還多」. Kahneman's *noise audit* — same case, many judges, measure dispersion — is the exact shape of "同一份規格跑十次". Anchoring the 總論 on *Noise* gives a book spine (the format that finishes best) and makes the point that variance is not an AI defect but a property of any judgment loop.
