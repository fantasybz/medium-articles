## 一句話的聲音

**用最短的句子下最硬的判斷，但每個判斷前面放一句話讓讀者站穩、後面放一句話告訴他這意味著什麼；證據一律外包給具名來源，意見一律掛第一人稱標記；不寫小結、不喊口號、不對讀者下命令。**

拆成三個可檢查的分項：

1. **判斷要硬**：「不是 X，而是 Y」是骨幹句型；「因此／然而／換句話說」在他筆下是零。
2. **證據要掛名**：數字一定帶樣本數與領域，意見一定掛「我認為」或「我的建議值（不是業界標準）」。
3. **軟組織不能省**：導讀句、解讀句、過場句、術語的第一句解釋。上一季四篇全都有，十月四篇大量掉了。

四個時期的骨架沒有變，變的只有外衣：

| 時期 | 自稱 | 標點主力 | 收尾 |
|---|---|---|---|
| 2021–2022 | 筆者／我／小弟 | `(半形括號)`＋`；`＋`~` | 【引】「留到後續的主題文章再咬文嚼字。」 |
| 2023 | 筆者（只在後記） | `(括號)`＋「」 | 「後記」推書＋連結卡 |
| 2025 | 我（開場一次「筆者」） | `：`＋「」 | 「結語：」＋反問 |
| 2026 | 無人稱（總論用「我」） | `：`＋`—`＋表格 | 金句 blockquote＋下一篇預告 |

**貫穿五年不變的四件事**：導讀句以冒號收尾、事實掛具名來源、意見掛人稱標記、收尾用「不是 A，而是 B」。這四件事是這本手冊的地基。

## 一、人稱、姿態與讀者關係

### 1.1 三檔聲音，由文類決定，不由段落決定

| 檔 | 用在哪 | 第一人稱 | 對讀者 | 逐字例 |
|---|---|---|---|---|
| **立場檔** | 總論、結語、後記 | 「我」可高頻 | 「你」＝要動手的工程主管 | 【引】「**我認為 2026 就是 Kubernetes 出現前後的那個時間點。**」（上一季總論） |
| **手冊檔** | 深掘三篇正文 | 幾乎歸零 | 「你」指涉組織資產 | 【引】「最後一條紅線：如果提案裡出現「我們要自研 agent runtime」，把它刪掉。」（組織篇） |
| **敘事檔** | 第一手經驗段 | 「我」＋場景 | 不喊 | 【引】「今年 8 月在模式語言工作坊，我用同一個需求—一個 Product aggregate 加一個 CreateProduct use case—跑了兩種方法」（測試篇 §七） |

切換點是「從敘事轉為下判斷」或「從轉述轉為表態」。這條規則 2021 年就成立：【引】「先假定大家跟**筆者**一樣有概略地認識Specification by Example(SBE)」（2021-12-28，前面整段都是「我」）。

**不可以**在手冊檔的規格段落裡插「我覺得」，也**不可以**把立場檔的「我認為」改寫成無主詞斷言。

### 1.2 「筆者」只剩三個合法位置

1. **AI 協作說明樣板**：【引】「本文由**筆者**提出初步構想與章節架構，文字撰寫由 AI（Claude）協作完成，再經**筆者**逐節校閱與修訂後定稿。文中觀點與判斷為**筆者**所持，文責亦由**筆者**自負。」（八篇一字不差）
2. **自我引用**（References 的「筆者筆記：…」）
3. **明確標記「這是我的估計／我沒實測」**：【引】「**比例是筆者暫定的啟發式，待 pilot 校準**」

【實測】上一季四篇「筆者」各 4 次，全部在樣板裡，正文 0 次。十月四篇正文出現 9 次（總論 L578／L594／L599、測試篇 References、Review 篇 L112／L219／L340、可靠度篇 L21／References），**逐條檢查後全部屬於第 3 類**，而且全在 §9.2 P11 的保護清單裡。**所以這一條在十月沒有事情要做**：不要把它們改成「我」，也不要因為「筆者」看起來老派就刪。新增文字才適用「用我不用筆者」。

### 1.3 「讀者」是禁詞，但要分清三種用法

【實測】上一季四篇「讀者」0 次；2025 春季三篇 0 次。舊期則相反：【引】「眼尖的**讀者**可能馬上察覺那裡不對勁？」（2022-02-28）、【引】「**請讀者細心品嚐**以下滋味。」（2023-05-12）、【引】「就留給**讀者們**發揮想像力了…..。」（2022-02-28）——這是 2022 的檔位，**不可回退**。

十月四篇三處【實測】：

- 可靠度篇 L212 **必改**：✗「**讀者**第一次算完多半會發現：可靠度目標訂在哪一格，比 agent 的準確率更決定人力。」→ ✓「**你**第一次算完多半會發現：…」
- 總論 L609 **建議改**：「台灣**讀者**的實況多半是 15 年的 legacy monolith」→「台灣團隊的實況…」（第三人稱指涉讀者群，同一種毛病）
- 總論 L31 **保留**：「有**讀者**回覆說，tester 現在用 vibe coding 做丟棄式的測試工具」——這裡的「讀者」指真實回覆的人，不是對本文讀者的稱呼。

### 1.4 「我們」只有兩種合法用途

- **他人口白**（2026 唯一用法）：【引】「- **我們**要不要成立一個 AI Agent Team？」（上一季總論的 VP 提問清單）
- **要避免的說法**被引述時：【引】「部署次數很多，所以**我們** DevOps 做得很好」

2025 另有一種「作者＋讀者＋工程社群」用法：【引】「在傳統程式設計中，**我們**習慣了確定性的世界」（2025-08-11）。**十月不要新增這一種**——上一季四篇的 5 個「我們」沒有一次是共同體用法。

### 1.5 自嘲已經退場，剩下冷面反諷

2021–2022 的自嘲密度極高且幾乎全在括號裡：【引】「讓其它組別笑一下**(誤)**」（2021-12-28）、【引】「**而筆者又太弱才補上的部份**」（2022-02-28）、【引】「**剩下3% 就是筆者加上的贅字 … 請多包涵 ！**」（2022-07-13）。2025 只針對過去的自己，一篇一次：【引】「**真的讓人哭笑不得**」（2025-08-11）。

2026 自嘲歸零，只剩冷面反諷，語氣仍是斷言：

> 【引】「組織應該刻意把「review agent 的 PR」設計成 junior 的訓練路徑，而不是把這件事全部留給 senior，**然後困惑為什麼三年後沒有人能接班**。」（上一季總論）
> 【引】「特別講 flaky tests：對人類是 5% 的煩躁，**對 agent 是毒藥**。」（技術篇）
> 【引】「Dependency 安裝要十分鐘的 sandbox，**沒有人會想用第二次**。」（技術篇）

【實測】上一季四篇與十月四篇：emoji 0、`！` 0。**潤稿時不要為了「讓語氣輕鬆一點」加任何一個，冷面反諷句一句都不要拿掉。**

### 1.6 從不對讀者下命令

2022 的祈使句一定加軟化詞：【引】「**試著**找出與關注資料有所接觸的功能、特性」（2022-05-09）、【引】「**別擔心**一直 Extract Helper 會不會造成 helper 滿天下」（2022-07-13）、【引】「**切記**過程中要記錄到過那些地標」（2022-05-09）。2025 改成無人稱規範句：【引】「**請務必**對個資與敏感內容進行遮罩或摘要化處理。」（2025-08-11）。上一季四篇零祈使句，建議一律寫成「我會核准／我不會核准」或「原則一句話：」。

**例外**：十月的紅線宣告是刻意的祈使句，**不要軟化**——【引】「**不要第一天就在全部 repo 套指派者禁令**：先有可驗證的格，再有禁令。」（Review 篇 L361）

## 二、句子與段落的節奏

### 2.1 目標值

| 指標 | 目標（依上一季四篇） | 十月現況 | 動作 |
|---|---|---|---|
| 平均句長 | 45–56 字 | 同區間 | 不動 |
| 句／段 | 1.5–2.1 | 1.8–2.6 | 拆段 |
| 每千字破折號 | **≤ 3.2** | 5.4–7.5 ✗ | **砍一半** |
| 每百句分號 | **≤ 5** | 24–33 ✗ | **拆句** |
| 全形冒號 | 50–70（高密度是特徵） | 同區間 | 不動 |
| 全形括號 | ≤ 20 | 總論 49 ✗ | 括號內容外提成句 |

**句長沒問題，段落數不夠、標點超載才是問題。**

### 2.2 連接詞：只有七個可以用

**允許**：但、所以、也就是說、其實、實際上、事實上、相反。
> 【引】「**相反**，正因為世界會變，**所以**才需要計畫。」（2025-05-10）
> 【引】「**也就是說**，你並不是「只為了萬壽菊」才這樣做」（2025-05-24）

**禁用**：因此、然而、但是、於是、不過、當然、換句話說、首先、其次、再者、總之、綜上所述。
【實測】上一季四篇與十月四篇：因此 0、然而 0、但是 0、換句話說 0、也就是說 0、當然 0、首先 0、其次 0、小結 0。2023 七篇同樣是 0，「但／但是」12 次是唯一高頻轉折詞。

**檢查時要排除的假陽性**：十月「不過」命中 2 次，但都是可靠度篇的「任一條**不過**」（＝任一條沒通過），不是連接詞。grep 要加 `-v "任一條不過"`。

承接靠三樣東西，不靠連接詞：**冒號導引句**（【引】「三種規模對照：」「寫作原則只有兩條：」）、**時間副詞**（【引】「久而久之，」「回頭看看，」）、**代詞回指**（【引】「這讓我聯想到 XP（Extreme Programming）的核心價值之一：勇氣。」2025-08-11）。

### 2.3 破折號：正確用法只有一種

**2021–2025 的中文正文裡破折號幾乎不存在**：2021–2022 四篇的「—」全落在引文署名（【引】「— 土井英司 <一流的人讀書，都在那裡畫線>」）、英文原句內部、圖說專名；2025-05 A 篇 0 次、2025-12 中文版 0 次。〔推測〕英文版憑空長出的 em dash 是譯文特徵，不是他的中文特徵。

**2026 起破折號成為正式工具，但只有一種功能：前半下判斷，後半立刻給理由或改寫，無空格、貼在句中。**

> 【引】「Agent Team 永遠不可能比 domain team 更懂 business context—而 context 恰好是 agent 產出品質的決定因素。」（上一季總論）
> 【引】「Context window 不是瓶頸，注意力才是—什麼都寫，等於什麼都沒寫。」（技術篇）
> 【引】「每個指標都會被 game—不是因為有人惡意，而是 Goodhart's law 的日常運作。」（營運篇）

**夾註型「—…—」全篇最多一次**，上一季總論只用了一次：【引】「agent 時代最稀缺的能力—拆解問題、定義驗收條件、判斷產出品質—恰好要靠大量 review agent 的產出來練成。」

**十月的四種錯用，各給改法**：

| 錯用 | 十月實例（逐字） | 改法 |
|---|---|---|
| 當「與」用 | 「兩條軸：**blast radius**—改到 auth、payment、schema、infra，還是內部工具—與**可機器驗證的程度**—有沒有 constraint tests 與 mutation 報告。」（Review 篇 L41，一句三個破折號、無動詞） | 拆成兩句，每軸一句，各配一個冒號 |
| 當冒號用 | 「「已核准」「資安同意」「緊急」—去 ticket 系統…查」（Review 篇 §六） | 改全形冒號 |
| 當引用標記用 | 「pass^k 掉了，先回頭修 harness—技術篇」（可靠度篇 L319） | 改成「（見技術篇第 X 節）」 |
| 一句裡兩個以上互相打架 | 「只在測試是 agent 自己寫或改過的時候—出題者與考生是同一個—它才變成「自我申報」」（總論 L21） | 插入語外提成獨立句 |

**規則**：一句話最多一個破折號；夾註型全篇最多一次；引用標記型一律改括號或獨立句。

### 2.4 他真正的停頓工具：冒號與「」

**冒號是主力**，四種職務，全部有逐字例：
1. 引出清單：【引】「它應該具備以下特徵：」（2025-05-10）／「Ownership 的切分如下：」（上一季總論）
2. 引出原文：【引】「書中提出三個理由，簡單卻犀利：」（2025-05-10）
3. 句中下定義（取代破折號）：【引】「Kent 形容自己出現恐慌反應：快速呼吸、視線變窄、起雞皮疙瘩。」（2025-05-10）
4. 引出直接引語：【引】「就在這時，有人說：「往山坡走，我們一定會遇到伐木路。」」（2025-05-10）

**「」不是引用，是他的加粗**：【引】「一份有效的計畫，不是「多詳盡」，而是「能否被用來思考與調整」。」（2025-05-10）。第三種用途是反諷（2025-12 特有）：「高級一點的監控」「開箱即用」「看起來沒事」。

### 2.5 分號只做對稱對比，一句最多一個

> 【引】「左側為對SUT一無所知**；**右側則代表百分之百了解SUT」（2021-12-28）
> 【引】「過去，寫程式像是在打造一座精密的鐘錶…可測、可控**；**未來，開發軟體更像是在馴養一隻寵物 AI」（2025-08-11）

**十月的錯用是拿分號串三件以上的並列**（Review 篇 §二第 4 條一格塞兩篇研究、七個數字、四個原因、一條處方；可靠度篇「處方三條」）——那是清單被壓成散文，不是對比，必須還原成列點。

### 2.6 段落與短句

段落 1.5–2.1 句，最典型的形狀是「一句導引 → 冒號 → 表格或清單」。雙句段落的固定形狀是「宣判 ＋ 後果」：

> 【引】「分級的原則：看的是**出錯後的回復成本**，不是操作的複雜度。開一個錯的 PR 可以關掉；發錯一封對外郵件收不回來。」（技術篇）
> 【引】「表裡最重要的一格是最後一列：**production ownership 永遠在 domain team**。任何把「agent 寫的 code 出事了」歸給 platform team 的設計，都會在第一次 incident 之後崩潰成互相指責。」（組織篇）

**短句永遠有主詞，永遠是宣判，從不是碎句**：【引】「這是兩件完全不同的事。」（上一季總論）／【引】「Prompt 只是 context 層裡的一小片。」（技術篇）／【引】「而如今情況已經改變。」（2025-08-11）／【引】「而這旅程不該獨行。」（2025-05-24）。**跨五年零例外：沒有任何一句是無主詞的名詞碎句。**

## 三、鋪陳一個論點的標準動作

### 3.1 數字：四拍，缺一不可

範本（上一季總論）：

> 【引】「**先用兩組調查數字定錨。**Google 的 2025 DORA report（**近 5,000 名受訪者**）顯示，**90% 的工程師已在工作中使用 AI**，每天中位數投入 2 小時—但對 AI 產出抱持高度信任的只有約 24%。Stack Overflow 的調查則顯示，AI agent 的使用率一年內從 31% 跳升到 59%，同時有 87% 的開發者擔心 agent 產出的正確性。**兩組數字合起來讀，訊息很清楚：採用早已不是瓶頸，信任與驗證才是**—這正是後面 harness 與 eval 兩章要解的問題。」

四拍：① 宣告我要用數字定錨 → ② 樣本數在數字之前 → ③ 數字本體 → ④「合起來讀」的收攏＋指向後文。**十月四篇的通病：只有第 ③ 拍。**

第二種形狀（先貶低表面數字，再指出真正意義）：

> 【引】「OpenAI 公開的 Harness Engineering 實驗最值得注意：三位工程師透過 Codex，在約五個月內產生約一百萬行程式碼、約 1,500 個 PR。**但真正的重點不是 LOC**，而是他們發現工程師的工作開始變成「**設計 environment、constraints、feedback loops**」，而不是直接寫程式碼。」

2021 年就有同一副骨架，只是解讀句是嗅覺式的：【引】「**嗅到了一點 The Three Ways 中 AMPLIFY FEEDBACK LOOPS 的味道**。」（2021-12-28）、【引】「**果然如此優良使用者流量站台，必然是地緣廣告商兵家必爭之地。**」（2022-02-28）

**十月最急的四處失守**（詳見第十章示範 3、7、13 與 §9.1 N6）：總論 L149 的「正確的有 74% 看得出來，錯誤的只有 49%」句子沒寫完；測試篇 L283 一句話七個數字；可靠度篇 L136「pass@1 是 66.50%，pass^20 是 47.53%」沒有一句人話；總論 READY 的「0.3 個百分點 vs 近 10 個百分點」沒有機制解釋。

### 3.2 引研究：名字與動詞在前，數字在後

- ✗ 「一項從 38,709 篇灰色文獻中編碼 3,100 篇、建構出 26 個構念與 67 條關係的因果理論（2026 年 7 月）把 review 定位成…」（47 字的名詞短語當主詞，Review 篇 L21）
- ✓ 「一項 2026 年 7 月的因果理論研究把 review 定位成…。它的基底是 38,709 篇灰色文獻，編碼了其中 3,100 篇，建構出 26 個構念與 67 條關係。」

固定三拍 2022 年就定型：`鋪陳句（≤1 句）→ 原文（常中英並列）→ 解讀（1–2 句）`。

> 【引】「Gerald Weinberg 也在《Perfect Software》中強調：」→ `"The goal of testing is to provide information, not to prove correctness."` →「測試不應背負「保證品質」的幻想，它的職責是協助揭露資訊」（2025-05-27）
> 【引】「OpenAI 那篇 Harness Engineering 文章裡，我認為最重要的東西甚至不是 Codex，而是一句話：」→ `> **Make the system legible to agents.**` →「把 logs、metrics、traces…全部變成 agent 可以直接 query / operate / validate 的東西。」（上一季總論）

引用後的收束句型（2025-06 一篇就有六種，直接可抄）：「這段話帶來了重要啟發：」「這句話背後的含義是：」「這段話道出了…的精髓：」「這段話令人聯想到…」「正如 X 所言」「由以上內容可知」。

### 3.3 引書與名人：第一次出現一定給身分

這條從 2022 貫穿到 2025，零例外：

> 【引】「而本書新舊版本推薦序都是由 **Enrich Gamma 大神**所撰寫 (附上大神的 wiki 給大家參考，**這些關鍵字之父: Design Pattern, Eclipse, JUnit, Visual Studio, Azure DevOps Service**)」（2022-05-16，錯字照抄）
> 【引】「再引述**日本第一書評大師**土井英司所說過的一段話:」（2022-02-25）
> 【引】「在一次 2025 年的專訪中，**極限程式設計（Extreme Programming）之父** Kent Beck 被問到…」（2025-06-23）
> 【引】「多年前參加泰迪軟體教育訓練時，**Teddy 老師**常常引用《建築的永恆之道》裡的概念」（2025-06-23）

**十月缺身分的人名／機構清單（各補一句）**：James Bach（作者自己 2025-08-21 那篇就寫過「Satisfice（James Bach 官方站）— Context-Driven 與 Rapid Software Testing（RST）方法論」，照抄這個定位最安全）、Uncle Bob、Birgitta Böckeler（只給姓）、Humble & Farley（未給《Continuous Delivery》）、Martin Fowler、Lada Kesseler、Greg Brockman、Teddy、Linear、Ramp。

〔推測〕上一季四篇沒有任何人名與書名，可能是刻意的文體選擇；十月引入人名是新做法，所以「有人名但沒身分」是這一季新出現的問題，不是舊病。

### 3.4 舉例：可查驗的具體物，或有代價的場景

**兩種合法形式：**

(a) **before/after 對照 code block，後面必接一句對比解讀**：

> 【引】

(b) **有時間、對白、後果、代價的場景**：

## 四、章節與整篇的開場與收尾公式

### 4.1 整篇開場：四拍

> ① 產業共同提問（三個 bullet）
> ② 【引】「這篇文章是我對這三個問題的完整回答。先講結論：」
> ③ 英文金句 blockquote：【引】「**Own your Agentic Engineering Platform, but don't own the whole agent.**」
> ④ 路線圖句：【引】「**以下從市場現況、DevOps 的歷史教訓、組織設計、Buy vs Build 的判斷，一路推到具體的決策建議與前 90 天的行動藍圖。**」

**十月四篇全部缺第 ④ 拍。**Review 篇連「以下／接下來／先講」都是 0 次。

舊期另有兩種合法開場，**十月不用，但不可誤刪已有的**：心得體的【引】「**源起** 應該是11月左右的某的凌晨，哄女兒入睡後…」（2021-12-28）；2025 的三件套（題詞 → 一張圖 → 前言段），題詞是純英文無譯無出處：【引】`"If things seem to be going exactly according to plan, that's usually a sign of trouble."`（2025-05-10）。

### 4.2 節的開場：四種，沒有第五種

| 型 | 範本（逐字） |
|---|---|
| **(a) 導引句＋冒號＋圖表** | 「整個產業已經明顯從左邊往右邊移動，而且重心正在壓到最後兩個階段：」 |
| **(b) 回指前篇＋宣告本節加值** | 「總論給了概念圖，這裡把三個角色的分工落到 RACI 的精度：」／「總論給了好壞對照，這裡給可以直接抄的完整版」 |
| **(c) 定義句** | 「先把定義講完整。所謂 harness，是 agent 與你的工程系統之間的全部介面，可以拆成六層：」 |
| **(d) 失敗場景預告** | 「讓每個 agent 直連各個 MCP server，會在三個月內失控：每個 agent 都拿著過寬的 token、沒有集中 audit、沒有 rate limit、tool 名稱互相衝突。」 |

**十月違規的節，逐一點名【實測】**：

- 測試篇 §二：**直接以表格表頭開場，全系列唯一零散文開場的一節**。
- 測試篇 §五：以粗體標籤開場（「**Check 1：red-then-green。** 適用範圍先講。」）。
- 可靠度篇 §一：以裸數字開場（「34% 是 SWE-Gate 在 75 個 Python repo…」）。
- Review 篇 §三：以無動詞名詞片語開場（「兩條軸：**blast radius**—…」）。
- 總論 §八「定義：」、§九「症狀清單：」：只有兩到四個字的冒號提示，屬 (a) 型但太薄，各補半句定位。

（草稿宣稱「測試篇 7/9 缺、Review 6/8 缺」等計數，本手冊實測不成立，已降級為上列具名清單。）

### 4.3 節的收尾：一句可被引用的紀律或反直覺斷語

> 【引】「反直覺的是，這個順序跟「讓新進工程師快速上手」的投資完全同構—agent legibility 與 human legibility 是同一件事。這也是為什麼即使 agent 路線失敗，這筆投資也幾乎不會白費。」（上一季總論 §七）
> 【引】「太早追求 coverage，是 platform team 死掉最常見的方式。」（上一季總論 §十一）
> 【引】「原則一句話：**指標成對出現—速度指標必配品質指標**。單獨考核任何一個數字，你就會得到那個數字，以及它背後被犧牲的一切。」（營運篇 §四）

**「小結」二字：2021–2023 是 0 次，上一季四篇與十月四篇也是 0 次**（唯一例外是 2025-06 永恆之道那篇明寫了三個「小結：」小節，那是那一篇的體例）。**不要加**——收尾是一句紀律，不是一個標籤。

舊期的等價物是「延後處理」句型，這個習慣從 2021 延續到十月的「留給 12 月」：【引】「此篇文章並不打算深入去探討每個版本之間的變化與演化故事，**可以留到後續的主題文章再咬文嚼字**。」（2021-12-28）

**十月違規的節，逐一點名【實測】**（以表格／code block／後設句結尾）：

- 以表格結尾：測試篇 §三、§四；Review 篇 §二。
- 以 code block 結尾：Review 篇 §六（reviewer agent 的 system prompt）；可靠度篇 §四（`eval-report.yaml`）。
- 以後設結構句結尾：可靠度篇 §一（「這一段只做一件事：把「綠燈量到什麼」分層。」）。

其餘各節都有散文收尾，而且多數已經是一句紀律（例：Review 篇 §五【引】「閉環的三種形狀全部禁止；開環才允許—同 vendor 不同 session 只能 comment，它的 approve 不進訊號欄。」）。**這些不要動。**

### 4.4 整篇結語：轉折句 → 金句 blockquote → 一句「這比什麼更長期」

> 【引】「現在確實到了該投資 Agentic Engineering 的時間，但投資標的不應該是「自己的 agent」，而是：
> > **讓任何 agent 都能在你的 Engineering System 裡工作得很好。**
> 這會是比押注 Codex、Claude Code、Copilot 或 Devin 哪一家勝出，更長期的資產。」

深掘篇再加一句「下一篇講什麼」：【引】「Harness 蓋好之後，下一個問題是：你怎麼知道它有沒有用、值不值得繼續投資？這是第三篇（營運篇）的主題」

**十月結語的三個病**：

- 總論：短而雜（回到 Bach ＋ 2027 預測 ＋ 11 月預告，三件不相干的事），**沒有回收第一節的三個情境**。
- 測試篇：第一句在引入全新概念（探索式測試）然後立刻推走——【引】「還有一件 testing 的事，Bach 說它不能自動化…那是另一篇文章的題目，這裡只點到為止。」
- 可靠度篇：散文只有三句，是一份交接清單（見第十章示範 15）。

**修法**：結語必須回收本篇最強的敘事素材。測試篇回收【引】「25 個檔案…5 個測試全綠」與「5 個測試全綠，規格要的 replay 路徑從未被執行。」；總論回收三個情境；可靠度篇回收 34%，並考慮把 §五【引】「agent 找到被快取的標準答案（answer key），拿到 100%，真實能力是 68%」的故事移過來——那是全篇唯一有戲的素材。

### 4.5 TL;DR 與結語的密度必須對稱

【實測】上一季總論 TL;DR 363 字元、0 分號、最長句 129；Review 篇 715 字元、**8 個分號**、單句 231 字。TL;DR 減負的方向是「術語只留名字，不留定義」，格式不動（見 §9.2 P12）。

## 六、事實、意見與 hedge 的分界

### 6.1 三層標記，五年沒變

| 層 | 標記方式 | 逐字例 |
|---|---|---|
| **事實** | 句首具名來源 ＋ 樣本數 ＋ 年份 ＋ 中性動詞（顯示／發現／量到） | 「依據 web.dev…定義:」（2022-02-13）／「**書中提到** Role (角色) 就是一種關係」（2023-05-12）／「Thoughtworks 技術團隊**曾分享經驗**」（2025-08-11）／「Google 的 2025 DORA report（近 5,000 名受訪者）**顯示**」（上一季總論） |
| **意見** | 第一人稱認知動詞開頭 | 「**筆者認為**不只是閱讀商業書籍…」（2022-02-25）／「**我認為**：LLM 帶來的不是單純更高的抽象…」（2025-08-11）／「**我認為 2026 就是 Kubernetes 出現前後的那個時間點。**」（上一季總論） |
| **估計** | 括號標「不是業界標準／不是量測」 | 「至於規模，**我的建議值（不是業界標準）**：」（上一季總論） |

**外部原文一字不改照抄**，連 typo 也是：【引】「This cookie was blocked because it had the "SmaeSite=Strict" attribute…」（2022-02-28）。這條紀律從 2022 延續到 2026 的 arXiv 引用。

### 6.2 允許的 hedge，只有五種（2026 檔）

1. **括號直接標非標準**：【引】「我的建議值（不是業界標準）」
2. **承認與主流相反**：【引】「我的看法與流行的悲觀論相反：」
3. **預測標成預測**：【引】「順帶一個預測：到 2028–2030 年…」
4. **範圍而非定值**：【引】「花費可能從幾十美分到幾十美元不等」「約五個月內產生約一百萬行程式碼、約 1,500 個 PR」
5. **技術版本免責**（2025-08 學到的一組，最該沿用）：【引】「屬於**正在形成的**最佳實務；實際欄位與寫法**可能隨**規範與 SDK 版本調整。」／十月的版本：【引】「GitHub 的規則也會變（本文寫於 2026 年 10 月）」

**舊期的社交型 hedge，十月不可回退**：【引】「應該是11月左右的某的凌晨」／【引】「下圖為本組所討論出來的答案**(非正確解答)**」（2021-12-28）／【引】「約 98 weeks、2年內**應該可以看的完吧 ？**」（2023-05-12）／【引】「跟Agile or Scrum 底層思維有 **87% 相似**」（2022-05-16，假精確玩笑）。

### 6.3 禁用的 hedge

【實測】上一季四篇「當然」0、「或許」0、「大概」0、「試著」0。另外全樣本沒有：「不一定適用」「我的經驗是」「純屬個人觀察」「僅供參考」「事實上」「老實說」「坦白說」「個人淺見」「本文將」。

### 6.4 十月的誠信裝置：一個字都不能刪

這些是全系列的信譽來源，也是潤稿最容易誤刪的東西。**允許拆成獨立句子讓它們更醒目，不允許刪除、合併或弱化**（完整清單見 §9.2 P11）。它是 2021 年「(非正確解答)」的 2026 版。

**注意兩個位置問題**（可以改，而且應該改）：

- 可靠度篇 §四 READY 段四道免責疊在一起（不是 code／數字不移植／全數字在別篇／不承諾重現），字數超過主張本身。**處理方式是把主張前移、免責分行，不是刪免責。**
- Review 篇 §二第 5 條的【引】「兩個各自的比例，不是巢狀」出現在誤解形成之前，反而製造困惑。**正確做法是先把兩個比例各自講成完整句子，讓誤讀不可能發生，而不是刪掉澄清。**

## 七、版面：圖表、清單、程式碼、引用區塊

### 7.1 圖：前有導讀、後有解讀（跨五年最穩定的一條）

**2022 的三段式**：【引】「將學習的知識再畫成下方簡單圖解、讓自己可以快速回想、理解:」→ 圖 →【引】「由第一張擷圖中 www.momoshop.com.tw/main/facicon.ico request 來說，domain為 www.momoshop.com.tw 所設定的 Cookies就是1st Party Cookies。」

**2026 的標準**：一句冒號導引 → 圖 → 一句解讀，且解讀直接講結論不回頭描述圖。

> 【引】「把這個 harness 放進整個系統，就是公司真正應該擁有的那一層：」→（flowchart）→「注意：**擁有中間那一層，不等於自己再寫一個 Claude Code。**」
> 【引】「多數公司已經有 DevEx team、Platform team 或 SRE。agentic 歸誰？用這棵決策樹：」→（flowchart）→「原則一句話：**agentic platform 是 IDP 的下一章，不是平行宇宙**。」

**禁止**：把圖表裡的數字念一遍。上一季四篇沒有任何一次。

【實測】上一季總論 mermaid 前有「：」導讀 6/8；十月：總論 2/10、測試篇 1/4、Review 篇 0/4、可靠度篇 0/4。

## 八、他不會這樣寫（反例清單）

每一條都經過跨時期逐字比對，可直接當紅線。

1. **沒有主詞的碎句**。最短句仍是完整主謂：「數量真是驚人！！」（2022）、「這是做好測試工作的第一步。」（2023）、「而這旅程不該獨行。」（2025）、「這是兩件完全不同的事。」（2026）。**沒有「很難。」「不行。」「就這樣。」**
2. **連續名詞短語當一段**。名詞短語只活在清單項、表格格與 mermaid 節點裡；一進正文段落就補完動詞。
3. **中文正文的句中破折號當插入語、當冒號、當引用標記**（見 §2.3）。
4. **「因此／然而／但是／於是／不過／當然／換句話說／也就是說」**（上一季四篇合計 0 次）。
5. **「首先／其次／再者」的三段式**。序列一律用帶編號的標籤：「第一時機點-／第二時機點-」「情境1-／情境2-」「Rule 1:／Rule 2:」。
6. **「小結／總之／綜上／總而言之／由此可見」當段落標記**。2026 的等價物是結語的「不是 X，而是 Y」金句。
7. **emoji 點綴段落**。2025-05 的 emoji 是版面元件（節標前綴、bullet），不是語氣元件。
8. **驚嘆號**。（2021–2022 的「！！」是那個時期的情緒峰值標記，不可回退使用。）
9. **直接對讀者下命令**。沒有「你應該」「請立刻」「記得」「試試看」。
10. **CTA**。沒有「歡迎追蹤」「按拍手」；2026 只有制式一句「…歡迎交流。」（2021–2022 的「歡迎在此篇下方留下寶貴地clap」已淘汰。）
11. **拿研究、統計當論證武器而不給具名來源與樣本數**。2021–2023 共 16 篇：零筆研究、零統計、零百分比；2025-08 出現的百分比一律是設定門檻（「成功率達 95% 才繼續」）。**2026 開始引 arXiv，但每一筆都掛樣本數與日期。**
12. **設問而不答**。2022 商業區 22 個問號全部緊接答案或清單。
13. **設問當節的開場**（2025-08 起）。設問只出現在節中段，且多半包在引號裡當自問。
14. **把英文技術詞翻譯掉**。agent／review／PR／merge／check／gate／repo／diff／commit／harness／prompt 一律保留原文，直接當中文句子的名詞用。
15. **圖說是名詞短語**。圖說是完整敘述句。
16. **校到零錯字**。這是判斷「是不是他寫的」最快的指標之一：`Broswer`、`SmaeSite`、「不熟悉的的部份」、「Implemnetation」、「Tidy Frist」、「Enrich Gamma」都是原樣。**十月是 AI 協作稿，這條不適用於新增文字，但已存在的引文一字不改。**

### 示範 11｜可靠度篇 §三 L130：最承重的定義寫成一個粗體長句

**Before**

> 定義沿用總論第八節：golden set 的每個 case 跑 k 次；**pass@1 是單次嘗試的成功率，用 k 次重複跑來估—每個 case 是 k 次裡過的次數除以 k；pass^k 是 k 次全部成功的 case 比例；兩者都先 per case 算，再對整個 golden set 取 aggregate。**「至少一次成功的比例」是 pass@k，是另一個數字，本系列不用。

**After**

> 能力與可靠度是兩個數字，很多人把它們混成一個，所以先把定義寫死（沿用總論第八節）。
>
> golden set 的每個 case 跑 k 次。
>
> **pass@1** 是單次嘗試的成功率——每個 case 算「k 次裡過的次數除以 k」，再對整個 golden set 取 aggregate。它回答的是「這件事它平均做得到嗎」。
>
> **pass^k** 是 k 次全部成功的 case 比例——一個 case 只要有一次沒過，就不算。它回答的是「這件事它每次都做得到嗎」。
>
> 舉個 k = 5 的例子：某個 case 五次過了四次，pass@1 貢獻 0.8，pass^5 貢獻 0；另一個 case 五次全過，兩邊都貢獻 1。所以同一批 golden case 可以同時是「pass@1 93%」與「pass^5 67%」——第一個數字說它很行，第二個數字說你還不能放手。授權看後者。
>
> 順帶把第三個容易混的排除掉：「至少一次成功的比例」是 pass@k，是另一個數字，本系列不用。

### 示範 13｜可靠度篇 §二 L39–81：三個 code block 連放，中間零文字

**Before**

> Before 是每次都要人重講的那句評論：「請不要在這裡直接 new HttpClient，用 `clients.http()`」。After 是它變成的三樣東西：

> ```

**After**

> Before 是每次都要人重講的那句評論：「請不要在這裡直接 new HttpClient，用 `clients.http()`」。它每次只審一個 PR，講完就沒了。After 是它變成的三樣東西——一個可執行的檢查、一條有主人的規則、一道 agent 改不動的門。

> ```python

> ```

> ```
> …（不動）…
> ```

### 示範 15｜可靠度篇 §六：結語是一份交接清單

**Before**

> 三個數字進月報：constraint pass rate、pass^5、oversight budget 的 r。G2 多四條。可靠度篇的兩個產出—pass^k 與 r—12 月會變成 SLI。
>
> > **綠燈告訴你 agent 沒把功能弄壞；constraint tests 告訴你它有沒有守住團隊的規矩；pass^k 告訴你能不能放手。三個都要，順序不能反。**

**After**

> 回到這一篇開頭那個 34%。SWE-Gate 量到的不是「agent 很爛」——那 644 個修補全部通過了功能測試，它們在多數團隊的 CI 上會是綠的、會被 merge。它量到的是：**綠燈這個訊號，從來沒有承諾過要涵蓋 reviewer 在乎的事。**過去我們不在意，因為寫測試的是人，出題者與考生不是同一個。現在不是了。
>
> 所以這一篇給的不是「更嚴格的 CI」，是三個各自回答不同問題的數字：constraint pass rate 回答「它守住團隊的規矩了嗎」，pass^5 回答「同一件事做五次還會對嗎」，oversight budget 的 r 回答「那我要付多少人看」。三個都進 leadership 月報，G2 因此多四條。
>
> > **綠燈告訴你 agent 沒把功能弄壞；constraint tests 告訴你它有沒有守住團隊的規矩；pass^k 告訴你能不能放手。三個都要，順序不能反。**
>
> 可靠度篇的兩個產出——pass^k 與 r——在 12 月會變成 SLI（service level indicator，你對外承諾的服務水準指標）。這一季量出來的東西，下一季要開始被追責。

**改了什麼**：回收開場的 34%、三個數字各配一個它回答的問題、金句前補鋪陳、SLI 補 gloss、加一句指向下一篇的判斷（不寫 12 月的內容，P17）。**所有數字、指標名稱與金句一字未改。**
