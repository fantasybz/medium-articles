> 2026-09-24 依作者要求更新。搭配 [STYLE.md](../../STYLE.md) 使用，適用於十月四篇與後續系列的撰稿、逐句潤稿及中英翻譯。作者當次指示優先，其次是共用風格；本檔說明如何落實。
> 舊文的逐字引文、統計、歷次 before / after 與當時的保護清單，完整保存在 [歷史分析](voice_brief.history.md)。它們描述的是舊稿，不是目前稿件的量測結果，也不是永久禁令。

## 一句話的聲音

**把動作與意思說完整，從真實經驗帶出思考，再作出有依據的判斷。** 保留技術立場，也讓接手問題的人、他面對的限制，以及作者為什麼在意這件事，留在文字裡。

舊分析把「短句、硬判斷」推得太遠，也把少見的用詞誤當成禁詞。現在以清楚、自然與可信為準：不追求最短，不要求每段都下結論，也不靠固定反轉句製造力道。

## 一、人稱、姿態與讀者關係

說明規格時把條件講清楚，談自己的經驗與判斷時自然使用「我」。段落可以從敘事走向分析，不必把整篇鎖成單一口吻。「我認為」有助於區分意見，但同一段已交代立場，就不必每句重複。

「筆者」「讀者」「我們」都不是禁詞。選擇取決於指涉是否清楚：「我們」是作者的團隊、作者與讀者，還是引文中的人物？不能用模糊的「我們」代替沒有依據的共同經驗。

讀者遇到的阻力要具體寫出來：時間不夠、資訊不足、流程尚未建立，可能都比「不夠仔細」更接近問題。建議可以直接，但要交代理由與適用情境。幽默、自嘲與感謝可以自然保留，不必刻意加，也不必因舊稿詞頻低而刪掉。

## 二、動作與句子的節奏

逐句確認誰做、對什麼做、為什麼做。上下文已清楚的主詞不必反覆寫；動詞的對象與必要步驟則不能省成筆記。

| 太省略的寫法 | 依情境補足 |
|---|---|
| 量 | 量測行為或結果、統計次數與比例、衡量效果 |
| 跑一次 | 執行一次測試、重播一次事件，或重新執行同一任務 |
| 收報告 | 收集、彙整或審閱報告，依實際動作選詞 |
| 擋掉 | 阻擋 PR 合併、拒絕這次工具呼叫 |
| 放出去 | 放寬哪一類任務的授權、開放哪些操作 |
| 綁人 | 讓核准紀錄對應到負責的人 |
| 接進去 | 把檢查納入 CI、把哪一份結果交給下一步使用 |

不是把單字一律改成雙字。「先看一個例子」「把問題說清楚」都很自然；「進行量測作業」通常也不比「量測」更清楚。

短句可以停頓，長句可以承載完整關係。讀起來吃力時，先拆開多重條件、插入語與過長的主詞，不要為了字數刪掉動作、因果或證據限制。

「因此」「不過」「也就是說」可以用，前提是前後真的有相應的因果、轉折或解釋。詞頻不是禁用清單。中文破折號依發布格式使用單一 `—`，避免多個插入語擠在同一句；分號、括號與冒號也沒有全篇配額。段落可以承擔提問、場景、解釋、轉折或判斷，不用平均句長或「每段幾句」當硬門檻。

## 三、讓經驗帶出故事與溫度

先從已有素材找：工作坊的需求與實作、閱讀時停下來思考的一句話、會議上的問題，或團隊真的遇過的限制。把「遇到什麼、看見什麼落差、為什麼值得追問、如何影響判斷」接起來。這是思路提示，不是每節必套的公式。

規格段落不必硬加場景，也不能替紀錄補出未曾記載的對話、情緒或事故。例如，工作坊裡「測試全綠、replay 沒有執行」的力道，來自交付看似完整、需求卻仍有缺口的落差。把它說清楚，比補一句「令人震撼」更能讓人理解作者為什麼在意。

## 四、語意、邏輯與證據

逐句精修同時核對相鄰句與整段論述：

- 指涉：這個「它」「這裡」「三個數字」指什麼？跨篇沿用時，定義有沒有變？
- 推論：觀察到差異，是否就寫成造成差異？個別案例，是否被推成所有團隊都適用？
- 條件：必要條件是否被寫成充分條件？通過已執行的檢查，是否被誤寫成沒有缺陷？
- 指標：分母是人、判斷、PR、任務還是執行次數？下限、上限與四捨五入是否一致？
- 前後一致：正文、圖表、程式範例與結語，有沒有對同一個流程作出不同承諾？

研究保留來源、樣本與領域；相關性、作者推論、示範值與實測分開寫。需要解釋機制時，有來源就歸因，沒有就明說是可能解釋，不能為了故事完整而填補研究沒有回答的部分。

## 五、開場、承接與結語

開場先讓人理解要解決的問題，可以用場景、提問、既有觀察或前文留下的疑問。術語初次出現時，補一句它在本篇的意思。段落之間交代前一步為什麼帶到下一步，不必每段都套「最重要的是」「這張圖要你帶走的是」或「不是 X，而是 Y」。

結語回到本篇的問題與最有分量的經驗，說明現在能作出什麼判斷、還有哪些界線。可以簡短整理重點，但不用為了金句省略限制，也不把下一篇的題目當成本篇唯一的收尾。

跨篇指涉用篇名或明確主題，首次提到另一個系列時交代名稱，必要時附章節與已確認的連結。不使用「幾月那篇」「下個月會談」「上一季營運篇」作為唯一線索。未定稿的主題若有必要提到，就明說仍在規劃；若只是交代限制，直接說明本篇未處理的問題即可，不必承諾發布月份。研究與事件日期照常保留。

後半部也要維持完整的敘述。規則清單前說明它解決什麼問題，清單後交代如何判讀與誰來接手；圖表後解釋意義，避免每節都用「這張圖要你帶走的是」重述一次。操作段落不必硬加故事，但結尾應讓讀者看見這些安排如何回應開場的困難。

## 六、台灣用語與英文技術名詞

使用自然的台灣繁體中文，沿用系列已建立的 agent、review、PR、CI、harness 等用法。動詞仍要選得準：審閱一份測試、核准一次合併、量測結果、統計比例。保留英文名詞，不代表周圍的中文也要壓成短語。

逐字引文保留原貌；作者自己的敘述可以修正錯字與不順的句子。不要為了模仿歷史稿件而保留新稿錯字。用語工具只提供建議，像「測試通過」不能機械替換成「測試透過」。

## 七、圖表、清單與程式碼

圖表前交代看什麼，後面解釋它如何影響判斷，不必逐格重述或硬配同樣長度的解讀。表格過長時，把推論移到正文，留下可比較的資訊。

清單用於並列或步驟，項目的動作要完整；幾個短例子也可以放在句中，不必遇到三項就強制列點。程式碼前說用途與前提，後面交代關鍵設定、限制與未完成的部分，區分示意、設計規格與可執行實作。文字精修改變公式、表格或圖的意思時，來源與發布圖片一起更新。

## 八、英文版保留相同的判斷

英文保留同樣的主張、動作對象、條件、證據界線與敘事順序，句子依英文語感重組。不必逐句對齊字數，也不能為了俐落增加中文沒有的斷言。中文修正推論後，英文對應段落、表格與圖說一起檢查，Medium 貼稿則由來源重新產生。

## 九、實際潤稿的順序

### 9.1 先讀全文，再逐句確認

先掌握這篇真正要回答的問題，再逐段確認動作、指涉、語意與前後關係。已經自然清楚的句子可以保留，不以修改句數當完成標準。

### 9.2 守住事實與作者立場

不虛構親歷、不改寫逐字引文、不把建議值寫成業界標準，也不把有依據的立場改成模糊口號。發現計算、推論或前後定義有誤時，依作者授權修正並留下理由；不能因舊保護清單鎖住一句話，就把錯誤留下。

### 9.3 檢查整篇與跨篇

對照 TL;DR、正文、結語是否說同一件事。系列共用的指標、流程、角色與授權條件，要逐篇核對。小樣本限制、人工核准與示範程式的邊界不能在另一篇消失。

另外從文章中段開始，把後半部連續讀到結束，涵蓋圖說、清單、操作步驟與跨篇交接。逐段確認是否退回省略的筆記語氣、轉折是否只靠標題、結語是否放大了前文的主張。最後掃描月份與相對時間的指涉，區分應保留的研究日期與應改成篇名的文章指引。

### 9.4 同步英文與發布包

英文依相同文意修正，再重新產生中英 `medium-paste.md`。改到表格或 Mermaid 時，更新 `figures.json` 與對應圖片，並檢查呈現結果。

### 9.5 驗證與紀錄

執行與變更相符的同步與格式檢查，重新計算動過的公式或例子。歷史句長、標點密度、逐字比對只能協助定位差異，不能取代閱讀，也不能用舊門檻阻擋作者新確認的修正。保留重要的前後對照與理由，讓作者能看見文意如何改變。

## 十、目前採用的示範

| 問題 | 修正方向 |
|---|---|
| 「這裡是量」只剩動作提示 | 「這裡則是量測 agent 的行為：先把邊界定清楚，才能記錄它多常嘗試越界，又有多少次被攔截。」 |
| 「綁人」省略責任如何留下 | 「每一次 merge 都需要一個人類 approve，核准紀錄必須對應到負責的人。」 |
| 「有 74% 的人能判斷正確」混淆分母 | 「面對正確斷言，判斷準確率是 74%。」保留研究實際量測的單位。 |
| 「測試全綠，所以功能沒壞」推得過遠 | 「測試全綠，只代表已執行的檢查沒有失敗。」再說明哪些需求仍未驗證。 |
| 「多讀一點」忽略現場人力 | 先交代 reviewer 面對的改動量與可用時間，再說工具如何整理證據、哪些判斷仍由人負責。 |
| 「11 月的契約篇」依賴未定排程 | 直接說明「來自規格契約的約束」這個主題；只有確實需要交接時，才註明是規劃中的延伸討論。 |
| 正文說 pass^k 描述樣本，結語卻說它回答「下次會不會成功」 | 結語同樣保留量測範圍：描述這批 case 在 k 次執行中的一致性，不保證下一次結果。 |

這些示範提供判斷方式，不是反覆套用的文句。舊範例留在歷史分析，引用前仍需核對目前的意思與證據。
