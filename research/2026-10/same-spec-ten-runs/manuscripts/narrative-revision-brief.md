# 敘事重寫：先讓讀者知道為什麼，再帶他走進研究

使用者讀後指出四個缺口：系列不連貫、缺少研究動機與問題、文字沒有故事性、看不懂每份 spec 的內容和差異。這是整體論述重寫，不是增加幾句過場或通過語言工具就能結案。

## 全系列共同追問

前面的 Agentic Engineering 系列討論誰對交付負責，以及文件、harness、驗收如何分工；已完成但尚未發布的「綠燈不是驗收」系列追問一份產出要有什麼證據才值得相信。這次往前一步：團隊如果把對 agent 的交代寫得更完整，怎麼知道這種交付方式值得反覆使用？一次成功不足以描述下一次；看到兩份程式不同，也不能直接把差異算成失敗。

現實決策用假設情境寫清楚：負責人可能考慮把一份精簡交代逐步補成細節、理由、自查與實作建議。這些內容需要維護。研究想知道增加的文字能改善哪一類結果，並先建立一個可以重複觀察的窄案例；本輪沒有量測人的工時或 ROI。不能寫成作者曾在會議被質問、親手看著四十次輸出、或一開始預期某組獲勝。

三個問題要在總論前半清楚提出，結尾及變異篇逐一回應：
1. 固定同一份指令包，重複生成十次，有幾次能完成相同驗收？
2. 換成精簡、展開、附理由與自查、再附可選寫法的文件條件，觀察到的驗收與資源是否不同？本輪僅做描述，無法分離各成分的因果效果。
3. 即使都通過，十份程式的實作是否相同；這些差異能告訴接手 review 的人什麼？

標題中的「同一份」指每一組內十次收到逐 byte 相同的 packet；四組合計四十次，不是同一份文字做四十次。跨組以 R01–R13 為共同基準，A0 和 A 仍有 CLI 範圍措辭差異。

## 真實的故事線與界線

真實起點：作者在 2026 年 8 月工作坊的單次實作中，看見測試全綠卻未完成要求的 replay。已有測試篇明確保留 N=1 的限制。這件事給出研究動機，沒有證明重複生成必然不穩定，也不是這次四十次的 task。只有總論詳講這個起點；其他篇不重演。

研究把問題縮小到作者文章 repo 的 codex_jsonl.py：能重現 text:123 被印成審查內容且 exit 0，以及 []/null 造成 crash。不是生產事故。研究代理從固定 commit 取出程式；作者提出方向、AI 協作設計執行，不冒充作者手動完成全部實驗。

為什麼選小 parser：有真實使用者介面與相容責任、起點可凍結、輸出與結束狀態可從外部驗證；可把一次性修補重複觀察。它無法代表大型 repo 或多回合 agent。禁止把研究動機偷換成「這篇教你修 parser」；parser 是用來讓研究問題具體的共同案例。

敘事轉折來自實際材料：一個看似簡單的型別修補必須交代相容與失敗優先序；四種文件把不同協助放進去；終態比對看不到 streaming 時點，所以另設 EOF 前 probe；最後四十份都通過，原本的組間問題未能分出高下，但實作與資源仍可分開描述。成稿時又查到 CLI 措辭缺口，必須留下限制。不能寫成不存在的執行中失敗、發現順序或研究者驚訝的回憶。

## 四篇各自完成一段路

- 總論：我為什麼從單次驗收追問重複交付；這次想知道什麼；為何選自己的小工具；四份交代大致給了什麼；結果摘要與研究仍未回答的決策。以 2–3 個必要表格為限，統計細節、全部 hash、停止路徑與 audit 計數移回研究附件。讀者不必先懂 AST 才能理解目的。
- 規格篇：真正把四份文件攤開。先交代共同任務和規範底線，用 R05 的同一問題連續展示 A0 的精簡規則、A 的展開說明、B 新增的理由與自查、C 新增的可選 helper/流程建議。標明是依凍結原文的中文節譯/摘要，不冒充實際送給模型的英文 prompt。再用 R08 的 usage 驗證與 R11 的 exit 優先序說明為什麼光寫「更健壯」不夠；全文和 R01–R13 留連結，13 行規格巨表不必原樣塞正文。說清楚哪些改動是說明、哪些是真正改了要求，包括 CLI 措辭缺口。讀者離開時能用自己的話說四組差異。
- 契約篇：承接四份交代寫好了，現在誰判斷做到沒有。從 R05 錯型案例的 stdout/stderr/exit 三個觀察，走到同樣文字何時輸出、EOF 前 probe，再到外部 driver 與三個 success 欄位；這是一份規格如何被翻成證據的故事。保留核准 F1 Mermaid 原文，但刪去重複研究背景與文獻導覽。驗收器也要驗證、隔離只涵蓋三 probes、涵蓋缺口都要交代，集中於一節即可。不要四處重播 CLI caveat。
- 變異篇：接過契約篇建立的計分方式，先看四個 10/10，說明每次的分母；回到三個研究問題回答觀察。用既有兩份 A0 實作例子讓讀者先看見不同，再解釋 hash/cosine 與 F2；不先扔一堆術語。成本與人力沒量到的部分分開。結尾回答團隊接下來能做什麼，並回到「一次成功是否足以評估交付方式」；結尾不能只剩限制清單。

## 用字與資料原則

遵守 STYLE.md：動作完整、台灣繁中、每段有承接、真實經驗推進思考、後半完成度一致。避免每段「不能、不是、未量測」佔據敘事，把限制放在主張出現的位置一次說清楚；研究附件仍保存所有方法細節。不要以問句標題接一個口號、不靠煽情形容詞製造故事，不把讀者當統計審稿人。

A0 已含完整邊界，不是含糊一行工單；A 本身也已有部分理由，B 是追加集中理由與六組自查，不能說 A 完全沒有理由。B 以 A 全文開頭，C 以 B 全文開頭；C 是可選純文字 pattern，不是原生 Skill、不強制 helper/類別/某種架構，也明示沿用原分支可以接受。R05 的 whitespace-only string 有效；missing/null/empty string 沒有訊息，所有其他非字串值 malformed（包含 0/false/空容器）。C 的 optional text helper 不能套到 root error，後者保留 str 轉換。

觀察：四組各十次全過 102 batch + 1 EOF probe；40 個預排名額無替補、重試或追加；每組 10 個正規化 AST hash，四十個亦不重複。驗收 ceiling 不等於四組等效，更不證明增加說明沒用。CP 雙側 95% 為 69.15–100，依賴獨立同分布共同 Bernoulli 假設；不必四篇都上完整統計課。模型生成 high，文章寫作 max。CLI 牌價估計 USD 5.692342 非帳單，不含研究/寫作/人力。

資料封存完全不改。本輪只改文章與發布包。舊品質通過紀錄只屬於舊稿，新的文字要重新核對、逐段潤飾及 MCP strict 檢查。

## 作者後續提醒：補齊讀者理解與判斷的過程

作者特別要求交代讀者從材料走到判斷所需的過程。這也符合 STYLE.md 對「前一句提出的問題，後一句是否真的回答」及「從觀察走到建議之間，是否少了理由或適用條件」的要求。不能只增加案例或解釋術語，還要讓讀者知道為什麼這些材料能支持眼前的判斷。

- 總論先解釋為何要重複同一份輸入，再比較文件條件；結果全數通過時，說明為何改讀資源與實作不能替可靠度排名。
- 規格篇用 null、false 與空白字串核對 A0／A 的預期行為；再用明標假設的錯誤，區分沒寫要求、實作判斷錯誤，以及仍不知道模型漏讀或誤解的部分。
- 契約篇逐行處理 `123` 與完成事件，累積狀態，再依 R11 和 R12 推到三個出口，讓讀者自行核對驗收預期值。
- 變異篇先用假設成功率說明十次全過仍有不確定性；先看真實候選，再用常數與簡化向量分開解釋 hash、cosine；讀資源時區分合計、中位數與停止門檻，最後把 review 工時紀錄接到維護判斷。

以上是逐段編輯的檢查方向，不是每段都要套用的固定句型。簡化例、研究觀察與後續建議應各自標明身分；後半部、圖表後的解讀與結語也要維持相同完成度。
