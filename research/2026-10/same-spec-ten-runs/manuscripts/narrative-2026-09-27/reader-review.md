# 讀者報告：「同一份規格，跑十次」四篇修訂稿

## 研究為什麼做、問什麼、四篇怎麼接

起點是 2026 年 8 月工作坊的一份實作：25 個檔案、5 個測試全綠，合規清單卻只通過 10/16。這次經驗說明測試可以和程式一起偏離需求，但只有一個樣本，說不出下一次會怎樣。作者因此想知道：團隊把給 agent 的交代補得更完整之後，這種交付方式能否反覆使用。研究問三件事：

1. 同一份 packet 生成十次，能通過幾次？
2. 換成四種文件條件，驗收與資源是否不同？
3. 如果都通過，程式是否相同？

四篇的分工如下：

- **總論**交代動機、共同任務與整體結果。任務是作者 repo 裡一支會把 `text: 123` 當成成功審查的 parser。
- **規格篇**攤開四份文件。
- **契約篇**說明要求如何變成 stdout、stderr、exit code 與串流時點這些外部證據。
- **變異篇**解讀分母、區間、程式結構與成本，並回答三個問題。

## A0／A／B／C 的差別

四份文件共享 R01–R13 這組要求。

- **A0** 是精簡條文，但邊界已經寫齊。例如 R05 明列 `0`、`false` 與空容器都算錯型。
- **A** 逐條展開，加上表格、固定的診斷文字，以及散在條文裡的理由。R13 另外多一句「新增 CLI 選項不在範圍內」。
- **B** 是 A 全文，再加一段非規範的集中理由與六組自查。理由包括：Python 的真假值不等於契約的判斷；逐事件驗證要和最終狀態分開。
- **C** 是 B 全文，再加一段可選的寫法建議。例如 text helper 不能套用到 root error；可以回傳結果物件，也可以就地分支。

所以三個層次的差別是：

- A0→A 改的是說明方式，外加一處措辭差異。
- A→B 增加「為什麼這樣要求」與「交稿前核對什麼」。
- B→C 增加「程式可以怎麼寫」。

規格篇 §三沿著 R05 並排四份文件，已足以讓讀者用自己的話說出差異，不再只剩抽象標籤。仍缺的是每份文件的篇幅量級（見第 4 條）。

## 問題清單

### Major

**1. 分工重疊：同一段背景要讀三到四次**
出處：總論 §五；規格篇 §四；契約篇 §一、§五；變異篇 §一、§五。

- **文本證據**：
  - 總論 §五已經給出 40/40、「69.15% 到 100%」、費用表，以及「四十份之間也沒有任何重複」。
  - CLI 措辭差異（「不需要」對上「範圍之外」）在四篇各完整解釋一次。
  - 變異篇 §一先用兩段重述前兩篇，才進入自己的問題。
- **影響**：篇與篇之間的交接句已經寫好，「連貫」的問題從斷裂變成了重複。依序讀的人到了變異篇，「然後呢？」的答案多半已在總論讀過。
- **建議**：
  - 在總論的系列導覽寫明「總論可單獨閱讀，後三篇各自展開一段」。
  - 後三篇的前情壓成兩三句，再附連結。
  - 措辭差異只在規格篇 §四完整說明，其他篇一句帶過。

**2. 「規格」一詞同時指 R01–R13 與四份文件**
出處：系列標題；總論 References「四份規格」；契約篇 References「四份凍結規格」。

- **文本證據**：
  - 總論 §四與變異篇 §一都得另外解釋「標題裡的『同一份』，指的是每一組的內部」。
  - 文中「交代」「文件」「packet」「指令包」交替使用。
- **影響**：初讀者容易把「同一份規格」理解成同一組 R01–R13 跑了四十次，正好和實際設計相反。同一個解釋需要出現兩次，就是用詞造成的摩擦。
- **建議**：在總論 §三定義一次：「要求」指 R01–R13，「文件」指 A0–C，「packet」指文件加上 seed。其後各篇照此統一。標題可以保留。

**3. 「實作各不相同」的推論超過 hash 能支持的範圍**
出處：變異篇 §三、§五。

- **文本證據**：
  - 變異篇說 hash 保留「屬性名稱、匯入路徑、常數與節點順序」。
  - 契約篇 §二說 REASON「只要求是非空的單行說明」。
  - 因此只要診斷文字或 docstring 不同，hash 就會不同。
  - 但變異篇 §五寫「差異落在狀態組織與控制流程上」，§三寫「每一次生成都寫出一份自己的程式」。
- **影響**：40 個不同的 hash 只能說明沒有兩份完全相同；組織方式的差異只由 A0 那一對示例展示。review 建議本身不受影響，因為檔案只要不同就得重讀。但「結構各不相同」這項發現被放大了。
- **建議**：
  - 在 hash 段落補一句：常數（例如 REASON 文字）也可能造成 hash 差異。
  - §五改成「至少在 A0 那一對上」。

### Minor

**4. 「由短到長」沒有量級**
出處：總論 §五、規格篇 §五、變異篇 §五。

- **文本證據**：三篇都拿篇幅順序對照費用，但規格篇的包含關係表沒有篇幅欄。
- **影響**：讀者無法判斷 C 比 A0 長一成還是一倍，也就難以理解費用差距的意義。這也是作者「各份 spec 大概內容」缺口剩下的一塊。
- **建議**：在規格篇的表格加一欄字數或行數，可以直接由凍結檔案計算，不需要重跑研究。

**5. 契約篇 §四流程圖的顏色沒有圖例**

- **文本證據**：原始碼有 `classDef own`／`buy`／`human`，其中 `human` 沒有被使用；正文只解釋了虛線。
- **影響**：讀者會去猜 own 和 buy 代表什麼。
- **建議**：刪掉顏色分類，或在圖前補一句圖例。

**6. 結語把方法設計和共變寫成了收穫**
出處：變異篇 §五、§六。

- **文本證據**：
  - §六把「分開記錄」列為「比一次綠燈多知道了幾件事」之一，同一段卻又說「三項判定每次都一致」。
  - §五寫「模型端費用則隨篇幅增加」，但 §四與總論都說明不把費用差歸因於長度。
- **影響**：前者是方法設計，不是本輪的發現；後者的語氣滑向因果，和前文保留的限制不一致。
- **建議**：
  - 把這一點移到最後談「做法」的那段。
  - 改寫成「費用合計也依 A0 到 C 的順序遞增」。

## 需要重組嗎

不需要整體重組。對照作者提出的四個缺口：

- **研究動機與問題**：已補齊。總論 §一、§二從工作坊的單一樣本，自然接到三個問題。
- **各份文件的內容與差異**：規格篇 §三基本到位，只差篇幅量級。
- **連貫**：問題已從「斷」變成「重複」，靠刪減就能處理，不必重寫。
- **故事性**：在總論 §一和契約篇的 `123`、`error:false` 例子最有效。

剩下的都是局部修正，除了上面六條，還有兩項：

- **變異篇開頭**：建議讓「exit 0 掩蓋錯誤」這條線帶出本篇的問題，取代開頭兩段前情回顧。這樣不需要虛構任何經驗。
- **跨篇格式與指涉**：統一系列導覽的格式（目前混用「→」和「｜」）。可靠度篇在規格篇和變異篇有 repo 連結，契約篇卻寫「目前沒有公開連結」，處理方式也需要一致。
