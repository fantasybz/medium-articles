# 規格修改卡：先辨認缺的是決定、說明，還是檢查

> **設計範例，尚未執行比較。** 第一張卡以本 repo 的真實 parser 與既有 R05 為背景，但卡中的「候選將 false 靜默略過」是假設錯法；正式四十份候選沒有出現這項驗收失敗。本卡提出的「展開規格加六點自查」比較、對應 packet 與跨任務評估都尚未執行。第二個 CSV 案例完全是假設，用來示範如何轉用這張卡。

這張卡供規格維護者、實作者與驗收負責人一起使用。先確認問題屬於哪一層，再選擇要改的內容。需求還沒決定時，增加理由不能替負責人作決定；要求已寫明、候選卻沒做到時，也不能只憑結果斷定模型沒有讀到規格。

## 一、先分清楚每種內容的用途

| 內容 | 它回答的問題 | 誰應確認 | 可以怎麼處理 |
|---|---|---|---|
| 未決需求 | 團隊還不知道應該接受哪種行為嗎？ | 擁有需求、介面或相容責任的人 | 保留問題、影響與暫行假設；會改變預期值的問題解決前，不把它寫成已定的驗收答案。 |
| 規範 | 交付必須做到什麼、不能做什麼？ | 規格 owner 與受影響的呼叫端 | 指出來源、版本、輸入條件、可觀察結果及例外。新增規範屬於要求變更。 |
| 理由 | 為什麼作這個選擇，容易在哪裡誤解？ | 規格 owner 與維護者 | 說明既有要求為何如此決定，以及考慮了哪些取捨；不能暗中新增限制。 |
| 例子 | 已定規則套到具體輸入，會得到什麼結果？ | 規格與驗收負責人 | 先由規則推導預期值，再核對例子；例子不會自動補齊未決政策，也不代表窮盡所有合法情況。 |
| 自查 | 交件前應重新核對哪個容易漏掉的要求？ | 實作者與驗收負責人 | 用問題指回既有條文；有實際執行結果時，連同證據記錄。自稱核對過不等於已通過外部驗收。 |
| 可選寫法 | 可以採用什麼實作安排？ | 實作者，必要時由架構 owner 協助 | 提供 helper、狀態或流程建議，同時說明其他符合同一契約的寫法也可接受。 |

若修改一段「理由」後，原本合法的實作變成不合法，就應重新檢查：這是否其實是規範變更。這項區分會影響文件審查，也會影響後續比較能回答什麼。

## 二、已填寫範例：R05 已有答案，候選卻可能把 false 當空值

### 先把事實與假設分開

既有 [展開規格 A 的 R05](../../../experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/A.md) 已規定：缺少 `text`、null、空字串表示沒有訊息；其他非字串值都算 malformed，包括 `0`、`false`、空陣列與空物件。非空字串原樣輸出，只含空白的字串也有效。[正式結果](../../../experiments/same-spec-ten-runs/RESULTS.md) 是四組各十份候選全數通過既定檢查，不能把下面的假設錯法寫回正式結果。

現在假設未來遇到一份候選，使用 `if text:` 作為判斷 text 的唯一分流，因而將 `false` 靜默略過。規格已有明文答案，這就不是「團隊還沒決定 false 的意思」。實際重現若確認這條程式路徑，能支持「實作把真假值與欄位契約混用」的診斷；仍不能從程式碼得知模型究竟漏讀、誤解，或受到其他上下文影響。

| 欄位 | 本例填寫內容 |
|---|---|
| 採用決定 | 指派本團隊 Python 工具 repo 的行為修補時，是否應在展開規格後附上自查，作為預設交代。本卡先示範 parser 版本；跨任務則須依同一項事前改寫政策建立各題版本，不能照貼 parser 原文。 |
| 已有依據 | R05 已定義錯型假值；R03 規定 malformed 的診斷與繼續讀取；R11 決定 EOF 的優先序。這些是已封存要求。 |
| 待調查症狀 | 假設候選靜默略過 `text: false`。這是未來可能遇到的錯法，不是正式四十份的觀察。若真的發生，先保留最小輸入、候選版本、stdout、stderr 與 exit。 |
| 目前診斷 | 若重現與程式路徑吻合，則已定要求未被實作；模型內部原因仍未知。 |
| 本次唯一改動 | 在這個 parser 任務內，P 是展開規格，Q 是相同規格**只加凍結 B 的六題原文**，另見下方來源說明；不附加 B 的兩段集中理由。P 與 Q 的既有要求、理由、例子、可選寫法、seed、工具權限與停止條件保持相同。兩份完整 packet 尚待建立及封存。 |
| 預期作用 | 希望六點自查減少不符合共同契約的交付；第二題可能提醒實作者重新區分各欄位的缺值、null、空值與錯型。false 靜默略過只是用來展開判斷過程的假設例子，並不是整份清單唯一的觀察目標。 |
| 不在本次改動內 | 不新增理由、不加入 helper pattern、不增加例子，也不改寫任何行為要求。本卡比較六點自查的整體效果，不能將結果拆成第二題或某個詞句的單獨效果。 |
| 驗收需要看到什麼 | 對假設的 false 訊息加有效完成事件，確認 stdout 沒有該訊息、stderr 有正確 malformed 診斷，並依 R11 得到 exit 6。也要保留 null、空字串與空白字串的正例，避免為抓 false 而破壞原本合法的行為。 |
| 相容風險 | 若日後把清單錯誤縮寫成「全部 text 一律嚴格」，就可能誤改 R09 根層 `error.message`。R09 保留舊的 `str()` 轉換，不能一律拒絕數字、bool 或容器。這是假設的清單措辭風險；凍結 B 的第四題明文要求保留此例外，本輪也沒有觀察到這項失敗。 |
| 合法自由 | 函式名稱、dict 或類別狀態、是否抽 helper，都不因自查清單成為新要求。外部驗收應容許契約內的不同安排。 |
| 負責人 | 規格 owner 核對自查沒有增加要求；QA owner 確認檢查能分辨已知錯法、也放行合法例外；接手 reviewer 記錄實際理解、修補與審閱投入。此範例尚未指派真人負責人。 |
| 採用所需證據 | 在事前選定的目標任務範圍，比較合格交付，另列各 requirement 的失敗，並一起記錄全部嘗試的模型費用、人工處理與文件維護成本。實務門檻、樣本規模及停止條件由實際負責人決定，不能沿用本輪四個 10/10 當效果證明。 |

### 用第二題走完一次自查，但比較單位仍是六題整體

完整清單見 [凍結 B 原文的自查區段](../../../experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/B.md)。從 `Possible self-review questions` 之後開始，共六題，依序指向 R01–R03、R04–R08、R08、R09–R10、R11–R12 及 R13。本卡在 parser 上的 Q 只採用這六題英文原文，不採用它前面的兩段集中理由；「R01–R13 才是完整契約」仍然成立。原研究 B 同時新增理由與自查，因此不能直接用原 A／B 結果估計本卡的清單效果。

第二題對應 R05 所在的欄位規則，中文節譯如下：

> R04–R08：是否依各欄位自己的規則，區分缺值、null、空值與錯誤型別？

讀到這一題時，先回到 R05，將容易混在一起的值分開：null 與空字串表示沒有訊息；false 雖然也是假值，卻是 malformed；只有空白的字串則是有效訊息。這一步是把已定的行為再核對一次，沒有新增規則。

再看假設候選如何處理這些值。如果 `if text:` 是唯一分流，false 就與 null 一樣被略過，這一題便有具體需要修正的地方。接著用卡片列出的輸入與三個出口確認結果；不能把模型在自查後回答「已符合」，當成實作已符合的證據。反過來，若錯把 null 也拒絕，或對空白字串做 strip，同樣沒有通過這一題所指向的要求。

六點清單涵蓋的要求比 R05 更廣。第二題讓讀者看見一個核對動作怎麼展開，但下一輪比較仍要觀察共同契約下的整體交付，也分別記錄各 requirement 的失敗。即使這類錯誤減少，也不能由此斷定是第二題改變了模型注意力，更不能忽略其他要求是否變差。

另一種可以研究的介入，是只增加一段理由，解釋 Python 真假值為何不能代替欄位契約。那需要另立 P、Q 與比較計畫；本卡的主要介入是六點自查，不包含那一段理由。兩者都可能有幫助，也都需要閱讀與維護，應各自用對應的證據判斷。

### 如何接到比較計畫

本卡與 [文件改動評估提案](document-change-proposal.md)、[比較計畫](comparison-plan-example.md) 共同處理是否把自查列為預設的問題。在同一任務內，P 是展開規格，Q 是同一份規格加自查。這裡用 R05 示範如何診斷與核對，比較計畫則處理目標任務、樣本與採用條件。實際使用時，請填寫該頁第六節的空白範本；示例任務數、效果門檻或成本上限都還需要實際負責人確認，不能直接當成標準。

跨任務時不能照貼 parser 的六題。CSV 若沒有串流、token 或根層錯誤事件，就沒有對應的 EOF、R08 或 R09 義務。跨任務比較要先固定自查改寫政策：每題只指向該任務 P 已揭露的要求，沒有對應時依事前規則標成不適用，不為湊滿六題新增限制。映射、例外與人工維護投入都要保存；詳見 [自查改寫政策](self-check-transfer-policy.md)。它衡量的是這套政策在目標工作上的效果，不能再稱為六句 parser 原文的普遍效果。各任務映射與完整 packet 尚未完成。

建立 P、Q 前，先確認驗收能抓到想研究的錯法，同時容許合法寫法；再核對 diff 只有六點自查，保留完整 packet 與 hash。若 pilot 發現要求或預期值本身有問題，先修正並另立版本。正式比較開始後，依預定規則保存每個名額，不在看到不喜歡的結果後修改清單、補跑或挑選樣本。

即使 Q 的通過率較高，也要考慮差異還有多大不確定性，是否足以支持跨過事前實務門檻，以及新增人力與費用是否可接受。若兩組仍全過，就回頭辨認缺的是辨別能力、任務代表性或樣本精度；不能直接宣稱六點自查有效或無效。

## 三、換到 CSV 匯出時，這張卡怎麼用

> **假設的產品需求，搭配固定資料教學。** 以下不是本 repo 原有的 CSV 功能，也沒有新增模型樣本。系列另以 [CSV 教學重播](workbench/csv-transfer.md) 實際檢查三種 oracle；它不驗證日期轉換或完整產品。

假設一個 CSV 匯出工具要新增日期欄格式化，呼叫端已要求保留輸入列序與重複列。沿用總論的三筆資料：第一筆姓名是`王,小明`，日期為 null，備註含換行；後面兩筆都是「李」、日期為 2026-09-28、備註為空，內容完全相同。既有要求表示，`王,小明`仍排第一，後面兩筆「李」都要留下。

但團隊還沒決定，缺日期時要輸出空欄還是拒絕。這時先留下問題，交給匯出功能的需求 owner；也要確認哪些輸入算缺日期。不能先讓 agent 選定一種表示，再把它寫成唯一正確的 expected CSV。總論後續假設 owner 決定保留空欄，並確認固定 header 為 `name,date,note`、每筆 record 可以用 LF 或 CRLF 結束、欄位內逗號與換行保持原樣，才繼續推導驗收。

| 內容層次 | CSV 案例怎麼填 |
|---|---|
| 已有規範 | 保留原列序與重複列；確認`王,小明`在前，兩筆「李」都保留。 |
| 未決需求 | 缺日期時輸出空欄或拒絕尚未決定。記錄 owner 與受影響的下游；依賴此政策的驗收預期值暫不定案。 |
| 理由 | 若已知下游依原順序對照來源、也把重複列當不同紀錄，就把這些依據寫下來；若不知道，不能為了讓規格完整而虛構用途。 |
| 例子 | Owner 決定空日期政策後，再推導三筆資料的完整輸出；不能拿一份 CRLF 範本排除同樣合法的 LF 表示。 |
| 自查 | 「輸出是否保留每一列的相對次序與重複次數？」這是可提出的自查問題，但是否加入文件並衡量效果，要另外定義一次介入。 |
| 可選寫法 | 可以建議抽出處理欄位表示的 helper；是否採用由實作者決定。helper 不得順便去除重複列、重新排序，或擅自決定未定的空欄政策。 |

如果候選自行排序，先核對它是否違反已定的列序要求，再考慮文件或執行回饋需要怎麼改。若分歧出在空日期的表示，就先處理需求決定。兩者都叫「匯出不對」，但修正的責任人與下一步不同；這正是修改卡需要保留內容層次的原因。

## 四、可填空範本

> **規劃範本，尚未接上執行器。** 可以留白，也可以明確寫「待 owner 決定」；把所有欄位填滿，不等於已經具備比較條件。

| 欄位 | 填寫內容 |
|---|---|
| 待作決定與 owner | ［誰需要決定是否保留哪一段文件；由誰承擔結果］ |
| 真實症狀／假設錯法 | ［分開記錄觀察證據與教學假設；附最小輸入、版本與輸出］ |
| 現有要求與來源 | ［條文、版本、caller 或相容依據；哪些行為已決定］ |
| 未決問題 | ［會改變預期值的問題、影響、暫行假設、需要誰回答］ |
| 初步診斷 | ［需求未決、表達有歧義、實作違反、驗收漏看、工具故障，或目前無法判定；附依據］ |
| 本次只改哪一類內容 | ［規範／理由／例子／自查／可選寫法；貼上唯一改動的確切文字］ |
| 為何選這項改動 | ［希望減少哪一種可觀察錯誤；機制是假設還是已有證據］ |
| 其他條件 | ［完整 P、Q 與 diff；共同 seed、例子、權限、停止與驗收版本；若改要求則另立新任務版本］ |
| 正例與反例 | ［一個應拒絕的錯法、一個應保留的合法例外；可觀察輸出與理由］ |
| 實作自由 | ［哪些函式、結構、措辭或策略不應被驗收暗中限制］ |
| 交互風險 | ［共用 helper、舊 API、其他欄位或下游行為可能被連帶改動的地方］ |
| 比較計畫入口 | ［任務範圍、抽樣與重複、主要結果、實務門檻、費用與人工投入、停止條件；連到獨立計畫］ |
| 未定時的處理 | ［缺哪一種證據、由誰補；何時保留現狀、暫停介入或另立版本］ |
| 最後 disposition | ［保留／撤回／修改／仍未定；證據版本、理由、負責人與重新檢視條件］ |

填完後，請規格與驗收負責人各提出一個反例：這段文件可能在哪裡讓合法行為被拒絕，又可能在哪裡仍抓不到想避免的錯誤。能回答這兩個問題，才比較容易判斷下一步該補說明、補檢查，或先回去作需求決定。

方法來源與限制見 [規格與契約基礎研究](spec-foundations-research.md)。本卡是依來源與本 repo 契約綜合提出的設計，沒有宣稱為任何單一研究已驗證的標準流程。
