# 文件改動評估提案

本頁是可供團隊改寫的**設計範例，尚未執行下一輪研究**。歷史基礎是作者 repo 的 parser 修補研究；下一輪改以可使用工具、在固定預算內自行檢查與修正的有限 agent session 為目標。它不是原四十次 tool-free one-shot 的續跑，也沒有已完成的人力或跨任務效果資料。

本頁比較的是要求不變時，可選自查是否改善交付。必要行為與相容責任依需求決定、記錄及驗收，不必等待這項效果比較。提案完整也不等於已有採用證據。

## 先填決定，再填方法

| 欄位 | 本案填寫示例 |
|---|---|
| 要作的決定 | 在限定的 Python 工具修補流程中，是否把六點自查列為預設附件。 |
| 為什麼現在需要決定 | 自查需要維護；團隊想知道它是否減少不合格交付，以及是否值得增加撰寫、驗收與 review 投入。人工工時尚未量測。 |
| 目標工作 | 固定期間全部 incoming 合格 work inventory，保留未完成與尚不能驗收的工作；正式量化集合若較窄，採用主張也限於該範圍。 |
| 已有證據 | 四份文件各十份候選都通過既定 103 項檢查，無法依通過率排序。A0 已有十三條要求，並非沒有規格。 |
| 尚不能推論 | 文件等效、自查無效、最短版本最佳、有工具流程已可靠，或模型費用等於總交付成本。原 B 同時新增理由與自查，不能拆出各自效果。 |
| 候選介入 | 每個 task 的 P 為展開規格，Q 只加依事前政策改寫的自查；parser 例可沿用 B 原六題。共同要求、起始程式碼、工具、預算、政策與驗收相同，先核對行為及範圍。 |
| 交付政策 | 每個排定試行從 fresh repo／session 開始，允許在固定工具與預算內執行公開 check 和自修；session 結束後由外部隱藏 grader 驗收，不另開 session 替補。 |
| 先決條件 | Owner 解決會改變預期值的未決問題；QA 以正反對照確認既定量尺能辨識主要錯法，也容許合法差異。先澄清需求或修錯誤 oracle，不急著比較文件。 |
| 主要結果 | 每個排定 session 的最終候選通過既定外部驗收，且操作條件成立；按 task 保留重複結果。人工救援不能回填原成功。 |
| 接手與投入 | 全量記錄人工處理、有限修補與最終交付；另做預選分層深讀，保留 reviewer 分派、順序與同題學習。所有失敗費用、補救及維護都納入。 |
| 什麼結果會改變決定 | 效果區間下界超過事前實務門檻，且成本／人力達標，才支持預設採用；上界低於門檻，可排除這個幅度的改善；區間橫跨門檻則未定。無人力資料不能通過共同採用條件。 |
| 誰負責 | 規格 owner 決定行為；QA 維護 oracle；平台 owner 保存執行環境；reviewer 記錄接手工作；EM／Staff 與實際承擔者共同決定。 |
| 下一次決策 | 達預定名額或成本／日期界線時，按事前規則檢視；異常暫停與缺失保留。需求、grader、model／harness 變更時，分清需要哪一層重評。 |

原六題針對 parser，不能直接套到沒有 EOF、token 或錯誤事件義務的工具。跨任務須先固定 [自查改寫政策](self-check-transfer-policy.md)，每題只對應 P 已揭露的要求；不適用項目依事前規則記錄。各 task 的 P、Q 都先核對差異、封存版本，再重複執行。全體映射及 packet 尚未完成，因此本頁不能直接當成已就緒的執行規範。

### 把分母與人的工作留下來

`task_id` 是原始需求與起始 repo；`work_id` 是一次排定 policy 試行，同一 task 在 P、Q 下可有多個 work_id。每個 work_id 對應 session／trial 及最終候選 hash；session 內中間程式版本不增加樣本數。先保存未經人工救援的原候選及判定，再保存人工 review、有限修補後的新 hash 與最終交付，不能把人工修補成果回填到 agent 主要成功欄。

人工 active time 與 wall-clock 分開。深讀可以抽樣，但抽樣與 reviewer 分派要在看到結果前定規則，遮蔽可遮蔽的條件標籤，記錄同題重讀與熟悉程度；不能只看成功者再估全部工作的維護成本。沒有這些資料時，就把人力欄留作待補，不用 AST 或原 one-shot 模型費用硬算 ROI。

### 比較之前有兩個更直接的出口

假設 CSV 匯出工具新增日期欄，caller 已要求保序與保留重複列，但缺日期要空欄還是拒絕尚未決定。此時先由 owner 作政策選擇；agent 不能以生成的 expected value 代替決定。若契約已允許 LF／CRLF，測試卻只接受一份逐 byte 範本，先修 oracle、記錄版本並重評相關候選。兩種情況都不需要先跑文件比較。

這份提案也不要求每個團隊先建立大型平台。**診斷 pilot** 只確認要求、正反對照與紀錄流程，不推論工作集合的收益；**有限部署 trial** 在原有人工核准下限定範圍、停止與回復，觀察真實接手成本，不宣稱已證明文件優勢；**預設採用或擴張** 才需要事前效果及成本／人力條件。三個出口需分開命名。

### 抽樣與回歸的邊界

正式 inventory 保留未完成、未可驗收與排除理由。若只有已合併歷史修補，就另立 retrospective backtest，seed 使用修補前 commit，結論限於該回溯集合；不能拿有答案的同題改寫當 fresh holdout。診斷 pilot 可刻意測錯法，卻不能把它的 fault 頻率當母體率；精度規劃需明示合理假設與敏感度。

回歸分三層：固定實作 fixtures 檢查 grader 是否改壞；同一契約 cases 檢查新候選；評估 model／harness 交付方法則需新生成及 task／trial 分布。舊候選重評只更新對那批舊產物的判斷，不能代替新候選驗收或第三層的新生成。公開或已在文件調整中使用的題目可留作回歸，不能重新稱未見保留題。

詳細分派、人工觀測、假設門檻、停止規則與空白範本見 [比較計畫](comparison-plan-example.md)。

## 可填空版本

```yaml
# 設計範本；不是已部署的執行設定。
decision: "要保留、採用或撤回哪一項文件改動？"
owner: "誰承擔結果與維護？"
work_inventory: "固定期間 incoming 工作、狀態、納入／排除與正式範圍"
current_evidence: "來源、版本、觀察，以及尚未回答的問題"
change_hypothesis: "改哪段文字，想減少哪種可觀察錯誤？"
requirements_revision: "已決定的行為、相容責任與未決問題"
policy: "工具、公開 check、自修預算、session 結案與外部驗收；是否另外有人接手"
identities: "task_id、排定 work_id、session_id、原候選與修補後 hash"
acceptance_evidence: "如何辨識已知錯法，也接受不同但合法的寫法？"
primary_outcome: "每個排定 session 的操作條件與原候選驗收；保留失敗／缺失"
human_observation: "全量實際時間、預選深讀、reviewer 分派、遮標籤與同題學習"
final_delivery: "人工有限修補與最後交付另列，不回填 agent 原成功"
minimum_worthwhile_change: "效益門檻、理由與區間判準"
costs_and_limits: "所有嘗試、補救、維護；人力與費用上限、日期及暫停規則"
next_decision: "診斷 pilot／有限部署 trial／預設採用，各自條件與責任"
regression: "grader fixtures／新候選 cases／新生成方法分布，分別何時重評"
```

填寫者不能只寫「提高品質」。例如「減少 `text: false` 被當成沒有訊息」已指出錯法；接著仍要分清規格未決、候選沒做到、驗收沒看見，才能選擇先修改哪裡。未決欄位照實保留，不能以排版完整的 YAML 暗示研究已就緒。
