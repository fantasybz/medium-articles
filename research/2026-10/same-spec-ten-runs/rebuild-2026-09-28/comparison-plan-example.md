# 比較計畫範例：六點自查是否值得成為預設交代

> **設計範例，尚未執行。** 本例規劃的是可使用工具、可在同一 session 內檢查與自修的有限 agent 工作流程。它不是原先 tool-free、one-shot 四十次研究的續跑。下列樣本與門檻數字都是規劃示例，不是業界標準、已完成的 power analysis，也不是已存在的真實任務清單。

本頁比較的是要求不變時，可選自查是否改善交付。必要行為與相容責任依需求決定、記錄及驗收，不必等待這項效果比較。提案完整也不等於已有採用證據。

## 一、先決定要採用哪一種工作流程

團隊想決定：在自己的 Python 工具 repo 指派行為修補時，是否把六點自查加到預設交代。規格維護者希望減少不合格交付；接手 reviewer 也需要知道，新增文字會不會增加理解、修正與文件維護的負擔。

本例比較 **P：展開規格**與 **Q：同一份規格加六點自查**。其他要求、範圍、例子、起始程式碼、工具權限、執行政策與驗收相同。原研究 B 同時新增理由與自查，無法拆出各自效果；本例另立單一新增成分的比較，不把 C 的可選 helper 一起加入。

這裡的「同一份規格」是指同一任務內的 P、Q，不表示所有任務都使用 parser 的十三條要求。原 B 六題提到 EOF、token 與錯誤事件，不能直接貼到沒有這些義務的任務。跨任務版本須先固定 [自查改寫政策](self-check-transfer-policy.md)，再由該任務 P 已揭露的要求推導自查；不適用項目依事前規則處理，不新增要求，也不用隱藏驗收或參考 patch 補資訊。每個 task 的 P、Q 都先審 diff 並封存，同條件重複時內容逐 byte 相同。

因此，跨任務比較的對象是「依固定政策建立自查」這套做法，不是六句 parser 原文在所有工作上的效果。改寫規則、全體任務映射與對應 packet 尚未全部完成，以下仍是設計卡，不能直接啟動 288 次執行。

每次排定試行從 fresh repo／session 開始，在事先固定的工具與預算內工作。agent 可以讀 repo、執行公開檢查，並在同一個 session 內修正程式。session 結束後才保存最終候選，由外部驗收程式執行不向 agent 開放的驗收；結果不再回灌給該 session，也不開新 session 替補失敗。

這一段定義了要比較的 **policy：一次工作可用什麼資源、如何嘗試、何時結束與由誰驗收**。先前四十次研究只量測 tool-free 一次生成，因此不能直接替這個有工具的流程背書。新比較即使成立，也只適用於事前界定的工作與政策，不自動包含任意次數的重試或人工救援。

## 二、已填寫的計畫卡

| 欄位 | 本例安排 | 避免的誤判 |
|---|---|---|
| 決策範圍 | Python 工具 repo 中，行為與相容責任能明確約定的修補；涵蓋 parser／資料驗證、內容轉換、子程序與串流處理。 | 不把一個 parser 的結果推到全部軟體工作。 |
| 任務來源 | 固定期間全部 incoming 合格工作清單，保留未完成、未能驗收與排除原因；分層及量化集合的範圍見後文。 | 不只留下已有成功解答的工作。 |
| 比較條件 | 各 task 的 P、Q 只差依事前政策改寫的自查；完整 packet、repo 起始版本、模型／harness／工具設定與預算在執行前封存。 | 「多一段自查」不夾帶需求、工具權限或補救次數的變動。 |
| 診斷 pilot | 使用不進入正式集合的任務，檢查 reference、正反對照、grader 與 runner；不拿故意錯法的比例估計日常失敗率。 | 把檢查並修正量尺與估計文件效果分開。 |
| 正式規模 | 預算草案上限為 48 個真實任務 × 2 條件 × 3 次 = 288 個排定試行。正式前仍須完成任務清單與精度規劃。 | 288 是預算草案，不是 power 保證。 |
| 分派 | 每個任務接受 P、Q 的重複試行，按任務與執行日形成區塊，區塊內次序隨機；記錄並行度與實際起訖。 | 不讓文件條件和不同日期／環境自然綁在一起。 |
| Session 政策 | 每名額 fresh 環境與 session；可在固定預算內使用工具、執行公開 check、自修；結束後外部隱藏驗收；不另開 session 替補。 | Session 內修改不冒充獨立樣本，救援也不洗掉原失敗。 |
| 主要結果 | 每個排定試行的最終候選是否通過既定外部驗收，且操作條件符合事前規定。兩欄分開保存，主要結果取交集。 | 候選綠燈與外層正常完成不互相代替。 |
| 人工與最終交付 | 全量記錄實際處理時間，另安排預選分層深讀；人工 review、有限修補與最終交付另外保存。 | 人修好後交付，不回填成 agent 原候選通過。 |
| 實務門檻 | 假設至少增加 5 個百分點才值得投入；以區間下界、上界與門檻比較，詳見第五節。 | 正向效果不直接等於值得採用，也不把不顯著寫成等效。 |
| 人力上限 | 假設每份最終合格交付新增人工時間，區間上界須不超過 2 分鐘；模型與維護費用另定上限。 | 沒有人力資料，就不能通過共同採用條件。 |
| 停止與責任 | 預先固定名額、費用／日期界線與暫停條件；各 owner 保存自己負責的證據，採用由承擔後續工作的人共同決定。 | 不為了換到想要的結果才追加、替補或改門檻。 |

### 任務從哪裡來，哪些工作仍未被涵蓋

抽樣框是固定期間內全部符合領域條件的 incoming work inventory，包含尚未完成、尚不能驗收與後來中止的工作。owner 先記錄每個工作的來源、狀態、納入與排除理由，再定義正式量化集合；不得先看到 P、Q 的表現才挑題。

規格未決或暫時無法建立公平驗收的工作，仍留在 inventory。它們可能先需要需求澄清，未必能立刻進入量化比較。若最後只比較可明確驗收的子集合，效果與採用範圍便限於該集合，不能用加權掩蓋沒有觀測到的工作。按工作類型、外部相依、狀態／串流與例外密度保留分層；若刻意多抽稀有類型，需另外報分層結果及預先選定的權重。

如果實際只能收集已合併的歷史修補，另立 retrospective backtest 範圍，明說它不代表全部 incoming 工作。輸入使用修補前的 repo commit，已知 patch／答案與 grader 隔離；題目與答案已曝光時，改寫同一道題也不能把它變成未見保留題。

診斷 pilot 可以刻意涵蓋邊界與已知錯法，其用途是找到量尺或執行流程的缺口。precision／power 規劃則應對合理的效果、基準表現及同任務相依程度作假設敏感度分析；不能把刻意選取的 fault 頻率當成日常工作失敗率。正式集合與評分資產在文件調整期間隔離，正式結果不得反覆回灌到同一份 Q，再用同一集合宣稱改善。

### Task、排定試行與候選的身分

`task_id` 指原始需求與 repo 起始版本；同一 task 可以在不同條件下重複試行。`work_id` 指一次事先排定的 policy 試行，關聯 task、文件條件與重複編號。每個 work_id 對應一次 session／trial，保存 `session_id` 及最後候選的檔案 hash。session 內各次中間程式版本可以留下 trace，卻不增加獨立樣本數。

主要結果的分母是排定的 work_id，不是 agent 產生過幾個中間檔案，也不是最後成功交付的工作。主比較先按 task 保留 P、Q 的重複結果，再依事前抽樣權重彙整；分析要處理同任務內相依，不能把所有 trial 當成不同任務。

模型／harness／CLI 版本、repo 起始狀態、工具、資源與停止預算要在執行前記錄；模型供應商未提供的取樣控制或隱藏狀態，則明列為不能固定的條件。公開 check 是 agent 可用的工作資源；正式評分資產由外部程序持有，不放進 agent 可讀的 repo／工具環境，兩者不能只靠不同檔名區別。

每個 session 的最終候選必須先凍結 hash，再執行外部隱藏驗收。若 agent 到點未完成、候選缺失或操作條件失敗，紀錄照樣保留；不能重開 session 補成成功。若整體預算／環境問題造成既定名額未啟動或重要資料缺失，另列狀態並保留原排程，停止採用判定，不宣稱完成原規模的比較。grader 致命錯誤需暫停整輪；修正後另立版本與重評紀錄。

### 人工接手如何量測

全量記錄每個 work_id 在 session 後發生的人工 review、必要驗證、有限修補及最終交付結果，修補上限先由 owner 決定。人工改動產生新的候選 hash，連回原 hash；即使最後交付成功，原 session 的主要結果不變。最終交付率與 agent 原候選通過率分欄，避免用人的補救掩蓋方法失敗。

人工紀錄區分讀碼、修正、核准、文件維護與被動等待，事先定義起訖與中斷。同時做別的工作時，不將 agent wall-clock 再算成人工 active time。失敗及未交付工作仍保留已花的時間；以最終合格交付為分母計算成本時，分子包括全部嘗試、驗證、失敗處理與有限修補，沒有合格交付則不計算該比值。平均每個排定工作的投入也另外保存，避免比值遮住工作總量。

深入閱讀不必假裝全量，但必須在看結果之前訂好抽樣規則：先指定 task、條件與結果的分層程序，取得原驗收結果後再依該程序抽取，保留抽樣機率與缺失，不能臨時只挑漂亮成功者。分派 reviewer 與閱讀順序，遮蔽可遮蔽的 P／Q 標籤；程式風格可能透露條件，應照實記錄盲化限制。同一個人先看過同題另一份實作時，記錄熟悉與學習效應，分析保留 reviewer／task 的群聚關係，不視為全新獨立閱讀。

若沒有真人觀測與完整時間資料，本輪就不能通過「效果與人力皆達標」的採用閘門。AST 相似度、代理 review 或原本 one-shot 的模型費用，都不能補成 ROI。

## 三、先分清楚三種起步與採用安排

**診斷 pilot** 用於確認要求、正反對照、grader 與紀錄流程。一個真實任務就可能揭露量尺缺陷，但它不估計整個工作集合的收益，也不改變原有授權。

**有限部署 trial** 在原有人工核准下，限定工作範圍、責任、停止條件與回復方式，觀察實際接手工作。這是可撤回的學習安排；它需要基本驗收與風險邊界，尚不宣稱文件效果已成立，也不必先冒稱達到下節的全面採用證據。

**預設採用或擴張** 才使用事前的效果、成本與人力條件，決定是否把做法推給目標工作集合。三者不能都叫 pilot，再由讀者自行猜測證據強度。

CSV 例子能說明何時根本不該開始比較：空日期要保留空欄或拒絕尚未決定，先交 owner 決定；若契約允許 LF 與 CRLF，而 oracle 只接受某份文字範本，先修 oracle。修正後依既定契約重評相關候選，保存版本與結果。這兩個動作都不需要先生成更多程式，也不能被算成六點自查已經有效的證據。

## 四、回歸資產分三層，公開題目不再是未見保留題

| 回歸對象 | 固定與變動 | 可作判斷 |
|---|---|---|
| Grader | 固定正反 fixtures（先核對其行為），換 grader 版本 | 新量尺是否誤拒合法行為或漏掉已知錯法？ |
| 新候選實作 | 固定同一契約的 cases，檢查新候選 | 這份候選是否仍滿足已涵蓋的要求？ |
| Model／harness 交付方法 | 取得新生成結果，保存適用 task／trial 分布與 policy 版本 | 新版方法在這批工作上是否退步？ |

重評舊四十份候選，只能更新對那批舊產物的判斷；新候選仍須實際接受驗收，方法比較仍需第三列的新生成。原封存題、答案與評分資產已在研究／成稿過程中揭露，並作為可查核附件，仍可用作回歸；另存副本不會讓它們重新成為未見的 capability holdout。新能力與文件比較需另設未被文件調整使用的正式任務與評分資產。這是後續設計要求，不是要求現在追加正式樣本。

## 五、先判斷效果，再檢查採用條件

假設 owner 事前決定，Q 相對 P 的主要結果至少增加 **5 個百分點**才值得維護六點自查。分析前需指定區間方法、信心水準、抽樣權重及同任務相依的處理；這份卡沒有完成這些估計，也沒有做出任何新信賴區間。

把 Q−P 的區間記成 `[L, U]`。以下三種效果判斷互斥；等於門檻的邊界依本例保守規則留在未定。

| 效果判斷 | 事前條件 | 純假設區間，單位為百分點 | 可以說到哪裡 |
|---|---|---|---|
| 支持超過最低實務門檻 | L > +5 | [+6, +9] | 指定方法與假設下，區間支持改善超過 5 個百分點；成本與人力也達標，才支持採用。 |
| 排除達到最低實務門檻的改善 | U < +5 | [+1, +4]，或 [−2, +3] | 排除了至少 5 個百分點的改善；前者仍支持較小的正向改善，兩者都不等於等效。 |
| 是否達到門檻仍未定 | L ≤ +5 且 U ≥ +5 | [+2, +8]、[−1, +7]、[+5, +8]，或 [+2, +5] | 尚不能依本例規則支持採用，也不足以排除達到門檻的改善。 |

**上表全是編製的判讀示例，不是四十次研究或新資料的估計。** [+2, +8] 的下界大於 0，支持正向改善，但還不能確定幅度已大到值得維護新流程。「方向正確」與「值得成為預設」之間，仍有實務門檻。

人力是另一項必要條件。本例假設，每份最終合格交付新增人工時間的區間上界須不超過 2 分鐘。若效果區間是 [+6, +9]、人工上界是 1.8 分鐘，且其他事前成本條件也成立，才支持採用；若人工上界為 2.4 分鐘，尚不能確認符合人力上限；若人工下界已超過 2 分鐘，則是人力負擔超限，**目前不採用，但不能說文件沒有改善效果**。人工時間區間同樣只是示例，尚未量測。

候選驗收與方法採用仍要分開。單份 CSV 候選若違反已約定的保序、保重複，就拒絕該候選，不能用它其他項目的得分抵銷；方法比較則如實保存不同試行的通過與失敗，不暗中把這條契約改寫成未事先決定的「觀測必須零失敗」門檻。owner 另外定義不能由平均改善抵銷的方法層必要條件與暫停規則，例如越權、驗收被改動或無法承擔的補救負擔，並在看結果之前確定。

結果仍未定時，要分辨缺的是任務代表性、更多同條件重複、公平且有保護力的量尺，還是人的投入，再限定下一步。四個 10/10 本身沒有提供這裡所需的組間差值區間，更沒有提供有工具政策與人工接手的資料。

## 六、可填寫的比較計畫範本

> **無預設數字的範本；不是已部署設定。** 填寫者應以真實工作、損失與預算提出門檻，不能把前面的示例數字照抄成標準。

| 欄位 | 填寫內容 |
|---|---|
| 待決定的流程與 owner | ［誰要保留、撤回或採用哪項文件改動；由誰接手］ |
| 目標工作與抽樣框 | ［固定期間 incoming 工作、未完成／未可驗收紀錄、正式子集合與排除理由］ |
| 分層與權重 | ［工作類別、目標組成與過度抽樣處理］ |
| P／Q 及共同契約 | ［改寫政策版本、各 task 映射與不適用項目、完整 packet、唯一介入、起始 repo 版本、需求與相容責任］ |
| Policy 與結案點 | ［工具、公開 check、session 內自修、停止預算、session 後外部驗收、是否另有救援］ |
| 識別與分母 | ［task_id、每次排定 work_id、session_id、候選 hash 及其關聯；中間版本不另算樣本］ |
| 診斷 pilot 與正式保留題 | ［調量尺的任務；未被文件調整使用的正式集合與評分資產］ |
| 規模與精度規劃 | ［任務與重複分別列出；合理假設的敏感度分析；費用／日期上限］ |
| 分派與環境 | ［隨機化／blocking、模型與 harness 版本、資源、並行度及不能固定之處］ |
| 主終點與操作條件 | ［最終候選的既定驗收、外層條件、交集、缺失／未啟動／中止處理］ |
| 人工觀測與最終交付 | ［全量實際時間、預選分層深讀、reviewer 分派／遮標籤／同題學習、有限修補與不同 hash］ |
| 最低值得的改善 δ | ［門檻及工程／經濟理由；區間方法、信心水準與邊界規則］ |
| 效果與採用判準 | ［L > δ；U < δ；其餘未定。效果達標後仍須通過哪些成本、人力與必要條件］ |
| 停止、回復與下一次決定 | ［診斷 pilot／有限部署 trial／預設採用的不同出口；誰補足何種缺口］ |
| 回歸與重新評估 | ［grader fixtures、新候選 cases、新生成方法分布各自的版本與觸發條件］ |

填完後，由規格、驗收、平台與接手維護的負責人一起確認：觀測真的能改變哪個決定，資料不足時誰處理哪個缺口。欄位填滿不表示研究已就緒。

## 七、與原研究及來源的關係

原研究仍是一個 parser 任務、四十次 tool-free one-shot 生成與既定 103 項檢查。本頁沒有修改原候選、評分或樣本，也沒有開始新的有工具實驗。人力採用條件尚未有實測資料，不能用原模型牌價估計推算 ROI。

方法依據包括 τ-bench 的 task／trial、Anthropic evals 與 infrastructure 實務、NIST randomized blocks、AI Agents That Matter 的成本與 holdout，以及 METR 對抽樣與工時計量的反省；版本與限制見 [來源台帳](reliability-source-ledger.json)。具體政策、數字門檻與角色安排是本頁的設計示例，不是這些來源已驗證的通用標準。
