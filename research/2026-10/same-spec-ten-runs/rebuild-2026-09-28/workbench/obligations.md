# 從要求到驗收義務：已填範例與空白模板

下表是後設教學設計，不是凍結研究新增的 requirement coverage。規範來源為 [R01–R13 凍結原文](../../../../experiments/same-spec-ten-runs/results/formal-2026-09-25/source/requirements.json)。表中的「負責人」描述團隊需要安排的職責，沒有宣稱本次教學已由真人盲審。

閱讀時沿同一列往右走：先由規則推出可觀察結果，再看預期哪種錯法會被分開。案例通過之後，最後一欄仍要保留，讓它沒有涵蓋的要求有機會繼續被討論。

| 要求與來源 | 本例的可觀察義務 | oracle 與合法自由 | 能分辨的已知錯法 | 負責判斷的人 | 還沒有證明什麼 |
|---|---|---|---|---|---|
| R05＋R03：非字串、非 null 的 text 算 malformed | `false` 那行不印出、不計發言；stderr 一則實體行號診斷；繼續後續事件 | stdout 精確比對，stderr 原因可用不同非空單行文字；結束狀態另依 R11 | 將 false 轉成 `False`；或用真假值把它當缺值 | 規格 owner 確認 false 的意義；QA owner 確認測試確實碰到它 | 一個 false 案例沒有窮舉所有 JSON 型別、欄位與 Unicode 狀況 |
| R02＋R03：decoded `[]` 是 malformed，仍須繼續 | 後面的 `after` 與合法 token 註記都要出現在 stdout | 不限制主迴圈／helper 結構；只觀察行為 | 一遇 malformed 就 return 6，exit 正確卻漏掉後續輸出 | QA owner 比較三出口，不能只看 exit | 更長事件串、交錯或多重 malformed 尚未全部覆蓋 |
| R09＋R11＋R12：明確失敗優先於 malformed | 先有 malformed、後有根層 error，EOF 必須回傳 3，並保留規定診斷 | 依優先序推導結果，不依數字大小或發生先後選擇 | 診斷全部正確，卻回傳 6 | 規格 owner 確認優先序；QA owner 用組合輸入核對 | 只觀察這一個組合，不代表已窮舉所有旗標與事件順序 |
| R03：每個 malformed 行恰好一則診斷 | false 案例的 stderr 恰好一則；exit 6 沒有結尾摘要 | 不固定 REASON 用字，但不接受缺行、多行、錯行號或空原因 | 漏診斷，其他兩出口全部正確 | QA owner 檢查完整 stderr 格式；不是人工判斷文案優劣 | 格式符合不代表原因的說明對使用者充分；本契約沒有量測可理解性 |
| R01：有效輸出必須在 EOF 前出現 | driver 保持 stdin 開啟時，讀到第一則有效訊息 | 使用 pipe 的外部觀察，不要求某個函式名稱 | 先 `stdin.read()` 才處理；批次終態完全相同 | harness owner 負責 driver 的時序與等待預算 | 只測第一則訊息；一秒是本機觀察窗，不是 production latency SLO |
| R02＋R03：空行忽略但仍計入實體行號 | 在開頭插兩空行，stdout／exit 不變，診斷 line 1 變 line 3 | 變形關係只讓指定觀察不變，另明訂行號變化 | 錯誤測試要求三出口全部不變，因而拒絕正確程式 | QA owner 提出關係，規格 owner 核對關係 | 多處插入需要按每個位置計算位移，不能一律把所有行號加 2 |
| R13＋R05＋R08：重複事件各自處理 | 完整「same＋完成」片段出現兩次，stdout 重複兩次；exit 0、stderr 空 | 不可新增 dedup 或完成後停止處理的要求 | 錯誤測試要求重複事件具冪等性 | 規格 owner 決定相容行為；QA owner 保留重複事件案例 | 本例沒有處理需要去重的其他協定；不能把 R13 推廣到所有事件系統 |

## 可複用的空白版本

| 欄位 | 填寫時要回答的問題 |
|---|---|
| 要求及版本 | 誰決定這項行為？來源是產品需求、相容決定、review 約束，還是測試作者的猜測？ |
| 適用前提／輸入 | 哪些前提成立時才套用？缺值、邊界或多個條件共存時如何處理？ |
| 可觀察義務 | 要觀察內容、狀態、時間、資源、權限還是它們的組合？從哪個出口取得？ |
| 預期值及推導 | 為什麼這個結果才符合要求？可否逐步推導，而不是只錄下 reference 的現況？ |
| 合法自由 | 哪些差異規格允許？一個 exact string 或固定結構會不會多加要求？ |
| 正例／反例 | 哪份已知符合行為的 fixture 應通過？哪種有效語法的錯法應被辨識？ |
| 變形關係 | 改造輸入之後，哪些觀察不變、哪些必須改變？關係從哪條要求得來？ |
| 不能判定的情況 | 時間／環境不足、規格歧義或工具失敗時，如何與產品違約區分？ |
| owner 與變更處理 | 規格歧義交給誰？修正 oracle 後需要重評哪些既有產物，如何保留新舊版本？ |
| 涵蓋缺口 | 哪些同一條要求的情況仍沒驗證？不要只寫 requirement ID 就宣稱整條已證明。 |

模板填完後，先請另一位接手者只看要求與輸入，獨立推導預期結果。若兩人需要新增口頭假設才能一致，先把未決問題交回規格 owner；不要在測試程式裡自行補出一份沒有人確認過的契約。
