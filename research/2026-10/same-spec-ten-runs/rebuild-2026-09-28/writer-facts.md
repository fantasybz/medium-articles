這份底稿供 Claude Code 以 max effort 主寫時核對事實，**不是文章結構**。不要把所有細節搬進總論，也不要複製舊稿的研究日誌節奏。四篇都應以讀者決策及有理由的工程建議為主，方法細節則提供可核對的連結。

## 正式研究的範圍與結果

- 原任務取自作者的 `medium-articles` repo，檔案是 `research/scripts/codex_jsonl.py`，固定 seed commit 為 `37f6c0ce9b536f95132d5e01a387f380bbb9639c`。這是一支單檔 Python 串流工具，讀取 JSONL，產生 stdout、stderr 與 exit code。它有真實呼叫介面與相容責任，但本研究沒有宣稱它對應某次生產事故。
- 在固定 seed 重現的問題有兩個：合法 JSON 的根層值若是 `[]` 或 null，程式呼叫 `.get()` 時會崩潰；若 agent text 是數字 `123`，後面再接有效的完成事件，程式會把 `123` 印成審查內容，並以 exit 0 結束。
- 正式研究有 A0、A、B、C 四種條件，各 10 份候選，共 40 個預定名額。這不是同一份 prompt 執行 40 次：每組十次收到的 packet 逐 byte 相同，四組 packet 則各自不同，共用 seed 與 R01–R13。沒有重試、修復、替補或事後追加樣本；全部生成完成後，才進入共同的外部驗收。
- 正式生成使用 `claude-opus-5-5`、**high effort** 與 CLI 2.1.282。模型沒有工具，以一次生成交付單一檔案；它不能像互動式 agent 一樣查 repo、提問或執行測試。這不是 max effort。文章以 max effort 主寫，屬於另一個流程，不計入正式樣本或生成成本。
- 每份候選接受 102 個 batch cases 與 1 個 EOF 前 streaming probe，共 103 項檢查，40 份候選全部通過。CLI、trace、模型固定與工具使用等操作條件，和 artifact 驗收分開判定；正式的 accepted 結果取兩者交集。103 項只是有限檢查，不是整份規格的形式證明。
- 每組結果都是 10/10。在各次觀測獨立、同分布，且共享同一 Bernoulli 成功機率的假設下，雙側 95% Clopper–Pearson 區間約為 69.15%–100%。這不能證明四組等效、長文字無用、已達高可靠度，或已可全面採用。
- 40 份候選的 normalized AST hash 全部不同。Normalizer 只正規化部分 identifier，保留屬性、import path、constant 與順序，也不處理 scope binding。Hash 不同不表示控制流程必然不同，更不表示品質較低。Cosine 只比較 AST node type 的分布，不保留順序。每組 45 個配對共用同一組 10 份候選，因此總計 180 個配對並非獨立觀測。
- A0、A、B、C 各組十次生成的 CLI 牌價估計合計，依序為 USD 1.248397、1.382626、1.513502、1.547817，總計 USD 5.692342。這不是帳單，也不包含研究、pilot、寫作或人工成本。正文可以圓整為 1.25、1.38、1.51、1.55，但必須標明是每組十次合計。本輪沒有量測真人 review 或維護成本，不能計算 ROI；費用排序也不能辨識理由、自查與 pattern 各自的因果效果。
- A0、A、B、C 的生成時間中位數依序為 37.273、37.300、40.277、37.161 秒；C 的最大值為 59.707 秒。這些不是包含驗收與人工處理的完成時間。
- 每個生成名額到 600 秒時送出 SIGTERM，保留最多 5 秒的停機寬限，之後若仍未停止，再送出 SIGKILL。USD 5 是**每個名額**的 CLI 停止門檻，不是四十次生成的費用硬上限。執行採四路並行，預先排成 10 個區塊，各區塊內打亂順序；實際執行時段彼此重疊，不是同步配對的時窗。Provider context、temperature、random seed 與完整 OS 狀態都無法固定，不能宣稱所有條件已固定。
- 本次研究在執行前完成本機封存，這不是第三方預註冊；部分 OS metadata 是開始後才補上。Seatbelt 的三項越界 probe 分別確認 oracle 讀取、檔案寫入與 localhost bind 遭到拒絕，不能據此證明所有通道都已封住。兩次 pilot 與四次停止路徑 probe 不計入正式資料；重評同一批 40 × 103 項結果，也不會增加模型樣本。

## 四份文件與 R05

A0 有 936 個英文字詞，雖然精簡，已包含 R01–R13 的完整目標，不是 bare user story。A 有 1,655 詞，逐項展開要求，包含固定輸出、表格，以及部分條文內的理由。B 有 1,923 詞，由 A 全文加上集中理由與六組交稿前自查構成。C 有 2,223 詞，由 B 全文加上可選的純文字 pattern 構成。詞數按空白切分，包含標題與 code，不含 seed，也不是 token 數。

B 以 A 全文開頭，C 以 B 全文開頭，這兩個包含關係可以逐 byte 核對。A0 與 A 則需要核對語義，且已有一處已知差異：對新 CLI 參數，A0 說「不需要」，A 卻在 R13 進一步排除，說它們「不在範圍內」；B 與 C 繼承 A 的文字。正式 grader 沒有全面檢查額外 CLI 選項與 `main` 介面，這處差異的影響仍未知。不能再宣稱全文語義相等，也不能修改已凍結的 packet；下一輪若要消除差異，必須先對齊要求，再重新生成。

B 同時增加理由與自查，因此無法單獨辨識兩者的效果。C 建議使用 helper，但沒有提供實作程式碼，也不是原生 Skill、plugin 或 hook；不能把它說成量測 Skill 效果，或強制架構限制。A 已在部分條文中說明理由，不能說 A 沒有理由。

R05 規定 agent message 的 `text`：缺值、null 或空字串都不輸出，也不記為發言；非空字串原樣印出並 flush，只有空白的字串也有效。其他非字串值都算 malformed，包括 false、0、陣列與物件。必須先驗證該行相關欄位，才產生一般事件的輸出或狀態效果；`turn.failed` 是保留明確失敗旗標的例外。

C 建議的 optional text helper 不限於處理 agent message，但不能套到根層 error：R09 必須保留 `str` 轉換。C 也明示兩種合法安排：由 handler 回傳一份小結果，或保留 if 分支、在各分支就地驗證。

## 其他易錯契約

- R02 忽略空行與無法解碼為 JSON 的文字，但仍計入實體行號。解碼後若不是物件，就算 malformed。根層缺少 `type` 時忽略事件；若提供 `type`，就必須是字串，null 也不合法。未知的字串事件型別則照舊忽略。
- R03 要求每個 malformed 行只產生一則診斷，並繼續讀取後續輸入。一般 malformed 事件不產生其他語義效果；`turn.failed` 仍須記錄明確失敗。
- R04 中，提供的 `item` 必須是物件，null 不合法。物件內若提供 `type`，它必須是字串。
- R06 的 command 文字只取前 160 個字元，不是前 160 bytes。
- R07 的 item error 只輸出 stderr 診斷，不設定明確失敗旗標。
- R08 中，缺少 `usage` 時視為 `{}`，但 null 不合法。Token 值必須是非負整數，並排除 bool；全部驗證完成後，才輸出用量註記。
- R09 對根層 error 的任何 JSON message 值都使用 `str` 轉換，並記錄明確失敗。
- R10 中，`turn.failed` 永遠記錄明確失敗。`error` 或其 `message` 為 null 時使用 fallback。若提供的 `error` 既不是 null 也不是物件，或其提供的 `message` 既不是 null 也不是字串，就算 malformed；先輸出 malformed 診斷，再輸出舊有的失敗診斷。
- R11 在 EOF 依序判定：3 表示明確失敗，6 表示 malformed，4 表示沒有有效完成，5 表示已完成但沒有發言，最後才是 0。這是優先序，不是數值大小，也不是哪個事件先到就決定結果。
- R12 只有 exit 3、4、5 會附上舊有的結尾摘要；0 與 6 沒有。
- R13 接受重複訊息、重複完成，以及完成後出現的其他事件。這不代表去重或冪等。

驗收 malformed 診斷時，REASON 的措辭可以不同，只需符合格式、行號與非空單行原因的要求，不應與 reference 的理由逐字比對。固定的 legacy 診斷字串則必須符合契約。新 workbench 已提供合法理由改寫，作為應接受的對照。

## 靜態程式閱讀

靜態 walkthrough 可使用 A0 在凍結執行順序中最前面的兩份候選：`formal-01-A0` 與 `formal-02-A0`。這是在研究完成後，先選定配對，再閱讀程式碼，沒有按 score 挑選；它不是研究前預定的分析，也不是代表性抽樣。

`formal-01-A0` 用區域 dict 保存 malformed 狀態，另以區域變數保存 done、spoke 與 failed；`formal-02-A0` 則使用 `_State` 類別與 handlers。閱讀時追蹤三個 review 問題：text 在哪裡驗證、合法事件何時改變狀態，以及 EOF 優先序在哪裡決定。這是靜態程式閱讀，不是人類維護實測。

原始檔案的 SHA-256 用來核對內容身分；normalized AST hash 只識別正規化後的表示，不代表原始檔案逐 byte 相同。這組配對的 cosine 為 0.9939804370606344，不帶品質意義。

## 共同假設 transfer 案例（四篇可輪流推進，不必全複述）

假設一個 CSV 匯出工具新增日期欄格式化。呼叫端已要求保留輸入列的順序與重複列，卻還沒決定空日期要輸出空欄或拒絕。這時先請 owner 回答，不能由 agent 生成 expected value 來代替決定。等 owner 決定缺值保留空欄後，才比較新增說明。

若沒有要求在 EOF 前讀到輸出，批次輸出也可能合法；parser 的 streaming probe 不能直接套用到所有工具。對資料列排序或去重會改變行為，因此不屬於合法的內部設計自由。只要滿足契約，則可以使用不同的 helper、類別或行內實作。這是教學假設，不是作者 repo 已有的第二個正式研究任務，也沒有實測 ROI 或失敗次數。

## 新架構審查補充（主寫必須遵守）

新比較卡採用可使用工具、但有明確限制的 session，與正式研究的 40 次無工具生成不同。Policy、人工救援，以及 task、work、session、candidate 各單位的定義，以 `rewrite-plan` 最後一節和 `comparison-plan` 最新文字為準。不得把新設計寫回正式研究歷史。

「留下回歸資產」必須分清三種動作：用固定 fixtures 檢查 grader、用契約檢查新候選，以及取得新生成結果來檢查 model／harness。已公開的題目不是未見的 holdout。

總論要把 CSV 案例完整走到一個可執行的出口：先修 oracle，就能恢復既有驗收，不必把所有團隊都送進 P／Q 比較。四篇主要工件應是同一份紀錄逐步完成各項判斷，不能重印四次十幾欄的表格。

工作坊數字的正確方向是：16 項中**通過 10 項、未通過 6 項**。新研究底稿早期曾誤寫為十項不符，已在主寫前對照《綠燈不是驗收》原文修正，不能沿用錯句。

「相同工具」指相同的可用工具、權限與預算，不是強迫 P／Q 執行完全相同的工具呼叫序列。自查讓 agent 多做哪些公開驗證，可能就是介入發揮作用的途徑，應記錄下來，而不是事先排除這些差異。不過，這仍不表示能從 trace 直接讀出模型的心理成因。

候選必要條件與方法採用門檻要分開：單份候選違約，不能用其他測項得分抵銷；跨 trial 比較仍須如實保留失敗，不能暗中增加一項事前未訂定的要求，規定零失敗才准採用。方法層有哪些風險不可接受、需要具備哪些補救能力，則須另行決定。


## 總論成稿後補正：自查的跨任務改寫

此補正晚於三篇主筆 prompt 的封存，供主代理潤稿及後續審查使用，不回寫已送出的 prompt。Parser 的 worked example 可比較展開規格與凍結 B 六題原文；跨任務則不能直接套用 EOF、token 或 R09 等義務。下一輪目標改明確定義為「依事前固定政策改寫自查」：只指向各 task 的 P 已揭露要求，不適用項目按事前規則處理，不藉 Q 增加要求或帶入隱藏 grader／參考 patch 資訊。各 task 的 P／Q 先核對、封存，同 task 同 arm 的重複內容逐 byte 相同。效果屬這套改寫政策，不是原六句或第二題的單獨效果；映射與維護也計入人工投入。

完整任務映射與 packet 尚未完成，48×2×3 仍只是預算草案，不能作為可直接執行的規範。詳見 [自查改寫政策](self-check-transfer-policy.md)。必要行為與相容責任不必等待此可選介入的效益比較。
