## 一、這輪 research 對全文結構的主張

現在的變異篇已經相當注意不過度解讀數字，問題是大量篇幅用在防止錯誤結論，卻沒有把限制轉成讀者可以做的工程判斷。讀者知道「40/40 不能證明可靠」，但讀完仍不知道該維護哪份文件、先補哪項驗收、下一筆研究預算該花在新任務還是重複執行。

10 月可靠度篇的完成度不只來自數字更多。它先說現場要決定授權，接著解釋現有綠燈缺哪一種證據，再展示怎麼取得證據，最後讓負責人面對一張有 pass／hold 條件的決策表。新系列應沿用這種推進方式，而不是把新的論文摘要加進現有六節。

本次最有用的新主線是：**一份可讀懂的交代，如何成為可以反覆採用的工程方法？當比較失去分辨能力，團隊又該把已完成的工作放到哪裡？**

這條主線有四個具體層次：

1. **Why：文件是一項持續投入。** 多寫理由、自查、helper 意味著有人維護，需求改動也要同步。如果不知道它預計減少哪種失敗，就無法知道後來的篇幅是否值得保留。這是提出比較的原因，不是預设長文件有用。
2. **What：先界定決策與觀測單位。** 選一份能交付的候選、選一種將來反覆使用的交代、允許某類任務增加自主權，是三個不同問題。它們分別需要產物驗收、跨條件且跨任務的比較，以及帶有人力與風險條件的部署證據。
3. **How：先保護量尺，再比較。** 一百次重複同一個漏檢，仍可能只是在穩定地漏掉要求。先把契約映射到能抓負例的驗收，保留環境與每次失敗的紀錄，再談通過率與成本。
4. **結果如何改變工作：** 這次四組 10/10 沒有支持排序，但不代表只得到一份「沒有結論」的報告。已封存的正例、負例與 grader 可以成為回歸資產；未來要辨識改善，則另設代表性任務集合、分離的 pilot 與正式保留題。這是用途的改變，不能寫成證明任何規格已達 production 可靠度。

## 二、八份來源：每一份補哪一個缺口

### REL01：τ-bench，可靠度首先是 task 與 trial 的關係

- **來源：** Yao et al., *τ-bench*, arXiv **2406.12045v1，2024-06-17**。正式定義在 §3，PDF pp.4–5；設計與限制在 §5。
- **可用的內容：** pass@k 問同一任務的 k 次獨立嘗試中是否至少一次成功；pass^k 問是否全部成功，再對任務取平均。原論文保留每個 task 的成功次數，並給出適用於 n≥k 的組合估計式。若每題恰好執行 k 次，pass^k 就是全部成功的題目比例。
- **讀者需要的中間一步：** 在同一個 parser 上生成十份程式，增加的是這個 parser 的重複觀測；它沒有讓資料多出九種工作。團隊想知道「哪些工作可以交給這套做法」，就必須保留多個任務及各自的結果，不能把所有 run 打散後只留一個總成功率。
- **限制：** 原研究是 retail／airline 模擬客服；使用者模擬器也會帶來變異。不要把原論文的客服成功率當成 coding agent 基準，也不要把現有單一 parser 計算成任務族群 pass^10。
- **額外價值：** 原文也承認最後資料庫狀態相符只是必要條件，可能沒檢查到「應先取得使用者同意」的過程約束。這可回扣契約篇：輸出與過程要求要有不同證據。
- **連結：** https://arxiv.org/pdf/2406.12045v1

### REL02：Anthropic evals 實務，讓「全過」有下一個用途

- **來源：** *Demystifying evals for AI agents*，2026-01-09。關鍵段落是 Capability vs. regression evals 及 Step 7。
- **短原文錨點（14 words）：** “An eval at 100% tracks regressions but provides no signal for improvement.”
- **可用的內容：** 能力題組需要能辨識改善；已有能力則要靠回歸題組防止退步。文中還要求 reference solution、明確可公平判定的 task、乾淨執行環境，以及一起讀 transcript 與 grade。
- **讀者需要的中間一步：** 這次四組都通過時，不必再從成功率挑勝者。先問原本 grader 是否真的能抓 parser 重要失敗；若可以，保留這些檢查作回歸資產。再用另外的題目回答「自查有沒有幫忙」，不能把這批題反覆調到某組贏為止。
- **限制：** 廠商工程實務文章，不是隨機對照實驗；這是用途與流程的建議。當前 40/40 仍不保證未來不會回歸。
- **連結：** https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents

### REL03：環境不是表格底下的註腳

- **來源：** Gian Segato, *Quantifying infrastructure noise in agentic coding evals*，2026-02-05。How we got here、How this affects measurement、Other sources of variance。
- **可用的內容：** 相同模型／harness／任務，資源保證與 kill threshold 的設定仍會改變結果。作者在 SWE-bench crossover 使用 **227 題、每題 10 samples**，RAM 1× 到 5× 的差距為 **1.54 個百分點**。文章沒有說清楚 samples 是否每個資源條件各十個，不能再自行乘出總請求數。
- **另一組數字需要保留缺口：** Terminal-Bench 2.0 六種資源設定端點差六個百分點，但文章未列這組實驗的任務／run 分母。如果篇幅不容納這個限制，就不要選這個數字當主證據。
- **讀者需要的中間一步：** 同一個 packet 只固定了我們送出的文字。若 agent 還會安裝、建置和測試，環境也會改變它能嘗試的解法。數學上的抽樣區間不能替沒有控制的環境變化背書。
- **限制：** 本次 parser 是 tool-free 生成，不能因此反推它的變異由 RAM 造成。資源倍數是該 benchmark 的校準結果，也不能照搬成所有 repo 的 3× 標準。
- **連結：** https://www.anthropic.com/engineering/infrastructure-noise

### REL04：EvalPlus，重複生成前要先問量尺能看見什麼

- **來源：** Liu et al., arXiv **2305.01210v3，2023-10-30**；§2.3 Program Input Contracts、§3 Setup／Table 3。
- **可用的內容：** 在 **164 個 HumanEval Python 函式任務、26 個模型**上擴充測試，找到了舊測試未辨識的錯誤，甚至改變模型間排序。這是同一批程式在不同保護力的驗收下得到不同判斷，不是模型突然退步。
- **重要機制：** 測試輸入也要遵守契約；未定義輸入不能隨意拿來處罰不同但合理的實作。研究以 precondition assertions 界定輸入域。
- **對 parser 的反例：** 本次規格刻意定義數字、null、列表等錯誤形狀如何處理，所以它們是要驗收的內容，不能因為看起來「不合法」就排除。究竟是 outside contract 還是 contract 指定的拒絕路徑，必須先讀要求。
- **限制：** HumanEval 小函式不等於 repo agent；更多測試仍非完整正確性證明。若引用摘要的 19.3–28.9%，要說這是不同 pass@k 的最大相對下降，不是平均、更不是 percentage points；正文可只保留機制與設計。
- **連結：** https://arxiv.org/html/2305.01210v3

### REL05：AI Agents That Matter，把比較接到使用者願意付出的成本

- **來源：** Kapoor et al., arXiv **2407.01502v1，2024-07-01**。§2.2–2.3、§4–6，Appendix G。
- **可用的內容：** 作者同時比較成功率、費用和簡單 retry baseline；在 HumanEval **164 題**上每個 agent 重複五輪。提醒 holdout 要符合想推論的範圍：新 task、新環境或新領域不是同一件事。
- **讀者需要的中間一步：** 「三次裡找出一份可用程式」可能是合理產品策略，但它的成功率必須連同另外兩次失敗、辨認哪一份正確的成本一起算。不能把這種 policy 和只允許一次生成的條件並排後叫做規格效果。
- **限制：** 論文本身明說沒有充分量測人工、標註與維護成本。不能拿其 Pareto 圖替本次 AST 差異或真人 review 時間背書；舊模型與價格只作方法例證。
- **連結：** https://arxiv.org/html/2407.01502v1

### REL06＋REL07：METR 的價值在於終點與方法反省，不是借一個熱門百分比

- **歷史來源：** 2025-07-10 RCT，**16 位熟悉自己 repo 的開發者、246 個真實 issue**，issue 分派允許／禁止 AI。完成的定義是開發者相信可以過 review，包括 style／test／documentation；這和只有生成耗時的終點不同。
- **歷史數字：** 19% 放慢是 early-2025 情境，主要工具為 Cursor Pro／Claude 3.5、3.7。當前頁面已明示這個結果過時，不能寫成現在 AI 對工程師的普遍影響。
- **更新來源：** 2026-02-24，**57 位開發者、143 repos、800+ tasks**。作者主動說研究受 developer／task selection、報酬變更與 agent 並行工時歸屬影響，無法可靠估計當前效果。原始 point estimate 不應拿來宣稱現在沒有改善，或改善了某個百分比。
- **讀者需要的中間一步：** 即使 task 已隨機分派，最前面的「哪些人與哪些任務願意進研究」仍會改變結果的適用範圍。當人等 agent 時在做別的工作，wall-clock 與 active human minutes 也不同。團隊需要先把自己實際要付出的時間定義清楚。
- **限制：** 兩份都是生產力研究，不是長期 maintainability 研究，也不等於專門量測 code review 的時間。它們示範缺資料時該改研究方法，而不是替這批 40 份程式補上不存在的維護成本。
- **連結：** https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/
- **更新：** https://metr.org/blog/2026-02-24-uplift-update/

### REL08：NIST randomized blocks，把「控制條件」寫成能檢查的安排

- **來源：** NIST/SEMATECH e-Handbook，§5.3.3.2，未標發布日期，查閱日 2026-09-28。
- **可用的內容：** 對已知而可控制的 nuisance factors 使用 blocking，在區塊內變動想研究的因素；其餘因素用隨機化減少與條件混在一起的機會。
- **讀者需要的中間一步：** 若 P 都在星期一執行，Q 都在星期三執行，模型服務或機器狀態改變就可能看起來像文件差異。把兩組交錯分派、保留日期與 block 才能查這個問題。
- **限制：** block 不是魔法；原四十次的重疊排程不能倒寫成同步配對時窗。一般 DOE 原則也不是二元成功率的現成分析方法。
- **連結：** https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm

## 三、兩個真正能教會讀者的假設例子

### 例子 A：同樣 80%，到底想解決一次工作還是反覆交付？

以下完全是假設，不是本次 40 個名額的估計。固定一個任務，每次獨立，單次成功率 80%。

| 想問的事 | 三次嘗試的假設結果 | 這個數字沒有說什麼 |
|---|---:|---|
| 三次中至少有一次做對 | `1−0.2³ = 99.2%` | 沒說你能找到那一次，也沒免除另外兩次的成本。 |
| 三次全部做對 | `0.8³ = 51.2%` | 沒說其他類任務也有相同成功率。 |
| 遇到成功即停止，最多三次的平均嘗試數 | `1+0.2+0.2² = 1.24` | 假設辨識成功完全正確，且只是重新生成。收到回饋再修正屬於不同 policy。 |

再假設每次生成 USD0.10、驗證 USD0.02，平均模型與驗證成本是 USD0.1488，而每次都先生成三份再挑則花 USD0.36。數字只是教學；真實 checker 的誤收／誤拒、人類比較、失敗處理與時間都還要記錄。這裡的實用問題是「團隊准許哪一種嘗試政策、誰來認出正確版本」，不是把 pass@3 當成品質保證。

算式與結果已列在表格及段落中；編輯核算紀錄另存私人 `.context/same-spec-ten-runs/research-rebuild-2026-09-28/reliability-hypothetical-arithmetic.json`，不構成新實驗資料。

### 例子 B：同樣 50% 平均成功，接手方式可能完全不同

假設有十個任務、每題兩次。系統 X 在五個任務兩次都過，另外五個兩次都失敗；系統 Y 在十個任務都剛好一過一敗。兩者總成功都是 10/20，但 X 至少在觀測中有一批可辨識的穩定成功任務，Y 則每一題都觀測到不一致。兩者觀測 pass^2 分別是 5/10 與 0/10。這是刻意構造的例子，不是母體機率估計。

實務上，X 提醒團隊調查失敗是否集中在特定工作類型；Y 提醒團隊同一類工作的每一次交付都需要能辨識失敗。僅保留總成功數會把這兩種情況混在一起。這也解釋了為什麼下一輪需要 task ID，而不只是多跑幾百次。

## 四、可交給讀者使用的決策流程

完整已填寫的草案與無預設數字的空白模板見 [比較計畫範例](comparison-plan-example.md)。它刻意包含「尚未有真實 task inventory」與「規模不是 power guarantee」，不把空白研究材料假裝已存在。

建議正文把流程接到三個角色的問題，而非列十幾個未解釋的欄位：

1. **規格 owner 先說要減少什麼。** 是不清楚 null 的意義、忘了 EOF 優先序，還是 scope 漂移？先把失敗型態與要變動的文件成分對應。若規格本身沒定義預期行為，補的是需求；若已定義而候選仍錯，才能研究提示／自查是否改善實作。
2. **QA owner 先證明量尺辨識得到它。** 參考修補通過、故意破壞那個行為的負例失敗；failure message 能回到原要求。若兩種明顯不同的行為都綠，就先修量尺，不急著選文件。
3. **實驗 owner 才分派有限預算。** 保留代表性 task 與重複 trial 的兩層資訊；pilot 調試不進正式集合；run／retry／missing 的規則先訂好；跨條件同樣的預算與環境。
4. **接手 reviewer 補上機器沒量的成本。** 真正接手某份 hash 固定的候選，記錄確認契約、閱讀、要求修正與補救所花的 active time；不把 AST 相似度翻譯成工時。
5. **決策人把效果與採用條件分開。** 差值區間下界高於事前門檻，才支持效果超過門檻；上界低於門檻，可排除達到這個幅度的改善；其餘未定。正向改善的下界仍未達實務門檻時，不能直接宣稱值得採用。效果達標後還要確認成本與人力；若人力確定超限，應記為目前不採用，不能說效果不明。完整互斥條件與純假設區間見比較卡第三節。

## 五、同一批四十份候選能再做什麼，不能偷換成什麼

下列都是**事後、描述性或驗收保護力的補充分析提案**，不是新的模型生成觀測。保留既定 103 項與 40/40，另開 revision／analysis 目錄及 hash。執行前先記問題與方法，避免先看差異再發明漂亮分類。

| 可做的補充 | 具體工件 | 幫讀者回答 | 不能宣稱 |
|---|---|---|---|
| R01–R13 的可觀測性地圖 | 每條要求列輸入、預期 side effect、現有案例、negative control、剩餘缺口。包含 streaming／EOF 等時點，不只 stdout。 | 103 項究竟量到哪些承諾？再重複時會重複驗證什麼？ | 13 條都有名稱就等於 coverage 完整。 |
| 手工 semantic mutants／負例檢查 | 針對數字當 text、bool 當 int、`if text:`、exit6/5顛倒、未 flush 等錯誤製作可追溯小改動；在新資料夾執行凍結 grader，記錄 killed／survived／invalid。 | 已有綠燈能否分辨作者說在意的錯誤？ | 把 mutant 數當新的 agent 樣本，或只挑全部被抓到的 mutants 報告保護力。 |
| 全部候選的窄範圍結構 inventory | 先定義「state 存放方式、dispatch 方式、text validation、exit priority 所在位置」等可直接指向程式碼的欄位，對四十份都列；模糊者保留未分類。 | 對 reviewer 而言，找到規則要沿哪條程式路徑？ | 用 category 數／LOC／cosine 排可維護性名次。 |
| 資源分布與執行順序檢查 | 40 次逐點 cost／elapsed／cache，按固定條件和真實起訖時間畫圖；全列缺失與 concurrency。 | 組合計是否被一兩個高值影響？單次 deadline 與中位數為什麼不同？ | 事後看時間趨勢就證明 provider drift，或十個 block 的重疊順序等於配對因果實驗。 |
| 針對既有契約缺口的新版一致重評 | 例如補 main 介面檢查、額外 metamorphic relations。新 grader 自己有正／負 controls，對四十份一次一致重評，原始判定旁列不覆寫。 | 既有 103 項以外，哪個要求仍需保護？ | 新版分數是正式先驗主結果；也不能稱新增四十個獨立樣本。 |
| 為真人接手準備 review task | 去除條件標籤、固定同一需求變更、隨機分派相同初始候選；記錄理解與完成修改時間、錯誤及回歸。 | 如何開始收集實際的理解／修改成本？ | 在沒有真人完成此流程前，報告「已改善 review」或「較好維護」。 |

最值得先做的是前兩列，因為這個系列真正想教的是如何信任判斷的過程。既有 AST 圖已能證明表示不同，繼續加更多抽象相似度未必增加讀者能做的事。本報告提供這些補充分析的設計與呈現需求；是否執行及結果如何，應由另外的分析紀錄說明，不能把提案當成已完成的結果。

## 六、作者可以明確下的判斷

「我不會因為這輪都過，就把最短那份宣布為最佳規格。我會先把已證實能抓缺陷的驗收留作回歸保護，再問長文件原本想省下哪一種錯誤與人工工作。若下一輪仍無法辨識那種改善，這份額外文件就還沒有取得成為預設流程的證據。」

以上是建議論點，**不是代寫作者的親歷敘事**，也不是正式資料已證明的因果。它的力量應來自前文清楚展示了如何判斷，而不是用更強烈的語氣抵銷樣本不足。

最後的 recall 可以接回 10 月的三層：test gate 先問量尺，review gate 問這一份產物與接手責任，reliability gate 問一種做法在目標工作上的重複結果。新系列則補上這三層之前的「交代如何形成，以及如何知道文件的維護投入值得」。這樣四篇會有延續，也有新的問題可解。
