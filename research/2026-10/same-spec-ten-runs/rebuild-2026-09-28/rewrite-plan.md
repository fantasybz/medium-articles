# 全面重寫的研究與寫作決策

作者最新要求以十月份《綠燈不是驗收》系列的 why/how/what 深度、故事與具體判斷過程對標，不以字數或通過 linter 為驗收。四篇主寫仍使用 actual Claude Code Opus 5.5 max；root 逐段精修，含後半部；最後 evidence／reader／editor／zh-TW 檢查。原先四稿被作者拒絕，不保留既有節數或篇幅上限。

核心問題：團隊準備把一種交代方式變成常態時，怎麼知道自己改善了什麼，又憑什麼保留這项改動？

三層判斷：需求是否已被決定（owner/領域）；候選是否做到（可觀察義務与oracle）；交付方法是否值得重複用（具範圍的比較与人力）。

誠信邊界：正式研究仍為一個作者repo parser 任務、A0/A/B/C各10份、103項共同檢查全過、模型high（主寫max是另一用途）。新workbench為既有可信fixture的後設教學，沒有新模型樣本；下一輪比較計畫純設計，不得倒寫成已執行。

## 三、建議的新四篇論證架構

以下為獨立重寫架構，不必保留暫題，也不是要求每節套同一種句式。全系列的中心問題可改成：**團隊準備把一種交代方式變成常態時，怎麼知道自己改善了什麼，又憑什麼保留這項改動？**

### 總論：你改善了規格，還是只是換到一次好結果？

**讀者與決策：** EM、Staff、QA／platform lead 決定要投資補文件、補驗收或補量測；讀完能拒絕沒有說清改善對象的「把規格寫詳細」提案，也能提出一個有範圍的 pilot。

**論證順序：**

1. 從工作坊的真實缺口出發，承接 October：先前處理一次產出何以可信，現在處理一種做法何以值得重複。
2. 寫清真實選擇壓力：一次改稿成功後，要不要將它變成所有任務預設？以假設情境展示維護與 review 責任，不冒充親歷。
3. 建立三層問題與三種不同證據：要求已決定嗎、候選做到了嗎、這套方式反覆使用值得嗎。
4. 說明有些實作自由是契約刻意保留的；追求所有程式相同不等於品質改善。
5. 綜合新研究的支持與反例，提出有條件的作者主張：每項文件修改先指向可觀察的問題；驗收要能區分錯法；採用與否看與目標一致的比較。
6. 窄 parser 研究作為方法示範：它讓哪些問題可核對，又在哪裡碰到上限。不要把未知藏掉，也不要讓未知成為整篇終點。
7. 按角色、資料完備度給起步順序，留下採用／保留現狀／補資料三個出口。

**主工件：** 一頁「文件改動評估提案」。欄位：要改善的工作問題、目標任務範圍、現況證據、候選介入、對應驗收、主要／次要結果、不可接受的代價、owner、下一次決策時點。至少示範一份以現有 parser 為背景、明確區分歷史事實與下一輪設計的填寫。

**驗收問題：** 不讀後三篇，讀者能否說出為什麼現在值得做、應先投資哪一層、什麼結果會改變決定？拿掉本輪 AST／成本數字，中心論證是否仍成立？若答案否，主幹仍太依賴資料展示。

### 規格篇：多寫一段之前，先決定它要替誰解決哪個選擇

**讀者與決策：** 文件作者、Tech Lead、任務設計者決定應澄清需求、補理由／例子／自查，還是把限制移到驗收與環境。

**論證順序：**

1. 以「把 parser 改得更穩健」開出多種合理解讀，展示需求尚未決定的代價。
2. 區分必須遵守的行為、相容決定、設計理由、例子、可選實作路徑；解釋各自如何幫助下一個動作，也如何造成額外維護。
3. 用 R05 逐字比較 A0／A／B／C，先問相同輸入允許什麼，再看補充內容改了什麼。
4. 用 null、exit 優先序與 CLI 措辭展示「看似同義其實變更要求」，交代語義對齊能做與不能做的事。
5. 引入新研究討論資訊、相關性、上下文長度、示例／程序和工具環境的不同效應；呈現至少一個補文字沒有幫助或有代價的相反條件。
6. 完整走一次文件修改：失敗紀錄 → 可觀察的實作問題 → 不越界的原因假說 → 一項介入 → 對應驗收與比較。別把模型心智狀態當事實。
7. 定義版本、owner 與撤回／過期檢視，不讓每次失敗都無限追加指引。

**主工件：** 「規格修改卡」＋附屬的四類文字標示示例。卡片要包含受影響要求、舊／新文字、行為是否改變、理由、想改善的錯誤、可能副作用、比較方式與保留條件。四份真實文件全文是查核附件，卡片是讀者可用的工具。

**驗收問題：** 讀者能否說出 A0 與 A、A 與 B、B 與 C 的具體差異，也能指出這個設計不能分離哪些效果？碰到不同於 R05 的需求，他是否能自行分類下一段文字的工作，而不是只照抄 B？

### 契約篇：把一句要求變成可信的驗收，不能省略哪幾步？

**讀者與決策：** QA／test lead、reviewer、驗收工具作者判斷 oracle 是否對準需求、何時可自動判定、何時必須退回澄清。

**論證順序：**

1. 先說成功的訊號為何可能錯：exit 0 的 parser 和「測試全過」的模型，分別省略了什麼。
2. 定義 oracle：誰依什麼判對错；舊輸出、reference implementation、規格推導與人工判斷各有盲點，不只說答案藏在哪裡。
3. 保留最強 R05 逐行推導，接上三種錯法的辨識；再從精確字串比對推出「允許多個合法答案」的問題。
4. 保留 streaming，抽象成「終態相同、過程仍違約」；把時間、資源、權限、相容性分成需另外觀察的義務，不承諾全部可用同種測試解決。
5. 用小對照驗證 evaluator：已知合法、已知非法、邊界／例外、不能判定；說明 mutation／metamorphic／property 等方法若被採用，分別補哪一種疑點。
6. 再談來源隔離、保護版本、生成與評分時間安排、工具紀錄，讓安全機制服務於讀者已理解的證據要求。
7. 示範 uncovered obligation 與 evaluator amendment 如何交給 owner，何時重評全部候選、何時必須重新生成。

**主工件：** 「要求 → 可觀察義務 → oracle → 已知錯法 → 涵蓋缺口」表與最小重播入口。若提供新可執行示例，放於補充教學區，標明不是凍結的 103 項正式資料。

**驗收問題：** 讀者能否自己推導一個未展示輸入的預期值？能否發現太鬆和太嚴的 oracle？看到通過時，能否指出下一個仍未回答的要求，並決定該補測、澄清還是停止判定？

### 變異篇：從一次改稿走到團隊採用，怎麼設計有用的比較？

**讀者與決策：** 研究／eval owner 與 EM 決定保留、撤回、擴大試行或再補哪種資料；reviewer 能將特定候選身分與長期流程評估分開。

**論證順序：**

1. 先拆清楚三種變動：同條件重複、文件條件介入、任務／模型／工具環境變更；指出各自比較單位。
2. 從要作的決定倒推主要結果：契約通過、失敗種類、完成成本、人工審閱／修改負擔。成本不能和品質混成任意總分。
3. 把正式 40 份結果當 worked example，保留分母、不重試、限制與 10/10 的區間；用假設數值解釋樣本不確定性。
4. 用「資料不足」「碰到上限」「行為不等價」「任務不代表目標工作」四種情況，分別推導下一輪改什麼；不要只說更多／更難。
5. 用 A0 兩份程式展示可接受自由與需要審閱的修改位置。只做靜態閱讀時明說，AST 指標不冒充維護品質。
6. 根據查證文獻交代 pilot、正式樣本、任務分層、重複與預先定義差距的取捨；不用宣稱一個通用樣本數。
7. 以決策紀錄把結果交回文件 owner：採用需什麼證據、保留現狀基於什麼理由、補資料如何限定範圍；建立下一次版本變動時重新評估的觸發條件。

**主工件：** 「比較計畫與決策紀錄」。包含目標工作、任務來源與分層、介入與不變條件、樣本／重複安排、成功定義、缺失／中止處理、主要結果、實務上有意義的差距、成本與人力欄、已知限制、最終採用／不採用／尚不能判定及理由。給空白模板與不捏造結果的範例。

**驗收問題：** 10/10 之後，讀者能否根據自己想知道的是什麼，選擇增加重複、增加代表性任務、改善 oracle 或重設介入？能否說清什麼觀察會讓自己保留或撤回文件修改？是否能把「本候選可交付」和「文件改善已成立」分開作決定？

## 四、新研究 loop 要填的缺口

本報告沒有瀏覽，以下是交給來源研究者的問題清單，不是已經查證的發現。每筆新來源應記研究單位、任務範圍、介入內容、對照條件、重複安排、成功定義、可用結論與不可移植之處。

1. **規格的工作是排除哪些未決選擇？** 找成熟需求工程、契約／相容性與可觀察行為的第一手論述，用來區分要求、理由、例子與實作指引。若借正式方法術語，必須展示它幫讀者判斷哪一段文字，不能只加書名。
2. **資訊增加與文件變長是同一件事嗎？** 查 coding-agent 指引／context 文件的實測；同時找改善與未改善／有代價的條件，檢查是否改變資訊、工具路徑或任務定義，而不是只讀成本百分比。
3. **為什麼單一固定 prompt 仍可能有不同路徑？** 區分模型抽樣、上下文、工具結果、環境與任務交互作用；對現有 tool-free 研究只主張可控制與可觀察的部分，不能由不可見 provider 設定推定某一個變異成因。
4. **好的 oracle 怎麼建立與反駁？** 查 oracle problem、property／metamorphic testing、mutation 的原始方法與限制；尤其是沒有唯一答案、過程要求、共同設計盲點与 expected output 的來源。
5. **少量反覆執行能回答哪種問題？** 查二項區間、等效／非劣比較與重複測量的第一手方法資料，服務於具體決策；分清 run 與 task、群內相依與任務代表性，不把單任務 40 次當成 40 種工程情境。
6. **結構差異何時轉成工程負擔？** 查讀程式、修改任務或可維護性量測；若找不到直接支持，應明確保持為待測假說，將 hash／cosine 降為描述工具。
7. **文件與 eval 如何持續維護？** 查 context／eval 版本、holdout 污染、規則過期與人力投入，讓 owner、撤回條件和改版觸發有機制依據，而不是流程清單。

每份來源進稿的門檻：它至少要增加一個現稿缺少的機制、反例、適用條件或可用判準。只重述「單次成功不代表可靠」的來源可以保留研究筆記，不必占正文。

## 五、交稿前應使用的內容驗收

這些問題比「語言 0 警告」「max 主寫」「又一次 xhigh 無 major」更接近使用者的要求。語言與工具驗證仍要做，但順序在論證成立之後。

1. **Why 的三層：** 每篇都說清楚工作困境、為何既有直覺不足，以及解決後會改變誰的哪個決定。若只答「學界還缺資料」，不通過。
2. **How 的三層：** 有概念與機制、有一步一步算／讀／判的 worked example、有把它移到讀者任務的程序與例外。只展示本研究操作日誌，不通過。
3. **What 的三層：** 清楚區分本輪事實、跨來源綜合與作者建議；每篇交出一個可用工件；說明該工件的判定出口與責任。只有結尾待辦清單，不通過。
4. **反例測試：** 每篇至少讓一條直覺解方遇到會失效的條件，然後修改建議。不是只附一句「不能推廣」。
5. **轉移測試：** 用另一個清楚標示的假設任務，讓 reviewer 按文中方法完成一次判斷；若必須由作者另行解說 R 編號才用得上，尚未形成一般方法。
6. **刪除測試：** 拿掉研究 CLI 版本、每列精確小數與封存路徑之後，文章主論證仍應成立；這些細節能核對，但不能代替思想。反過來，刪掉任何一篇，都應少掉一項不可替代的決策能力。
7. **限制的用途：** 每個重要限制都要交代會阻止哪個推論、改變哪個動作；避免反覆「沒有量測」但沒有下一步。尚不能判定也是出口，但要指出缺什麼才可能改變。
8. **跨篇承接：** 概念、角色與主要工件前後相接；讀者不必在每篇重讀同一段 40/40、103 項檢查的背景才能開始。R05 可以貫穿，但每次回來必須承擔新的推論。
9. **證據誠信：** N=40 正式資料、後續重評、靜態教學 walkthrough、新研究設計、外部資料彼此分開；不修改封存、不追補正式樣本、不把假設的失敗或人工成本寫成觀測。
10. **全文完成度：** 尤其重新審閱各篇後半部：表格後有沒有真的推論，工件後有沒有接手／例外，結尾能不能回答開場的選擇，而不是只再預告下一篇。



## 研究審查後的主寫決定（2026-09-28）

本節優先於前述初稿架構的模糊描述。它不是新的正式實驗結果。

### 一条紀錄跨四篇前進

主要文件介入固定為 **P＝展開規格，Q＝相同規格加六點自查**。Q 不包含原 B 額外的集中理由，也沒有 C 的 pattern。總論說明為何值得提出這個問題；規格篇填寫修改卡；契約篇把卡片中的行為連到可觀察義務與正反對照；變異篇才決定要用什麼範圍與比較來回答是否值得採用。各篇只展示本篇增加的判斷，不重印四次完整計畫。

理由、例子、自查與實作建議各自可能改變人的理解或模型下一步，但這些是工程作用假設。沒有觀測能支持時，不把『看見 truthiness 寫法』解釋成已知模型漏讀，也不把 B 的套件效果拆給其中一段。來源在不同工具與任務上的結果用來理解條件與替代解釋，不組成通用效果排名。

### 三個讀者出口

1. **先修明確缺口：** 如果空欄政策未定，需求 owner 決定；如果 oracle 誤拒合法 LF／CRLF，QA owner 修量尺並一致重評受影響產物。這兩件事不需要先用模型比較規格長短。
2. **有限學習：** 診斷 pilot 確認量尺／runner／紀錄可運作，不估群體收益；有限部署 trial 維持原有人類核准，限定工作、owner、停止及回復條件，取得真實工作證據。兩種用途不能只用一個『pilot』名稱混在一起。
3. **改為預設或擴大：** 才依事前確定的效果、成本、人力與不可妥協的行為判準作決策。效果達標但人力超限，是目前不採用；效益幅度或人的投入未定，就明說還缺哪一筆證據。

主文至少以 CSV 假設走完第一個出口，再以 parser 背景的 P/Q 提案走向後兩個出口。讀者不該以為改善一份交代之前，一律需要 288 個名額的研究。

### 下一輪比較的 policy 是新的設計

原正式四十次仍是 tool-free one-shot。下一輪範例改為有限、可使用工具的 agent session：同一套 repo／工具／预算下，允許 session 內依公開檢查自修；外部驗收在 session 結束後進行，沒有額外新 session 替補。`task_id` 是工作題目，`work_id` 是一次事前排定的 policy 試行，`session_id` 是該名額的執行階段，`candidate_id` 對應產物 hash。中間程式版本不增加獨立樣本數。

主要結果是每個排定名額的最終候選是否通過操作條件與既定外部驗收。之後人工 review、有限修補及最終交付另外記錄，不回填 agent 的主要成功。成本包括所有嘗試及補救；只有模型費用時，不算端到端 ROI。實際採用的政策、預算、工具、人的責任必須在執行前填妥；此處尚未執行。

任務母體從固定期間全部進入的合格工作建立清單，保留無法驗收／未完成／排除理由。若實際只能用已合併歷史題，就將結論限於回溯 backtest，從修補前 commit 開始。已看過答案的同題改寫不變成 fresh holdout。pilot 的刻意錯法用於查量尺，不能當作母體錯誤率來宣稱 power。

人工觀測要有分派與分母。至少分開讀碼、修正、核准、被動等待與文件維護；記錄同題重讀與熟悉程度，不能把某人第二次看同題當作獨立的時間改善。若没有安排真人觀測，數字門檻只能留在未執行計畫，不能通過聯合採用條件。

### Regression 的三個不同動作

- 固定合法／非法 fixture，換 grader，檢查驗收器是否退步。
- 固定契約案例，測新候選，檢查新實作是否保留已涵蓋行為。
- 固定適用任務與 policy 版本，取得新生成結果，保留 task／trial，觀察新的模型／harness 方法。

重評舊候選不產生第三類證據。原題目與評分資料已作為可查附件揭露，可留作回歸資產；另存副本不會讓它重新成為未見保留題。

### 不能作為達標替代品的數量

研究來源數、article 字數、圖表數、Claude effort 與 zh-TW 零警告都不是內容通過的證明。全篇要沿可指認的材料讓讀者完成判斷；每篇後半部另讀一次，檢查表格後的推論、owner 接手與結語的限制。原四十次封存不能改，教學、重評、靜態閱讀與未来设计也不能合成新的實驗分母。


## 總論成稿後補正：自查的跨任務改寫

此補正晚於三篇主筆 prompt 的封存，供主代理潤稿及後續審查使用，不回寫已送出的 prompt。Parser 的 worked example 可比較展開規格與凍結 B 六題原文；跨任務則不能直接套用 EOF、token 或 R09 等義務。下一輪目標改明確定義為「依事前固定政策改寫自查」：只指向各 task 的 P 已揭露要求，不適用項目按事前規則處理，不藉 Q 增加要求或帶入隱藏 grader／參考 patch 資訊。各 task 的 P／Q 先核對、封存，同 task 同 arm 的重複內容逐 byte 相同。效果屬這套改寫政策，不是原六句或第二題的單獨效果；映射與維護也計入人工投入。

完整任務映射與 packet 尚未完成，48×2×3 仍只是預算草案，不能作為可直接執行的規範。詳見 [自查改寫政策](self-check-transfer-policy.md)。必要行為與相容責任不必等待此可選介入的效益比較。
