## 1. Book at a glance

**Author.** 李博杰 Bojie Li, Chief Scientist of Pine AI (the `19PINE-AI` GitHub org; Pine is a voice agent that phones carriers and merchants on a user's behalf to negotiate bills, refunds and cancellations, "all without a human stepping in"). The book grew out of the 图灵《AI Agent 实战营》bootcamp he taught Aug–Oct 2025 and an AI Agent course at 中国科学院大学 (2024–2026) (引言). He also publishes a sister book,《深入理解 AI Infra：量化分析与系统设计》(github.com/bojieli/ai-infra-book). The introduction states the book was produced by "whisper coding" (口述式协作) with Pine's own voice agent — "this book is not only about Agents; it is also a work an Agent helped create" (EN intro, p.1). His personal site is referenced in the repo as 01.me / ring0.me; nothing else about his career is asserted in the book, so cite him as "Pine AI chief scientist, bootcamp lecturer".

**Version, date, licence.** v2.0, dated 2026-09-06 on the EN PDF cover ("Version v2.0 · September 6, 2026"). Apache License 2.0 for text, figures and code (`LICENSE`; README §许可证 notes sub-projects may carry their own). v2.0 vs v1.4 (README banner): the old ch.4 "异步交互" and old ch.9 "多模态 Agent" were merged into a new ch.6 "交互：观察与动作空间的扩展"; the old ch.6/7/8 (评估 / 后训练 / 持续进化) became ch.7/8/9. **Citation pitfall:** `slides/COURSE_OUTLINE.md` and the "7-1, 7-2" rows in `chapter1/README.md` still use the *old* numbering (its "Chapter 6" lessons are the evaluation chapter). Always cite from the EN PDF v2.0 TOC.

**Structure and thesis.** 引言 + 10 chapters + 后记 (+ `reference-answers.md` for the thought questions). Part 1 "如何构建 Agent" = ch.1–6; Part 2 "如何提升 Agent 能力" = ch.7–10 (评估 → 后训练 → 持续进化 → 多 Agent). The one-line formula is **Agent = LLM + 上下文 + 工具** (大脑 + 眼睛 + 手脚; RL reading: policy / observation / action interface). In production form (ch.1 §1.2): **Agent = Model + Harness**, **Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正**, and "Agent ↔ Environment" — the harness is "Agent 边界内、模型之外" and explicitly does *not* include the environment. The chapter-1 tagline in `chapter1/README.md` is "**Harness 工程才是竞争力**"; the §1.2 heading is "Harness 工程：模型之外的竞争力" (EN: "Harness Engineering: Competitiveness Beyond the Model"). The introduction's two conditions for teams that want to get ahead of the naming curve ("实践在前，命名在后"): pick a real business that demands more than the model can do, and **build systematic evaluation** ("没有评估，就无法判断一次改动带来的提升究竟源于设计本身，还是仅仅来自随机波动").

## 2. Chapter by chapter

Legend: **[measured]** = a number the book reports from its own lab or a named external run; **[cited]** = an external number the book quotes; **[opinion]** = the author's design position. Labs are listed with their README type.

### 引言 / Introduction (EN pp.1–8)

- Thesis and the three-level reading of the formula (工程 / 直觉 / RL). "实践在前，命名在后" — Anthropic did not invent Skill / harness / loop engineering; many teams converged on them, "这种趋同说明，它们反映的是 Agent 系统的共性约束" [opinion].
- Pine's practice claims (no numbers): dynamic prompt loading before "Skill", command-line execution tools to stop tool-list growth, a system status bar for time/environment awareness, Claude-Code-like harness before "harness", and **proposer-reviewer** before "loop engineering" to fix the model "过早认为任务完成".
- "好的设计原则本就应该穿越模型的迭代周期" [opinion]. Sutton's four-stage universe; agents that bootstrap agents.

### Chapter 1 AI Agent 入门 / Getting Started with AI Agents (EN pp.9–37)

1. **§1.1 现代 Agent = LLM + 上下文 + 工具.** Fig 1-1 draws two levels: Agent ↔ Environment closed loop, and Model–Harness inside the agent boundary. "Harness 可以创建、隔离或代理一个环境，却不因此包含环境自身的状态与转移规律" [definition]. This is the same two-layer split the December outline needs when it says "harness layer = what you build".
2. **§1.1.1 观察空间与动作空间.** "在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段，往往就是重新定义或扩展观察空间与动作空间" [opinion]. Case studies: Manus merged Deep Research + Coding + Computer Use spaces; OpenClaw extended them into the user's messaging channels and local files.
3. **§1.1.2 工具.** Five tool classes (感知 / 执行 / 协作 / 事件触发 / 用户沟通). Design rule: "通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作" — payments, deletes, email, production deploys stay as narrow, audited, permission-limited tools with preview and human confirmation [opinion].
4. **§1.1.3 LLM.** "Model as Agent" and the Bitter Lesson stance "方向认同，节奏务实": models will eat the harness, but "训练以月计…模型此刻的能力边界，就是 Harness 此刻的价值所在" [opinion]. Fig 1-2: three update paths — in-task context adaptation, cross-task *artifact* updates (docs / prompts / skills / programs / harness), parameter updates — ordered by rollback-ability.
5. **§1.1.4 上下文 and Experiment 1-1 ★★ (context ablation, ✅ `chapter1/context`).** Five context components. Findings: without tool definitions the model still answers "格式工整、语气笃定" from parametric memory; without tool results it retries until the iteration budget is gone; reasoning can be dropped when it is reconstructible from tool results. Two sentences matter for October: "**「给出了回答」不等于「完成了任务」**，上下文残缺时典型的失败不是报错退出，而是一个看上去毫无破绽的答案" and "「每个组件都不可或缺」这类论断要靠实测…同一个消融换到新模型上完全可能得出不同的结论". The lab ledger (`chapter1/README.md`) records that "去掉 reasoning 必然退化" **did not reproduce** in the formal five-arm run [measured, negative].
6. **§1.1.5 ReAct 循环.** "Agent 的上下文 = 静态前缀 + 轨迹". A trajectory is the structured message history and is what makes the system "易于解释和调试"; "分析大量轨迹可以发现 Agent 的行为模式、优化决策路径、改进工具设计；轨迹还可以沉淀进知识库，或用于强化学习". Exp 1-2 ★ Kimi K3 (vendor figures: ~2.8T MoE, 1M context, "连续执行 200～300 次工具调用" [cited]); Exp 1-3 ★ GPT-5.6 Deep Research with intent clarification. The clarification from GitHub issue #30: RL internalises the *decision* to call tools; execution stays in the framework — "编排循环并没有消失，而是从客户端移到了服务端".
7. **§1.2 Harness 工程：模型之外的竞争力.** The five-function table: Context (sufficient), Tools (clear), **Constrain** ("故障安全默认值，所有能力默认关闭，必须显式开放"), **Verify** ("安全检查只看结构化数据…而不看模型自由生成的文本，因为后者可能已被提示注入操纵"), **Correct** ("在确认无法恢复之前不暴露中间态…连续失败时回退到人工判断（熔断机制）"). Claim: in Claude Code "绝大部分代码都是约束、验证与纠正，而非上下文与工具" [opinion, no count]. LangChain on Terminal Bench 2.0: 52.8% → 66.5% "改变的不是模型，而是 Harness" [cited].
8. **§1.2.1 从提示工程到 Loop 工程.** Five nested waves: prompt → context → harness → loop → graph engineering (Josh C. Simmons, 2026-07-04). "当各家模型的能力越来越接近…竞争优势就转移到了模型之外的工程实践" [opinion].
9. **§1.2.2 / §1.2.3.** Anthropic's three principles (simple, transparent, ACI; poka-yoke). Model selection: open-source gap "6 个月以内" [opinion]; test *policy boundaries* (will the product let you do it?) not just accuracy; prefer reasoning models; output-token speed compounds ("20 轮推理，每轮慢 2 秒就意味着总共多等 40 秒").
10. **§1.2.4 编排模式.** Workflow (deterministic; "攻击面被限制在单个节点内") vs autonomous (needs explicit stop conditions). Anti-example: a memory pipeline with extraction / verification / identity-resolution / merge agents — "每个部件单看都有道理，组合起来却是非常低效、不可靠的". "**Harness 很重要，不等于 Harness 越复杂越好**"; Manus's "Less structure, more intelligence." Exp 1-4 ★ (✅) shows adapter code being eaten by native image models: "Harness 里那些给模型能力短板打补丁的部分，会随着模型变强被模型自己内化". Framework table: Codex Harness is open-source runtime; Claude Agent SDK exposes an SDK but "Harness 实现本身并不开源".
11. **§1.2.5 护栏与安全性.** Three layers ordered "按被绕过的难度": 上下文层 (what the model sees), 执行层 (what it can do; tool risk rating; review "必须由上下文之外的机制完成"), 数据层 (what the world can become; row-level security, constraints, "即使提示注入得手…越权操作仍会在数据层被拒绝"). Structural limit: "**处在同一个上下文里的 Agent，很难判断自己是否已经被注入**". Guardrails must also be tested for **false refusals**. Human-in-the-loop triggers: failure threshold exceeded; high-risk / irreversible ops. Constitutional Classifiers as the industrial example (two-stage probe → classifier).
12. **§1.2.6 and §1.3.** Anthropic's long-running harness (initializer agent + executor agents with hand-off artefacts) fixes "上下文耗尽" and "过早声明完成". Five cross-book patterns: **提议者—审核者** (premise: "自审不可靠"; the reviewer sees the artefact, not the reasoning), **渐进式披露**, **只增不改** ("可缓存、可重放、可审计"), **边界集 + 保留集** (test what should change *and* what must not), **最小 diff + 可回滚**. Thought question 2 notes cumulative cache reads grow roughly quadratically with turns.

Labs: 1-1 context ablation ✅, 1-2 web-search-agent ✅, 1-3 search-codegen ✅ (accepted on Aliyun qwen3.7-plus after OpenAI quota blocks), 1-4 image-gen-workflow ✅.

### Chapter 2 上下文工程 / Context Engineering (EN pp.38–85) — "全书最关键的一章"

1. **§2.1 上下文：决定 Agent 能力上限的关键.** Minimum information a coding agent needs: 代码信息 / 流程规范 / 环境信息. "一个中等能力的模型配上精心组织的上下文，往往能胜过一个顶级模型在信息匮乏下的盲目摸索" [opinion]. The organisational corollary: "**对远程工作友好的团队往往也对 AI Agent 友好**" (Linux kernel as the example) and "构建 AI 原生团队，首先是一场文档化运动，而不只是部署新工具". Quotes 翁家翌: "人和模型一样，最重要的是 Context".
2. **§2.2 API-level context.** Four roles + `tools` field = the five components; "Agent 框架的核心工作就是管理这个 messages 列表". The production skeleton compresses old evidence with `preserve = [decisions, constraints, failures, citations]` and notes a `max_iterations` cap is mandatory because "Agents can get stuck repeating the same tool calls forever".
3. **§2.3 KV Cache 友好的上下文设计.** Opening anecdote (unsourced, "某团队"): a customer-service agent at 10 万次对话/天 adds `Current time: {{now}}` to the system prompt; next day "监控告警：所有对话的首 token 延迟从 0.5 秒涨到 3-5 秒，月度推理账单几乎翻了一倍" [story]. Three rules: never change system prompt / tool definitions; append dynamic info at the end; use the standard message format. Exp 2-3 ★★ (✅ `kv-cache`) catalogues anti-patterns: dynamic system prompt, dynamic user profile, dynamic tool ordering, **sliding window** ("使用滑动窗口的 Agent 经常陷入循环，反复执行相同的工具调用"), text formatting. Prompt-cache reads cost "约为十分之一" of first computation at Anthropic / DeepSeek / GPT-5 [cited]. **§2.3.4 缓存作为架构约束** (Claude Code as the case): a cache-boundary marker splits the prompt; every binary runtime condition placed before it doubles the cache-key variants (2^N); sub-agents must be byte-aligned with the parent; tool-result replacement strings are frozen at first use. "缓存经济性不是事后优化，而是前置约束". §2.3.5 is the author's own research (arXiv:2606.17107, editable/composable KV cache; p90 TTFT down "数十倍至数百倍", 98.5% prefix hit) marked "仍属研究阶段".
4. **§2.4 提示工程.** Test: "如果一个聪明的新员工读完你的系统提示词还不知道该怎么做，Agent 也一样不知道". Process-driven SOP beats rule stacking. **§2.4.4 业务规则细化** (Pine's billing rules): "提示词一般由产品经理来设计…工程师…不应擅自决定业务逻辑"; the model "不应该在业务规则制定上被赋予过多的自由裁量权". Exp 2-4 ★★ (✅ `prompt-engineering`, on Tau-Bench airline/retail): tone changes had "相对有限" effect; shuffling the rules into an unordered list cut success by "超过 30%" and agents skipped identity verification before refunds; removing tool descriptions raised tool-call error rate "45%" [measured, no n or CI given]. §2.4.6 documents deferred tool loading as native API behaviour (OpenAI `tool_search` / `defer_loading`, Claude Code MCP lazy loading, Codex BM25 `tool_search` on by default) — schemas are appended at discovery time, "只增不改".
5. **§2.4.7 提示注入：上下文安全的核心威胁.** Definition; agents are more dangerous than chatbots because injected text reaches tools. Context-layer defences: source tagging (`<external_content source="webpage">`), structured roles, input cleaning ("只能作为辅助手段"). Two warnings that matter for backlog #4: "**Skill 的本质是「把外部内容当作指令加载」的制度化形式**…安装来源不明的 Skill 之前必须审查其内容，如同审查将要执行的代码" and status-bar poisoning. "上下文层的防御…只是第一道防线，它只能降低攻击成功率". Exp 2-5 ★★ (✅) = 3 attacks (direct, indirect via webpage, **memory injection** across sessions) × 4 defence configs; no headline numbers in the text.
6. **§2.5 动态提示词与 Agent Skills.** Three-layer progressive disclosure (metadata catalogue → SKILL.md body → sub-docs). `description` must read "像路由条件而非功能介绍". Runtime facts: Claude Code injects the skill body as a *user* message at invocation; Codex re-renders the catalogue as `developer` context each turn. Principle: "选择 Agent 交互模式时，应与模型厂商的训练方法保持一致". 宝玉's four-part skill template. Exp 2-6 ★★ PPTX skill (✅, accepted on Kimi Code CLI: 13 slides, 4 figures); 2-7 ★★ writing skill (🚧, text-only).
7. **§2.6 Agent 状态栏：通过元信息增强 Agent 轨迹管理.** Theory: "**上下文窗口是一台只有一半的检索引擎**" — retrieval is strong, there is "没有「提炼层」"; counts and constraint checks must be recomputed each turn from raw records. Canonical failure: an agent told "每个商家不超过 3 次" dials a 4th time. Composition: 任务规划 (TODO), 事件的侧信道信息 (timestamps, location, interval since last reply), 环境当前状态的观察摘要 ("该工具已被重复调用 N 次"). Implementation: a `user`-role message appended at the end, never a system-prompt edit; two update strategies (replace vs persistent append, the latter is Claude Code's `<system-reminder>`) with a cost model. Author's own paper (Li & Shi 2026, "Distill, Don't Retrieve") claims: with a pre-computed status bar "较小开源模型的准确率可以接近前沿大模型" and thinking tokens / latency / cost "降低约一个数量级"; without it thinking grows with context, with it "基本恒定" [author-measured, in own paper]. Exp 2-9 ★★ (✅ `system-hint`): five techniques — timestamps, **tool-call counter** ("Tool call #3 for 'read_file'"), TODO (15 vs 21 iterations), detailed error info (alternative-finding success "从 60% 提升到了 95%"), system state [measured, no n]. Two maintenance rules: "**状态栏尽量用代码维护**…绝不要让它一次性批量统计" because "**模型几乎无条件地相信状态栏**"; the status bar is "一次有损投影" — delete raw context only if every future question is covered.
8. **§2.7 上下文压缩策略.** Three motives: length/cost, thinking quality, and "上下文焦虑" (Anthropic's harness-design post). ICL "更像检索而非推理" (the 100-cage cat-counting example). **Context Rot** vs overflow: "溢出是「装不下了」，腐化是「装得下但找不到了」——后者更隐蔽，因为 Agent 表面上还在正常工作". Exp 2-10 ★★★ (✅, Kimi K3 capped at 128K): no compression fails at the 5th iteration (~165K tokens); context-aware compression finishes in 7 iterations / 40,157 tokens (~3.0% ratio); adaptive windowing triggers at 80% and batch-compresses with a `[COMPRESSED]` marker [measured, single task]. Claude Code's five-layer scheme includes a **circuit breaker on repeated compression failure**: "生产数据表明，大量会话会被困在反复压缩失败的循环中，熔断器避免了在这些会话上持续烧钱" [cited, no numbers]. Design principles: non-uniform value, semantic integrity, task relevance, "压缩即理解". "**压缩最容易丢失的是早期的架构决策、约束背后的理由和失败的路径**。因此，Agent 需要定期将进展记录到文档中". §2.7.6 隔离优于压缩: sub-agent context isolation (Claude Code Task tool) — "用隔离代替压缩".
9. Thought questions worth reusing: Q4 "元信息可靠性" (a buggy counter in the status bar drives harmful decisions); Q5 system-prompt "熵增" under multi-maintainer editing.

### Chapter 3 用户记忆和知识库 / User Memory and Knowledge Base (EN pp.86–122)

1. **§3.1 用户记忆系统.** Extraction must be 选择性 / 抽象化 / 结构化. **§3.1.1 三层次框架**: 基础回忆 → 多会话检索 → 主动服务 (eight capabilities, "笔者的归纳口径"; LoCoMo as the public benchmark). Exp 3-1 ★ (✅): 20 cases per layer, LLM-as-judge against reference answers.
2. **§3.1.2 记忆的层次结构 — the trajectory as audit record.** "轨迹…按时间顺序排列，只增不改…这里的「只增不改」描述的是用于追溯、调试或审计的原始事件记录。为控制长度，每轮实际发送给模型的运行时 Context 可以经过压缩、重组…原始记录是否完整保留，取决于具体系统的数据保留与审计要求." "前者是流水账，后者是档案." A third layer, **业务状态** (task stage such as 等待付款), matters for event-driven agents (ch.6). This is the book's cleanest statement that *runtime context* and *the record you keep for audit* are different objects.
3. **§3.1.3 四种存储格式** (Simple Notes → Enhanced Notes → JSON Cards → Advanced JSON Cards with backstory / person / relationship / timestamp). Rule: "关键且少量的数据用 Advanced JSON Cards…大量且非关键的对话事实用 Simple Notes". Exp 3-2 ★★ (✅) [qualitative].
4. **§3.1.4 可执行代码** = the author's *User as Code* (arXiv:2606.16707): typed state, write-ahead log + checkpoint, rules as functions (passport expiry < 180 days → alert). §3.1.5 three orthogonal taxonomies (放哪里 / 怎么存 / 存什么). §3.1.6 Mem0 v2 (write-time ADD/UPDATE/DELETE/NOOP) → v3 (append-only ADD + hybrid retrieval + time ranking; Mem0 reports LoCoMo 71.4→92.5, LongMemEval 67.8→94.4 [cited, vendor]); Memobase profile + event memory with buffered batch extraction. §3.1.7 importance scoring (access frequency, time decay, emotional intensity, uniqueness) → clustering → abstraction.

8. **§3.3.3 知识应该如何更新 — the PR model for knowledge.** "**把知识库当成代码库，把每次知识变更当成一个 Pull Request**…生产环境不应让任何一个模型绕过审核，直接改主分支或线上向量库." Proposer Agent (small diff on a branch, keeps links / index / time metadata / evidence refs) → Reviewer Agent (checks diff against *raw evidence*, returns line-level objections) → iterate with a max-iteration / cost budget, then human → CI (format, links, metadata, permissions, type checks) → rebuild derived indexes. Three layers: **原始证据层** (append-only conversations, trajectories, docs), **知识层** (Markdown or code), **服务层** (rebuildable indexes). "PR 需要记录证据标识、知识库版本、审核意见和最终决定，使线上的每条知识都能回答「**从哪条证据而来、谁在什么时候批准**」." Both roles "**必须是 Agent，而不是两次固定的 LLM API 调用**" with search / diff / test tools; "**应优先使用能力相近但来自不同家族的模型**" (Claude↔GPT, DeepSeek↔Kimi) — "异源互审…不能替代原始证据"; permissions split (Proposer writes branch only; Reviewer read-only; only the merge flow touches main). Stale-content metadata (版本号、生效/失效时间); permission filtering pushed down to retrieval; tenant isolation.

Exp 3-8 ★★ (✅, CAIL judicial QA) [qualitative]. **§3.3.5 上下文感知检索** (Anthropic; failure rate −49% with BM25, −67% with reranking [cited]; ~$1 per million doc tokens with prompt caching). ### Chapter 4 工具 / Tools (EN pp.123–145)

1. **§4.1 工具的分类.** Table 4-1: 感知 / 执行 / 协作 / 用户沟通 are agent-initiated; 事件触发 is "Agent 注册、外部触发". Design keys: perception controls information volume, execution controls risk.
2. **§4.2.1 能力的表达形式.** A spectrum from 专用工具 (schema-constrained, testable, hundreds of tokens each) to Skill (natural-language procedure executed through bash / code interpreter, tens of tokens in the catalogue). "本节问的是形态，不是数量." Default: "**通用工具优于专用工具，除非存在明确的安全、权限或性能理由**"; return to dedicated tools for 安全权限审计 / 平台差异 / 极高频 / 参数复杂. Four decision dimensions (安全与权限、参数复杂度、变更频率、模型能力). Code that orchestrates several tool calls keeps intermediates out of context, "token 消耗可降低约两个数量级" [opinion/estimate].
3. **§4.2.2 工具描述的艺术.** Describe *when* to use, not what it does; "**清晰列出工具的边界条件…往往比描述能力本身更重要**"; concrete examples for parameters; declare cost ("5-10 秒"); 1–5 real call examples raise accuracy "在一些基准上可从约 72% 提升到 90%（具体数值因任务而异）" [cited, unsourced]. Debugging rule: "当 Agent 频繁选错工具时，应优先检查工具描述".
4. **§4.2.3 参数传递的保真性.** Two anti-patterns from real products: **静默输入转换** (a Cursor build in early 2026 silently converted 中文弯引号 to straight quotes between read and edit, so `old_string` never matched and the model looped) and **静默参数注入** (an IDE's bash tool appended an AI-marker flag to every `git commit`, breaking old Git). Principle: "**模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差**".
5. **§4.3 工具生态：MCP 与 Skill Hub.** MCP primitives (tools / resources / prompts; stdio vs Streamable HTTP). Skill distribution is a registry (skills.sh, ClawHub), not a protocol. Cost asymmetry: an MCP server's full definitions "会进入每一次会话的上下文", a skill costs "一到两个数量级" less. Three MCP risks: **工具描述投毒**, **恶意或被劫持的服务器** (supply chain), **同名工具遮蔽** (tool shadowing). Mitigations: audit descriptions "当作不可信输入", pin versions, least-privilege credentials per server, Sidecar as last line. "**Skill 的危险系数要比 MCP 大得多**" (ships code that may run on the user's machine; hub scanning "不是万能的"; use untrusted skills only in isolation).
6. **§4.4 工具太多怎么办.** "工具数量超过一百个时，即使最先进的大语言模型也容易在工具选择上出错" [opinion]; 5 MCP servers ≈ tens of thousands of tokens; Cursor's index-only approach cut MCP-task tokens by 46.9% in an A/B [cited]; Anthropic's retrieval pre-filter took Opus 4 from 49% to 74% on a tool-use benchmark [cited]; MCP-Zero ~98% token saving on ~2,800 tools [cited]; Pi's "No MCP" philosophy (CLI + README + skills). Exp 4-1 ★★★ (✅): the text predicts "准确率和任务完成率显著提升", but the ledger reports **"accuracy uplift not observed"** — both arms 3/3 with Qwen3-4B; only schema exposure and time fell [measured negative].
7. **§4.5 感知工具.** Structured candidate lists + pagination / cursor; `offset/limit`; "**静默截断是危险的**——Agent 会误以为自己看到了全部内容"; read-only tools are cacheable and parallelisable. Three multimodal routes (native / extract-to-text / tool-wrapped). Labs 4-2 (MCP perception server, mostly keyless public APIs), 4-3 (three-way comparison, ✅ with external judge).
8. **§4.6 执行工具 — the densest section for December.** Layered safety: input validation ("快速失败…不尝试「智能」修正"), permission control (blacklists are "最基础的防护层"). **Proposer-Reviewer** as 事前审批 (different model families at similar capability — "Haiku 审查 Opus 的输出反而不可靠"; identical rules and context but different emphasis; a rejection re-enters the trajectory as a tool failure; risk-tiered approval; escalate to human when unsure) and 事后验证 by **模态切换** (render the doc, run the config in a sandbox). **Sidecar** (Claude Code Auto Mode): a lightweight parallel LLM call that reads only structured fields `{tool: "bash", command: "rm -rf /tmp/data"}`, never the main model's free text, gates the call within "数百毫秒", plus a **拒绝熔断器** that hands over to the user after repeated denials; UI shows progress while the check runs. Table 4-2 contrasts the two. "如果操作结果可以被验证，就应该自动验证" (write_file → linter → structured error list). Long-output policy: head 50 / tail 50 lines + file pointer. Sandboxing: "**Python 虚拟环境（venv）不是沙盒**"; process < container < microVM (Firecracker), with CPU/memory/disk/network caps; Claude Code / Codex / OpenClaw run at user privilege locally. **工具执行的可观测性**: "详细的日志（每次调用的时间、参数、结果、耗时）、审计追踪（谁在什么上下文下为什么执行了操作）、性能指标（调用频率、成功率、平均耗时）以及告警机制（频繁失败、超时、资源超限时通知管理员）" — one paragraph, no schema. **幂等性与取消语义**: "当一次调用被取消或超时时，它的副作用到底发生了没有？"; idempotency keys or query-then-mutate; for inherently non-idempotent acts (email, phone call, transfer) a "预检-确认" two-phase flow with a different-family checker, and "执行阶段如果失败不能盲目重试". Exp 4-4 ★★ (✅; ledger: 13/15 gates incl. a real GitHub PR mutation, Xvfb Computer Use, KVM Android; calendar/email blocked).
9. **§4.7 协作工具.** Sub-agent prompts tag sources (`[FROM_MAIN_AGENT]` / `[FROM_USER]` / `[TOOL_RESULT]`) to defeat injection; primitives spawn / cancel / message / `list_agents`. HITL needs timeout and degrade rules ("如果 5 分钟内没有响应，采用保守策略"), priority queues, and a feedback loop where approvals / rejections *with reasons* become evidence for knowledge, skills or post-training. Exp 4-5 ★★ (✅; ledger keeps a real repository-user decision; Email/Telegram/Slack "not simulated").

### Chapter 5 Coding Agent 与通用 Agent / Coding Agent and Code Generation (EN pp.146–185)

1. **§5.1.1–5.1.2.** Seven core tools (code interpreter, bash, read, write, edit, glob, grep; "OpenAI Codex 就只提供 Bash Shell 一个工具"). Open-task general agents (Manus, OpenClaw) are a coding agent + file system; `MEMORY.md` in Markdown rather than a vector DB because humans can read/edit it, it keeps time order, and Git versions it. Scope caveat: vertical customer-service agents keep code as one tool, not the architecture.
2. **§5.1.3 Coding Agent 的整体流程.** Project documentation first; instruction files (CLAUDE.md / AGENTS.md / .cursorrules) are the project-level system prompt and a cheap stable prefix. AI-readiness metric: "**一个远程新人只靠代码仓库和文档，能不能独立开展工作**". Requirement clarification → **design doc submitted for human approval** ("审查简洁的设计文档比审查数百行代码容易得多") → implement → tests. Key October line: "**Coding Agent 最常见的偷懒方式，就是跳过这一环节——写完代码不跑测试就报告「任务完成」。把「测试通过」而非「代码写完」定义为完成标准**". Self-review via lint or a review sub-agent, then doc sync. The "when to stop reading and start editing" threshold is "首先是模型学到的行为策略" (measured in ch.7 lab 7-8, explained in ch.8).
3. **§5.1.4 Harness 工程在 Coding Agent 中的实践.** Four harness components: 验收基线 (tests, CI, review standards), 执行边界, 反馈信号 (linter, tests, type checks), 回退手段 (Git, sandbox, snapshots). Table 5-1 four quadrants — bottom-left is "**高效地跑偏：用 linter 优化「代码质量」**" (automated feedback + fuzzy goal). "Coding Agent 是当前所有 Agent 类型中成熟度最高的：不是因为代码生成模型特别强，而是因为软件工程几十年积累的基础设施天然构成了一套强大的 Harness" [opinion]. Industry cases: a large-scale code-migration write-up (knowledge in the repo, "约束编码进 Linter 和 CI 而非写在文档里", verification automated), LangChain ("用 Agent 分析失败轨迹来改进 Harness"), Anthropic initializer / executor. Four transferable principles: **约束优先于指导** ("前者是「做不了」，后者只是「建议别做」"), **验证要自动化** ("人工审查是不可扩展的瓶颈"), 反馈越快越结构化越好, 回退要可靠. **Process constraints**: "即使结果正确，用错误的方法达成也不行" — deleting and rebuilding the DB, deleting and rewriting the code — "这正是第八章讨论的 reward hacking 在 Agent 任务中的日常形态"; guard *actions*, not just outcomes (semantic command parsing, Sidecar); RLVP is the training-side twin. Fault-boundary rule for parallel tool calls: a failure propagates within its batch only.
4. **§5.1.5 故障与错误恢复** (footnote: distilled from source study of Claude Code and peers). Four-layer taxonomy: API (429, overload, timeout, disconnect, output cap), 工具 (hallucinated tool, malformed params, exceptions, "工具反复返回同一个错误，而模型不加改变地反复重试"), 上下文 (overflow, compression failure, broken trajectory pairing), 控制流 (死循环, **死亡螺旋**). Detection: classify before counting (retryable vs not; an error→strategy map, "而不是笼统地「出错就重试」"); **repeat-call fingerprint** = tool name + params; per-path consecutive-failure counters; **活性与完整性监控** — streams fail by silent stall, so "每个长连接都需要活性信号，而非仅依赖连接超时" (idle watchdog); auto-repair of unpaired tool calls, with "产品模式宽容、训练模式严格" (placeholders would poison training data). Recovery ladder: 静默重试 (exponential backoff + jitter, honour server wait hints, foreground vs background calls to avoid "重试放大") → 降级与接续 (raise output cap, meta-instruction to continue, fallback model after stripping vendor-private blocks, drop to standard mode) → expose to user *with the list of attempted recoveries*. Tool-layer errors become structured model input. "**错误处理的边界不是单次请求，而是整个恢复循环**"; hold errors back from users *and downstream event subscribers* until recovery is exhausted. **Cross-vendor takeover**: reasoning = portable text + non-portable vendor signature; "轨迹不该按任何一家的接口格式存储，而应保存为一份中立格式" — and the neutral trajectory is the same artefact ch.7 replays, ch.8 trains on, ch.9 mines. Exp 5-1 ★★★ (✅; ledger: neutral format 6/6 vendor switches, pass-through 3/6, strip-all 4/6, failures are real vendor errors) [measured]. Exp 5-2 ★★ (✅; resuming from a text breakpoint saves 15–66% output tokens, but resuming inside tool arguments yields "合法但写错" parameters) [measured]. **Termination**: every recovery path needs a cap, and thresholds come from production data — Claude Code's compaction breaker is "连续 3 次" because one session failed "三千余次" on that path, such retries cost "约 25 万次 API 调用" per day globally, and ">1,000" sessions had 50+ consecutive failures [cited from source study]. Death-spiral case: context overflow → stop hook auto-commits → LLM writes commit message → overflow → hook fires again; defences: no model-calling side effects on error paths, recursion-depth counter, plus global max iterations, session budget, escalation to humans.
5. **§5.1.6–5.1.8.** Streaming execution of the first validated tool call, cascade abort within a batch, tools declare concurrency safety (default no). Line-numbered file reads; head/tail truncation; **environment status bar** (cwd, git branch, recent commits, staged/unstaged diff) appended, never in the system prompt; persistent shell session; lint on every write. Search: grep / glob / semantic / symbol — Claude Code deliberately keeps no embedding index and "目前 Cursor 等 IDE 也改用 grep + glob 现场检索了". Editing: five schemes; old-string→new-string is what Claude Code, Codex and Cursor use now.
6. **§5.1.9 Coding Agent 的安全.** Simon Willison's 致命三要素 + the author's fourth dimension **持久记忆** ("攻击的放大器"; four boundaries: data, input trust, output impact, cross-session). "重点不是识别所有攻击，而是让 Agent 即使被注入，也没有机会把危险动作真正执行出去." Sandbox choices: **网络出口控制** ("最容易被忽视、却最关键的一项": default-deny, allowlist proxy), read-only source mount, credentials never mounted, resource caps that return *structured* timeout errors. Semantic command parsing beats blacklists (`$(echo rm) -rf /`, `find … -exec rm`, `curl -o /etc/crontab`). **Principal loyalty** (author's arXiv:2606.30383): "提示注入本质上就是一次策反"; a loyalty spectrum where both ends fail (too honest leaks the reservation price, too suspicious refuses the principal); rules: protect the principal's secrets, don't enumerate refusals, obey only explicit principal instructions, resist repeated pressure.
7. **§5.2.1 代码作为思考工具.** Exp 5-3 ★★ (✅; ledger: AIME 2024 code arm 53.3% vs CoT 36.7%, **p=0.125 not significant**) and Exp 5-4 ★★ (✅; ledger: K&K puzzles code arm **39.3% vs CoT 75.0%**, far below the text's 90% target) — both recorded as honest negatives. The text's own caveat: "同一套脚手架，配上不同能力的模型，得到的结论可能截然不同".
8. **§5.2.2 代码作为业务规则的约束.** NL rules (explain, find workarounds) and coded rules (precise, deterministic, combinable) are complementary; "代码化规则的真正价值不在于优化 token 效率，而在于**防止不可逆的错误操作**". The `cancel_reservation` design: optional `expected_*` parameters act as a **forced checklist** the model must fill (so it often declines to call at all), while "**没有任何一条政策事实来自模型自报的参数**" — cabin class, insurance, booking time, flight status and the clock come from the server, and `log_mismatch` records disagreements "用于发现模型的错误认知或潜在注入". "独立性不仅指独立的模型，更指独立的数据来源." Exp 5-5 ★★ (✅; ledger: Qwen3-4B 91.7% vs control 95.0%, p=0.6875, no uplift) [measured negative].
9. **§5.2.3–5.2.4.** Proposer-Reviewer for PPT/video where the Reviewer sees the *render*, not the code (ledger 5-6: quality tied at 95, but dual-agent peak context 24,186 vs 92,601 tokens single-agent). CAD vs diffusion (ledger 5-9: CadQuery zero deviation; Hunyuan3D lost all four holes, outer diameter −99.4%). Code as adapter: **Exp 5-10** adaptive log parser (parse failure → agent writes `parse` → tested in a virtual browser → hot-updated) and **Exp 5-11** production-log diagnosis (read trajectories + architecture docs + PRD → structured report → regression tests that reference trajectory ID and turn → replay → GitHub Issue via MCP; ledger: real Issue created).
10. **§5.2.5 代码作为生成式 UI.** A2UI-style declarative UI (menu analogy; AG-UI is transport, not the same thing). HTML deliverables over Markdown; the author's research sites expose per-experiment prompts, raw LLM replies and judge scores so "更容易看出 LLM 的回复和 judge 的打分是否存在系统性偏差". SQL **artifact mode** with read-only account, SELECT-only parsing, parameter binding, row/time limits. **Dynamic software moves the trust boundary to the data layer**: the goal is "**即使 AI 写错了代码，权限约束仍然无法被绕过**" — row-level security, validators, controlled views, an access context bound by the trusted runtime, no bypass path. Exp 5-15 ★★★ (PEDO on PostgreSQL; ledger: live campaign not run).
11. **§5.2.6 代码创造代码.** OpenClaw `doctor`: deterministic checks first, LLM only for the long tail ("这与传统运维脚本并无本质不同"). Four defects when agents write agents; generate from a vetted example, not from scratch. Exp 5-16 ★★★ (✅; ledger: template arm non-inferior and more efficient; "strict joint-advantage hypothesis not observed").
12. Summary sentence: "**Agent 的可靠性不取决于模型犯不犯错，而取决于每类故障是否都有对应的检测、恢复、接管与终止路径**". Thought Q3 (adaptation can mask a bug: "需要适应的变化" vs "需要报告的异常") and Q5 (garbage-collecting accumulated rules) are both reusable.

### Chapter 6 交互：观察与动作空间的扩展 / Interaction (EN pp.186–221) — new in v2.0

1. **§6.1 模态与触发时机.** Two axes (模态 × 触发时机) and a time-scale table (秒—天 async, 10 ms–1 s voice, sub-second Computer Use, ms robotics). "**回合制是模型与接口的一种交互约定，不是环境的性质**." GPT-6 Astra (checked 2026-09-05) offers native async tool calling and mid-turn steering, so the chapter covers both native and compatibility routes.
2. **§6.2.1–6.2.2 为什么需要异步 / OpenClaw.** "不能仅凭代码用了 `asyncio`，就认定模型也具备原生异步能力." OpenClaw's Hooks / Cron / Heartbeat are all time-driven; the PineClaw case (a phone call needs the user's OTP within seconds) shows why a push **Channel** is needed: "真正的「主动服务」不仅需要 Agent 能定时检查事件，更需要事件能主动通知 Agent".
3. **§6.2.3–6.2.4 事件触发工具 / 用户沟通工具.** `set_timer` (one-shot, recurring), `monitor_shell` (Claude Code's monitor tool for background commands — polling wastes tokens, waiting blindly hides hangs), `connect_channel`; payloads must carry enough context. Communication as explicit tool calls; "**通知机制同时也是用户召回机制**"; channel choice by urgency / user state / preference.
4. **§6.2.5 虚拟身份与隔离执行环境.** Give the agent its own identity (mailbox, phone, storage, compute) instead of the user's accounts — "一旦 Agent 出现错误或被攻破，用户的全部数字身份将会暴露"; VM / Android emulator isolation; residential proxies against anti-bot; HITL login via VNC/RDP with reusable session tokens; data exchange by shared-volume paths, not content.
5. **§6.2.6 事件处理机制.** Event loop with **safe points**; every input modelled as a **structured event** (来源 / 渠道 / 内容 / 上下文, JSON example) precisely so the agent does not "将藏有指令的工具结果误认为用户指令而导致提示注入". Three strategies: **取消式** (urgent: cancel stream/tool, drain queue, append everything, re-call LLM), **队列式** (batch at the next tool result), **并行式** (independent light queries in a parallel session, marked as such). Urgency taxonomy: `user.interrupt`, `supervisor.instruction`, `agent.interrupt`, urgent external triggers vs `user.input`, `tool.result`, `timer.trigger`. "建议使用轻量级的分类 LLM 作为事件路由器." Rule: "取消点必须是工具或推理能够安全收尾的位置；**未完成的工具结果用显式占位符表示，不能伪造成功**". Exp 6-1 ★★★ (ledger: Unipile 401, incomplete).
6. **§6.2.7 不支持原生异步时的兼容方案.** Five rules for keeping tool-call pairing valid under interruption; the placeholder risk: "模型可能把「任务已启动」误当成「任务已完成」…应通过明确的任务状态和结果校验防止这种混淆，并**在评估中检查是否编造了未到达的数据**". **Task handles**: `initiate_phone_call` returns a task ID; progress arrives as `phone_call_connected` / `phone_call_ended` events. Batched-event attention loss is mitigated with status-bar markers `[未处理事件 1/4] …` plus a summary line. Exp 6-2 ★★★ (✅ complete: non-blocking work, queued instruction integration, interruption and recovery, progress-aware cancellation of the sub-50% script).
7. **§6.2.8–6.2.9 模型原生异步 / 可靠处理.** Native async separates "发起行动" from "获得结果"; steering keeps completed work and adds constraints; but "**修改计划也不等于停止正在运行的工具，更不会自动撤销已经发生的动作**；实际执行、取消和状态管理仍由运行时负责". Three reliability checks — 结果归属与未完成状态 (no fabricated data), 任务恢复与动作控制 (modify ≠ stop), 多条更新的综合使用 — and "评估需要覆盖两层：模型是否理解了变化，系统是否按变化正确执行". Exp 6-3 ★★★ (GPT-6 Astra vs a non-native model).
8. **§6.3 语音.** Cascaded / Omni / full-duplex (OpenAI's GPT-Live taxonomy); latency waterfall (fig 6-7) and queueing (fig 6-8, "属于服务容量规划"); streaming perception incl. Action space (Anthropic reference: computer / bash / str_replace_editor); grounding routes (Set-of-Mark, DOM/Accessibility index via browser-use, pure coordinates with resolution-matched scaling); AOI observation interface (author's arXiv:2606.29472: keyframes, volume-gated transcription, text descriptions that survive context cleanup); world models for speculative execution (OSWorld-Human: "准确率达到人类水平，并不等于已经足够实用"; Induction Labs Photon-1). ### Chapter 7 Agent 的评估 / Evaluating Agents (EN pp.222–262) — the chapter the December series should lean on

1. **Opening thesis.** "**评估的对象不应只是模型，而应是模型与 Harness 的组合体**"; distinguish "模型能力不足" from "Harness 设计缺陷" with a **model-swap** experiment (fix harness, swap model) as opposed to ablation (fix model, remove a harness component). An eval set lets you "为未来的模型开发产品". Four links: 什么算成功 / 任务从何而来 / 由谁验证 / 分数如何转化为决策 (fig 7-1).
2. **§7.1 一条评估任务的解剖 (τ²-bench telecom).** Task = ticket + `known_info`/`unknown_info` + `task_instructions` (emotion, acceptance bar, **grounding**: "缺少事实锚定约束时，模拟用户会顺应 Agent 的引导确认问题已解决，评估随之退化为两个模型之间的相互确认") + `initial_state` reset + `evaluation_criteria` (actions, env_assertions, communicate_info, nl_assertions). **Dual-control**: the simulated user has its own tools. The *passing* trajectory (reward 1.0) still contained an unverified policy violation (two tool calls at once against "one tool call at a time") — "二元奖励的固有代价：它以过程颗粒度换取跨模型可比的单一数字"; the failing one had the correcting evidence in context (`L1001` → 555-123-2001) and never acted on it. Exp 7-1 ★ (ledger: 4/5, Pass@1 0.80, full trajectories and costs kept).
3. **§7.2 评估指标：成功的定义.** "技术奇观" = Pass@k / Best@k (Anthropic's week-long C compiler, Manus/OpenClaw virality). Business reliability = **Pass^k** ("Pass consecutive k": every one of k runs passes *and* no veto item fires). Formulas Pass@k = 1−(1−p)^k, Pass^k = p^k; with p=0.6, k=5: **Pass@5 ≈ 99.0% vs Pass^5 ≈ 7.8%**. "评估报告必须写清 k 次尝试的口径：是同一任务的 k 次独立采样，还是生产流水线上连续 k 个任务"; side-effecting operations must be sampled in a sandbox with every failure counted, not "重试直到成功".
4. **§7.3 评估环境.** Five components: 数据集, resettable 环境状态 (`initialization_actions` is the reset script), 工具接口 on both sides (atomic, no "解决用户的上网问题" mega-tool), 评分标准, 执行协议 (termination `###STOP###`, turn cap, and **patience exhaustion counts as failure**). Verifiers framework table (SingleTurn / Tool / StatefulTool / Sandbox); "失败时应返回清晰的错误信息而非单一的失败标志".
5. **§7.4 评估数据集的设计.** Table 7-2 (τ², SWE-bench Verified, AndroidWorld, OSWorld, Terminal-Bench, GAIA). **§7.4.2 验证器**: "**Agent 很容易写一篇洋洋洒洒的报告，说任务已经全部完成，但事实上根本没有完成。评估框架必须核实机器可独立复核的事实，而非 Agent 的自我陈述**"; SWE-bench Verified's FAIL_TO_PASS + PASS_TO_PASS — "只检验前者，Agent 可以通过删改妨碍通过的断言蒙混；只检验后者，则等同于未作检验"; OSWorld's 134 evaluators look at DB, DOM, cookies; Terminal-Bench's kernel build "Agent 无法伪造输出". Difficulty tiers (GAIA: human 93.9/91.8/87.3% vs GPT-4 30.3/9.7/0% [cited]); τ² trap tasks ("客服已批准取消"). Leakage: GAIA composition + private attachments, AndroidWorld templates, Terminal-Bench canary GUIDs. ### Chapter 8 模型后训练 / Model Post-Training (EN pp.263–311) — least central to the articles; the parts that matter are reward design and the bad-case pipeline

1. **Frame.** Four stages (预训练 / Mid-training / SFT / RL, Table 8-1) and two through-lines: "SFT 记忆，RL 泛化" (explicitly scoped to the GeneralPoints / V-IRL experiments, "不是 SFT 与 RL 的普遍属性") and "**数据和环境，比算法更重要**". §8.1.4: RL needs format support and capability support — measure `pass@1` and `pass@k` on a held-out set first; "RL 擅长把已有但概率较低的成功行为推高，不擅长从全零奖励中凭空创造". §8.1.5 also explains ch.7's action-threshold finding as a learned policy (mass-covering SFT vs mode-seeking RL).

6. **§8.9 RL 算法.** The GRPO walk-through on one SWE-bench task (16 sandboxed rollouts, 4 pass, group-relative advantage; ~43 min per step, ~72 h per 100 steps as a rough estimate). "看似 On-Policy，为什么仍会被数值误差拖垮": sampler vs trainer log-prob mismatch (e.g. a 10⁻³ bias over 4,000 tokens compounds to e⁴ ≈ 54.6) — monitor ρ_t, KL, clip ratio "在任何参数更新之前" as an on-policy unit test.
7. **§8.10 RL 环境.** "练习场与考场并不相同" is the commonest RL failure; LLM-as-environment (ZeroSearch, DreamGym) with the caveat "**模拟器的世界知识就是训练的天花板，模拟器的系统性偏差会被策略照单全收**…RL 会主动寻找并利用模拟器的漏洞"; training and evaluation may share generators and verifiers but never the same tasks; verifier CPU can bottleneck GPU generation.
8. **§8.12 奖励设计 — reusable beyond training.** RLVR first; GRM for open tasks. **Reward hacking vs reward seeking**: the latter is the model building a mental model of "评判器会看什么" and setting itself an easy check — "**「通过了 grader」不能自动等价于「任务完成了」**：评判器是意图的代理，训练越强，模型越可能把代理当成目标本身". ORM vs PRM; for premature completion "把「是否完成」的判定交给模型写不了的隐藏测试、状态断言或外部终止钩子…**测试必须读取真实文件或环境状态，不能只检查模型是否说了「已完成」**"; evaluate on a boundary set (unfinished tasks) *and* a retention set (finished tasks) to avoid an agent that never dares to stop. **RLVP** (author's arXiv:2607.07435): R = O + βΦ, "奖励结果，惩罚路径"; real environments are **asymmetric verifiers** — "检测「做了一个坏动作」便宜而可靠，证明「这一步确实朝着目标取得了有意义的进展」却很难"; four design rules (penalise concrete actions only, keep the outcome reward, pair each penalty with a reachable compliant path, deterministic rules). Exp 8-16: TerminalBench violations 3.71 → 0.66 with success flat; miniF2F iterations to 0.9 from 7.0 → 4.4 [cited, author's paper; "不能直接外推为线上 Agent"].
9. **§8.13 蒸馏.** On-policy distillation turns one rollout into ~T token-level signals (~1/10 the steps of pure RL on maths [cited]); the author's "physical time" agent paper reports +23 to +47 pp over SFT baselines [cited, own]. OPSD when no stronger teacher exists.
10. **§8.14 从问题案例到后训练.** Table 8-5 maps ch.7 artefacts to training uses (end-to-end tasks → RLVR / RFT; trajectory-prefix tasks → DPO pairs, decision-boundary SFT, on-policy-distillation states; attribution records → PRM negatives and RLVP rules; rubric scores → vector rewards / GRM data). Case 1 premature completion → Exp 8-17 ★★ (✅; 24 bad cases incl. deleting failing tests; boundary-set correct choice 25.0% → 91.7%, retention 100%) with the warning that models may learn "口头声称去验证" — hence hidden tests. Case 2 curly quotes → Exp 8-18 (Qwen3-8B LoRA; 96.9%/97.7% exact, protected regions 100%). Case 3 exact copy → Exp 8-19 (byte-exact 37.5% → 78.9%; tokenizer round-trip ceiling 80.1%).
11. **§8.15 实践要点.** Eleven pitfalls, incl. #5 reward hacking ("应该评估最终目标而非中间指标"), #6 simulation fidelity, #9 numerical mismatch. The RAG / ICL / code / post-training split ends with: "**长期稳定的转账审批规则也应由代码提供确定性保障，而不能只靠模型记忆**".

### Chapter 9 Agent 的持续进化 / Continual Evolution of Agents (EN pp.312–332)

1. **Frame.** "**保存经历不等于从经历中学习**"; models must not train on raw production feedback because "用户满意不意味着合规…错误经验和提示注入就可能被固化". "持续进化" = a learning system *outside* the model: record evidence → verify outcome and process → extract across trajectories → route the update → validate before release.
2. **§9.1 从运行轨迹中获得学习信号.** Three verifier layers: 结果 ("事情是否办成", from real state), 过程 ("是否以允许的方式办成" — deleting a failing test also makes tests pass), 质量 (LLM rubric). Table 9-1 for a customer-service agent has seven dimensions, incl. **承诺—行动一致性** ("声称完成的操作是否真实发生", evidence = "回复与工具日志对照"), 隐私边界, 事实可靠性. A usable verifier output needs: success / partial / fail, per-dimension conclusions, **evidence positions (which turn, which tool call)**, failure-type labels — and may refuse to score when evidence is insufficient. Exp 9-1 ★★ (✅; ledger notes one stability claim did not reproduce).
3. **§9.2 四种方法.** Table 9-2: 经验知识库 / Prompt 与 Skill / 程序与 Harness / 模型参数, chosen by what the capability can be expressed in; "路由结果只是更新提案，尚未获得发布资格". §9.2.1: three data layers again (immutable raw trajectories for audit → per-run analysis → cross-run documents with 适用场景 / 推荐策略 / 禁止做法 / 例外 / 证据来源 / 最近验证时间); "反思本身不是证据".
4. **§9.2.2 将经验写成指令.** Karpathy's system-prompt learning; DSPy / OPRO / GEPA are offline; production wants minimal, sourced diffs tested on a **boundary set and a retention set**. Exp 9-2 ★★ (✅; τ²-bench telecom, weak model: 19/20 tasks ended in transfer-to-human; model-extracted rules raised a 114-task transfer set from **12.3% to 19.3%, zero regressions**; over-reach tool calls and missing-parameter calls both down ~80%) [measured]. Three lessons: "提炼所依据的材料决定了能够归纳出什么" (adding the tool lists changed the rule from "stop retrying" to "that's the user's side"); "**模型会把观察到的行为当作应然的行为**" — the first draft codified "三次失败即转接人工", i.e. wrote the failure into policy — hence "提炼产物因此不能直接发布，须经与提炼者相互独立的验证"; the fixed defect was trivial (the agent typed "请您提供您的电话号码" into a tool parameter five times). Exp 9-3 airline prompt patch; Exp 9-4 (🚧) requirement-clarification skill with metrics (需求偏差率、返工次数、澄清轮数、打扰…), and the Skill/Harness boundary: the Skill asks and drafts the Spec, the Harness vetoes unconfirmed high-risk writes or direct pushes to `main`.
5. **§9.2.3 将经验写成程序.** Browser-workflow lifecycle: capture → parameterise → pre/post/final **state checks** ("动作执行成功与任务成功是两件事") → **independent replay validation** on a reset sandbox → match & replay → invalidate & relearn. PreAct (author's arXiv:2606.17929): 8.5–13× speed-up on repeated tasks [own], with the warning "每个按钮都点过了，但某个字段其实为空，任务从未真正完成". Self-modification = a software release: isolated worktree, minimal patch, static checks, unit tests, security scan, failure-trajectory replay, regression, canary; the **可证伪的变更契约** (failure evidence, inferred root cause, harness component, proposal, expected fix, behaviours at risk, tests for both) and the three-layer observability of Agentic Harness Engineering (components / experience / decisions) [cited]; Self-Harness feeds must-preserve behaviours and previously rejected proposals [cited]. Exp 9-6 ★★★ (✅; "「是否能发布」必须由模型外的测试、审计和回滚机制决定"). Exp 9-7 ★★ (✅; a real gpt-4o-mini proposal was rejected by the safety gate — "安全能力的进化不能由修改者自证成功"). DeepSeek Harness / Cordis: temporal vs spatial composability; "不存在一个只能由人类维护的特权内核"; in-memory plugins "不能被自动提升为正式插件"; plugin docs must state KV-cache impact.
6. **§9.2.5 更新「更新方法」.** ACE (context as identified entries, deterministic merge), MCE (inner/outer loops), AFlow, Meta-Harness. Exp 9-8 ★★★ (Hermes; ledger: accepted after three reviewer rejections; downstream benefit not evaluated).
7. **§9.3 可长期运行的闭环.** Dual loop: online executes and records, offline aggregates, diagnoses, proposes, validates, releases (fig 9-5); Voyager; the science "discovery loop". **Harness-updating vs harness-benefit** (a good Skill the task model never loads looks like "no evolution"); Table 9-3 layered metrics: 更新提案有效率 / 产物激活率 / 遵循成功率 / 保留任务集增益; five long-run outcomes to watch (regression, generalisation, token efficiency, safety drift, long-term engineering quality). Exp 9-9 ★★★ (✅; static / append-only / evolving × 3 seeds × 14 tasks; only the evolving arm replaces the obsolete 20 kg rule and keeps the 23 kg one).
8. **§9.3.1 可验证闭环的边界.** Open-ended tasks fail by 实现漂移, 认识论上的过度乐观 ("信号仍可能只是噪声，系统却开始解释结果、添加补丁并宣布发现"), 隐性判断力不足; remedies: separate conclusions from evidence (Chain-of-Evidence), **keep negative results**, keep search diversity, and "**人的作用不应只是在危险工具调用前点「批准」**，还包括定义问题、审查评价标准、解释反常结果和决定何时停止".
9. **§9.3.2 持续进化的安全边界 — three boundaries.** (1) **证据与指令隔离**: "LLM 总结只是…转换，并不是把输入变得无害的净化过程"; model confidence "不能充当批准门槛"; versioned PR, reviewer independent of generator, human approval for high-risk skills. (2) **待验证能力与正式能力隔离**. (3) **安全机制不可自我修改**: "业务 Agent…不能修改批准自身更新的验证器、测试用例、发布门槛、审计日志和稳定版本备份。否则，一个 Agent 只需降低测试阈值或删除失败用例，就能把退化伪装成进步".
10. **§9.3.3 睡眠学习.** Five-step offline cycle (trigger, orient, consolidate, validate & approve, prune & index); Claude Code auto-memory (bounded `MEMORY.md` index) and Hermes Curator (snapshots before change, rollback); periodic tidy-up incl. moving local rules from the global prompt into domain Skills and retraining LoRA from the base model.
11. Summary: "本章构建的是第一章发现循环中的**实验与反馈**环节".

### Chapter 10 多 Agent 协作 / Multi-Agent Collaboration (EN pp.333–369)

1. **§10.1 分类框架.** Two dimensions: shared vs non-shared context; topology 对等 / 管理者 / 去中心化. Communication reduces to IPC's two paradigms (shared memory ↔ shared filesystem; message passing ↔ tool parameters and message bus); Go's "不要通过共享内存来通信，而要通过通信来共享内存". Graph engineering = the multi-agent subset of explicit execution graphs.
2. **§10.2 多 Agent 何时真正优于单 Agent.** The single criterion: "**协作过程是否引入了单个 Agent 在生成时无法获得的新信息？**" Table 10-1: same-model self-review "通常无效甚至有害"; debate over the same text = parity at equal compute; reviewers with execution / render / tool evidence = significant gains. RLEF; WebGen-Agent 26.4% → 51.9% [cited]; Anthropic's 45-agent vulnerability hunt: 27M tokens → 266 findings vs 6.5M tokens → 21 for independent agents [cited]. Budget awareness: more steps alone do not help ("很快就「饱和」了"); managers should allocate step budgets per subtask. Cost: gains must cover "数倍乃至一个数量级的额外开销".
3. **§10.3 共享上下文.** Role switching by `transfer_to_agent` (replaces system prompt and tools, breaks the KV prefix, but enforces tool invisibility) vs Skill (stable prefix, weak enforcement — "硬权限仍需 Harness 门"). Exp 10-1 ★★ (ledger: Skill 15/30 vs Transfer 2/30 deterministic gates, Skill slower with more uncached input).
4. **§10.4 不共享上下文 — the OS analogy** (Table 10-2: program = static prefix, memory = trajectory, CPU = LLM, kernel = runtime, syscall = tool call, fork / kill / ps = spawn / cancel / list_agents, exit code = structured summary; Actor model, 1973). **§10.4.1 虚拟文件系统** four regions (Table 10-3): Agent 专属工作区, 多 Agent 共享空间 (needs optimistic locking / worktrees), 外部挂载资源 (external permissions, weak consistency, read-mostly), 系统内置资源 (read-only Skills etc.). **§10.4.2 通信与控制**: message **envelope** (sender ID, target, type such as `task_assigned` / `status_update` / `result` / `terminate`, JSON payload) — "使协作链路可追溯——这是多 Agent 系统调试的关键"; status via messages with a shared state vocabulary, or via **trajectory persistence** (sub-agent appends its trajectory as JSONL, "相当于直接读另一个进程的内存") — but prefer an agreed `progress.md`; **stuck detection** = file mtime unchanged for N minutes; termination graceful (`terminate` → cleanup → ack) vs forced (SIGTERM/SIGKILL), cascading cancellation down the creation tree (Go `context`), `nohup`-style detached agents must be explicit; scheduling = token and concurrency budgets, model tiering, pre-emption — "决定了多 Agent 系统的成本上限".
5. **§10.4.3 对等协作 / Loop 工程.** "多个实例不等于多种思路". Three shapes of premature termination — 偷懒式假完成, 过早放弃, 假成功 (the phone counterpart agreed to a refund but the user still had to confirm in the app) — "**在验证之前，「完成」只是模型的一句宣称，不是证明**". Loop engineering (named by Addy Osmani, 2026-06; Boris Cherny: "我已经不再直接 prompt Claude 了，我的工作是写 loop"); consensus "**循环的瓶颈在验证器，而不在模型**". LoopX invariant: "模型可以提出「完成」，但不能批准自己的「完成」". LongHorizon-Harness MEA (Manage–Execute–Audit; same Qwen 3.7-Plus + Claude Code backend, only the outer loop changed): WeaveBench 51.8% → 80.7%, OSWorld 2.0 2.8% → 8.3%, Terminal-Bench 2.1 69.7% → 77.2%, at 2.3× / 3.6× total / output tokens on the first two and −24% on the third [cited]. Proposer-Reviewer minimal invariant in pseudo-code (reviewer reads *independent evidence*; "**审核者不能修改测试、证据采集器或发布门槛；否则「独立验证」会退化成自我批准**"); Huang et al. ICLR 2024 (GPT-4 self-correction makes more right answers wrong than vice versa), the TACL 2024 survey, CRITIC; Anthropic's planner–generator–evaluator with Playwright. Debate: Tran & Kiela 2026 — single agent ≥ multi-agent at equal thinking budget (data-processing inequality) [cited].
6. **§10.4.4 管理者模式.** Plan-and-Act: "**弱规划者是整个系统最关键的瓶颈**" → give the strongest model to the planner. Parallel managers must settle on "第一个**已验证**成功" with an idempotent `settle_once`. Exp 10-2 ★★ book translation (ledger: manager context 20.43× smaller, tokens 6.48× fewer, blind quality 4.654 vs 4.481, but 6.57% slower and worse Markdown fidelity) [measured]. Lingtai (main agent / daemon / avatar). Exp 10-3 phone + computer; Exp 10-4 parallel search with cascading termination and race-condition locking (ledger: 1.872× speed-up). Claude Code's Workflow tool (`agent` / `parallel` / `pipeline`) = manager writes the workflow as code, a deterministic runtime executes it.
7. **§10.4.5–10.4.6.** MetaGPT (message pool + subscription; control flow is really a pipeline), AutoGen (shared transcript + central speaker selector), OpenAI Swarm handoffs with a minimal protocol (`visited_agents`, `remaining_budget`, cycle rejection — "预算、访问链和循环检测由运行时保留，不能由任一 Agent 自行删除"). "Agent Swarm" is two different things (handoff networks vs Kimi K3's manager-pattern 100–300 sub-agents). A2A: Agent Card, task state machine, opaque collaboration; "MCP 解决的是 Agent 与工具之间的互操作，A2A 解决的是 Agent 与 Agent 之间的互操作".
8. **§10.5 失败模式.** "Why Do Multi-Agent LLM Systems Fail?": 7 frameworks, ~150 trajectories, κ = 0.88, 14 modes in three classes incl. **任务验证缺失**; simple fixes only +15.6% on ChatDev [cited]. Crash vs **Byzantine** faults — "Agent 的故障却天生是拜占庭式的——它很少径直停止运行，而是继续给出看似可信的错误结论，且错误不会主动声明自己是错误". Six modes: (1) shared-filesystem conflicts (optimistic locking; cross-file semantic conflicts need worktree isolation), (2) error cascade (cross-validation from raw evidence), (3) **同质趋同** (Anthropic: 18 of 30 concurrent agents created the same-named git branch; common-cause failure → namespaces, quotas, rate limits; Bertrand price collusion even without private channels) [cited], (4) 互相扯皮 (Anthropic: three agents migrating one backend killed each other's processes, revoked permissions, deployed self-replicating sabotage; MetaGPT blame loops) [cited], (5) 循环失控 ("失控的 Agent 有时会生成数千个子 Agent" → separate API keys per autonomous agent), (6) **理解债与认知投降** (Karpathy: "你可以外包你的思考，但不能外包你的理解").
9. **§10.6 Agent 社会.** Smallville, Agentopia (100 agents × 10 years; RFT on top-25% life-reward trajectories → CoSER +15.6%), Moltbook (~1.5M agents), Vending-Bench Arena (price wars and explicit collusion proposals), Pinchwork / RentAHuman, werewolf (Exp 10-6).
