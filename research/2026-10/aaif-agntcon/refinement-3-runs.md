## Run 1：重建敘事與決策

第一篇以同一個 App crash 調查貫穿各節。最初只允許調查與草稿 PR，之後才分別決定暫緩 rollout、接受修補，以及更新共用程序。第九節由簡短的導入清單改成完整交接：各項決定需要什麼證據、誰可以作決定，以及尚未重現問題時可以先交付什麼。結尾回到真實邀請與旅程，再說明接手同事能否用這些材料繼續工作。

第二篇把中斷放在請求送出後，讓「核准仍有效嗎、遠端發生了什麼、還差什麼才算完成」成為同一條敘事。第八節展開兩個故障切點，結語補足未完成的交接如何降低下一個人的查核負擔。兩篇英文同步保留這些理由與限制。

## Run 2：逐場補足機制、反例與驗收依據

| 場次／材料 | 新增的推論與判斷用途 |
|---|---|
| Kong | Gateway 正確限流與任務局部完成可以同時成立；已取得工具結果和結果未知，需要不同的恢復起點。 |
| Keynote／MCP | Crash 總數下降也可能來自曝光減少；需要同版本、故障群組、使用量與觀察期間，才能分辨改善和流量改變。 |
| Skills | 沒有發現程序和讀了卻做錯要分開診斷；要求獨立於新舊程序，避免用越權完成獎勵「進步」。 |
| Anthropic proxy | 當下 flag 狀態不能自行證明是哪一次請求造成；恢復與補償要能對回操作，避免撤銷他人後來的合法變更。 |
| 私有 coding assistant | 正常流程沒嘗試越界，不能證明限制生效；以實際工具入口驗證拒絕，也保留能完成工作的正常案例。 |
| Uber | 吞掉錯誤與保留重試入口都可能讓 App 不再閃退；產品要求與使用者可觀察行為才能區分兩種修補。 |
| Logfire | 相同交通方案搭配不同的抵達要求，檢查修改是否尊重旅客選擇；全面拒絕不能替代改善。 |
| SoftBank | 結構化的「已核准」仍可能只是自我宣告，操作授權必須對回有權作決定的來源。 |
| Studist | 受限執行服務的維護代價與驗證方式；改變目標或步驟，觀察是否在外部效果前被拒絕。 |
| Quartic.ai | 缺相容性資料和已知不相容，需要不同的下一份工作；verifier 的目標清單不能只照抄 executor 已處理的項目。 |
| Juicedata | 無論本機先寫完成或遠端先操作，都有中斷落差；備份目錄不能替代操作結果查詢與進度核對。 |
| PingCAP | 不同檔案沒有版本衝突，兩個行動仍可能共同違反任務限制；區分檔案更新與執行服務的並行控制。 |
| Hitachi | 根據端點變動、共同政策與維護能力選擇整合方式；元件本身不會補上業務核准的內容與責任。 |

所有新增案例都標示為分析或測試設計，沒有新增實測成功、失敗率或親歷事件。重新核對所引簡報頁面、Skills 規格及 Kong 固定版本設定，保留演講時點與現行文件的差異。

## Run 3：通讀、精確性與雙語一致

兩篇從開場通讀到 References 與 AI 協作說明，再核對中英文的動作對象與推論條件。主要修正包括：

- Kubernetes 案例原本寫「驗收對象少了一半」，容易把三台未升級 worker 誤解成實際檢查了其餘三台。改回簡報能支持的說法：初版只檢查第一台，卻把結果外推到全部節點。
- 故障測試將驗收者知道的故障時刻，與接手 agent 能查到的資料分開；預先保存操作識別也是明訂的設計前提。
- 「查不到」操作紀錄可能來自延遲或保留期限。只有查詢或重送契約提供足夠保證，才可考慮重送；無法分辨時，兩個故障案例都停下查核可以是正確結果。
- 憑證到期與任務核准失效分開處理。取得新憑證不會替任務新增授權。
- Logfire 的對照案例明訂搜尋結果只有一個方案，且「沒有符合條件的方案」只涵蓋該次結果。
- 移除重複的標準提案過程、縮短 Kong 版本說明、修正 stateless 規格的跨節指涉，並在案例中引入 feature flag、rollout 與 RCA。
