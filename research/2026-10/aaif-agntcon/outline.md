# 兩篇的論證路徑

本篇問題：工具接通後，團隊還需要什麼證據，才願意讓 agent 多做一步？敘事由真實旅程進入，以同一個假設的 crash 調查串起工程分析，再回到社群參與。六場演講各補足一部分依據，不各自拆成薄短文章。

| 段落 | 觀察與前提 | 因果推導 | 改變的判斷 |
|---|---|---|---|
| 一、邀請與出發 | 8/24 邀請、9/9 出發、9/10 參會動機 | 臨時行程與真實使用旅帖，帶出工具在具體任務中的限制 | 讀者知道作者為何參加；不虛構受邀理由 |
| 二、Kong 午休實作 | gateway 路由、failover、限制請求 | 通行政策與任務正確性需要不同資訊；換模型也可能換行為 | 可用性恢復後仍檢查任務；UI 成功不作外部效果證據 |
| 三、程式以外的回饋 | 程式有可重跑的回饋，其他工作也需要外部狀態 | 連接使工作可執行，仍須定義預期結果與驗收 | 區分 capability、授權及當下行動的理由 |
| 四、程序發現與採用更新 | 程序透過三次讀取交付，身分與 digest 用於識別 | 取用程序與採用更新是兩次判斷；相同雜湊不等於內容可信 | 保留來源、版本、變更及導入後的行為證據 |
| 五、失敗後的安全重試 | 多 worker、token rotation、遠端回應遺失、舊快取 | lock 協調競爭，reread 修正等待後的舊資料；逾時留下未知狀態 | 依錯誤意義查狀態、重試或重授權；清單相同不能取消存取控制 |
| 六、私有環境 | 推論位置與工具權限可分別設定 | 本機模型仍可讀檔／連網；全部拒絕也不能完成任務 | 用正常與越界案例觀察執行邊界，不拿指示文字代替隔離 |
| 七、調查步驟與模型判斷 | 固定資料蒐集與推理分工；相關 flag、mitigation、PR | 時序不是因果；測試須先能看到原缺陷；合併分母不等於事故消除 | 按問題選擇重現層級、限制重試，交付來源與未驗證條件 |
| 八、生產錯誤與修正 | 生產遇到未知案例，觀測可能偏向錯誤／慢請求 | 發現問題不等於證明更新普遍更好；改 prompt 影響未來任務 | 保留正常與未調整案例、人類採用決定、版本與外部效果紀錄 |
| 九、三個決策時刻 | 同一份 crash 調查包含影響、修補與程序更新 | 止血依現在的影響，修補依重現與回歸，程序更新依不同案例的效果 | 值班人員、工程師／發布負責人、程序維護者依各自證據作決定 |
| 十、離開澀谷 | 9/12 雨天、未完成晨跑、T-shirt 與伴手禮 | 將參會所得整理成可質疑與重用的材料，回應那張邀請 | 從一個反覆任務追查授權、程序變更與完成證據 |

## 第二篇：授權、狀態與復原

獨立問題：交接或重啟後，接手者如何知道可以做什麼、已做過什麼，以及何時算完成？以一個明示的叢集升級假設流程逐步增加條件，沒有假稱重跑 PoC。

| 段落 | 推進的問題 | 會改變的決定 |
|---|---|---|
| 一、會議前的東京鐵塔 | 9/9 快閃辦公室與雨夜照片，接回留存分頁及共同問題 | 個人故事依原貼文；用公開簡報重讀，不以分頁證明出席 |
| 二、允許對話後的行動 | 可以對話，是否等於下游可以行動？ | 執行邊界核對委派範圍；語意檢查定義等待與失敗路徑 |
| 三、任務範圍與強制限制 | 帳號權限如何縮成當次任務限制？ | 控制須涵蓋 CLI／API 旁路且不受 agent 修改 |
| 四、升級建議、核准與驗收 | 評估、核准與完成各指向哪份狀態？ | UNKNOWN 停止；修復後重評估；逐台驗證與服務驗收 |
| 五、重啟後要恢復的狀態 | 重啟該保留什麼，又該重查什麼？ | 六種狀態分開；外部控制紀錄、runtime secrets、commit point 與故障測試 |
| 六、檔案與工作衝突 | 沒有覆寫衝突，是否代表工作可以合併？ | 檔案版本以外仍需任務協調；記憶不是持續有效的核准 |
| 七、整個流程的責任 | 元件整合如何維持使用者最初的要求？ | 關聯 task／run／tool 並在動作前檢查條件；不虛構失敗率 |
| 八、中斷交接驗收 | 接手者無法直接知道故障切點，查不到紀錄也未必等於未執行 | 依查詢與同識別重送的契約判斷；不足時保留未知；按證據放寬一種操作 |
| 九、結語 | 如何留下下一個人敢接的工作？ | 保存可重查的依據與未知，讓社群接續檢查與改進 |
