- [B 全文：A 加理由與自查](results/formal-2026-09-25/source/specs/B.md)（1,923 詞）：先保留 A 全文，再增加兩段集中理由與六題自查，明言不新增要求。

詞數按空白切分，包含標題與程式區塊，不含起始程式碼，也不是模型的 token 數。B 開頭與 A 全文、C 開頭與 B 全文都逐 byte 相同，也就是每個位元組都保留；新增內容各在文件末尾。

## 先知道十三條要求在談什麼

四份文件處理同一支 Python 工具：它從逐行 JSON 工作紀錄取出審查文字，另外傳出診斷，最後回報整次工作是否成功。這次修補要處理的是「JSON 本身合法，裡面的值卻不是程式預期型別」；例如收到陣列時不能崩潰，收到數字訊息時不能把它當成成功的審查。

閱讀時可以先用下列編號定位。這張表是內容地圖，判斷細節仍要回到各版本原文。

| 要求 | 主要決定的行為 |
|---|---|
| R01 | 交付哪個檔案、保留什麼命令列介面，以及輸出必須在輸入結束前逐步送出 |
| R02–R04 | 如何計算行號、辨認事件與項目，以及遇到事件結構或型別錯誤時如何繼續處理 |
| R05–R07 | 如何處理代理文字、命令註記與項目錯誤，分清缺值、空值與錯誤型別 |
| R08 | 完成事件的用量欄位接受什麼值，何時可以輸出 token 註記 |
| R09–R10 | 如何保留兩種失敗事件的既有處理方式，包含診斷欄位本身有錯的情況 |
| R11–R12 | 多種情況一起出現時選哪個結束碼，以及附上什麼摘要 |
| R13 | 保留重複訊息、重複完成事件與其他既有容忍行為，並界定修改範圍 |

## 怎麼對照差異？

建議分三步閱讀。以下 diff 檔是直接用凍結原文產生的逐行比較，沒有先翻譯或整理措辭。以 `-` 開頭的是前一版文字，以 `+` 開頭的是後一版文字；沒有增刪標記的行提供上下文。`@@` 後的數字標示兩份檔案的行數位置，不是要求編號。

1. **[A0 → A：逐行差異](spec-comparison/A0-to-A.diff)。** 先對照相同的 R 編號。例如 R05 在 A0 用一段交代哪些 `text` 值可以輸出，A 則分段展開，特別解釋 Python 的真假值判斷。這部分適合拿來看說明如何增加，但還要檢查其他條文有沒有改變要求。
2. **[A → B：逐行差異](spec-comparison/A-to-B.diff)。** A 全文保留，新增的是末尾 `Non-normative rationale and checklist (B)` 一節。它先解釋容易犯錯的原因，再用六題提醒實作者依既定條文自查。
3. **[B → C：逐行差異](spec-comparison/B-to-C.diff)。** B 全文保留，新增的是末尾 `Non-normative implementation pattern (C)` 一節。它提供可選的處理流程與函式安排，並沒有安裝或執行 Skill。

**A0 與 A 的一處重要差異：** A0 的 R01 寫「No new CLI arguments or external dependencies are required」，意思是不要求新增 CLI 參數或外部依賴。A 的 R13 則把「adding CLI options」列入「outside this task」，也就是超出任務範圍。不要求新增，與把新增排除在範圍外，約束並不相同。B、C 沿用 A，也繼承了這句話；四份文件不能直接視為語義完全等價。正式驗收也沒有完整涵蓋 CLI 介面，因此無法用四組全過判定這項差異沒有影響。

逐行差異只告訴我們文字改在哪裡，不會自行證明哪份規格更有效。四組各十份候選都通過本次驗收，仍不足以替四份文件排序。更完整的逐句分析見[規格篇第三至第五節](../../../2026-11-same-spec-spec/article.md)，結果與限制見 [RESULTS.md](RESULTS.md)。
