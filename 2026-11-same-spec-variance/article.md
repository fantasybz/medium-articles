# 同一份規格，跑十次（三）：變異篇—十次都通過，下一筆證據該怎麼找？

> **TL;DR** — 四種交代各跑十次，四十份程式全部通過檢查。接下來該多跑幾次、換一批任務、補強驗收，還是找人實際接手？這些做法都要花錢，回答的卻是不同問題。本篇寫給設計評估的人與工程主管，從「下一筆證據要改變哪個決定」往回推。先分清同題重複、文件改寫、換任務與環境，再看十次全過為什麼還不能證明四種交代一樣好。接著用「三次全都成功」與「三次裡挑一份成功」的例子，說明成功率必須連同使用方式一起讀。後半部回到實務：兩份都通過的程式該怎麼讀、舊結果怎麼保存，以及新比較要記哪些工作與人工成本。下一輪 P／Q 設計比較的是共同要求加不加可選自查，仍未執行；288 個名額只是預算草案。已決定的必要行為照樣要遵守，但若要把額外自查設為團隊預設，現有資料還不夠。

## 一、四組都十次全過，下一筆預算要花在哪裡？

假設團隊修補一支 Python 工具，交稿前多加六題自查。下一份程式通過了，有人於是提議：以後同類工作都附上這六題。這是〈[總論](../2026-11-same-spec-overview/article.md)〉第二節的假設情境。真正值得追問的地方在下一次派工：這六題會持續幫忙，還是只是與這次成功一起出現？

總論把問題拆成三層。需求先由有權決定的人（owner）確認；每份待驗收的程式，也就是候選，再依那些要求檢查。本篇接手第三層：要求已經清楚、也能驗收之後，新增的自查是否值得反覆使用？必要行為與相容規則原本就必須記錄、驗收，不必等待平均收益的證明。需要比較的，是要求不變時額外附上的可選自查。

這一層主要有兩種讀者。負責設計評估、維護驗收資產的人，本文稱為 eval owner；他要說明每筆結果能支持什麼判斷。工程主管（EM）則要分配預算與人力，決定採用、維持或撤回。兩者都得回答同一件事：再買一筆證據，有可能改變哪個決定？

本系列的正式研究已經交出一批結果。一支逐行讀取工作紀錄的工具，其修補任務，四種交代各生成十份候選，四十份全部通過 103 項共同檢查。沒有任何候選在已知檢查上出錯，這讓人放心；可是四組都是 10/10，比較也就失去了區分力。接下來很容易出現幾種提議：同一題再重複三十次、換一批更難的題目、把驗收做得更嚴，或者找人讀程式，並記錄審查花了多少時間。每一種提議都要花錢，但它們買到的證據不同，能回答的問題也不同。

《綠燈不是驗收》系列的〈[可靠度篇](../2026-10-green-reliability/article.md)〉（尚未發布）處理過相近的決定：一類任務要累積多少證據，才能放寬 agent 的授權。那篇關心多次交付是否都能成功，以及人工複核要保留多少預算；其中 pass^k 的讀法，第四節會用例子重說一次。本系列把對象換成一段交代：它值不值得跟著之後的每一次派工。對象雖然換了，分母的紀律同樣重要。哪些觀測彼此獨立、哪些只是同一題的重複、哪些其實屬於另一種工作流程，都會影響一個數字能支持多大的結論。

本文先確認「這次改了什麼」，再解讀四組全過的結果。接著把同一個成功率放進兩種工作方式，看看數字為什麼會變；再看總成功率相同時，失敗落在哪些任務上。這些判斷會帶到下一筆預算的選擇，最後落在一張尚未執行的比較卡：寫清楚怎麼派工、怎麼計數、怎麼記人工時間，以及何時採用。

## 二、先說清楚這次變的是什麼：三種變動，三種比較單位

在評估工作的討論裡，「再跑一次」至少有三種意思。三者都會產生新的候選，但固定的條件不同，能回答的問題也不同。

第一種是**同條件重複**。同一題、同一份交代、同一組模型設定與執行政策，再交付一次，讓無法固定的生成過程自然變動。例如把同一個 parser 修補交代原樣送十次，問的是這個做法在這一題上有多穩。

第二種是**文件介入**。同一題的要求、工具、預算與驗收不變，只改交代。我把共同規格叫 P，加上自查的版本叫 Q；比較的是「多附這段自查」是否改變結果。介入在這裡就是刻意改動、準備比較的部分。

第三種是**任務或環境更換**。例如把這套做法搬到 CSV 修補，或改用另一個模型。這時先固定交代的建立程序與驗收原則，各題仍要依自身要求準備文件，不能把 parser 的原句照貼過去。執行工具（harness）也可能更換；它負責安排工具使用、執行與觀察結果。這類比較問的是結論能不能帶到其他工作與環境，第九節會說明各題的 P／Q 怎麼建立。

下表把三者並排。表中的 task 指原始需求連同 repo 起始版本；packet 是一次交給模型的完整輸入。逐 byte 相同，表示輸入的每個位元組都沒變。先看各列固定與改變了什麼，再看正式研究實際做到了哪裡。

| 變動 | 固定什麼 | 改變什麼 | 比較單位 | 正式研究 |
|---|---|---|---|---|
| 同條件重複 | 任務、交代、模型設定、執行政策 | 無法固定的生成過程。 | 同一 task 多次試行。 | 每組十次收到逐 byte 相同的 packet。 |
| 文件介入 | 任務、要求、工具與預算、驗收 | 交代的寫法 | 同一 task 內，條件之間的差 | A→B→C 是累加套件；B 同時加入理由與自查 |
| 任務或環境更換 | 交代的建立程序與驗收原則；各題依自身契約建立文件與案例 | 題目、repo、模型、harness 或資源 | 任務的抽樣方式、環境的區塊 | 只有一個任務；provider 端設定無法固定 |

從最後一欄可以看出，正式研究讓四種 packet 各自在同一題上重複十次，也安排了組間的文件差異。B 以 A 全文為基礎，同時加入集中的理由與六組自查，因此 A／B 無法分開兩者各自的作用。C 則在 B 上加入一整段可選的實作安排建議（pattern）；B／C 原則上能比較這整段增量，但不能再拆成個別建議、字數或模型理解方式的效果。

本輪四組全部通過，沒有提供支持效果排序的差異。研究也沒有安排跨任務或環境的比較，所以結論仍限於同一個修補任務。

計數也要跟著問題走。四十次生成仍然是同一個修補任務的四十次試行，不是四十種工程情境。103 項檢查則是在問同一份候選，例如能不能處理錯誤型別、會不會保留空白；檢查再多，也不會變成 103 次模型交付。

讓工具自動產生更多輸入的 property-based testing 也一樣。Hypothesis 文件說明，生成分布以找 bug 為目的，不模擬真實生產流量（[Hypothesis, Domain and distribution](https://hypothesis.readthedocs.io/en/latest/explanation/domain.html)）。測過一萬個生成輸入，不等於一萬次生產成功。

結構比較還有另一個容易放大的數字：每組十份候選兩兩配對，有 45 對，四組共 180 對。同一份程式會反覆出現在不同配對裡，所以這些配對共用原來的四十份程式，不能當成 180 個獨立觀測。

下一輪如果允許 agent 在同一個工作階段（session）裡使用工具，還會出現另一種容易誤算的單位。agent 可能先寫一版、執行公開檢查、看到失敗後再修改，於是一個 session 內留下好幾個中間版本。這些版本都是同一次試行的過程紀錄；只有 session 結束時凍結的那份候選，才會進入外部驗收。中間版本再多，也不會增加獨立樣本數。

第三種變動需要單獨列出，因為環境本身就會改變結果。Anthropic 在一篇工程文章中，固定模型、harness 與任務，只調整可用資源與強制停止的門檻（kill threshold），結果就隨之改變。在 SWE-bench 的交叉比較中，作者使用 227 題、每題 10 個 samples；RAM 從 1× 調到 5×，差距為 1.54 個百分點，也就是成功比例直接相減的差距（[Segato, 2026](https://www.anthropic.com/engineering/infrastructure-noise)）。文章沒有說清楚每個資源條件是否各有十個 samples，所以我不自行推算總請求數。

另一篇研究 coding agent 的論文也顯示，harness 執行政策（policy）不同，提高 effort 所帶來的效果也會改變（[Prompt-Induced Waste in Coding Agents, arXiv 2608.01347v6](https://arxiv.org/html/2608.01347v6)，§6.1）。兩篇研究都提醒同一件事：換模型、換 harness 或換資源，都屬於另一種變動；在舊環境下得到的文件比較結果，不能直接替新環境背書。

這些研究不能倒推本系列的成因。正式研究是無工具的一次生成，模型不會安裝套件、建置專案或執行測試。四十份候選結構各不相同，但供應商實際使用的上下文、取樣設定 temperature 與 random seed 都無法固定，也看不到；我不能把差異歸因於 RAM 或任何看不見的設定。random seed 在這裡用於取樣，與前面固定起始程式碼的 seed commit 不同。

能說清楚的是研究的停止規則：每個名額跑到 600 秒時送出終止訊號 SIGTERM，最多再等 5 秒，仍未停止才以 SIGKILL 強制結束。另設每個名額 USD 5 的 CLI 停止門檻。

停止規則本身也會改變比較。一篇研究在 5 個 SWE-bench Verified 任務上重複量測，原先最多允許 60 回合，簡略規格有較多執行因此被截斷；改成 120 回合後，研究者重跑 112 筆（[Can your AI agent be cheaper?, arXiv 2608.25399v1](https://arxiv.org/html/2608.25399v1)，Appendix A）。允許做多少工作，是方法的一部分，不能只寫模型名稱就當成相同條件。

## 三、四組 10/10：結果字面相同，不代表等效

現在回到正式結果。任務來自我的 `medium-articles` repo：`research/scripts/codex_jsonl.py` 讀取 JSONL 工作紀錄，也就是每行一筆 JSON 資料。正常內容送到 stdout，診斷送到 stderr，最後由 exit code 回報整次處理結果。固定起始版本有兩個可重現問題：根層值是 `[]` 或 `null` 時會崩潰；訊息 `text` 是數字 `123`，後面再接有效完成時，會把數字印成審查文字，並回報成功的 exit 0。

四份交代以十三條共同要求 R01–R13 建立，但措辭未必完全同義，第六節會回來查新增 CLI 選項的範圍差異。A0 有 936 詞，已包含完整目標；A 有 1,655 詞，逐項展開；B 有 1,923 詞，在 A 全文後增加理由與六組自查；C 有 2,223 詞，再加一段可選的純文字實作建議。詞數依空白切分，含標題與程式碼，不含起始程式碼，也不是模型處理文字的 token 數。

要核對這些差別，可以直接開啟四份英文 spec 全文：[A0](../research/experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/A0.md)、[A](../research/experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/A.md)、[B](../research/experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/B.md)、[C](../research/experiments/same-spec-ten-runs/results/formal-2026-09-25/source/specs/C.md)。[全文與逐行差異導讀](../research/experiments/same-spec-ten-runs/SPECS.md)另附 A0 → A、A → B、B → C 的逐行比較，讓讀者先確認每一步改了什麼，再判斷結果能支持哪一種比較。

每組十個名額事先排定，不重試、修復、替補或事後追加。生成使用 `claude-opus-5-5` 的 high effort，模型沒有工具，每次只能交一個檔案。全部生成結束，才共同驗收：102 個批次案例在送完輸入後讀結果；另 1 個 streaming probe 刻意不送出輸入結束訊號 EOF，先看訊息能不能傳出。操作條件也另行核對，兩者都成立才算 accepted。

四十份候選全部 accepted。

這很容易被讀成「四種交代一樣好」。先做一個純假設的計算，就能看出缺口：若每次獨立、成功機率都是 95%，十次全過的機率約為 59.9%；即使成功機率只有 80%，仍有約 10.7% 的機會交出十次全過。表現不同的做法，都可能留下同樣的 10/10。

統計區間處理的，就是觀測相同時仍存在的不確定。在每組十次觀測彼此獨立、條件相同，且共享同一成功機率的假設下，10/10 的雙側 95% Clopper–Pearson 區間約為 69.15% 到 100%。它是二項比例的精確區間方法；本例下界可由一個問題算出：成功率低到多少時，十次全過的機率會只剩 2.5%？解 p¹⁰ = 0.025，就得到約 0.6915。

這不是保證下一次至少有 69% 成功機會，也不是說成功率有 95% 機率落在這個已算出的區間。95% 描述的是：在假設成立的重複抽樣中，這種區間方法至少有 95% 的涵蓋率。四組得到相同的寬區間，仍沒有把各組未知成功率辨認成同一個數值。

如果團隊真正想說「差距小到可以當成一樣」，那是等效判斷，需要另一種證據。團隊要先定出「差距在多少以內就視為相同」的門檻，再估計兩組差值的區間，確認整個區間都落在門檻內。正式研究沒有事先訂出等效門檻，也沒有提供支持等效判斷的差值區間與精度規劃。因此，這批資料不能證明四組等效，也不能證明長文字沒有用。

它支持的結論比較窄：在這個任務與這些條件下，四份 packet 各自在十個名額中都交出通過 103 項檢查的候選，沒有觀察到失敗。這個結論還有一個條件：103 項是有限的檢查。

EvalPlus 在 164 個 HumanEval 函式任務、26 個模型上擴充測試後，找出原有測試沒有辨識出的錯誤，甚至改變了模型之間的排序（[EvalPlus, arXiv 2305.01210v3](https://arxiv.org/html/2305.01210v3)，§3）。所謂「沒有觀察到失敗」，只涵蓋量尺看得見的範圍。

費用與時間也只能作為描述。依 CLI 牌價估計，A0、A、B、C 各組十次生成的費用合計依序約為 USD 1.25、1.38、1.51、1.55，全部約為 5.69。這不是帳單，也不含研究、流程試跑、寫作或人工成本。生成時間的中位數依序約為 37.3、37.3、40.3、37.2 秒；C 組最長的一次為 59.7 秒。這些只是模型生成的時間，不含驗收與人工處理。

費用大致隨文件變長而上升。A／B 同時改動理由與自查，無法拆開兩者的作用；B／C 雖可比較整段 optional pattern 的增量，本輪費用仍只是描述，不能據此拆解個別建議或字數的效果，也不足以替交付品質排名。

成本本身也會隨重複執行而變動：前一節提到的 SWE-bench 研究中，同一種規格與 effort 重複執行時，研究以幾何標準差（geometric SD）描述成本的倍數散布，其中位數為 ×1.34；這種量尺用倍數而非相差幾美元表示離散程度（arXiv 2608.25399v1，§4.3）。因此，只看一次執行花了多少錢，無法說明同條件下費用如何變動。

更關鍵的是，EM 最需要的人力成本，包括讀程式、修正、核准與維護文件所花的時間，本輪完全沒有量測。

那麼，把同一題再重複幾十次，能不能補上這個缺口？在相同的獨立同分布假設下，若 n 次全部成功，95% 區間下界就是 0.025 的 n 次方根：30 次全過時約為 88.4%，100 次全過時約為 96.4%。

這筆預算讓我們更有信心判斷：這份 packet 在這一題上很少失敗。如果四組都繼續全過，組間仍然分不出高下，也看不出另一支工具或另一種工作的情況。只有當團隊關心的是同一個凍結修補任務、同一份 packet 與交付政策下的表現，這筆重複才直接有用。這支 parser 未來若有新的需求或起始版本，就屬於另一個 task，不能由這裡的重複次數代替。

## 四、同一個成功率，不同的使用政策

假設一種做法每次成功的機率都是 80%。團隊連續收到三份結果，每份都直接採用，關心的是「三份都沒出錯」；若同一題跑三次，再挑出一份成功結果，關心的則是「至少找到一份」。雖然都說成功率，問的事情已經不同。

τ-bench 用 pass^k 表示 k 次全部成功，pass@k 表示 k 次獨立嘗試裡至少一次成功，兩者先在各任務計算，再對任務取平均（[Yao et al., arXiv 2406.12045v1](https://arxiv.org/pdf/2406.12045v1)，§3）。原研究是零售與航空的模擬客服；本文只借用定義，不借用它的成功率。

下面是一個純假設的例子，不是本輪估計。正式研究的四組都是 10/10，可以報出觀測比例與依假設得到的區間，但區間仍很寬，不能把未知成功率精確定為 100%，也不能拿來支持下面的 p=0.8。現在另假設某個固定任務的每次嘗試彼此獨立，成功機率都是 0.8，並考慮三次嘗試（k=3）。表中每一列代表一種使用政策。需要挑選的列，假設有一個每次都能辨認正確結果的選擇機制，稱為 selector；這個理想前提稍後還要拿掉檢查。先看第二欄要回答的問題，再看第三欄列出的成立條件。

| 使用政策 | 回答什麼問題 | 成立條件 | 假設數值（p=0.8） |
|---|---|---|---|
| 只執行一次，直接採用 | 單次交付有多可靠 | 沿用上文每次 p=0.8 的假設 | 80% |
| 連續交付三次，每次都採用 | 三次都不出錯的機會（pass^3） | 中間沒有人挑選或攔截 | 0.8³ = 51.2% |
| 執行三次，挑出成功的一份 | 三次裡至少有一份可用（pass@3） | 有能辨認成功的 selector；三次都要付費 | 1 − 0.2³ = 99.2% |
| 依序執行，成功就停 | 同上，但少花幾次嘗試 | selector 每次都能立即判定 | 99.2%，平均 1.24 次嘗試 |

同一個 p，放在第二列和第三列，結果相差將近一倍。第二列描述無人看守的情境：agent 每次交出的東西都直接被採用，任何一次出錯都算失敗。〈可靠度篇〉討論是否擴大授權時，關心的正是這種情境。第三列描述的是另一種工作方式：團隊願意為同一題付出三次嘗試，再由某個機制挑出成功的一份。

第四列說明，選擇政策也會改變成本。如果每次嘗試後都能立即判定成敗，第一次成功的機率是 0.8，只有前兩次都失敗，才需要第三次；期望嘗試次數是 1 + 0.2 + 0.04 = 1.24。假設每次生成花 USD 0.10、驗收花 USD 0.02，成功即停的期望成本約為 USD 0.1488；每題固定跑滿三次再挑，則是 USD 0.36。兩者的成功率都是 99.2%，花費卻差了一倍多。下面這段程式可以用來驗算：

```python
# 驗算示意（純假設數值；本文未另行執行這段程式）
p, k = 0.8, 3
pass_at_k = 1 - (1 - p) ** k                       # 0.992：三次裡至少一次成功
pass_pow_k = p ** k                                # 0.512：三次全部成功
expected_n = sum((1 - p) ** i for i in range(k))   # 1 + 0.2 + 0.04 = 1.24 次
cost_each = 0.10 + 0.02                            # 假設：生成 0.10、驗收 0.02 美元
print(expected_n * cost_each, k * cost_each)       # 約 0.1488 對 0.36
```

99.2% 這個數字要打兩個折扣。第一個折扣來自 selector。表中假設它永遠判斷正確，但真實的 selector 本身就是一把驗收量尺，可能放過錯的候選，也可能拒絕對的候選。被放過的錯誤候選會混在「成功」裡交付出去；被誤拒的正確候選，則讓團隊多花嘗試。量尺有多可靠，正是〈契約篇〉處理的問題。

第二個折扣來自回饋。如果 agent 看到上一次的失敗訊息後再修正，後一次嘗試就不再獨立於前一次。這屬於另一種政策，不能用上面的公式估算，只能把整個流程當成一次試行來量測。

Kapoor 等人比較 agent 時，把只用重試、不增加其他複雜策略的比較基準（retry baseline）與費用一起納入比較，提醒讀者「多試幾次」本身就可能是很強的對手（[AI Agents That Matter, arXiv 2407.01502v1](https://arxiv.org/html/2407.01502v1)，§2.2–2.3）。放到本文的決定裡，如果 Q 的優勢只是讓 agent 多做了幾輪檢查，團隊應該先問：把同樣的預算拿去讓 P 多重試，是否也能得到相近的交付結果？這篇論文也明白表示，它沒有充分量測人工、標註與維護成本；這一段仍要由團隊自己補上。

下一輪比較卡採用的政策，允許 agent 接收回饋。每個名額是一次有限的工具 session：agent 可以執行公開檢查，看到失敗後再修正；session 結束後，才進入外部驗收。session 內的每一輪修正，都是同一次試行的一部分，不能算成 pass@k 裡的 k。要比較的是兩種政策各自的最終結果，也要一併比較為了得到這些結果所花的預算。

## 五、同樣 10/20，失敗集中在哪幾題也重要

上一節假設只有一個任務。實際比較時，任務通常不只一個，每題也會重複幾次，這時會浮現另一個問題：只看總成功率，就會失去失敗落在哪裡的資訊。

下面也是純假設的例子。X、Y 兩個方法各自處理同樣十個任務，每題執行兩次，總成功次數都是 10/20。表中的 pass^2 與 pass@2 是這批觀測的描述：分別計算兩次都通過、至少一次通過的任務比例，不能由兩次結果反推出每題真正的成功率。先看第二欄，確認成功與失敗如何分布，再比較最後兩欄。

| 方法 | 每題兩次結果 | 總成功 | pass^2（兩次都過） | pass@2（至少一次過） |
|---|---|---|---|---|
| X | 五題兩次都過，另外五題兩次都失敗 | 10/20 | 5/10 | 5/10 |
| Y | 十題都是一次通過、一次失敗 | 10/20 | 0/10 | 10/10 |

如果只保留總成功率，X 與 Y 都是 50%，看起來完全相同。保留每筆結果屬於哪一題的 task ID 之後，才能看見兩種不同的觀測型態，提出下一步要查的問題；這張表還不足以替兩個方法診斷失敗機制。

X 的十次失敗都集中在五個任務上。我會先查這五題是否碰到共同的義務、量尺或工作類型：需求是否仍未決定，判斷對錯的依據與比對方式（oracle）是否誤拒合法寫法，或者目前做法是否在某類工作上較常失敗。每題只有兩次結果，還不能判定它們的成功機率是零，也不能說重試再多次都無效。另外五題的兩次結果雖然一致，也只代表這兩次都通過，尚不足以保證之後的單次交付。

Y 則在每一題都出現一次通過、一次失敗。這顯示本批資料中，同題的結果並不一致，但不能據此假設每次真實成功機率恰好是一半，或每次嘗試彼此獨立。它提供的診斷線索是：挑選、複核或有限重試是否值得列入下一輪比較？若要採用這類流程，selector 的誤判與成本也必須一起評估。X 與 Y 讓我們看見該追查的方向；它們還沒有回答是哪個原因造成失敗，或哪個補救方法一定有效。

這個差別也會影響文件比較。假設 Q 的總成功率只比 P 高一點，可能是少數幾題的觀測改善很大、另外幾題卻變差，也可能是改善分散在許多題上。保留每題在 P 與 Q 下的結果，才有機會分辨這些型態、追查退步的義務，並估計任務之間的差異。即使每題觀測都朝同一方向，也還要處理樣本不確定性與任務代表性，才能討論自查是否有較廣的用途。

所以，紀錄從一開始就要保留身分資訊。`task_id` 對應原始需求與 repo 起始版本；同一個 task 底下的每一次試行，都要能對回所屬條件，以及它是第幾次重複。分析時要把同題結果當成一群，而不是拆成完全無關的資料；這稱為保留任務群聚，並允許同題的多次結果相依：它們共用同一份需求、同一個起點，也可能卡在同一個難點。若忽略這種相依，區間可能顯得過窄。τ-bench 先保留每個 task 的成功次數，再對任務取平均；這種計算方式保留了任務這一層的結構。

## 六、從想回答的問題，倒推下一筆證據

前面幾節各自處理了一種誤讀。把它們放在一起，就能回答開場的問題：下一筆預算該花在哪裡？我的做法是先確認目前卡在哪一種不確定，再選能解決它的證據。下表整理六種常見情況。表中用 incoming 表示實際進來的工作；AST 則是從程式碼整理出的語法結構，第七節會再說明。請先在第一、二欄找到眼前的處境，再看第三欄該補的證據；第四欄列出最容易被拿來頂替、卻回答不了問題的做法。

| 遇到什麼問題 | 看起來像什麼 | 下一筆證據 | 哪些做法無法代替 |
|---|---|---|---|
| 資料不足 | 差值區間跨過實務門檻 | 依想估的效果、任務差異與同題相依，事前規劃任務數、重複數與精度 | 看到結果才決定追加 |
| 觀測沒有區分力 | 各組都全過或全敗 | 能代表目標工作、也有機會辨識差異的任務，或事先定好的其他結果 | 只為等組間分出高下而追加；只挑更難的題。 |
| 行為不等價 | 條件之間除了想比較的成分，還有其他要求差異 | 先對齊要求，再重新生成 | 替舊 packet 補樣本 |
| 任務不代表目標工作 | 研究題和實際進來的工作不同 | 從 incoming 工作清單建立抽樣框，保留排除理由 | 把已公開的題目改寫成新題 |
| 量尺看不見 | 合法差異被拒絕，或已知錯法被放過 | 修 oracle、補正反對照，對既有候選一致重評 | 多生成幾份候選 |
| 人力未知 | 只有模型費用與結構描述 | 真人接手紀錄，以及事先抽樣的深讀 | AST 相似度、代理 review、模型牌價 |

**資料不足。** 區間跨過門檻時，最直接的反應常是「再多跑一點」。先要分清目標：是估計某個固定任務有多穩定，還是一類工作的平均效果？接著評估任務差異與同題相依如何影響精度。上一節的 X／Y 只有兩次觀測，能提示該查什麼，不能直接告訴我們預算應移向哪一邊。若獨立的先導資料與合理假設顯示任務之間差異很大，可評估增加任務；若問題是看清同題的波動，則可評估增加重複。兩種安排仍要對照同一個目標，事前比較所需成本與可得精度。追加與停止的規則也要在看到正式結果前決定；不能看到哪個結果接近期待，就一路追加到它成立。

「未定」也是正當的結果。Skill Issue 使用 Claude Code 與 Sonnet 4.6，在三個 Kotlin repo 最佳化 SKILL 文件；保留到評估時才使用的題目分別有 20、26、23 題（[Skill Issue, arXiv 2609.12742v1](https://arxiv.org/html/2609.12742v1)，§3–4.2）。解決題數分別從 13 到 16、16 到 20、14 到 15，看起來都有增加。

研究也計算配對綜合分數，把改寫版與原版在同題上的表現相比；以 0.5 為自比基準，三個 repo 得到 .554、.567、.525，平均約高 4.9 個百分點。這不是解決率，還納入測試竄改、成功宣稱與隱藏測試等因素。作者用 sign test 檢查配對結果的方向差異，每次最佳化都未達 .05 的顯著門檻，最低 p 值為 .29。

這不能證明 SKILL 文件無效，也不能把 p=.29 讀成「文件有 29% 機率無效」。在這個資料量下，收益仍無法和重新執行造成的自然變動分開。實務上的文件改動，很可能也會停在這種位置：觀測有改善，證據卻還不足以作採用判斷。

**碰到上限。** 正式研究就是這種情況。第三節已經算過，若同一題繼續重複，而且各組仍全部通過，這一題的區間下界會逐漸升高，組間仍沒有觀測差異。新試行也可能出現失敗，因此不能事先斷言追加後一定維持全過。另一篇研究的延伸實驗也出現相同情形：5 個任務、5 種條件，每種條件各重複 3 次，共 75 次執行，每種條件都是 15/15 成功（arXiv 2608.01347v6；該延伸實驗在那個設定下，量測增加 effort 的作用）。在這批成功率全部飽和的觀測中，沒有可用來區分條件的成功差異。

這時「換更難的題」只對了一半。題目要能產生差異，也要代表團隊真正準備採用這項做法的工作；為了拉開差距而特地挑出的難題，得出的結論只適用於那些難題。另一個選擇是改看成功率以外的結果，例如失敗種類或人工投入。這些結果必須在比較前定好，不能看到成功率打平後，才臨時換一個指標。

**行為不等價。** 如果條件之間夾帶了比較對象以外的差異，樣本再多也分不開效果。正式研究就有一處：對新增的 CLI 參數，A0 寫的是「不需要」，A 則在 R13 進一步排除，說它們「不在範圍內」；B 與 C 沿用 A 的文字。正式 grader 沒有全面檢查額外的 CLI 選項與 `main` 介面，因此這處差異造成什麼影響，至今仍不清楚。已凍結的 packet 不能事後修改；替它補樣本，只會反覆重現同一個額外差異。下一輪若要比較，應先對齊要求，再重新生成。

P 與 Q 的設計也照這個原則：每個 task 的 Q 以共同 P 全文開頭，只追加依事前政策核定的自查區段。Parser 範例可以使用凍結 B 的六題原文；其他任務必須先把每一題自查對應到自己的既有要求，這一步稱為映射，不能照搬 EOF、token 等不適用的義務。第九節會說明映射政策。P 被 Q 完整保留的關係可以逐 byte 核對，但語義上有沒有偷加要求，仍需另外審查。

**任務不代表目標工作。** 一支 parser 可以用來示範方法，卻不能代表一個團隊的日常修補。若要讓結論適用於「Python 工具修補」，任務就要從這類工作的實際來源取得。第九節會說明如何建立這份清單。

**量尺看不見。** 如果問題出在驗收，例如〈總論〉的 CSV 案例中，契約容許 LF 或 CRLF 兩種紀錄結尾，逐 byte 比對卻只接受其中一種，錯拒了合法輸出，增加生成只會產出更多被誤判的候選。下一步應該修正 oracle，保留舊版與原本的判分紀錄，再對同一批既有候選一致重評。這一步不需要新的模型生成。

**人力未知。** 這是 EM 最常問、也最常被機器指標頂替的問題。AST 相似度描述程式結構的樣子，模型牌價描述生成的費用；兩者都無法說明一個人理解並接手這份程式要花多少力氣。要回答人力問題，就要安排真人接手並留下紀錄。第十節會說明該怎麼記錄。

## 七、兩份都通過的候選：差異該導向哪個 review 動作

先想像把兩份程式攤在眼前：都能通過，函式安排卻不一樣。電腦可以把程式整理成抽象語法樹（AST），保留「這裡是判斷、那裡是函式呼叫」之類的結構，再將這份表示算成一個內容指紋，也就是 hash。表示有任何保留的差別，hash 就可能不同。

本研究先統一部分識別字名稱，稱為正規化，再算 AST hash；四十份都不同。不過，這個轉換保留屬性名稱、匯入路徑、常數與程式順序，也不追蹤變數在不同作用範圍究竟指向誰（scope binding）。因此 hash 不同只代表轉換後的表示不同，不保證控制流程不同，更不表示品質較差。完整描述統計見[正式研究結果](../research/experiments/same-spec-ten-runs/RESULTS.md)。

對 reviewer 而言，下一步是帶著一項要求去找實作：這個差異讓我必須多查哪裡？下面實際讀兩份，看看這個問題怎麼問。

為了回答這個問題，這次靜態閱讀在研究完成後，先選定 A0 在凍結執行順序中最前面的兩份候選：[formal-01-A0](../research/experiments/same-spec-ten-runs/results/formal-2026-09-25/formal-01-A0/candidate/codex_jsonl.py) 與 [formal-02-A0](../research/experiments/same-spec-ten-runs/results/formal-2026-09-25/formal-02-A0/candidate/codex_jsonl.py)，之後才閱讀程式碼。挑選時沒有參考分數或差異程度；不過，這仍是事後的教學選擇，不是研究前預定的分析，也不是代表性抽樣。兩份候選都通過了 103 項檢查。以下只是靜態閱讀，沒有量測任何人理解或修改程式所花的時間。

打開程式之前，先知道要找什麼。R05 是訊息欄位的要求編號：`text` 缺值、為 `null` 或空字串時，不輸出，也不算發言；非空字串要原樣印出，立即送給呼叫端（flush），只有空白的字串也有效。其他非字串值，包括 `false`、`0`、陣列與物件，都算格式錯誤，稱為 malformed。R03 接著要求：每個壞行只留一則診斷，仍要繼續讀後面的輸入。

最後才決定整次結果。R11 要求在 EOF 時按順序問：有明確失敗嗎？有就回傳 3；否則有 malformed 嗎？有就回傳 6；再依序檢查沒有有效完成的 4、已完成卻沒有發言的 5，全不符合才回傳 0。前一項成立，就不讓後一項作最後結論，與數字大小無關。R12 則要求只有 3、4、5 附上舊有結尾摘要。

先示範一次推導。輸入有兩行：第一行是一則 agent message，`text` 為 `false`；第二行是有效的完成事件。`false` 不是字串，屬於 malformed，所以第一行只輸出一則診斷，不印出任何內容，也不算發言。第二行記錄有效完成。到了 EOF，沒有明確失敗，但有 malformed，因此結果是 6，而且不附結尾摘要。

接著換你推導一次。輸入的第一行是 agent message，`text` 為數字 `123`；第二行是格式正確的 `turn.failed` 事件；之後直接結束，沒有完成事件。依 R10，`turn.failed` 一定會記錄明確失敗。到了 EOF，明確失敗、malformed 與沒有有效完成三個條件同時成立；依優先順序，明確失敗勝出，所以結果是 3，並附上結尾摘要。這組輸入值得推導，是因為它同時觸發三個條件；只要 EOF 的判定順序寫錯一處，結果就可能變成 6 或 4。

有了預期結果，再帶著三個 review 問題閱讀兩份程式。下表標出兩份實作各在哪裡回答這些問題。請橫向比較：同一項義務，在兩份程式中分別要到哪裡找。 表裡的 dict 是存放資料的 Python 字典；handler 是處理某一類事件的函式，`_State` 則是第二份程式用來保存狀態的類別名稱。

| Reviewer 的問題 | formal-01-A0 | formal-02-A0 | 這次閱讀能確認什麼 |
|---|---|---|---|
| `text: false` 在哪裡被拒絕？ | `main` 的 agent message 分支（115–125 行）：先處理 null，再拒絕非字串，接著排除空字串，最後計入發言並輸出 | `_handle_item`（83–91 行）：先處理 null 與空字串，再拒絕非字串，最後計入發言並輸出 | 兩者都能指出 R05 的路徑，但檢查順序不同 |
| 壞行如何影響後續與 EOF？ | 73–80 行把 malformed 放在函式內的 dict；完成、發言、失敗是其他區域變數；`malformed()` 更新 dict 並印出診斷 | 26–31 行的 `_State` 集中保存四種狀態；60–63 行的 `_malformed` 更新物件並印出診斷，各 handler 共用同一物件 | 狀態存放的位置不同，追蹤路線也不同 |
| 為什麼明確失敗先於 malformed？ | 189–200 行的 EOF 分支先檢查失敗，再檢查 malformed，之後才檢查完成與發言 | 223–233 行依失敗、malformed、完成、發言的順序判斷 | 兩者都能直接找到 R11 的判定順序 |

第一列最值得停下來看。`formal-02-A0` 先處理 null 與空字串，再拒絕非字串。這個順序本身沒有錯，卻讓第一個判斷成為關鍵：如果那一行用 `if text:` 判斷值是真還是假（truthiness），把所有「看起來是空的」值一起放行，`false` 與 `0` 就會被當成沒有訊息，直接略過。這次閱讀確認，兩份程式都能指出 `false` 走向拒絕的路徑；但未來若有人修改這一段，reviewer 要特別檢查的就是那個條件。

`formal-01-A0` 的關鍵則在前兩步的先後：如果有人把非字串的拒絕移到 null 處理之前，`null` 就會被誤判成 malformed。兩種順序都能符合契約，只是 reviewer 需要盯住的那一行不同。這些是 review 的焦點，不是推測模型「讀漏了什麼」。

第二、三列顯示，狀態放在哪裡，就決定 reviewer 要從哪裡開始追蹤。閱讀 `formal-01-A0` 時，要在函式內的 dict 與幾個區域變數之間來回確認；閱讀 `formal-02-A0` 時，則要從 `_State` 出發，檢查各個 handler 如何更新同一個物件。單憑這張表，無法判斷哪一種比較容易維護。「狀態集中在一個類別」聽起來比較整齊，但這次沒有人實際修改過這兩份程式，也沒有量測理解或修改所需的時間。

從這次閱讀可以得出三個 review 動作。第一，核准要針對具體候選作出。即使兩份程式通過同樣的檢查，也不能把第一份的核准直接套用到第二份；換了一份候選，就要重新找出同一項義務的實作路徑。

第二，契約允許這種實作自由。R05 的選擇在別的產品中可能不同；本次已由凍結契約決定，並與其他條文要求保留的既有相容行為一起驗收。只要行為符合契約，用 dict 或類別都屬於合法差異，不能用「和上一份長得不一樣」作為退件理由。

第三，如果團隊是以降低理解或修改成本為理由，想選定一種共同架構，就要另外設計比較；已成立的相容與架構義務，仍依原本的權責執行。比較可以這樣安排：讓兩份候選接受同一項已決定的修改任務，觀察不同接手者理解要求、完成修改與通過驗收所花的時間，並保留失敗結果。這次閱讀沒有做這件事，所以不能用上表估算「少看幾個位置」或「快了幾分鐘」。

兩份原始檔案都以 SHA-256 雜湊值核對版本身分：`formal-01-A0` 為 `7cc9bf5a24969310f18a50aad43ac26d4a59066321b2256ec03806da076dd2b2`，`formal-02-A0` 為 `f2a65e9e26aaa195ab1c0b8caf2c1920cb4e3d2ee3ad2abf30d1620a78008a57`。逐行閱讀筆記位於[靜態閱讀 walkthrough](../research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/static-review-walkthrough.md)。

這組配對的 AST node type cosine 約為 0.994。它先數各種語法節點出現幾次，再比較這些計數的分布方向，沒有保留節點順序。兩份程式即使用了相近數量的判斷與呼叫，也不代表判斷放在同一位置、執行路徑相同。因此數值接近，不能取代剛才逐條找義務的閱讀。

## 八、保存舊結果：下次改了量尺、程式或方法，要重查什麼

四組都是 10/10，這批結果無法替文件排序，但仍然有用。Anthropic 一篇討論 agent evals 的工程文章，把 capability eval 與 regression eval 分開：能力題組要能看出改善，回歸題組則用來防止既有能力退步。文中有一句話說得很直接：「An eval at 100% tracks regressions but provides no signal for improvement.」（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，Capability vs. regression evals；Step 7）。這是廠商的工程實務建議，不是對照實驗；但它為 40/40 找到下一個用途：把這批結果整理成回歸資產，也就是之後有改動時，拿來確認原本能做到的事沒有退步。

整理回歸資產時，要區分三種動作。它們固定的東西不同，能回答的問題也不同。

第一種動作檢查評分程式（grader）。先固定一組行為已核對的測試材料（fixtures）：正對照應被接受，反對照應被拒絕，再換上新版 grader，確認新量尺不會誤拒合法行為，也不會放過已知錯法。四十份通過的候選，可以在目前已核對的行為上作為正對照；它們不是整份契約都已證明符合的實作。為某一項 grader 斷言建立 fixture 時，仍要先核對該斷言需要的行為，而且只有正對照還不夠，還需要已知錯法。

事後建立的教學工具組（workbench）補上了這兩種對照：一份只改寫 malformed 診斷理由的合法輸出應該被接受，六種刻意製造的錯法也都得到預期判定。這些 fixtures 屬於教學裝置，不屬於正式研究的 103 項檢查。

第二種動作檢查新候選。固定同一份契約的 102 個批次案例與 streaming probe，用它們檢查之後每一份新的 `codex_jsonl.py` 修補，確認它仍滿足已涵蓋的要求。這一層回答的是「這份新產物有沒有退步」，與它由人或 agent 撰寫無關。

第三種動作檢查交付方法。模型、執行工具或工具使用政策更換後，要取得新的生成結果，保存它在適用任務上的分布與政策版本，才能判斷新方法有沒有退步。拿新 grader 重評舊的四十份候選，只會更新對那批舊產物的判斷；它沒有檢查任何新候選，也無法取代新的生成。

這三種動作對應不同的變更事件。下表可作為維護時的觸發規則：先在第一欄找到發生的變更，再看要重新確認什麼，以及是否需要新的生成。

| 發生什麼變更 | 要重新確認什麼 | 需要重新生成嗎 |
|---|---|---|
| 需求或相容責任改版 | 重新推導預期值與正反對照，判斷哪些舊結果不再適用 | 重評既有產物不需要；若要比較新版交代的交付方法，則需要。 |
| Grader 改版 | 用已核對的正反 fixtures 檢查新量尺。 | 不需要。 |
| 出現一份新的修補 | 用契約案例檢查這份候選 | 不需要，候選已經存在 |
| Model、harness 或工具政策更換 | 新方法在適用任務上的結果分布 | 需要 |

另外還有一條界線要守住。這批題目、答案與評分資料，已在研究與成稿過程中揭露，並整理成可查核附件。它們仍可以作為回歸資產；但在本流程評估新能力時，不能再把它們當成設計與調整方法時不曾接觸、留到最後評估的題目（holdout）。另存一份副本、換個檔名，或把同一題改寫一次，都不會讓已經看過答案的題目重新變成新題。

若要比較文件或評估新能力，就要另設正式任務與評分資產，並在調整文件的過程中把它們隔離起來。正式比較的結果，也不能回頭拿來修改同一份 Q，再用同一批任務宣稱有所改善。Kapoor 等人也提醒，holdout 要符合想推論的範圍：新任務、新環境與新領域，是三種不同的保留方式（arXiv 2407.01502v1）。

## 九、下一輪比較卡：怎麼派工、怎麼計數、從哪裡選題（尚未執行）

如果前兩層都已處理完畢，團隊仍想知道新增可選自查是否值得成為預設，就需要一場新的比較。以下是我為這個問題設計的比較卡。**這是設計，尚未執行，各正式任務的映射與封存也尚未完成。** 它規劃的是可以使用工具的有限 agent session，和正式研究中四十次無工具的生成是不同流程，不能倒寫成那輪研究的延續。完整欄位與空白範本見[比較計畫範例](../research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/comparison-plan-example.md)；〈總論〉已節錄過[文件改動評估提案](../research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/document-change-proposal.md)的主要欄位。本篇只說明比較卡中的三件事：政策、分母與任務來源。

**先定政策。** 比較必須貼近團隊準備採用的工作流程，因此要先在卡片寫清楚一次工作怎麼進行。每個排定名額都從重建到指定起點的 repo 與全新的 session 開始，並在事先固定的工具、權限與預算內工作。agent 可以讀 repo、執行公開檢查，也可以在同一個 session 內修正程式。session 結束時，先凍結最終候選，再由外部程式執行 agent 無法取得的驗收。驗收結果不回傳給這個 session；失敗時，也不另開新 session 替補。對同一個 task，P 與 Q 只差核定的自查區段，其他要求、起始程式碼、工具設定與預算都相同。

**跨任務先定改寫政策。** Parser 修改卡使用凍結 B 的六題原文，能讓讀者看清一次具體介入；但六題含有 EOF、token 與根層 error，不能直接貼到所有 Python 修補。本設計改為比較一套事前固定的[自查改寫政策](../research/2026-10/same-spec-ten-runs/rebuild-2026-09-28/self-check-transfer-policy.md)：保留六個位置，依每題共同規格 P 的既有條文改寫問題。改寫者只能使用 P 與兩條件都能取得的公開起始 repo 資訊。

沒有對應義務的子項不加入問句；整個位置都沒有對應義務，且 owner 確認本次不需要時，保留「不適用」與理由，不用新要求湊滿六題。每題要記錄有效位置數，不能把六個位置當成六項相同要求。未決政策則先交 owner，補回共同 P 後再建立 P／Q，不能只在 Q 補答案。

每題都要核對完整 P／Q、diff、條文映射與不適用理由，並在試行前封存版本與內容雜湊值。同題、同條件的重複使用逐 byte 相同的 packet；不同 task 的文字可以不同，但建立與審查程序必須相同。不使用隱藏 grader、參考修補、正式結果或 grader 回饋調整 Q，

也不能用流程試跑（pilot）的題目調整 Q，再把那題列入正式比較。pilot 用來先找出流程問題，既然看過答案來調整做法，就要與正式題分開。診斷 pilot 若促使通用範本改版，要先封存新版，再另建隔離的正式集合。如此得到的效果屬於整套改寫與審查政策，不能歸給凍結 B 的某一句話。

目前尚未完成全部目標任務的映射；比較卡因此仍是待補齊的設計，不能直接啟動 288 個名額。

這裡的「相同工具」，指的是相同的可用工具、權限與預算，不要求 P 與 Q 產生一模一樣的工具呼叫序列。如果依政策建立的自查讓 agent 多執行了幾次公開檢查，這很可能正是它發揮作用的途徑，所以應該記錄下來，不必事先排除。不過，記錄操作過程的 trace 只能告訴我們 agent 做了什麼，不能讓我們讀出它為什麼這樣做。

**再定分母。** 假設一個修補任務在 P 下做三次、Q 下也做三次：這是一個 task、六個排定工作，每個工作各有自己的 session。某個 session 內修改五版，仍只占一個工作。下面的 `task_id`、`work_id`、`session_id` 就分別記住這三層身分；欄位尚未填入資料。

```yaml
# 試行紀錄欄位（設計規格，尚未執行；欄位示意，不含資料）
task_id: 原始需求與 repo 起始 commit
work_id: 事前排定的一次 policy 試行（關聯 task_id、P/Q、重複編號、區塊與日期）
session_id: 這個名額的執行階段；每個 work_id 只對應一個，不另開替補
candidate_sha256: session 結束時凍結的最終候選；中間版本只留在 trace
operational_ok: 工具、權限、預算與停止條件是否符合事前規定
external_acceptance: 隱藏驗收的結果與 grader 版本
primary_outcome: operational_ok 與 external_acceptance 同時成立
status: 完成／逾時／候選缺失／未啟動／中止，連同原因
human_handoff: 人工處理與最終交付另列（見第十節），不回填 primary_outcome
```

主要結果的分母，是事先排定的 work_id。它不是 agent 產生過多少中間檔案，也不是最後成功交付的工作數。逾時沒有完成、候選缺失或操作條件不符時，紀錄都要保留，並計為失敗。如果整體預算或環境問題使部分名額沒有啟動，就另外標記狀態並保留原排程；這時暫停採用判定，也不宣稱已完成原規模的比較。grader 若出現致命錯誤，就暫停整輪；修正後另立 grader 版本與重評紀錄。

**分派與環境。** 如果 P 都在星期一執行、Q 都在星期三執行，這兩天之間模型服務或機器狀態的任何變化，都可能被誤讀成文件差異。NIST 的工程統計手冊建議，把已知且可控制的干擾因素分成區塊（blocking），在每個區塊內安排要比較的條件；其他因素則靠隨機化，降低它們和條件混在一起的機會（[NIST/SEMATECH e-Handbook, §5.3.3.2](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)）。因此，比較卡依任務與執行日形成區塊，在區塊內隨機安排 P、Q 的順序，並記錄並行度與實際起訖時間。

正式研究同樣採四路並行，並預先排成 10 個區塊、在區塊內打亂順序；但實際執行時段互相重疊，不是同步配對的時間窗，所以不能倒寫成已經控制了時間因素。

agent 可以使用工具之後，環境的影響會更直接，因此資源配置、kill threshold、模型與 harness 版本，都要在執行前記錄；供應商沒有開放控制的取樣設定，則要列為無法固定的條件。

**任務從哪裡來。** 先列出固定期間內所有符合範圍、實際進來的工作，再從中選題；這份可供選題的完整清單就是抽樣框，本例的範圍是 Python 工具 repo 中，行為與相容責任都能明確約定的修補。清單要包含尚未完成、暫時無法驗收與後來中止的工作，並記錄每項工作的來源、狀態，以及納入或排除的理由。規格尚未決定，或暫時無法建立公平驗收的工作，也要留在清單上；它們可能需要先交給 owner 澄清。若最後只能比較可明確驗收的子集合，結論就只適用於那個子集合，不能用加權方式補回沒有觀測到的工作。

任務可以依工作類型、外部相依、狀態與串流處理，以及例外密度分層；若刻意多抽某個稀有類型，就要另外報告分層結果與事先選定的權重。

納入正式比較之前，每題還必須完成共同 P 的確認、自查映射、P／Q 審查與封存。映射遇到未決行為時，要回到共同要求處理；不能在看到正式失敗之後，才把該項追認為不適用。

如果手上只有已合併的歷史修補，就另立一個回溯測試（backtest）：以修補前的 commit 作為起點，將已知的修補內容（patch）、答案與 grader 隔離在 agent 無法取得的環境，結論也只適用於這批回溯題目。已經看過答案的題目，即使改寫過，仍然不是新的保留題。

選題方式會決定結論能推廣到哪裡。METR 在 2026 年 2 月的研究更新中，把研究擴大到 57 位開發者、143 個 repo 與 800 多個任務；但作者主動說明，哪些開發者與任務進入研究、報酬的變動，以及 agent 並行時的工時歸屬，都讓他們無法可靠估計目前的效果（[METR, 2026](https://metr.org/blog/2026-02-24-uplift-update/)）。這項研究量測的是生產力，不是文件效果。它提醒的是：即使任務分派已經隨機，最前面「哪些工作進入研究」的篩選，仍會改變結果的適用範圍。這也是比較卡堅持保留完整清單與排除理由的原因。

**試跑題與正式題分開。** 診斷 pilot 使用不會進入正式集合的任務，用來檢查 reference、正反對照、grader 與執行腳本（runner）是否正常。pilot 可以刻意涵蓋邊界情況與已知錯法，因為它的目的，是找出量尺與流程的缺口。不過，這些刻意挑選的錯法出現頻率，不能當成日常工作的失敗率，也不能用來估算正式比較辨認出指定差異的能力，統計上稱為檢定力（power）。在調整文件期間，正式任務與評分資產都要隔離。

## 十、人工接手與規模：288 個名額買不到的東西

比較卡的主要結果，只回答 agent 交出了什麼。EM 還要付出的，是接手的人所花的時間。這一欄最難記錄，也最常被省略。

**主要結果與人工補救分欄。** 每個 work_id 的 session 結束後，人工 review、必要的驗證、有限修補與最終交付，都要完整記錄；修補上限由 owner 事先決定。人工修改會產生新的候選 hash，並連回原本的 hash。即使最後交付成功，原 session 的主要結果也不變。因此紀錄裡會有兩個比例：agent 原始候選的通過率，以及經過人工處理後的最終交付率。兩者分開計算，人的補救才不會掩蓋方法本身的失敗。

**時間要怎麼記。** 人工時間要分開記錄自查映射與核對、讀碼、修正、核准、文件修訂與維護，以及被動等待，並事先定義每一段的起訖與中斷方式。等待 agent 時，如果同時在做別的工作，那段從開始到結束經過的時間（wall-clock）就不能再算成人工投入。

METR 在 2025 年 7 月的隨機對照研究中，把「完成」定義為開發者相信這項工作能通過 review，包括風格、測試與文件（[METR, 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)）。那份結果反映 2025 年初的工具情境，頁面也已標示為過時。前一節提到的 2026 年更新則說明，agent 並行工作時，工時該歸給誰本身就很難判定。

這份比較卡也先定義完成點，但不沿用 METR 的終點：session 結案先保存原候選，接手階段則繼續記錄 review、有限修補、核准與最終交付。每個階段都分別記錄主動投入幾分鐘、總共經過多久，不能到「可以交給 review」就停表，漏掉後續接手成本。

計算每份合格交付的人工投入時，分子要包含全部排定工作已花掉的時間，包括驗證、失敗處理與有限修補；失敗或沒有交付的工作也要算進去。分母才是最終合格交付的份數；沒有合格交付時，就不計算這個比值。

例如兩個排定工作分別花了 6 與 4 分鐘，最後只有一份合格交付；先假設沒有其他共同成本，每份合格交付的投入就是 (6＋4) ÷ 1＝10 分鐘，不能只保留成功那份的時間。每個排定工作的平均則是 5 分鐘。

另外還要保存每個排定工作的平均人工投入，避免單一比值遮住總工作量。共同準備、自查映射與維護費用如何分攤，也要在分析前定義；它們發生在模型執行之前，並不表示可以省略。

**深讀要事先抽樣。** 不必深讀每一份候選，但抽樣規則要在看到結果之前訂好：先把任務、P／Q 條件與通過或失敗等結果類別列為分組，訂出各組如何抽取；這就是分層抽樣，取得驗收結果後，再依程序抽取，並保留抽樣機率與缺失紀錄。

reviewer 的分派與閱讀順序也要事先安排；能遮蔽的 P／Q 標籤就要遮蔽。程式風格本身也可能透露條件，這項盲化限制要照實記錄。同一個人如果先讀過同題的另一份實作，第二次可能因為更熟悉題目而變快；這種學習效應不能誤算成文件的效果。分析時要保留哪些資料來自同一位 reviewer、哪些來自同一個 task，不能把這些共用經驗的觀察當成彼此無關。

**門檻是示例，不是標準。** 比較卡用兩個門檻示範如何判讀：Q 至少比 P 高 5 個百分點，例如從 80% 到 85%；每份合格交付新增的人工時間，區間上界不超過 2 分鐘。這兩個數字都是為了說明而假設的，不是業界標準。團隊應依自己的工作、損失與預算訂出門檻，並寫下理由；例如，維護一段自查需要多少人力，每一次不合格交付平均造成多少重做，這些才是門檻的依據。

**288 個名額，未必看得清想知道的差異。** 比較卡的預算草案是 48 個任務 × 2 個條件 × 3 次重複，共 288 個排定名額。這個數字說明團隊願意花多少，卻不說明它能看清多小的差異。

以下是一個粗略的假設計算，只用來說明規模與精度之間的距離，不是這份設計的 power 分析。假設 P、Q 的成功率都在八成左右。若把每組 144 次試行當成彼此獨立，Q−P 的 95% 區間半寬，也就是區間從中心到一側的距離，約為 1.96 × √(2 × 0.8 × 0.2 ÷ 144)，大約 9.2 個百分點。

若同一任務的三次結果幾乎總是相同，有效資訊就接近每組 48 題，半寬會擴大到約 16 個百分點。P、Q 在同一批任務上配對，可以抵銷一部分任務難度造成的變動，實際區間可能更窄；至於能窄多少，要看改善在不同任務之間有多一致。

把這兩個粗略數字放在 5 個百分點的門檻旁邊，就會看到一個應該事先知道的結果：如果真實改善只有五、六個百分點，這個規模很可能得到「未定」。這不代表設計失敗；團隊應在執行前就把它當成可能的結果。

團隊可以接受這個可能性，也可以依目標效果、任務差異與同題相依的合理假設，重新評估任務數與重複數；或者重新檢查門檻的實務意義，甚至暫時不做比較，先在原人工核准下進行有限試行。不論選擇哪一種做法，都要在看到結果前決定。正式執行前，仍需依合理的基準表現、效果大小與同任務相依程度，換用幾組合理假設試算，確認結論有多依賴那些假設；這一步稱為敏感度分析。

## 十一、決策紀錄：聯合條件，與資料不足時的出口

比較卡記錄如何取得證據；決策紀錄則寫明證據回來後，由誰依什麼條件作出哪個決定。兩份紀錄要分開保存；否則，團隊很容易在看到結果之後，才回頭調整「什麼算成功」。判定規則要在執行前封存。正式研究在執行前做過本機封存，但這不是交由第三方在執行前保存研究計畫的預註冊，部分作業系統資訊也是開始後才補上。下一輪若要讓判定規則更可信，我建議由承擔決定的 owner 以外的人保存封存版本。

**採用要同時滿足哪些條件。** 若要以改善交付為理由，把可選自查採為預設，先看效果。把 Q−P 的估計區間寫成 [L, U]，L 是下界，U 是上界。沿用前面的 5 個百分點示例：整個區間都在 5 之上，才支持改善超過門檻；整個區間都在 5 之下，則排除了達到門檻的改善；碰到或跨過 5 都屬於未定。〈總論〉第九節列有完整的假設區間例子。

效果之外，還要同時看人力、其他成本與必要條件。每份合格交付新增人工時間的區間上界，不能超過事先上限；模型費用、文件維護也要納入。沒有越權、驗收未被改動，以及補救負擔可承擔等方法層條件，由 owner 在看到結果前決定，不能用平均改善抵銷。已決定的必要行為與相容責任則照原要求執行，不受可選自查的效果門檻支配。

先用人力的三個假設區間，練習一次這個判斷。若新增時間的區間上界為 1.8 分鐘，就符合本例「不超過 2 分鐘」的條件；上界為 2.4 分鐘時，只能說尚未確認符合，不能單憑上界就斷言人力已超限；若連下界都高於 2 分鐘，才支持負擔超過上限。這些只是讀法示例，並非已量到的時間。

這幾個條件不能互相代替。效果達標，但人力區間下界已超過上限時，結論是「目前不採用」，不能說成文件沒有改善效果。效果還未定時，也不能因為「人力看起來還好」就改判為採用。

也要分開判斷候選是否符合必要條件，以及方法是否達到採用門檻。單份候選若違反保序、保留重複列這類已約定的要求，就拒絕那一份，不能用其他項目的得分抵銷；方法比較則要如實保存每次試行的通過與失敗，不能在事後加上「觀測必須零失敗」的門檻。

**缺人工資料時，算不出投入是否值得。** 本輪只有依 CLI 牌價估計的生成費用，沒有任何人工時間。缺了讀碼、修正、核准與維護的時間，就算不出投資報酬（ROI）；AST 相似度與代理 review 也補不了這個缺口。缺少人工資料的比較，不論效果看起來多好，都無法滿足聯合條件。

資料不足，不代表只能停在原地。〈總論〉第十節區分了先試走流程的診斷 pilot、在小範圍真實工作中試行的部署 trial，以及預設採用。在人工資料還沒補齊前，團隊可以進行有限部署 trial：維持原本的人工核准，只在指定範圍的工作中，依同一套事前政策附上適用的自查，事先寫明 owner、停止條件與回復方式，並記錄 reviewer 實際多做了哪些事。

這項安排可以撤回，也能替之後的比較先測試紀錄流程，例如時間該如何分段、深讀該如何抽樣。它不是隨機比較，結果不能當成文件效果已經成立的證據。它的價值在於，讓團隊不必改變授權，就能開始累積真實工作的觀察。

下面三份決策紀錄示範目前的證據能把三個決定推進到哪裡。請橫向閱讀：第二欄是手上真正有的證據，第三欄是依這些證據能作出的判定，第四欄則列出若要改變判定，還缺什麼、由誰補。

| 決定事項 | 目前證據 | 判定 | 缺的證據與負責人 | 下一次檢視 |
|---|---|---|---|---|
| 正式四十份結果怎麼用 | 四組各 10/10，通過 103 項檢查；題目與答案已在研究／成稿過程揭露 | 保存已核對行為的候選 fixtures 與契約案例；不替文件排序 | 保存資產不需新生成；檢查方法變更仍需新生成，新比較另設隔離正式題（eval owner） | grader、需求或 model／harness 變更時 |
| 自查改寫政策是否成為 Python 工具修補的預設 | 原研究的 B 同時加入理由與自查，效果拆不開；跨任務映射與封存尚未完成，P／Q 尚未執行，也沒有人工資料 | 尚不能判定；維持現狀，或在原核准下有限試行 | 完整任務清單與映射、比較結果（eval owner／EM）、人工接手及維護紀錄（reviewer） | 準備與比較完成，或達到事先訂好的費用與日期界線時 |
| CSV 匯出修補是否預設附上自查（假設案例） | null 日期政策已決；oracle 已修正；一份擅自去重的候選被拒絕（假設） | 方法效果尚不能判定；候選層問題已處理。 | 匯出類工作清單與比較（eval owner）；人工紀錄（reviewer） | 工作量足以建立抽樣框時 |

第一列決定的是保存哪些資產，這個動作不需要新生成；它不表示三層回歸的證據都已具備。要檢查新候選，仍要實際驗收那份候選；要檢查 model 或 harness 的交付方法，仍要依事前任務與 trial 分布取得新生成。

第二列的判定則是「尚不能判定」：正式研究沒有提供可辨別自查效果的比較，也沒有人工資料。這時維持現狀是有理由的決定，在原核准下有限試行也是；兩者都不需要宣稱自查已經有效。

第三列用〈總論〉的 CSV 假設案例，示範同一套判斷如何套用到另一種工作。假設 owner 已決定 null 日期輸出空欄，QA 也已把逐 byte 比對改成先解析，再核對標題列（header）與完整、有序的資料紀錄（records）。之後，某一份候選擅自刪除重複列，被驗收拒絕。這時有人提議：「既然會出錯，就在所有匯出修補的交代裡加上自查。」

先分清楚哪些部分已經處理。保序與保留重複列是呼叫端已要求的行為，屬於契約；不論是否採用自查，每一份候選都必須做到，違反就拒絕。這一層已由驗收處理。去重這個輸出差異本身，也無法說明模型是漏讀要求、理解錯誤，還是選錯了輔助函式（helper），更不能證明補上一段自查就會改善結果。

剩下的提議，才是本文要處理的方法層問題，所以要回到第六節的表格。眼前的處境同時屬於「資料不足」、「任務不代表目標工作」與「人力未知」：只有一個假設工具、一份被拒絕的候選；沒有匯出類工作的清單，也沒有任何人工紀錄。第三節那種同題重複，無法單獨補上跨任務代表性與人工資料的缺口。這時需要的是匯出類工作的 incoming 清單、P／Q 在相同工具與預算下的比較，以及 reviewer 的接手紀錄。

還有一個容易照抄的地方要避免：這個工具只要求交出完整的 CSV 檔案，沒有要求逐筆即時輸出。因此，這份比較不應採用 parser 的 EOF 前 streaming probe。自查也要遵守相同界線：不能把 parser 的第一題原句貼進 Q，平白增加串流義務；沒有對應承諾的位置依政策標示不適用。保留列序與重複列的自查，則可連回共同 P 中已成立的要求。

在那之前，團隊可以作的決定很清楚。若 owner 願意，就先確認各題共同 P 與自查映射，在少數匯出修補中附上適用的自查，維持原本的人工核准，寫下停止條件，並記錄 reviewer 花費的時間。這份紀錄的用途，是讓之後的比較有一套可用的流程，而不是證明自查有效。

**撤回與重新檢視。** 採用為預設之後，也要把重新檢視的觸發條件寫進紀錄。需求補齊了，或驗收已能攔下某種錯法時，都值得重新檢視。不過，驗收能攔下錯誤，只證明它具備偵測能力，不會自動讓一段預防性的自查變得多餘。自查仍可能減少失敗、重做與人工接手；移除之前，要先確認移除後的這些負擔仍可接受。若自查與任務要求衝突、比較結果已排除值得投入的改善，或人力超過事先訂好的上限，才依相應理由撤回或縮小適用範圍，並記錄撤回時的版本。

## 十二、結語：十次都通過之後

回到開場的問題：四組都十次全過，下一筆預算該花在哪裡？

看到這批結果時，最自然的提議是再多跑一點。讀完前面幾節，我會先問這筆預算想改變哪個決定。如果要估計同一個凍結修補任務在固定交付政策下的成功率，同題重複可以補資訊；若後續仍全過，前面那個全成功公式的區間下界會繼續升高；若出現失敗，就要依新的成功次數重算。如果要決定的是某段交代是否跟著所有 Python 工具修補一起使用，同題重複就不能單獨回答；這時需要的是能代表那類工作的任務、保留 task ID 的紀錄，以及真人接手所花的時間。

所以我的立場有條件。如果我是 eval owner，而且要決定的是跨任務的預設做法，面對四組 10/10，我會先把這批結果依三層回歸用途整理成資產，標明已在研究與成稿過程揭露，不再是本流程的未見保留題。方法層回歸仍需新生成，不能只重播舊候選。接著，我會把預算放在能改變決定的地方：量尺有疑點，就先修量尺；任務範圍不清，就建立 incoming 清單；要討論人力，就安排真人觀測。

如果我是 EM，我會要求每份以改善交付為理由新增可選自查的提案，先寫清楚改寫政策、分母、門檻與人工紀錄方式。必要義務仍按需求執行。在比較結果回來，而且效果、人力與其他事前條件同時成立之前，我會維持現狀，或只在原人工核准下有限試行，不把它推成所有任務的預設。

如果結果落在「未定」，就寫下還缺哪一種證據，依事前規則決定是否另作比較，不一路追加到出現想要的答案。

這些判斷建立在一個窄案例上：一支 parser、四份交代，以及四十次無工具的一次生成，全部通過 103 項檢查。這個案例能示範如何讀分母、區分三種變動，以及把通過的候選整理成回歸資產；但它不能替任何文件排名，也不能替可使用工具的流程背書。比較卡上的 288 個名額、5 個百分點與 2 分鐘，都是尚未執行的設計與示例，不是業界標準。各任務的自查映射與 P／Q 封存也尚未完成，CSV 案例則是教學假設。

《綠燈不是驗收》從一次產物的驗收，談到一類任務的授權證據。這個系列把同樣的紀律帶回交代本身：需求先由有權決定的人確認，候選再由能分辨已知錯法、接受合法差異的量尺驗收。若要以改善交付為理由，把額外的可選自查設為預設，還需要與目標工作一致的比較。十次都通過，是這一個固定任務與有限檢查下的結果。當決定已經超出這一題，下一筆證據就要補上任務範圍、量尺盲點與人的投入。

> **十次都通過之後，先問下一筆證據要改變哪個決定。同題重複不能單獨回答可選自查是否值得跨任務採用；需要先固定改寫政策，再取得對應的任務與人工證據。缺少人工資料時，不計算 ROI，可以維持現狀，或在原本的人工核准下有限試行，記下之後比較需要的資料。**
