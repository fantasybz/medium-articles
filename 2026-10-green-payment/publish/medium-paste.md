# 綠燈不是驗收（四）付款實作篇：買一瓶無糖純喫綠茶，從 Review 約束走到 mutation score

> **TL;DR** — 想買一瓶無糖純喫綠茶，付款畫面卻遲遲沒有回應。再按一次會不會多扣一筆？這篇用一筆示範售價 35 元的訂單，把「綠燈不是驗收」的三道閘串起來：先依風險挑選 reviewer 與需要深讀的變更，再從 Review 意見中挑出值得長期保護的約束，把它們寫成測試，最後選擇相關程式碼做 mutation testing。隨文附上可執行的 Python 範例。實際執行七個指定 mutant，只測正常購買時殺死 2 個，mutation score 是 28.6%；補到 8 個測試、只缺逾時案例時，分數已達 85.7%，卻仍抓不到「把不確定的付款標成成功」；完整 9 個測試辨識出這七種變異。100% 只描述這次選定的範圍，也不能替並行、重新啟動與真實金流整合作保。

> 系列導覽：[總論：綠燈不是驗收](https://medium.com/p/582f24223eea) → [一、測試篇](https://medium.com/p/b01055139451) → [二、Review 篇](https://medium.com/p/ccbf0cbe2691) → [三、可靠度篇](https://medium.com/p/3c64a9622777) → **四、付款實作篇（本篇）**。本篇可以獨立閱讀，總論與前三篇則提供方法的研究背景與組織安排。

## 一、先把那一瓶綠茶買清楚

先想像一個很小的情境。你選了一瓶無糖純喫綠茶，確認金額，按下付款。畫面轉了一會兒，沒有顯示成功，也沒有明確說失敗。你手指停在付款按鈕上，接下來那一下，到底是在查詢上一筆交易，還是重新付一次錢？

這是為了教學而設計的情境，不是我的事故紀錄，也不是特定商家的付款實作。以下把示範售價設成 **35 元新台幣**，不代表商品的實際售價。金額以整數「元」表示；折扣、稅額、其他幣別與找零先不放進這個例子。

我想讓這一瓶綠茶承擔一件事：把抽象名詞還原成可以觀察的結果。對購買的人來說，期待很具體：訂單裡是無糖綠茶，金額是 35 元，不會因為重按按鈕多付一次，也不會在商家還不知道付款結果時，就收到一張宣稱成功的收據。

範例的起點，是後端已經完成身分授權、從伺服器讀出的訂單。商品代碼 SKU 用來辨識品項；`order_id` 辨識訂單；`key` 是這次付款嘗試的 idempotency key，讓重送的請求能對回同一次操作。這三個識別不能混為一談，也不把瀏覽器傳來的任意價格當成權威資料。

為什麼要先花時間分清楚識別？因為「再按一次」在畫面上是同一個動作，背後卻可能代表兩種意圖。如果只是上一筆請求沒有收到回覆，就應沿用原本的訂單與 key；如果真的要再買一瓶，則是另一張訂單與另一次付款嘗試。只比較 SKU 與 35 元，系統無法區分這兩件事。相反地，若每次按鈕被按下就產生新 key，原本想重試的人也可能被當成開始另一筆付款。後面的 C2，就是要保護這個差別。

```python
# 示範資料：已授權、由伺服器讀出的不可變訂單。
# 完整程式在 examples/tea_payment/，不會呼叫真實金流。
order = Order(
    order_id="tea-001",
    sku="UNSWEETENED_PURE_GREEN_TEA",
    amount_ntd=35,
)
key = "buy-tea-001"
```

先由人確認這份付款契約，再請 agent 實作。正常付款要把訂單金額送到金流端，收到成功回覆後回傳 `PAID`，收據保留同一個訂單、SKU、金額與付款識別。相同訂單與 key 再送一次，要取得既有結果，不再發出新的扣款請求。key 不能移到另一張訂單；已開始付款的訂單，也不能靠換一個 key 或改寫內容重新開始。

拒絕與逾時則要分開。明確拒絕是 `DECLINED`；逾時只是我們沒有收到確定的回覆，金流端可能已經扣款，因此維持 `PENDING`。這份示範不會在逾時後自動重新扣款，也沒有實作查詢與對帳流程；後續必須由另外設計、驗證過的流程處理。

本例也約定：其他未分類的 provider 例外要向外傳遞，交由呼叫端處理，不在 Checkout 裡擅自轉成付款成功或失敗；已登記的嘗試則保留 `PENDING`，讓相同請求重送時不再呼叫金流。這是 C4 對未知結果的另一項要求。如此既保留需要調查的錯誤，也保留重送所需的紀錄；本例沒有實作呼叫端的錯誤呈現與復原流程。

這些是本例約定的行為，不是所有金流 API 共同採用的狀態名稱。[Stripe 的官方文件](https://docs.stripe.com/error-handling#connection-errors)也提醒，連線錯誤留下的是不確定結果；但在它的 idempotency 契約下，可以使用相同 key 安全重試。這份示範沒有實作 provider 端的冪等能力，因此先保留待確認結果。兩者的差別在於重試受到什麼保證，不能把這裡的保守處理推成「真實金流一律不得重試」。

## 二、先挑誰來 Review，再決定要讀哪裡

假設 agent 送來一個 PR，說明是：「付款 API 現在支援重送，相同請求會拿到既有結果。」這句 intent 讓 reviewer 知道目標，卻還沒有回答實作是否達到目標。

我會先看改動碰到什麼責任：訂單識別、金額、扣款呼叫、付款狀態，以及用來驗收它們的測試。這些共用邏輯可能影響許多筆訂單，所以不能因為眼前的綠茶只值 35 元，就把整個 PR 當成低風險改字。反過來說，若 PR 真的只修改不影響付款流程的說明文字，也不該只因資料夾叫 `payment` 就要求相同深度的審查。

下面是這個付款邏輯 PR 的分工建議。角色可以由同一位具備相應能力的人兼任；需要的是責任與能力，不是湊滿職稱。

Reviewer agent 可以先整理 diff、找出扣款呼叫與例外處理，或提出反例，讓人更快進入問題。但它不能自行確認付款契約，也不能把自己的 approve 當成人類核准。沿用 Review 篇的建議，高風險付款邏輯由任務指派者以外、具備相關責任的人核准。

具體挑 hunk，也就是 diff 裡的一段變更時，我會優先讀「既有付款是否存在」的判斷、「哪一個金額被傳給金流」、「例外如何變成付款狀態」，以及這幾處相連的呼叫者。不能只讀被改色的那一行：guard 的位置、資料從哪裡來、例外在哪裡被吞掉，都可能在相鄰的程式碼裡。測試與驗證設定的變更也要一起看，確認這份綠燈沒有靠放寬斷言取得。

以逾時分支為例，reviewer 先看到的是一個例外處理，接著才要判斷它能代表什麼。第一步是向外追：`charge()` 丟出逾時時，有沒有保證尚未扣款？本例沒有。第二步是向內看：如果程式在這裡填入 `PAID`，依據是什麼，又有沒有收到付款識別？缺少成功回覆與付款識別時，「成功」就是實作多作的承諾。第三步才是回到測試：現有案例有沒有製造這種不確定結果，並檢查對外狀態？這樣讀，才知道該補的是情境，而不是替同一條正常路徑增加更多斷言。

三種審閱責任也因此接得起來。Payment owner 確認未知結果應保留 `PENDING`；QA reviewer 把「扣款前或後失去回覆」安排成可觀察的案例；整合 reviewer 接著追問，真實 provider 如何查回結果、誰負責處理久未確認的付款。這三個判斷可以出現在同一次討論裡，但不能只留下一句「測試已通過」，讓後續的人猜測哪些問題已有人確認。

[Google 的 Code Review 指引](https://google.github.io/eng-practices/review/reviewer/looking-for.html)要求 reviewer 理解受託審閱的程式碼、必要時擴大閱讀脈絡，並找具備相應能力的人處理專門問題。上面的三種責任是我依付款情境提出的分工，不是 Google 規定的三人編制。誰只審了測試、誰確認了付款狀態，都應在核准紀錄裡寫清楚。

如果目前只有正常購買的測試，這個 PR 還缺少足夠的可機器驗證證據。我會先深入審閱相關 diff，補出重要約束；等報告真的涵蓋了那些要求，才有依據調整往後的審閱方式。不能先把人撤掉，再希望分數補上原本沒有人確認的事情。

## 三、哪些 Review 意見值得留下來變成測試？

現在假設 reviewer 留下幾則評論。以下都是教學用的評論，不是從某個真實 PR 複製出來的紀錄。

第一則問：「相同訂單連按兩次，會不會發出兩次扣款？」第二則問：「如果重試時 key 被換掉，或被拿去付另一張訂單呢？」第三則提醒：「逾時之前，金流端可能已經扣款。」另外還有兩則：「這個區域變數換個名字比較清楚」與「這個活動要不要提供退款？」

它們都可能有價值，但要走向不同的下一步。挑選的依據不是評論寫得多長、按讚數多少，也不是只收集曾經造成事故的問題。我會依序確認：它想避免什麼後果、要求是否跨越這次 PR 仍然成立、預期結果由誰確認，以及能否用穩定、可維護的方式觀察。

📌【在此插入表 table-02.png】

一條高影響的要求，即使第一次被提出，也值得保護；不必等第二次扣錯款才算「反覆出現的規則」。另一方面，單次遷移的暫時限制可能只需要有期限的檢查，不應永遠留在 CI 裡。

挑中的評論還要改寫成一張可追問的規則卡。以 C4 為例，來源是本次示範 Review 的「回覆遺失」風險，適用範圍是付款嘗試與重送，要求是「逾時維持結果未知，不標示成功，也不自動再扣一筆」。逾時測試是 `test_timeout_stays_pending_without_another_charge`；C4 也包含第一節約定的未分類例外處理，由 `test_unexpected_provider_error_preserves_pending_attempt` 驗證例外向外傳遞、前置紀錄保留與重送不再扣款。維護責任由 payment owner 承擔；provider 契約或對帳流程改變時，重新檢視這條規則。

真正的團隊應補上實際 PR、需求或事故的連結。`owner` 不是為了填欄位，而是讓下一位 reviewer 知道誰能解釋或修改預期結果。很久沒失敗，也不能單獨成為刪除付款安全規則的理由；可能正是因為規則持續有效，錯誤才沒有再進來。

從評論走到規則，最需要補的是預期結果。「請處理 timeout」還不夠清楚：是回傳失敗、重新扣款，還是等待查詢？如果沒有先決定，agent 可能合理地寫出三種不同答案。C4 要補成：第一次呼叫逾時時回傳 `PENDING`，不附上成功付款識別；相同請求重送時，回傳同一個結果，而且 provider 的呼叫次數仍為一。這樣才有可以共同檢查的答案。

「扣款前逾時」與「扣款後逾時」還要一起保留。前者避免把未知結果一律想成已經付錢；後者避免把例外一律想成沒有副作用。兩種情況對應相同的應用程式狀態，理由是應用程式掌握的資訊相同，而非金流端發生的事相同。若日後接上查詢流程，owner 應重新定義哪些新證據允許 `PENDING` 轉為確定結果，並增加對應測試。規則可以隨契約演進，修改理由也要跟著留下來。

## 四、把約束寫成會辨識錯誤的測試

**Constraint tests 描述的是測試的來源與保護責任，不是一種與功能測試互斥的技術。** 「同一筆付款不能重複扣款」既是產品行為，也是 reviewer 決定長期保留的約束；可以用 unit test、integration test 或其他合適的檢查來實作。把兩者分開報告，有助於追蹤責任，不能因此宣稱它們保護的是完全不同的世界。

為了比較測試選擇，本例從兩個正常購買的測試說起：收據保留無糖綠茶的 SKU、35 元與付款識別；假金流記錄到一筆 35 元的成功扣款。接著把另外七個測試納入比較，涵蓋 C1 的重送、C2 的三種錯誤關聯、C3 的拒絕，以及 C4 的逾時與其他連線例外。C2 一條規則對應三個案例，所以規則數與測試數不必相同。

這裡的 `FakeGateway` 是測試替身。它分別記錄每一次扣款呼叫 `calls` 與成功扣款 `captures`，**刻意不替應用程式去重**。如果替身偷偷幫忙攔掉重複請求，應用程式即使少了 guard，測試也可能仍然全綠。

以下節錄完整範例中 `ConstraintTests` 的第一個測試。先用相同訂單與 key 呼叫兩次，再檢查結果與副作用；預期的 35 元直接來自前面約定的案例，沒有呼叫待測程式幫自己算答案。

```python
def test_same_attempt_is_not_charged_twice(self):
    gateway = FakeGateway()
    checkout = Checkout(gateway)
    first = checkout.pay(tea_order(), "buy-tea-001")
    second = checkout.pay(tea_order(), "buy-tea-001")
    self.assertEqual(second, first)
    self.assertEqual(gateway.calls, [("tea-001", 35)])
    self.assertEqual(gateway.captures, [("pay-1", "tea-001", 35)])
```

只比較兩次收據相同還不夠：程式也可能先多扣一次錢，再回傳舊收據。因此測試另外檢查金流呼叫與成功扣款的紀錄。反過來，只有 `assert checkout.pay(...)` 也太弱；收到任何非空物件就會通過，並沒有確認關鍵行為。

下一個測試保護 key 的邊界。第二張訂單不是第一張訂單的重送，必須拒絕；而且拒絕不能發生在另一筆扣款之後。

```python
def test_key_cannot_move_to_another_order(self):
    gateway = FakeGateway()
    checkout = Checkout(gateway)
    checkout.pay(tea_order(), "buy-tea-001")
    with self.assertRaises(PaymentConflict):
        checkout.pay(tea_order("tea-002"), "buy-tea-001")
    self.assertEqual(gateway.calls, [("tea-001", 35)])
```

最容易漏掉的是逾時的替身怎麼安排。完整測試涵蓋「還沒扣款就逾時」與「**金流已經記錄一筆成功扣款，回覆才遺失**」兩種情境。下面把後者單獨寫出來，完整程式則使用 `subTest` 同時涵蓋兩種情境。應用程式不知道那筆扣款是否完成，所以對外保留 `PENDING`。重送仍然查到同一個待確認結果，不產生第二次扣款。

```python
def test_timeout_stays_pending_without_another_charge(self):
    gateway = FakeGateway("timeout_after_capture")
    checkout = Checkout(gateway)
    first = checkout.pay(tea_order(), "buy-tea-001")
    second = checkout.pay(tea_order(), "buy-tea-001")
    self.assertEqual(first.status, "PENDING")
    self.assertIsNone(first.payment_id)
    self.assertEqual(second, first)
    self.assertEqual(gateway.calls, [("tea-001", 35)])
    self.assertEqual(gateway.captures, [("pay-1", "tea-001", 35)])
```

`captures` 有一筆、收據卻沒有 payment ID，正是這個 fixture 想保留的不對稱：測試能看見替身內部發生的事，應用程式只能依它收到的回覆判斷。不能因為測試知道扣款成功，就要求應用程式在失去回覆時也宣稱成功。

讀這個測試時，先看安排的情境是否真的走到付款程式：兩次呼叫都經過 `Checkout.pay()`。再確認預期答案的來源是已確認的 C4，沒有複製當前實作的回傳值。最後看斷言如何觀察承諾與副作用：它既檢查 `PENDING`、沒有付款識別及重送結果相同，也檢查 provider 只收到一次請求。少了其中一邊，就可能只保護到一半。

例如，把 `first.status` 與 `second.status` 比成相同，看起來也在驗證重送；但兩次都錯誤回傳 `PAID` 時，一樣會通過。預期值必須有獨立的來源。另一方面，若替身在收到第二次呼叫時自行回傳舊結果，即使 `captures` 仍只有一筆，應用程式也可能已經多呼叫一次。這就是分開記錄 `calls` 與 `captures` 的理由：先讓錯誤有機會被看見，測試才能判斷它。

## 五、先看付款程式如何回應，再故意改壞它

範例把付款結果存在記憶體裡。每次先確認 key 沒有被拿去付另一張訂單，再查這張訂單是否已有付款嘗試；有的話核對 key 與訂單內容，直接回傳既有結果。只有新的、有效的嘗試才會呼叫金流，並且在呼叫前先留下 `PENDING`。

以下節錄扣款與狀態處理，完整 guard 與資料結構在隨文程式碼中。這幾行值得 reviewer 深讀，因為一個看似方便的例外處理，就能把「不知道結果」改成「已付款」。

```python
try:
    payment_id = self.gateway.charge(order.order_id, order.amount_ntd)
except Declined:
    receipt = replace(receipt, status="DECLINED")
except TimeoutError:
    receipt = replace(receipt, status="PENDING")
else:
    receipt = replace(receipt, status="PAID", payment_id=payment_id)
```

若要理解這段程式，先沿著回覆種類讀這張圖。它描述的是本例在付款邊界能知道的狀態，不是金流端的完整交易生命週期。

📌【在此插入圖 diagram-01.png】

圖中保留 `PENDING` 的分支，沒有直接通往 `PAID` 的箭頭。查詢與對帳需要新的證據，這份示範尚未實作。保存 `PENDING` 是為了讓後續處理有明確的起點，不是把未解決的付款永遠擱著就算完成。

再把「已扣款、回覆遺失」沿時間走一遍。Checkout 先登記這次嘗試，接著呼叫金流；替身記錄成功扣款後丟出 `TimeoutError`，Checkout 才回傳 `PENDING`。當相同請求再次進來，程式先找到那筆嘗試，因此能在再次呼叫金流之前返回。重送是否安全，依賴的是前面已經留下什麼紀錄，以及查詢紀錄發生在哪個位置。

這裡有一個容易被忽略的細節：對已捕捉的 `TimeoutError`，程式在例外處理之後還會寫回付款嘗試。假如把呼叫前的紀錄刪掉，只測這個逾時分支，仍可能全部通過。要驗證「呼叫前就留下紀錄」是否真的受到保護，還需要一個會跳過後續寫回的例外。完整範例因此安排 `error_after_capture`：替身已記錄扣款，接著丟出不在上述兩個分支內的 `ConnectionError`。

第一次呼叫會把這個 `ConnectionError` 向外傳遞；測試明確預期它發生。第二次以相同訂單與 key 呼叫時，前置紀錄仍在，所以取得 `PENDING`，也不再呼叫 provider。若刪掉那筆前置紀錄，第二次就會再次進入扣款，測試因而辨識出差異。這個案例保護的，是例外中斷控制流程時仍然需要成立的要求。

這段不是事後替範例補上的想像情節。整理程式時，Claude Code 的獨立 Review 確實指出前置 `PENDING` 沒有相應的非逾時例外測試；後續修訂才加入這個案例，以及刪除呼叫前紀錄的變異 M7。原先選中的測試與變異，都沒有把這個風險完整呈現出來。獨立 Review 的價值在這裡很具體：先找出原本沒問到的問題，再讓可執行測試把新要求留下來。這條要求的依據是第一節明列的教學契約，實際團隊仍須由負責的人確認。模型提出反例，讓缺口變得可見；執行結果則證明測試能辨識違反契約的改動，不能反過來代替人判斷契約是否合適。

先確認未修改的程式通過所選測試，再每次只改一處，執行同一組測試，最後丟棄那份變異程式。測試因預期行為差異失敗，代表這個 mutant 被辨識，通常稱為 killed。本例的簡化 runner 把沒有被辨識的變異統一標為 survived；它沒有量測覆蓋率，因此這個標籤也包含根本沒有執行到的分支。正式工具會再區分 NoCoverage 與執行過卻未被辨識的 Survived，讀取下表時要記得這個差別。

## 六、依 Review 風險挑選 mutation 的範圍

第三種「挑選」，是決定哪些程式碼與變異值得執行。我的起點是前面已確認的付款要求，再對回實作它們的程式位置：扣款金額、既有嘗試的 guard、key 的綁定、例外處理與收據內容。

這次只變異 `payment.py`，不修改斷言、fixture、`FakeGateway` 或 mutation runner。否則就可能把題目或裁判一起改掉，無法回答產品程式是否受到測試保護。若真實 PR 改的是共用付款 helper，也要沿呼叫關係選出會受影響的測試，不能把 diff-scoped 誤解成「只看新增那幾行，其他都不必管」。

這種限縮 mutation 範圍的做法，也有較早的實務研究可以參照。Google 的 [Practical Mutation Testing at Scale](https://research.google/pubs/practical-mutation-testing-at-scale-a-view-from-google/)（2021）描述了在 Code Review 中針對變更執行 mutation、過濾較無用的變異，並依歷史表現選擇運算子的做法。它支持的是把成本與可採取行動的結果一起考量，不是為本文的七個 mutant 或 70% 門檻背書。

為了讓讀者能逐項核對，本例**人工指定七個 mutant**。它們是實際執行的變異，不是 Stryker、PIT 或 mutmut 自動產生的完整清單，也不代表已涵蓋所有可能的付款缺陷。

📌【在此插入表 table-03.png】

七個變異都有可以指出的行為差異，這次沒有排除的等價變異。若換用正式 mutation 工具，還要記錄工具版本、變異運算子、檔案範圍與測試選擇；把無法編譯、沒有覆蓋、逾時及確認等價的結果分開。例如 [Stryker 的計分文件](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/)把 killed 與 timeout 都列入 detected，沒有覆蓋的有效變異則仍在一般 mutation score 的分母裡。把 timeout 和 no coverage 都當成無效結果刪掉，分數的定義就變了，不能再直接與別人的報告比較。

挑選變異與解讀存活結果時，都需要找出能區分原始程式與錯誤版本的操作。M2 需要對同一張訂單呼叫兩次，觀察是否再次執行扣款；M5 則需要讓 provider 丟出逾時，再檢查收據是否仍為待確認。完整測試把扣款前、扣款後的逾時都納入，避免把未知結果一律想成已經扣款。這兩種缺陷需要不同的輸入與斷言；在正常購買的測試裡多加五個 `PAID` 斷言，仍然碰不到它們。

若某個 mutant 存活，下一步也不一定是馬上補測試。先確認這個行為是否在本次承諾的範圍內、預期結果是否已由人確認。例如退款政策尚未決定，這時硬寫測試，只會把尚未討論的答案固定下來。相反地，C4 已有清楚的付款契約，M5 的存活就能直接指向一項必須補足的驗證。Review 提供了判讀依據，讓團隊能從 mutation 結果決定下一步。

若找不到反例，要釐清是需求未定義、輸入不可達、測試缺口，還是行為確實等價。「目前沒測到」不能當成等價證明。[Stryker 的等價變異說明](https://stryker-mutator.io/docs/mutation-testing-elements/equivalent-mutants/)也提醒，工具無法替所有這類情況作出判定。團隊若決定排除，必須留下適用的輸入範圍、理由與審閱紀錄；高後果的存活變異，則要在核准前處理或明確承擔，不能躲在總分裡。

## 七、從 85.7% 的綠燈，追到一個確實會失敗的測試

在本例，七個 mutant 都能執行、都不等價，所以分母固定是 7。mutation score 就是被測試辨識的個數除以 7，再乘上 100%。分母是變異數，不是測試數；它也不是產品沒有 bug 的機率。

隨文的 `mutation_demo.py` 已實際執行三組測試選擇，原始程式在每一組都先通過。先看整體結果，再沿著第二列的 M5 找出缺少的證據。

📌【在此插入表 table-04.png】

第一列的兩個測試都是真的，也都會執行付款；它們只是沒有要求程式處理重送、key 衝突、拒絕與逾時。M2、M3、M7 改動的位置有被執行，測試卻沒有辨識出行為差異，這是 mutation 比「那一行有跑過」多問的一步。M4、M5 則根本沒有進入對應的例外分支，單看分支覆蓋率也能發現這部分缺口。

第二列已經辨識六個 mutant。如果團隊只採用測試篇提出的 70% 起始建議，85.7% 已超過門檻。但那個仍然存活的 M5，修改的正是 C4 所保護的行為。下面是它實際做的單行替換，其他程式與測試都保持不變：

```diff
 except TimeoutError:
-    receipt = replace(receipt, status="PENDING")
+    receipt = replace(receipt, status="PAID")
```

八個測試仍然通過，原因並不神祕：這組測試沒有安排 provider 逾時，程式因此沒有進入這個分支。若使用有覆蓋率資訊的正式工具，這類結果會歸為 NoCoverage；依前述 Stryker 的定義，它仍在一般 mutation score 的分母裡，查看分支覆蓋率也能發現缺口。這裡的重點，是總分過線之後，仍要有人檢查那個尚未回答的問題。再讀一次這八個測試得到的綠燈，意思就清楚了。它們確認的是各自安排的案例，沒有回答「結果未知時，是否會宣稱付款成功」。程式執行沒有報錯，也不能替一個未被提出的問題提供答案。

接著補回第四節的逾時測試，讓同一份測試分別檢查 M5 與原始程式。這次另在隔離副本中只執行該測試方法，實際輸出節錄如下；省略完整測試名稱前綴、traceback 與執行時間，將兩個 subTest 相同的斷言訊息只列一次，保留情境與計數：

```text
# M5：兩個 subTest 分別安排扣款前、扣款後逾時
(outcome='timeout_before_capture') ... FAIL
(outcome='timeout_after_capture') ... FAIL
AssertionError: 'PAID' != 'PENDING'
Ran 1 test
FAILED (failures=2)

# 相同測試，換回原始 payment.py
Ran 1 test
OK
```

這裡是**一個測試方法、兩個失敗的 subTest**，不是新增兩個付款測試。完整付款測試數仍為九。失敗發生在 `first.status` 的斷言，因為錯誤版本回傳 `PAID`，而契約要求 `PENDING`；不是 import 失敗、環境故障，或測試根本沒有被收集。換回原始程式後，同一方法通過。讀者現在可以追到「哪個要求、哪個輸入、哪個斷言」辨識了 M5。

這是用已知錯誤版本確認測試的辨識力，不能把它寫成這份功能 PR 曾經歷過的 TDD 開發順序。完整 runner 再執行全部九個測試時，七個指定變異都被辨識，分數因此成為 100%。這個結果支持的範圍仍然很具體：所選測試抓得到這七種改動。並行、重新啟動與 provider 整合，需要各自的案例與證據。

**總分過線，不能抵銷尚未驗證的關鍵付款約束。** 這裡借用 70% 作為對照，是為了呈現只看總分會漏掉什麼。七個人工指定的 mutant，和正式工具針對修改範圍產生的集合不同；這個小分母不能用來校準真實 repo 的通用門檻。

### 100% 為什麼還需要讀取逐項結果？

下一張表從完整實驗的 JSON 整理而來。每列是一個測試方法；「●」表示該方法至少有一個斷言或 subTest 因這個 mutant 而失敗，「—」表示沒有辨識出差異。它是失敗對照表，沒有量測程式碼覆蓋率，也不把「—」一律解釋成沒有執行到。

📌【在此插入表 table-05.png】

先沿 M5 那一欄往下看，只有逾時測試辨識它，所以省略該測試會留下第二列的缺口。再看 M2，許多測試都會辨識它；它們各自驗證拒絕、重送或例外，但共同碰到了既有付款嘗試的 guard。某一條約束的測試失去斷言時，其他測試仍可能把 M2 辨識出來，總分因而維持不變。

這不是只靠表格推測。先前已在隔離副本中，把 C1 的重送測試，以及 C2 的「新 key 不重啟同一訂單」與「重送不改寫訂單內容」測試都改成空的 `pass`，三組分數仍然是 28.6%、85.7%、100%。正式範例保留原有斷言；這項反例指出的是總分的盲點。空方法仍會被 unittest 計入測試數，其他案例又繼續辨識 M2，所以「九個測試、100%」這兩個數字都沒能揭露三個測試已經失去內容。

因此，reviewer 收到報告後，還要回到該條約束的測試，閱讀它安排的輸入與斷言。必要時像剛才的 M5 一樣，單獨執行這個方法，確認它會對違反要求的程式失敗，再確認原始程式通過。如果仍沒有對應的反例，就把這項證據缺口記下來；不需要為了維持漂亮的分數，把未知結果寫成已驗證。

### 報告的產生方式，也要能被檢查

本例 runner 先確認原始程式通過，核對各組測試數量與逾時測試名稱；再把每個 mutant 放進獨立暫存目錄執行，區分斷言失敗與執行錯誤，列出失敗測試名稱。它沒有逐一鎖定全部測試身分，也沒有把斷言訊息寫入 JSON，因此前面的失敗訊息來自另外執行的單一測試。

若發生 import／執行錯誤、沒有收集到預期數量的測試，或執行超過時限，runner 就中止示範，不把這些情況悄悄算成 killed。這是教學採用的保守處理方式。M5 所模擬的是付款程式收到 `TimeoutError`，測試本身正常完成；mutation 工具的 timeout 則是等待測試行程超過時限。Stryker 把後者列為 detected，本例直接中止；讀報告時要先確認採用哪一種定義。

三組結果並列，是為了比較測試選擇。真正的驗收流程必須固定範圍，保護規則與執行器，變更時另外審查。若 PR 作者能任意刪掉不利測試，再交回一份新綠燈，分數就失去了共同判準。

## 八、把同一份證據交回 Review，再談可靠度

現在回到第二節那個「支援付款重送」的 PR。reviewer 已經知道它要承諾什麼，也看見 M5 的具體反例。這時需要作出的決定，是這份變更是否有足夠依據可以核准，以及核准涵蓋到哪裡。

若交來的仍是 85.7% 版本，我會留下這樣的評論。以下是教學示例，不是真實團隊的核准紀錄：

> 暫緩核准。M5 把逾時結果改成 `PAID`，目前八個測試仍全部通過，C4 的未知付款結果尚未受到驗證。請補上扣款前與扣款後逾時的案例，透過 `Checkout.pay()` 檢查狀態、付款識別與重送的副作用。請附上測試對 M5 失敗、對原始程式通過的結果，再由 payment owner 複核。這次審閱只處理單一行程、依序呼叫的教學實作；production 的復原與整合證據另行確認。

這則評論把拒絕核准的理由與解除條件寫在一起。作者不用猜測是分數不夠高，還是測試命名不合偏好；下一位 reviewer 也知道該檢查哪一項變更。補件後，若測試只是直接比對替身裡預設的字串，沒有經過付款程式，就尚未符合條件。必須確認同一條產品路徑在正確與錯誤版本之間呈現可解釋的差異。

實際交回 PR 的內容可以精簡，但應讓判斷所需的證據連得起來。下面是一份填好的教學範本；實際使用時，要補上可開啟的 revision、規則版本與報告連結。它是審閱紀錄格式，不是已實作的自動核准工具。

```text
Intent:
  同一個付款嘗試重送時，回傳既有結果且不再次呼叫 provider。
Constraints honoured:
  C1 重送；C2 訂單與 key 邊界；C3 拒絕；C4 未知結果與未分類例外。
Evidence:
  原始程式通過 9 個付款測試。
  7 個指定 mutant 全部被辨識；排除數為 0。
  C4 的單一方法對 M5 失敗、對原始程式通過。
Revision / rule version / report:
  [填入實際受審版本、受保護規則版本與執行結果連結]
Remaining scope:
  尚待驗證持久化、並行、重新啟動、provider 整合與授權。
Decision / approver:
  [由具責任的人填寫核准範圍、決定與身分]
```

補齊這份證據後，payment owner 可以判斷教學實作是否已符合 C1 到 C4；QA reviewer 檢查測試與變異之間的對照；整合 reviewer 記錄部署前仍需處理的範圍。若審閱目標只是把這個教學範例合併進文章 repo，這些界線可以被明確接受。若目標是部署真實付款服務，同一份報告就還不足以核准。決定不同，是因為承諾的範圍不同。

規則與候選程式也需要保留獨立性。候選 PR 可以提出約束修改，但不能自行改弱測試，再用改過的綠燈證明自己合規。正式流程應讓人核准規則變更，從受保護的規則與 runner 版本評估候選程式碼，並把核准紀錄對應到實際審閱的 revision。若核准後又改了付款分支，就要對新的版本重新取得相關證據。把測試放進 `constraints/` 目錄，本身不會建立這些權限與版本保護。

走到這裡，還不能直接填寫 agent 的可靠度報告。本例九個測試描述的是一份候選程式在選定情境下的表現。若要量測 constraint pass rate，評估單位要改成多個候選修補：在功能檢查通過的候選修補中，有多少也通過全部適用約束。先固定任務集合、功能要求與約束，再記錄每份候選結果，才知道分母是什麼。單一修補通過七個約束測試，回答不了 agent 往後多常能遵守要求。

pass^k 也需要另外設計實驗：讓 agent 對相同任務獨立產生並驗證多次成果，以事先固定的功能與約束要求判定每次是否成功。把同一份確定性的 unittest 重跑五次，只檢查了同一份程式，沒有新增五次 agent 產出的證據。本篇沒有執行這組實驗，因此不提供 pass^5 數字；若團隊要進一步討論任務授權，應先依可靠度篇的方法蒐集這份資料。

三道閘在這瓶綠茶上，於是有了明確的交接。Test gate 交出測試辨識力的證據，review gate 檢查要求、證據與剩餘風險，reliability gate 再觀察一組固定任務的多次產出。每一步都接收前一步的資料，接手的人也要重新確認：這份資料能回答現在要作出的哪個決定？

## 九、從重跑範例，到安排下一份證據

完整程式、九個付款測試、七個 mutant 與規則對照，放在 [examples/tea_payment](https://github.com/fantasybz/medium-articles/tree/main/examples/tea_payment)。使用 Python 3.10 以上版本，從儲存庫根目錄執行：

```bash
python3 -B -m unittest discover -s examples/tea_payment -p test_payment.py -v
python3 -B examples/tea_payment/mutation_demo.py
```

第一個命令執行九個測試；第二個命令輸出三組實驗的 JSON。讀取時，先確認各組 `baseline_passed` 與 `baseline_tests`，再看 `scored_mutants`、`excluded_mutants` 與逐項的 `failing_tests`。只看最後一個 `mutation_score`，就又回到這篇想避免的閱讀方式。

可以先找 `without-timeout` 裡的 M5：它標為 survived，失敗測試清單為空。再找 `full` 裡的 M5，會看到逾時測試兩個 subTest 的名稱。這兩份紀錄把第七節的解讀對回執行結果。runner 每次把原始來源複製到新的暫存目錄，只在副本中植入一個 mutant；過程使用標準函式庫與本機檔案，不會接觸真實帳號或扣款，也不會把正式 `payment.py` 留在錯誤版本。

目錄裡另有十二個 runner 回歸測試，涵蓋載入失敗、異常測試結果、測試數量變動、逾時測試缺失等選定情境，並核對預期被辨識的 mutant 集合。它們不計入九個付款測試，也不計入七個 mutant 的分母；若用 `test_*.py` 執行整個目錄，合計會看到 21 個測試。這個數字是在檢查實驗工具本身的部分行為，不能加到付款服務的覆蓋率或可靠度上。

### 把未知結果交給能處理它的人

這份實作以記憶體字典保存付款嘗試，驗證的是**同一個行程、依序呼叫**的情境。兩個服務行程不會共用記憶體；行程重新啟動後也會失去紀錄。要把同樣的要求帶進真實服務，先沿著一個中斷情境推想，就能看出下一份證據該放在哪裡。

假設金流已完成扣款，但服務在保存最終結果前停止運作。重新啟動後，程式若只看見一張尚未完成的訂單，就再次呼叫金流，便可能把「沒有記錄結果」誤當成「先前沒有扣款」。把字典換成資料庫，還需要決定何時登記嘗試、哪些操作具備原子性，以及外部扣款完成、本地結果未寫入時怎麼復原。單一本地資料庫交易，無法自動把外部 provider 的扣款一起包進同一個原子操作。

這是從程式邊界推導出的後續設計問題，本文沒有實作或測得 production 的 exactly-once 保證。下表把需要補的證據對回第二節的審閱責任。每列都應成為能被驗證的工作，而非在 PR 尾端留下一句「上線前再處理」。

以第三列為例，owner 不能只指定狀態叫 `PENDING`，還要確認由哪個流程查詢、取得什麼證據才能更新狀態，以及超過多久仍未確認時由誰接手。面向購買者的畫面，也要依真正具備的能力說明目前狀態與下一步；尚未建立通知流程，就不能承諾稍後一定會主動通知。保留未知結果的目的，是讓後續處理有根據，而不是把等待的責任交給購買者。

識別碼的生命週期同樣需要設計。[AWS Builders’ Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)討論了相同 request ID 帶入不同意圖、延遲抵達的請求等問題；[Stripe 的 idempotency 文件](https://docs.stripe.com/api/idempotent_requests)則說明，key 保存至少 24 小時後可能被清除，清除後重用會產生新的請求。應用程式不能只記得「曾經用過這個 key」，還要確認 provider 的保存期限與重試契約。自己的訂單識別、付款嘗試 key 與 webhook 事件識別，各自保護不同的邊界，不能拿其中一個代替全部。

身分授權也需要真實服務的證據。本文的 fixture 從已授權訂單開始，沒有驗證跨帳號讀取或支付的拒絕行為；收據上的 SKU 正確，也還沒有檢查倉儲交付。這些是接手時應明確安排的工作，不會因為七個 mutant 都被辨識就消失。

### 團隊可以從一個 PR 開始

如果要把這套做法帶回團隊，我會先選一個影響清楚、能完整看懂的變更，找出其中一條後果嚴重而且預期結果已確定的要求。讓 reviewer 說明來源，由實作者加入案例，再人工植入一個對應的錯誤版本，確認測試能辨識差異。先把一條證據鏈走完，團隊才知道規則卡、測試與審閱紀錄需要留下什麼。

接著觀察維護成本。當規則失敗時，負責的人能否分辨是實作退步、契約改變，還是測試安排已不合用？若實作退步，就修正程式，重新確認它遵守原有要求；若契約改變，就一起更新規則、反例與核准紀錄；若 fixture 已不符合約定的情境，就修正測試安排，重新驗證它的辨識力。環境故障造成測試未能執行，則是另一類問題：先修復環境，再取得結果，不能直接算成產品符合或違反要求。累積這些判讀經驗之後，再擴大保護範圍與自動化程度，會比一開始大量收集沒有 owner 的約束更容易持續。

## 十、回到那個等著付款結果的人

開場那位等著付款結果的人，只是想買一瓶茶。對方不需要知道 mutation score 的分母，也不應該靠猜測決定可不可以再按一次付款。這些判斷應該先在需求、程式與驗收流程裡被處理清楚。

對工程團隊來說，這個例子把三種挑選接在一起：依付款風險挑選 reviewer 與深讀範圍；從評論中挑出有長期價值、可判定且有人維護的約束；再把約束對回程式碼，挑選能檢驗測試保護力的變異。每一步都需要說明理由，才能讓下一個接手的人繼續判斷。

這樣的交接也能減少不必要的猜測。實作者知道補件的條件，reviewer 知道要重新確認哪個分支，接手維運的人知道哪些未知結果尚未有復原流程。留下推理過程，讓審閱紀錄更容易理解，也讓一次審閱的投入，能被下一次修改繼續使用。

我想留下的，不是「補到 100% 就好」這句新口號，而是第二列那個 85.7%。數字看起來已經足夠漂亮，付款結果卻仍然可能被說錯。當 reviewer 能指出是哪個情境、哪條規則與哪個 mutant 尚未被保護，綠燈才開始成為有內容的證據。

四部曲談了測試、Review 與可靠度，最後仍要回到那個等著付款結果的人。那瓶綠茶的價格在這裡只是示範。值得被認真對待的，是有人把付款交給了這套系統，而團隊需要能解釋：我們確認過什麼，還有哪些問題需要繼續驗證。
