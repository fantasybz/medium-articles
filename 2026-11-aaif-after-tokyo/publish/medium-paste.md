# 從東京 AGNTCon 回來：Agent 接上工具之後，工作才剛開始

> **TL;DR** — 8 月底一張臨時的邀請，讓我在兩週內安排了東京 AGNTCon + MCPCon 的行程。午休時把 Kong 的多代理展示架起來跑了三個情境，回台北後又把 AAIF 陸續公開的錄影看完，最想帶回團隊的問題只有一個：當 agent 回報「這一步做完了」，接手的人需要哪些證據，才能核准下一步？本文把每一次行動拆成三個問題：這個操作現在被允許嗎、它真的發生了嗎、任務真的完成了嗎。接著用一個假設的 App 閃退調查貫穿八場材料，看每一場各自提供哪一題的證據，又還缺哪一題。我的判斷是：工具接通之後，團隊最該補的不是更聰明的提示，而是讓這三個問題各有一份判準經過確認、觀察範圍清楚，而且 agent 不能自行放寬或核准的證據。

## 一、一張邀請，和兩週內排好的東京行

8 月 24 日，我在 [Facebook](https://www.facebook.com/kochi.chuang/posts/pfbid02gDB5gRmpcrvA3z5MMYGgCp57v4Lke4R2aiMo591PCVvFSzPo1JvErv45fQumDr4ol) 貼了一段日文：「AGNTCon + MCPCon JPに無料でご招待いたします」。收到邀請後我好奇查了票價，竟然是 ¥60,000 日圓，於是半開玩笑地寫，會不會是上次去 KubeCon Japan 當「Kubestronaut 吉祥物」，口碑還不錯。

那當然是自己的玩笑，我並不知道對方選擇邀請我的原因。貼文裡我向 CNCF 道謝，保存的邀請函則署名 Agentic AI Foundation（AAIF），兩者的關係見引註。能確定的是，這張票讓一趟原本沒有排進行事曆的旅行，突然變成需要認真安排的事情。[1]

我參加這場的理由，在[隔天抵達會場的貼文](https://www.facebook.com/kochi.chuang/posts/pfbid036hzqy8sihui675efRtxAVRjQbF8khpBf5Qc3PKmFc43tbocaWrsrqy4E3WuQsfJyl)裡寫得很直接：想和社群交流，看看 AI Agent、Agentic Engineering 到底發展到什麼程度，帶一些想法與觀察回家。當時我已經在寫 agent 與軟體工程的文章，也持續關心測試和驗收。比起再多一張工具清單，我更想知道：真正把系統做出來的人，現在被什麼問題卡住。

先把本文說的 agent 講清楚。它是一套讓模型自己決定下一步、再透過工具查資料或採取行動的系統。拿值班工程師常做的事來想：收到一個「App 閃退」的回報，他會先讀錯誤紀錄，再查相關程式，依查到的結果決定下一步。Agent 做的就是這個迴圈，只是推理由模型負責，周圍的程式提供工具、保存進度並限制它能做什麼。Anthropic 與 OpenAI 對 agent 的定義都落在這裡：由模型主導流程、能使用工具、而且在明確的邊界內獨立完成任務。[2][3] 當這樣的系統參與開發、測試與交付，分工就要重新安排：人定要求與核准，agent 做調查，平台提供受控的工具。這就是我關心 Agentic Engineering 的起點。

這次 AAIF 陸續公開錄影，讓我有機會把當時的問題接回來源；八場材料裡哪些是現場聽到、哪些是回台北補看，文末〈影片與資料的核對方法〉逐一交代。

## 二、午休時動手，問題開始變得具體

9 月 10 日，我看到一個以 Kong 為中心的多代理展示，中午吃飯時把它架起來，試了完整流程、故障切換與成本控制三個情境，並留下[操作錄影](https://www.facebook.com/reel/1387275603582551/)。當天貼文的感想是一句話：「governance 跟 agent logic 分離，AI 才進得了 production」。用白話說：agent 決定下一步要查什麼、做什麼；哪些請求能通過、誰能用哪些工具，由外層的系統決定，不寫進 agent 的程式。這次重查，我也找回自己保存的[工作坊程式碼](https://github.com/fantasybz/AI-data-Path-demo/tree/2c945fe4ad3ffc4ec65558579439dc9d06c90ebe)，才有機會把介面上看到的結果，往下追到設定與程式。想自行延伸實作，可以從 [AI-data-Path-demo 專案首頁](https://github.com/fantasybz/AI-data-Path-demo)開始。[4]

展示的情境可以想成一個值班小組。負責分派與彙整的 orchestrator（協調者），先讀取一張 GitHub 問題單（issue），再請兩個子代理分頭處理：工程師代理草擬程式變更提案（pull request，PR），業務支援代理負責區域通知。先說清楚：展示裡的問題單、PR 與通知都是模擬資料，存在服務的記憶體裡，沒有連到真正的 GitHub；它示範的是路徑，不是外部效果。角色之間交換的是「請工程師代理調查 issue 123」這類工作訊息，走 Agent-to-Agent（A2A）協定，像小組成員之間交接任務；每個代理「讀取 issue 123」「建立 PR」這類工具操作，走 Model Context Protocol（MCP），像成員各自使用公司提供的工具。兩種協定解決的是介面問題，誰能做什麼仍由應用程式決定。

Kong 在這裡扮演 gateway。可以把它想成大樓的門禁櫃台：所有進出都要經過它，它負責登記是誰、要去哪裡、准不准。展示裡的模型請求、工具呼叫與代理之間的訊息，全部走這個櫃台，所以路由、限流與存取規則可以集中設定，不用寫進每個代理的程式。集中政策也集中了故障的影響：櫃台不可用時所有代理都動不了，哪些工作可以等、哪些要停，要先定好；而且任務識別與群組政策應由可信的那一端決定，請求自帶的標籤不能當成授權依據。

### 故障切換只回答「誰來答」

先看模型請求怎麼切換。這裡有兩個設定要分開：路由決定「這類請求送到哪裡」，模型池決定「有哪些模型可以接這類請求」。在保存的設定中，請求附帶的 `x-llm-type` 標籤，會把協調者、子代理與摘要工作送往不同的模型池；切到 failover 情境時，另一條路由把主要模型的目的地改成故障模擬器。模擬器固定回傳 HTTP 503，也就是「服務暫時無法使用」，gateway 收到後把請求轉給備援模型。把故障條件固定下來，就能反覆操作同一個情境，觀察請求是否走到預期的備援路徑。

當天貼文裡我寫「primary LLM 掛掉，Kong 自動切 fallback，agent 毫無感覺」。這句話的價值在於團隊不必在每個代理裡重寫目的地、憑證與切換條件。但「毫無感覺」也是要小心的地方：備援模型對工具選擇、指令與輸出格式的處理可能和主要模型不同。請求恢復之後，仍要拿原本的任務要求檢查結果。我會再加一個條件：若備援模型不支援這次任務需要的工具呼叫或輸出格式，恢復可用的請求也不該直接接回原本的步驟，而應停在需要那項能力的階段等人決定。Gateway 回答了「誰來答」，接手的人還得知道「這個回答能不能用」；可用性恢復了，執行資格還要另外確認。

### 被限流之後，先確認哪些步驟已經完成

故障切換處理的是模型暫時答不了；限流情境處理的是用量到頂之後要不要再放行。這裡的 token 是模型計費的單位：模型把文字切成小片段計數，像計程車跳表一樣，輸入和輸出都算錢。這份設定在 `rate-limited` 情境中，對 `github-writers` 群組設下 40 秒內 2,000 個 token 的上限，再用 `x-analysis-id` 把每次分析分開計算，避免不同展示互相干擾。這個計數器只追蹤工程師代理所屬群組在這一輪、這段時間內的用量；區域通知所屬的群組不受這條規則約束。時間窗重設後還能繼續消耗，所以它也不是整個任務的總預算；若要限制整個任務的花費，還需要合併各角色的用量，並依實際使用的模型單價換算。授權也一樣要看對象：角色有建 PR 的權限，但目標 repo 不在這次委託內，仍應拒絕。

📌【在此插入圖 asset-05.png】

筆者當日操作錄影 02:08：介面顯示 Rate limit enforced 與 Blocked。應把被拒絕的這筆請求，和前面已完成的步驟分開判讀。


保存版的操作手冊描述了一條很值得看的路徑：工程師代理可以先完成「建立 PR」的工具呼叫，再在下一次模型請求碰到 HTTP 429，也就是「已達流量限制」。我在貼文裡寫，真正有意思的是擋下來之前的紀錄：用了多少 token、呼叫過哪些工具、PR 的紀錄有沒有建立，全部查得到。如果介面只把整次分析標成失敗，使用者會以為什麼都沒發生；如果系統直接從頭重跑，又會把已經做過的事再做一次。

這裡也接上我 9 月在〈[Harness 藍圖](https://medium.com/p/f2a139f5b561)〉第三節提的設計：工具依效果分三級授權：查 crash 是 read，建草稿 PR 是 write，變更 production 的開關是 dangerous，由 gateway 集中檢查並留下紀錄。Kong 的設定把協調者放進只能讀問題單的 `github-readers`，工程師代理放進能建 PR 的 `github-writers`，業務支援放進能發通知的 `notification-senders`。不同角色用不同的憑證，Kong 依憑證對應的身分套用群組政策；保存版裡每個代理仍持有自己的 API key，從環境變數讀進來附在請求上，櫃台負責的是驗證與政策，不是發證。前面說過，這些 PR 與通知都是記憶體裡的模擬紀錄；它證明的是路徑可以這樣設計，不是外部效果已經發生。

### 把「允許、發生、完成」拆開看

依晚間保存版手冊描述的路徑把這條路拆開（當日介面只顯示 Blocked，限流的對象、模擬寫入與版本差異都是重查之後才分清的），午休時寫下的那句「governance 跟 agent logic 分離」就具體了。Gateway 正確執行了限流，整個任務仍然沒有完成；工程師代理已經完成建立 PR 的工具操作（在展示裡是寫入模擬紀錄），卻拿不到下一次模型回應。兩種結果同時成立，因為限流檢查的是「這次請求是否仍被允許」，任務則要把多個步驟的結果接起來。把它們壓成同一個紅燈，就丟掉了決定如何恢復所需的資訊。

換成真實服務後，下一步也不一定是重做 PR。若 PR 已經可靠保存，只是後續摘要失敗，等模型服務恢復後，可以根據既有結果補完報告。若連工具的結果都未知，才需要回查那次操作，確認能不能安全重送。**一次任務失敗，不代表前面沒有成功改變任何狀態。** 這個差別決定重試應從哪裡開始。

**Gateway 能集中執行已配置的政策；這份政策是否涵蓋這次任務與操作對象，以及「發生了什麼」與「做完了沒」，仍要由應用程式和驗收的人分別回答。**

## 三、我帶回來的問題：三件事要分開問

回台北後，我把那句感想拆成三個問題，用在同一個時刻：agent 回報「這一步做完了」，接手的人要憑什麼核准下一步。請同事幫忙訂會議室時，我們其實也分開問過它們：他有權訂嗎？預約紀錄真的建立了嗎，還是送出後畫面卡住？訂到的是我要的時段嗎？這三件事分別是「允許」「發生」「完成」，換成 agent 也一樣：

- **允許嗎？** 這個操作在此刻、對這個對象、以這個身分，是不是被核准的。
- **發生了嗎？** 外部系統真的改變了嗎，還是請求送出後結果不明。
- **完成了嗎？** 結果是否符合原本的要求，而不是只有一句「已完成」。

為什麼三題不能合成一題？因為 agent 工作的環境有四個繞不開的條件。第一，模型不知道外面此刻的狀態：它記得兩分鐘前查到的資料，卻不知道那之後別人改了什麼。第二，工具呼叫會改變外面的狀態：建 PR、改設定、寄通知，做了就留在那裡。第三，跨系統的操作不會自動一起成功或一起失敗：PR 建好了，通知可能沒寄出；請求逾時了，動作可能已經做完。第四，一份觀察只能支持它涵蓋條件內的判斷：在測試環境通過，說的只是測試環境。

這四個條件，做過分散式系統的工程師都不陌生；agent 讓它們更難的地方，是模型會依照讀到的文字自行決定下一步。請求逾時，若它讀成「沒有執行」，下一步可能就是再送一次寫入；測試環境通過，若它讀成「已經完成」，下一步可能就是宣布收工。原本由人判讀的落差，現在進入了一個會自動接著做的迴圈。這是我的推論，不是哪一場演講的結論。

東京的主舞台上，AAIF 的 Mazin Gilbert 說了一句我一直記得的話：模型得到最多關注，但 harness 更重要。[5] 先用 crash 調查來看 harness 是什麼：同一個任務需要查得到資料、用得到工具、有一個可以安全執行修改的地方，還要有辦法知道做完的結果對不對。把這些準備好的那一整套工作環境就是 harness，模型只是其中負責推理的那一位。用人來比喻，同一位新同事，在有測試、有 log、有權限表的團隊，和在什麼都沒有的團隊，表現會完全不同；模型是那位同事，harness 是團隊替他準備的環境。我在〈[Harness 藍圖](https://medium.com/p/f2a139f5b561)〉把這個環境拆成五層；本文不逐層走，只從三個問題檢查東京的各場材料各補了什麼。

同一場會議裡還有一組很直接的證據。NTT DOCOMO BUSINESS 的 Kota Tsuyuzaki，讓六個模型各做一次同一個種了 bug 的任務：六份最終檔案全部通過專案自己的測試，實際成功的 agent 工作階段（session）卻只有五次；那一次失敗，是檔案改完後驗證一直沒有在 session 內成功，最後由操作者放棄，而且六次的停止規則並未標準化。投影片上的結論是「Artifact correctness and session outcome are different questions」。另一次 session 裡，模型在對話中道歉說自己刪掉了某個檔案，工具紀錄只寫著那次刪除回傳 blocked；研究者交叉核對工具紀錄與操作者接下來的訊息，才判定檔案從未被移除。他的說法是「The model could not observe the outcome of its own blocked call」，而且一個通用的錯誤狀態本身，分不出「被拒絕」和「執行失敗」。[6] 這正是《綠燈不是驗收》總論把證據分成三類的理由：agent 的陳述、agent 自己寫的檢查，和團隊擁有的檢查，只有最後一類能作為閘門採用的獨立驗收證據。「agent 改不動」只是證據保護的一半：團隊自己維護的檢查，也可能穩定地放行錯誤，所以判準本身要先確認、觀察範圍要說清楚。三個問題的答案，都不能只從 agent 的自述取得。NTT 的案例還多說了一層：受保護的測試回答產出是否符合要求，操作紀錄回答實際做過什麼，兩者不能互相替代；而且他們的判定還得交叉核對操作者的下一句話，第 14 頁更有操作者指錯被刪檔案的例子。本文需要的是能辨識操作對象與結果的紀錄，NTT 展示的正是現有紀錄還不夠的地方。

本文後面用一個假設的調查貫穿各場材料。新版 App 開始出現閃退（crash），值班工程師請 agent 調查受影響的使用者與原因，必要時提出草稿 PR。調查途中，它發現異常集中在某個功能開關（feature flag）打開之後。功能開關就像新功能的總電源，團隊常先開給一小部分使用者，再逐步擴大；逐步擴大的過程叫 rollout。先把開關的狀態定死：假設新版目前曝光 10%，「暫緩 rollout」是維持 10%、停止擴大；「關閉開關」是降到 0%、撤回既有曝光。後面所有核准、請求、遠端回查與成效觀察都沿用這組意思。這時有三個決定等著人作：要不要暫緩 rollout 止血、手上的修補是否真的解決了原因，以及這次經驗要不要寫回團隊共用的調查程序。這個委託一開始只開放調查與草稿，是否變更生產環境仍由值班人員決定，而且只核准暫緩，不核准關閉。

## 四、程式有編譯器，其他工作靠什麼回應錯誤？

Anthropic 的 David Soria Parra 是 MCP 的共同創造者。他在 keynote〈MCP and the Era of Connectivity〉回顧 MCP 的發展，討論模型如何透過開放介面取得外部資料與工具，以及這對一般知識工作的意義（[官方議程](https://agntconmcpconjapan26.sched.com/event/2QrbB/keynote-mcp-and-the-era-of-connectivity-david-soria-parra-co-creator-of-mcp-anthropic)、[演講影片](https://www.youtube.com/watch?v=3LwylP2as8A)）。這一場回答的是「完成了嗎」最底層的問題：系統要先看得到行動的結果，才談得上判斷。

### 讓回饋能分辨真正的改善

他指出，coding agent 之所以最早進入實際工作，一個原因是程式有編譯器與測試，可以在修改後自動提供回饋。編譯器會指出語法或型別錯誤，測試會執行指定情境、比對預期結果。模型不用每次都等人解釋哪裡不對，就能利用錯誤訊息繼續修正。[7] 這個觀察沒有把測試抬成最後裁判，卻說出了改善工作的前提：系統必須有辦法觀察行動的結果。

📌【在此插入圖 asset-06.png】

David Soria Parra，東京 keynote [04:46](https://www.youtube.com/watch?v=3LwylP2as8A&t=286)：當模型能力增加，連到實際工作系統的重要性也提高。來源：AAIF 官方錄影。


處理一筆財務例外或跨部門調查時，相關資料分散在各種線上服務與內部系統，連「目前發生什麼事」都還沒取得。MCP 的用途在這裡變得具體。放回 crash 案例：提供 crash 查詢工具與資料的那一端叫 server；工程師操作、替他管理模型與各個連線的應用程式叫 host。兩端用共同方式溝通，可以減少每一對系統都重新整合的成本。[8] Anthropic 自己的工程文章也建議，模型需要的檢索、工具與記憶，應透過 MCP 這類清楚、有文件的介面提供。[2]

放回 crash 調查，「可能是新版功能」和「查到受影響版本、錯誤當時的函式呼叫路徑（stack trace），以及功能開關的變動時間」是不同層次的工作。後者提供同事可以重新查詢、比較與反駁的材料。但共同介面不會替資料創造共同的業務意義。暫緩 rollout 後 crash 總數下降，至少有兩種解釋：同樣的使用條件下錯誤變少了；或者接觸新版的使用者變少，錯誤只是少了發生機會。只拿總數回饋給 agent，這兩種情況長得一樣。要讓回饋有辨識力，比較單位就要先定下來：同一個版本、同一種觸發條件下，每千次 session 發生幾次 crash，而不是全站的 crash 總數。分群之後仍可能有偏差，例如新版使用者剛好集中在某個地區或機型；分不開的時候，結論就只能保留為假設；暫緩之後也可能根本沒有相同觸發條件的曝光，分母是零就不能判定修補有效，只能安排受控的觀察。這裡的 session 指 App 的一次使用，不是前面 agent 的工作階段；曝光與 crash 的量測口徑要有人負責確認，資料源漏記 session，標準化後的比例仍會誤導。MCP 解決的是取得資料，沒有驗證量尺。這是我的推論，keynote 沒有談到這個案例。MCP 讓查這些證據變容易；哪個觀察足以支持哪個結論，仍來自團隊對問題的理解。

### 請求可以無狀態，任務與授權仍要接得下去

回饋還有一個時間問題：結果晚了二十分鐘才回來，原本處理請求的執行單元（worker）已經換了一個，這份回饋還找得到原來的任務嗎？他後面談的請求傳送與任務接續，處理的就是這件事：2026-07-28 的核心規格讓每筆請求自帶版本與能力資訊，減少對先前連線脈絡的依賴，這就是 stateless 的意思；Tasks extension 則像先拿一張案件編號，稍後憑編號查進度、領結果。[8] 但請求可以無狀態，工作本身仍有狀態：已蒐集哪些 crash、哪一份修補還在驗證、誰核准暫緩 rollout，不會因為傳輸層改成 stateless 就可以丟掉。工作識別只讓結果找得到，進度與結果怎麼保存、worker 更換後怎麼接續，仍由應用程式安排，而且它不會自動使外部操作只執行一次。這些交接問題第二篇展開。

身分委派處理的是另一個時間差。啟動調查的是某位工程師，真正呼叫工具的可能是另一個服務，而二十分鐘後那位工程師的權限也可能已改變。若系統只知道「這個 agent 有一把可用的鑰匙」，就無法解釋它此刻代表誰、為哪件事採取行動。他說授權與身分可能不是技術上最有趣的部分，卻是 agentic 系統概念上最重要的部分之一；這和長時間任務直接相連。[7] 第二篇會沿著這個問題往下走。

取得版本與曝光資料之後，仍需要程序規定怎麼比較、何時不得下結論；新加入的同事如此，agent 也一樣。這份工作程序的缺口，正是下一場 Skills 要處理的問題。

**工具接通之後，團隊仍要讓回饋能分辨結果，並讓任務進度與行動授權都有依據可查。**

## 五、從找到工作程序，到決定是否採用更新

Nordstrom 的 Ola Hungerford 同時是 MCP 的維護者。她在〈Skills Over MCP: From Experiment to Extension〉說明如何把專業知識、工作程序與工具一起提供給 agent，從社群實驗走到協定擴充（[官方議程](https://agntconmcpconjapan26.sched.com/event/2QlLo/keynote-skills-over-mcp-from-experiment-to-extension-ola-hungerford-principal-engineer-nordstrom)、[演講影片](https://www.youtube.com/watch?v=3oHLjC3wZNE)）。這一場回答「允許嗎」裡最容易被忽略的一題：agent 拿到的工作程序，是誰核准的那一版？

先用新同事來想。給他一個 SOP 資料夾，裡面有一頁總覽、一份步驟，還有幾個腳本和參考文件，這就是一份 skill。工具說明告訴 agent 每個工具能做什麼，卻不告訴它該用什麼順序、什麼條件下該停下來。放回 crash 調查：agent 會查 crash、讀程式、改開關，但它不一定知道應該先比對版本再檢查 rollout，也不知道證據不足時要保留假設，不能看到時間最接近的 commit 就宣布根因。這些知識跨越多個工具，正是能力與程序之間的缺口。[9]

### 先找到程序，再按需要載入

過去 skill 與 MCP server 常透過不同管道安裝：工具從一條路來，程序從另一條路來。使用者可能已經升級工具，卻還沿用舊程序。她的比喻是把說明書和工具裝進同一個箱子出貨：一個管道、一套存取控制、一種版本方式。[9][10]

投影片把讀取拆成三個時刻。先讀一個精簡入口，知道這份 skill 用來做什麼；確定需要它，再載入 `SKILL.md`；實際走到某個步驟時，才讀取相應的腳本與參考檔。像翻一本手冊：先看封面，需要才翻開，走到那一步才拿附件。這個順序讓讀取成本跟著工作需要增加，也避免把和目前工作無關的程序全部塞進模型這一輪能讀的內容（context）裡。

📌【在此插入圖 asset-07.png】

Ola Hungerford，Skills over MCP [06:10](https://www.youtube.com/watch?v=3oHLjC3wZNE&t=370)：Three reads，把發現、載入程序與讀取支援材料拆開。來源：AAIF 官方錄影。


放回 crash 案例，host 先看到「調查行動裝置版本回歸」的描述，需要調查時才讀步驟，走到 Android 堆疊分析才取得對應材料。這把工作分成兩次判斷：先決定值不值得讀，再決定讀到的程序怎麼用。入口描述若沒讓 host 辨識出適用情境，內容再詳盡也到不了執行階段。因此「加了 skill 沒改善」還不是足夠精確的診斷：先檢視它是否被找到、是否真的載入必要檔案；若漏在發現階段，就固定程序內容、修改描述，再檢查同一批適用與不適用任務的選取結果；若已載入卻走錯步驟，才回到程序本身。

截至 10 月 25 日，這套做法已是 MCP 的正式可選擴充（extension）：提案編號 SEP-2640 的狀態是 Final，定義 `skills/list` 與 `skills/get` 等發現介面，檔案則沿用資源讀取機制。規格狀態是一回事，產品支援是另一回事：這不代表每個 host 都支援相同的載入與核准流程，導入前仍要核對自己的 host 怎麼實作。[10]

### 來源與內容要一起核對

取得程序之後，另一個問題才開始：這次拿到的內容，和先前核准的那份相同嗎？講者用「哪一台 server 上的哪一份程序」識別一份 skill，技術上是 server 加上這份程序在它上面的位址（URI）；不能只靠同名的「crash-investigation」，就把兩個 server 的內容視為同一份程序。內容則靠內容指紋核對。指紋（digest）是根據檔案內容算出來的一串字，內容改一個字，指紋就不同；host 拿它比較的是「這次讀到的檔案」與「當初核准的檔案」。沿用 SOP 資料夾的比喻，核准的不只是那一頁總覽，還包括附件清單，以及每份附件的指紋。規格要求 server 列出完整的檔案清單，每個檔案的位址、指紋與大小都在其中，host 讀取時逐一核對；內容是動態產生的 skill，例如同一個位址每次依即時資料產生不同的程序，無法提供穩定指紋，就必須標成 dynamic。兩條路的保證不同：完整清單可以逐檔核對；dynamic 的內容每次都可能不同，舊核准涵蓋不了新內容，host 可以拒絕載入。[10]

📌【在此插入圖 asset-08.png】

Ola Hungerford，Skills over MCP [07:36](https://www.youtube.com/watch?v=3oHLjC3wZNE&t=456)：skill 的來源識別與內容變更，是取得工作指引之後仍需處理的問題。來源：AAIF 官方錄影。


這裡有兩個容易混淆的地方。第一，指紋相同只證明內容相同，不證明內容可信：指紋和檔案都由同一個 server 提供，正確的指紋也可以對應一份錯誤的程序。第二，內容檢查不能只看 `SKILL.md`。文字沒變、它呼叫的腳本改了，實際行為仍然不同；再往下一層，腳本沒變、它呼叫的工具換了版本，行為也可能不同。內容指紋保護的是程序文字與附件；工具與執行環境的版本，規格沒有替我們保存。我會這樣分：平台保存工具契約與環境版本，程序維護者確認相容範圍，任一項變更就觸發對應的回歸；代價是要維護完整的依賴關係。執行期間應保留當初核准的那份清單，之後 server 多出一個檔案，不能因為重新列目錄看得到就直接納入；讀到的內容不符摘要時，應停止使用並更新判斷。

我在〈[Harness 藍圖](https://medium.com/p/f2a139f5b561)〉第二節把 AGENTS.md 依適用範圍分成 Org、Repo、Dir 三層，各有負責人，再用自動建置流程（CI）檢查文件裡的指令是否失效、用一組固定的代表性任務（golden tasks）在文件改版後重跑，比較結果。那篇處理的是組織內的文件治理，三層分發與維護都在自己的團隊之間；Skills 多出來的問題，是跨來源的識別，以及程序從別的 server 分發過來之後，host 的核准怎麼綁定到完整的內容。OpenAI 今年 2 月的〈Harness engineering〉也談文件治理，本文未取得原文全文，只列為延伸閱讀。[11] 程序能被機器分發，就要像程式一樣有版本、有核對、有人負責。

### 驗證更新時，把授權要求留在比較裡

程序效果因此還要另外驗證。把「先請值班人員確認」改成「符合條件就暫緩 rollout」，即使一行應用程式碼都沒改，決定由誰作出的約定已經變了。若只比較調查完成時間，新程序可能因為省去核准而看起來更快，卻違反原任務。驗證的預期應先來自服務負責人確認的要求，再交給新舊程序接受同一組案例的檢查。即使工具最後攔住越權動作，也不能把程序嘗試越權的行為算成改善。

研究量到的是效益差異，不替授權變更的驗證背書；但它支持逐項檢查。SkillsBench 在七組 agent 與模型配置、7,308 條執行軌跡上比較沒有 skill 與人工整理的 skill，其中 Claude Code 與 Codex 的五組配置再加比較模型自己產生的 skill：人工整理的 skill 跨領域平均提高通過率 16.2 個百分點，但軟體工程分組只有 4.5 個百分點，84 個被評估的任務裡有 16 個反而退步，自己產生的 skill 在該設定下沒有平均效益。[12] 跨領域平均不是 crash 調查程序能預期的收益；值得記住的是任務間的退步與領域差異。 對維護者而言，知道哪類任務改善、哪條要求退步，才足以決定接受更新、縮小適用範圍或退回修改。

**更新一份 skill 時，應分開驗證它能否被找到、內容是否與核准的那版一致，以及實際行為是否仍符合任務要求。**

## 六、請求失敗後，哪些事情可以安全重試？

Anthropic 的 Camila Rondinini 在〈Running an MCP Proxy at Scale〉分享替產品連接大量外部 MCP 服務的經驗，聚焦三件事：維持使用者的登入授權、減少對遠端服務的重複請求，以及出錯時辨認問題在哪一端（[官方議程](https://agntconmcpconjapan26.sched.com/event/2QlDa/running-an-mcp-proxy-at-scale-camila-rondinini-anthropic)、[演講影片](https://www.youtube.com/watch?v=e8DMLtP5ibk)）。這一場回答「發生了嗎」：請求失敗之後，我們憑什麼知道外面有沒有改變。

Proxy 可以想成公司的總機。員工不直接打給外面的服務，而是由總機代為轉接、代為出示證件；各家服務的差異集中在總機處理，員工只要記得一個號碼。[13] 它和第二節的 gateway 都是中介，兩個展示各自著重的職責不同：Kong 那場集中管請求能不能通過（它也轉送對外的模型請求），這場的 proxy 替自家產品對外連接各家服務並保管憑證；這是兩個案例的分工，不是兩個詞固定的進出分類。前一節核准了程序的內容，為什麼仍然無法知道一次呼叫有沒有生效？因為執行時會遇到憑證到期、網路中斷與多個 worker 同時工作，每一樣都可能讓「送出了」和「做到了」分開。

### 先處理憑證取得與更新的競爭

這裡的 token 和第二節計費用的 token 是同一個字、兩種意思：那裡是模型算錢的字數單位，這裡是進門用的通行證。Access token 是短期通行證，用來存取服務；refresh token 則是換發新通行證用的憑證。講者先點出一個比到期更早的問題：服務宣稱支援換發，不代表這次授權真的發了 refresh token。有的要求額外的授權範圍（scope），例如 `offline_access`，意思是允許使用者不在線上時仍能換發憑證；有的靠供應商自己的參數。連取得憑證的條件都沒弄清楚，再完美的更新迴圈也派不上用場。

接著是競爭。假設兩個 worker 同時發現通行證到期，手上又是同一枚 refresh token。像兩個人同時拿同一張舊證去櫃台換新證：若授權服務會在換發時作廢舊證，第一個人成功後，第二個人再拿舊證就會被拒絕；有些授權服務甚至把這種重複換發當成竊用訊號，把整組憑證作廢。增加重試次數沒有處理兩人競爭同一張證的原因。

她的做法是用分散式鎖協調：同一時間只有取得鎖的一方更新憑證；取得鎖之後，先重新讀取儲存的 token，再決定要不要換發。鎖控制同時進行的工作，重讀則修正排隊造成的資訊落差：排隊期間，別人可能已經把新證存好了。只加鎖、卻繼續使用進入等待前讀到的值，仍會把過期資訊帶到真正執行的時刻。投影片把鎖設成短效的：拿到鎖的一方才和授權服務說話，其他人只讀儲存的結果。[13] 我會再往下追一步：鎖到期時原本的 worker 若還在換發，接手者怎麼避免再拿同一枚舊 refresh token 去換？到期不等於競爭已解決，所以要替每家供應商填一張小契約：明確拒絕時能查什麼、換發回覆遺失時能查什麼、鎖到期時能查什麼，以及各自在什麼條件下必須停止自動恢復、改走重新授權。維持單一更新者的代價是等待，這段等待也要設計，不能只寫正常的競爭路徑。

等待策略也要分情境。通行證還有效時可以提早換發，其他請求暫時繼續用舊證；已到期就必須等更新結果。等待者還要知道前一次更新是不是失敗了，否則每個人輪到鎖後都再試一次，只是把同時爆發的重試改成排隊爆發。

### 結果未知時，先查操作與目前狀態

我會再往前問一步：授權服務已經換發新證，回應卻在網路中遺失，本地仍只有舊證，鎖能幫忙嗎？這是本文延伸的情境，不是講者披露的事故。鎖可以協調本地 worker，卻不能讓遠端換發與本地儲存一起成功或一起失敗。復原要依供應商的換發規則決定，必要時重新授權。[14]

這裡的差別是「明確被拒絕」與「不知道結果」。想想轉帳按下去之後網頁一直轉圈圈：錢到底扣了沒？對有副作用的工具也一樣。暫緩 rollout 的請求逾時後，呼叫者只知道自己沒及時收到結果，不能推論開關沒改。接下來應查目前狀態，或使用服務明確支援的操作識別與重送機制，再決定是否重試。否則我們把通訊失敗，錯當成業務操作沒有發生。

不過，查到「現在已暫緩」也只回答目前狀態，未必證明是剛才那筆請求造成的。可能另一位值班人員已先操作，也可能查詢期間又有新變更。若接下來要判斷這筆操作是否完成、是否應補償，就需要能關聯到原請求的結果紀錄，或服務提供的版本與條件檢查。先看目標是否達到，再分清哪些行動能歸到這次任務，才不會為了「復原」撤銷別人後來的合法變更。

### 錯誤要能定位，快取要能失效

演講對錯誤分類的處理因此很實際。沒有收到回覆、HTTP 層的回覆、JSON-RPC 的錯誤、工具結果，是四種不同的情況。用同一筆「暫緩 rollout」的請求來看：HTTP 回覆可能來自中間的 proxy 或 gateway，說的只是那一層怎麼回應，收到 504 之後，後端仍可能已經執行；JSON-RPC 是 MCP 使用的訊息格式，它的錯誤可能是找不到方法、參數不合規，或訊息本身無法解析；工具結果裡的 `isError` 說的是工具回報了失敗，可能在檢查參數時就拒絕，也可能做到一半。這些狀態用來定位回應在哪裡失敗，不能拿來判定外部效果：工具可能先改了開關，才在後續步驟失敗，HTTP 成功也不證明目標狀態已經成立。操作是否生效，要看操作回執與目標狀態；任務是否完成，再依原要求驗收。同樣是 401，沒有附上憑證和附上被拒絕的憑證，處置不同；404 也可能是失效的 session 或錯誤的服務位址。全部化成「工具失敗」，接手者就失去了決定更新憑證、重新授權、退避或修正設定所需的資訊。

她也給了數字，但口徑要說清楚：投影片統計的是換發失敗的錯誤分布，約 74% 符合 OAuth 規格、10% 是 HTTP 伺服器錯誤、16% 是其他非預期回應，例如端點消失的 404、回了 2xx 卻沒有 token；口述時她說的是「只有 74% 的服務」，兩者分母不同，本文只採投影片的分布，不下服務比例的判斷。[13] 規格外的錯誤讓 proxy 不知道該重試還是放棄，只能逐家學習。這提醒我們，「可以安全重試」不是通用常識，而是每個服務各自的契約。

Camila Rondinini 演講 [17:00](https://www.youtube.com/watch?v=e8DMLtP5ibk&t=1020)：一筆請求彙整成結構化紀錄，保留上下游結果與失敗位置。來源：AAIF 官方錄影。


一筆請求保留一份可關聯的結構化紀錄，能把下游使用者看到的錯誤、上游回應與當時的憑證狀態接起來。團隊可以先找失敗所在層，再決定找哪個維護者，而不是先要求模型換一句提示試試看。〈Harness 藍圖〉第五節的 legibility checklist 已要求 log 附上可關聯的 request id、版本與環境；proxy 的紀錄多出來的是上下游各自的結果、當時的憑證狀態與失敗所在的那一層，這些欄位會直接改變處置：更新憑證、重新授權、退避，還是修正設定。紀錄不應包含憑證內容，卻應留下足以判斷有無附帶、是否更新及何處被拒絕的狀態。

失敗紀錄處理的是呼叫結果；重試還有另一個前提：快取的工具清單仍列有某個工具，不代表此刻仍有執行它的權限。講者提到約 92% 的受觀察 server 對不同使用者回傳相同的工具清單。這個觀察指出的是可以省下的重複請求；實際要跨使用者重用一份清單，仍要符合 server 自己的宣告與快取契約：官方快取規格要求 private 回應只在相同授權脈絡下重用，而且工具執行仍要授權。[15] 分母是 server，觀察對象是清單相同；它不能推論所有使用者的執行權限相同。問答裡有人問到依角色配置的存取權限（RBAC，例如值班工程師能建 PR、實習生只能讀）改變後怎麼辦，她的回答是快取必須失效，而且 proxy 在收到請求時知道使用者是誰，可以在那一層再檢查一次。[13]

不過，proxy 的紀錄只涵蓋經過它的那條路。Agent 在本機執行的 shell 指令、直接連出去的其他工具，有沒有在觀察範圍內？下一場提供另一種部署方式，讓我們檢查限制是否涵蓋整條路徑。

**是否重試，應由失敗所在的層、仍有效的授權與可查證的操作結果一起決定；三者都不是從錯誤訊息猜出來的。**

## 七、模型搬回私有環境，整條工作路徑也要接通

Red Hat 的 Daniel Oh 在〈Build Your Own Open-Source Claude Code With Local LLMs〉示範如何組合開源開發工具與本機或私有模型，建立能讀取程式、提出修改的 coding assistant，並討論資料保護與操作限制（[官方議程](https://agntconmcpconjapan26.sched.com/event/2QlEY/build-your-own-open-source-claude-code-with-local-llms-daniel-oh-red-hat)、[演講影片](https://www.youtube.com/watch?v=kwKVe27xnw4)）。這一場先回答「允許」的範圍：哪些資料能離開、哪些指令能執行；至於「發生了嗎」，只有實際的讀寫與連線紀錄才能回答。

演講開頭點出的兩難很熟悉：開發者希望 coding assistant 能完成工作，平台與資安團隊則要知道程式和資料在哪裡處理、誰能使用哪些能力。如果程式與資料需要留在自己的環境，把模型部署在本機或私有環境就有明確價值。[16]

### 私有部署需要重新分配營運責任

他的架構把幾個工作拆開。OpenCode 提供開發者互動與 agent 工作迴圈；LiteLLM 處理模型介面、路由與配置；模型由自己的推論服務提供；搜尋檔案、修改程式與執行測試，則由工具所在的執行環境負責。拆開來看，團隊才知道某個問題該從哪裡調整：換模型、增加服務資源，和限制 agent 透過終端機啟動其他程式（shell）的範圍，不是同一個設定。

Daniel Oh，私有 coding assistant 演講 [10:50](https://www.youtube.com/watch?v=kwKVe27xnw4&t=650)：模型服務、開發工具與執行環境需要一起考慮。來源：AAIF 官方錄影。


共用程式呼叫介面（API）的好處，是 assistant 可以用熟悉的介面呼叫不同的推論服務。但介面接受同一種請求，不代表不同模型會同樣可靠地選工具、保留限制或產生可編譯的修改。若筆電放不下需要的模型，私有叢集可以提供另一種資源；相對地，模型服務的容量、更新與可用性就成為自己的營運工作。

### 資料邊界必須在讀寫與連線時生效

完整的 coding 工作不止一個模型回應。Agent 先讀專案內容、安排步驟、修改程式，再執行建置與測試，把結果帶回後續修改；最後才走到人工審查、記錄版本（commit），以及自動建置與測試的持續整合（CI）。任何一個階段都可能接觸資料或造成副作用。「推論留在內部」只回答其中一段資料流，還要確認工具能讀什麼、寫什麼，以及能連到哪裡。

講者列出的控制有四類：遮蔽憑證與金鑰、封鎖 `sudo` 或對外 `curl` 這類危險指令、用靜態分析（不執行程式就查出危險寫法）檢查不安全的程式碼，以及在建立目錄、存取舊系統資料庫、改資料表結構或安裝相依套件這類關鍵動作前要求人工確認。[16] 這裡要分清「封鎖指令」與「限制效果」：擋下 `curl`，同一個連線仍可由其他程式發出，真正要限制的是對外連線這個效果。驗證因此要涵蓋 agent 實際使用的每個入口，檔案工具、shell 與 MCP server 都算，並記下沒有測到的通道。〈Harness 藍圖〉第四、六節已經指出白名單的限制，允許連 GitHub 不代表允許把資料寫進公開的 comment，也要求檢查內容與目標範圍；本篇新增的是下一段的做法：經實際入口送出越界請求，確認效果被拒絕。真正值得繼續問的是，這些控制放在哪個時刻，以及團隊如何知道它們生效。

Daniel Oh 演講 [18:20](https://www.youtube.com/watch?v=kwKVe27xnw4&t=1100)：秘密資料遮蔽、指令過濾、程式碼分析與人工確認。本文進一步追問如何驗證這些控制生效。來源：AAIF 官方錄影。


最後的人工 review 能檢查修改前後的差異（diff），卻無法撤銷 agent 十分鐘前已透過網路送出的資料。限制若要阻止那個效果，就必須在讀取或對外傳送的路徑上生效。OpenAI 的建置指南建議替每個工具評一個風險等級：看它是唯讀還是會寫入、能否回復、需要什麼權限、有沒有財務影響，再決定高風險工具是否要先暫停等人核准。[3] Anthropic 談 Claude Code 的隔離執行環境時，也把檔案系統隔離與網路隔離分開處理，用執行環境限制 agent，而不是只靠模型遵守指示。[17] 每一層都有用途，團隊要知道哪一層在模型選錯動作時仍然會攔住它。

### 同時驗證工作能完成、越界會被拒絕

延續 crash 案例，我會準備沒有敏感資料的測試環境：工作目錄放可修改的範例程式，目錄外放不得讀取的假秘密檔案，再準備可觀察的測試網路端點。這種「只有指定目錄可寫、指定端點可連」的隔離環境，就是一般說的 sandbox。先讓 agent 正常找出錯誤、修改與執行測試，確認允許的工作能完成。這是本文的驗證設計，尚未在生產環境實測。

接著要另外驗證限制本身。正常流程沒有讀到假秘密，可能只是 agent 沒選那個動作；這不能告訴我們，選錯時環境會怎樣。測試應透過實際使用的工具入口，明確送出跨目錄讀取、唯讀位置寫入與未允許的對外連線，並觀察檔案、行程與接收端。如此才分得出「這次沒有嘗試」與「這條路徑確實拒絕」。這和《綠燈不是驗收》可靠度篇第二節把 review 約束寫成 constraint tests 是同一個習慣：規則要寫成會失敗的檢查，才知道它有沒有在守。那篇驗的是程式與合併約束，這裡驗的是執行環境有沒有真的拒絕指定的效果。

這兩組結果要一起看。全部拒絕也能得到零次越界，卻可能連建置所需的套件都抓不到；全部開放則讓正常案例很順，卻沒有維持資料邊界。平台負責人要找的是能完成授權工作、同時拒絕指定越界效果的配置；一個同時滿足兩邊的驗收例是：建置需要的套件能從允許的套件庫取得，而未允許的端點收不到任何資料、假秘密檔沒有被讀取，觀察的是接收端與檔案，不是拒絕訊息。錄影片尾仍在確認建置結果，28:00 畫面也有編譯錯誤。展示讓架構與操作過程可見，沒有提供私有模型與外部服務的受控比較；若要比較品質、完成時間或成本，必須記錄模型、工具、記憶體、執行時間與任務條件。[18]

**我會先在小型工作範圍內，同時驗證任務品質與執行邊界，再決定是否擴大私有部署。**

## 八、哪些調查步驟應該固定，哪些需要模型判斷？

Uber 的 Kriti Dangi 在〈MCP-Powered Crash Investigation〉介紹 Debug Assist：它把錯誤紀錄、程式搜尋、原因調查、修補與測試接成流程，最後交出供工程師檢視的 PR（[官方議程](https://agntconmcpconjapan26.sched.com/event/2QlDI/mcp-powered-crash-investigation-how-11-mcp-servers-help-an-ai-agent-debug-production-issues-at-uber-kriti-dangi-uber)、[演講影片](https://www.youtube.com/watch?v=iVCDIOf7vXw)）。這一場回答「完成了嗎」最具體的一段：一條線索要經過什麼，才變成值得交給工程師的工作。

回到那個 crash 調查。Agent 現在可以取得資料、載入程序，也有一個能執行修改的環境；但它提出的「開關打開後出現異常」還只是一條線索。若此時直接要求它寫修補，等於替尚未證實的原因選好了處置。這套系統值得仔細看的正是中間這段。[19]

### 固定資料蒐集流程，把判斷留給需要推理的步驟

Uber 不是先有 agent，才開始蒐集事故資料。演講先介紹既有的 Wisdom 使用者回報，以及 Healthline 自動捕捉的 crash 與效能訊號：版本、裝置、城市、各種 log、截圖與 stack trace 早就有收集來源。這個前提很重要：如果自己的團隊連問題發生在哪個版本都查不出來，接上同樣數量的 MCP server，也不會憑空補出可用證據。

在資料來源之上，他們用 LangGraph（一個安排多步驟流程的工具）把流程排成固定順序，而且刻意分成兩種節點。已知該從哪些 API 取得資料，就讓資料蒐集器（context collector）照預先寫好的程式執行，順便把過大的 log 整理過；後面的根因分析（RCA）、修補、建置測試與建立 diff 四個節點仍然使用模型，但順序由流程控制，每個節點各有指定的模型與回合上限。Anthropic 的工程文章把「由預先寫好的程式路徑安排模型與工具」稱為 workflow，把「由模型自己決定流程與工具」稱為 agent，並建議能用前者就先用前者。[2] Uber 的做法正是兩者的混合：能寫死的步驟寫死，需要推理的節點才交給模型。這同時減少每次重新規劃的成本、等待時間與無關內容，也讓資料漏失和推理錯誤比較容易分開定位。代價是流程維護：固定的蒐集器依賴穩定的資料契約，新型事故需要還沒接上的資料來源時，流程不會自己長出來，要有人擴充，或在那一步轉給人處理。省掉每次規劃的錢，是用維護流程的錢換來的。固定流程也要有停止條件：事故類別不在既有的資料契約內，就不能繼續把缺資料送進 RCA，要在那一步轉人工。

不過，整理 log 也可能丟掉原因所在的那一行。我會要求調查者知道摘要出自哪些原始材料，必要時能回頭讀取，並分清「沒有觀察到」和「已被刪去而無從判斷」。壓縮的目的是讓推理集中；如果連證據來自哪裡都消失，後面的人就很難反駁一個過度自信的結論。

RCA 階段先判斷問題比較可能來自自己的程式、第三方套件、網路還是基礎設施，再輸出類別、是否需要改程式與信心估計。若問題不在程式，直接要求生成修補只是製造一份無用 diff。信心估計可以幫助安排路徑，但它仍是系統的估計；沒有和實際結果校準，不能把一個高分當成根因已證實。子代理也有具體分工：一個整理使用者操作的時間線，一個比較版本與 crash 的關係，另一個在給定「最後正常版本」與「首次異常版本」的範圍內找出可疑的 commit。兩個子代理都說同一件事，不等於兩份獨立的因果證明，它們可能讀到同一組錯誤資料。

投影片還分配了不同模型與最多互動回合數：RCA 用較小的模型、上限約 20 回合，修補用較強的模型、回合數較高。講者說，試誤之後發現超過 20 回合通常表示走錯方向。回合是這套 harness 自己的計數單位，留存材料沒有給精確定義，不能直接換算成工具次數或通用的成本門檻。回合上限控制的是消耗，不能判定資料足夠：缺原始 log、證據互相衝突或無法重現時，要有轉給人的出口，不然固定流程會把缺資料包成高信心的結論。這和 OpenAI 建置指南裡「超過失敗門檻就交回人」的觸發條件是同一件事：把成本與停止條件放在各階段，而不是讓一個 agent 在所有工具之間無窮迴圈。[3]

### 從線索走到修補，先建立有辨識力的重現

回到功能開關：開啟後 crash 增加，可以成為調查方向，卻不足以證明因果。Uber 的做法是，若開關與 crash 的關聯很強，就先把開關關回去，讓影響止血，再慢慢修。演講沒有交代這一步的核准機制；本文的委託不把相同權限交給調查 agent，關閉開關要另外核准。緩解可以在因果尚未完全確定時進行，依據是當下影響、撤回代價與授權政策，不是模型的信心分數；它不必等根因全部確定，也不能拿來替修補的正確性背書。

要往修補前進，就得重現原來的錯誤。問答裡講者說得很實際：能用單元測試重現就用最短的路，不行再用元件或整合測試，真的無法用程式重現，才動用模擬器。她舉的例子是機場附近網路很弱時才出現的問題：她以這個案例說明單元層級的重現不夠，於是用既有的模擬器基礎設施重建網路強度與功能開關狀態，反覆建置並測試，直到通過或達到重試上限。[19]

先用一個例子。假設調查發現 crash 可能發生在網路請求逾時後，畫面繼續使用尚未取得的資料；這是分析用的例子，不是 Uber 披露的根因。若產品要求是「逾時時保留可重試的錯誤狀態，不要閃退，也不要顯示操作成功」，重現就必須把逾時和後續畫面行為一起帶進測試。為什麼只測不會 crash 還不夠？一份修補可以吞掉所有錯誤，讓畫面不再閃退，卻把失敗的操作顯示成成功；另一份修補保留錯誤與重試入口，也不會閃退。只看 App 是否繼續運作，兩者都會通過；檢查使用者仍能辨識失敗並採取下一步，才把它們分開。預期答案應來自已確認的產品要求，不能由 agent 選了哪種修法反推。

接著才看修補前後。測試在原版本必須因這個缺陷失敗，且不是缺套件或環境壞掉；修改後通過，才支持缺陷已被這項檢查辨識並修正。《綠燈不是驗收》[測試篇](https://medium.com/p/b01055139451)第五節把這個順序叫 red-then-green：先紅再綠，紅燈證明測試看得見這個缺陷。Anthropic 談 agent eval 時把這件事說得很直接：真正該評的 outcome 是「環境最後的狀態」，例如資料庫裡那筆預約真的存在，而不是 agent 聲稱它存在。[20] 重現條件、觀察對象與預期從哪裡來，合起來才是 reviewer 能用的驗證。

### 把驗證依據交出去，才有可接手的 PR

這套流程打包成共用的執行環境，按 agent 類型載入需要的 skill 與 plugin；plugin 是 Uber 市集裡的擴充套件，可能包含 skill 與工具配置；它和第五節的 MCP 分發不一定是同一種封裝或核准機制，共通的是程序要有人維護。平台團隊維護 harness，領域團隊提供調查知識；講者說 Uber 的 skill 市集已有約 3,000 個 plugin，所以不能全部塞進一個 agent，只能依類型挑選。這種分工讓新領域能接入，也要求領域程序與共同流程各自有版本、驗證和維護者；接手 PR 的工程師，也要能取得同一版的流程與程序，才能重跑驗證。這個分工可以接回我在〈[組織篇](https://medium.com/p/9d9353ef7f3a)〉第二節的責任分工：蒐集器程式漏取資料，由平台修；來源根本沒收資料，由資料來源的 owner 補；領域契約缺欄位或領域 skill 誤判，由領域團隊改；工具越權，由平台的權限政策擋；production 的責任仍在領域團隊。

Uber 演講 [19:55](https://www.youtube.com/watch?v=iVCDIOf7vXw&t=1195)，slide 14。圖中數字是團隊自述；RCA accuracy、PR merge rate 與事故實際消除，是不同層次的結果。來源：AAIF 官方錄影。


數字也要回到它回答的問題。演講畫面與口述是：每月約 9,000 次 RCA；與工程師最後的修法比對，RCA 準確率 50%；剩下的一半裡又有約四成方向正確；PR 合併率從一年前的 5% 升到約 48%。影片說明欄仍是約 5,000 次與 5% 到 30% 的舊版本；本文採用演講畫面與口述，不把兩個版本拼在一起。[19] 這些是團隊自述的規模與方向，沒有足以重建比較的取樣期間、判定細節與控制條件。RCA 被認為正確、PR 被接受、事故在使用者環境中消失，分母各不相同；把合併率叫成「自動修好事故的比例」會跳過部署與上線觀察那段工作。

我認為最值得帶回團隊的，是交付內容的改變。一份可接手的修補，應一起交出假設、資料來源、重現方式、修改、測試，以及還沒確認的條件。接手者才知道自己是在核對結論、補一塊證據，還是決定先做風險較低的緩解。

PR 通過驗證之後，受測對象換了：上一節驗的是修補，下一場驗的是調查者本身，它在生產環境裡仍可能做錯。

**好的修補交接，應讓下一位工程師能沿著證據核對根因、驗證修改，並看見還沒回答的問題。**

## 九、從生產錯誤找到真正該改的地方

Pydantic 的 Marcelo Trylesinski 在歐洲場的〈Self-Healing Agents Need Observability〉，用 agent 的執行紀錄追查錯誤，再展示如何提出指令修正、檢視變更並決定是否採用（[官方議程](https://agntconmcpconeu26.sched.com/event/2WNSu/self-healing-agents-need-observability-marcelo-trylesinski-pydantic)、[演講影片](https://www.youtube.com/watch?v=JzBLYv1BTTM)）。這是我回台北後補看的一場。它回答「完成了嗎」的下一層：上線之後發現沒做對，該改哪裡，又怎麼知道改對了。

他的出發點是，再完整的事前評估也猜不到使用者會問什麼，所以要先上線，再從實際執行紀錄找問題。我接受這個主張，但會限定範圍：先從唯讀查詢、草稿輸出或一小部分流量開始，有外部效果的動作仍先驗證再開放；生產裡的學習有價值，不代表每一種失敗的代價都付得起。展示中的旅客要重新安排行程：隔天早上要到柏林、帶著腳踏車、預算 €250。整次重新安排行程是一條 trace，其中一次查班次是一個 span（和程式錯誤的呼叫堆疊 stack trace 不是同一種 trace）。展示中的 trace 保留了已納管的步驟、工具互動與結果，讓調查者能往前追；沒有 span 的步驟不等於沒有執行，缺失的紀錄要列為待查。往前追的是：agent 有沒有保留旅客要求、選了哪個工具、把什麼參數交給訂位服務。只看最後一句「已完成」，看不到這些決定如何發生。[21]

### 先分清要求被放寬，還是工具參數用錯

13:40 的提案畫面裡有兩個值得分開看的修改。第一個釐清：預設容許十五分鐘的抵達差異，不可以凌駕旅客明確表示不願放寬的要求。第二個要求訂位時使用搜尋結果的 `offer_id`，不能拿 `route_id` 代替。前者是誰有權改變要求，後者是工具介面裡兩種識別的意義，它們不該被壓成同一個「模型不夠聰明」。

📌【在此插入圖 asset-16.png】

Logfire 演講 [13:40](https://www.youtube.com/watch?v=JzBLYv1BTTM&t=820)：提案釐清旅客條件的優先順序，並修正訂位所需的 offer_id。來源：AAIF 官方錄影。


第二種錯誤有一個很便宜的預防方式。Anthropic 談如何替 agent 寫工具時建議，參數名稱要讓人一眼看懂指的是什麼，例如用 `user_id` 而不是 `user`，也建議把難以辨認的識別碼換成有意義的名稱，因為模型選錯參數的機率會跟著降低。[22] 把搜尋結果裡的路線識別當成可訂購方案的識別，字串格式可能完全合法，工具收到的物件卻不對。改善說明可以減少選錯的機會；工具仍應在產生訂位效果前核對：屬於這次搜尋、仍有效的 offer 可以送出；route_id、過期的 offer 或其他使用者的 offer 要被拒絕，而且訂位資料裡沒有新增紀錄，這才把「工具回報失敗」接到「外部效果未發生」。這組正反例就是工具的契約，可以直接驗收。

如果旅客已經說不能晚到，系統再套用預設寬限，就算訂到票，任務仍然做錯。我會依這個展示設計一對案例：兩者的搜尋結果都只有同一個可訂方案，預算與腳踏車條件都符合，但抵達時間比期限晚十分鐘；第一位旅客明確不接受延後，第二位則明確同意十五分鐘內的彈性。第一種情況應回報沒有符合條件的方案，第二種則可以接受。若新提示只是把所有稍晚的方案一律拒絕，第一個案例變好，第二個卻失去原本允許的選擇。這是我的驗證設計，沒有聲稱演講已執行這組對照。

### 把生產錯誤變成有明確預期的測試

Trace 的價值在於幫團隊找到該改的位置。有些失敗來自模型誤解指令，有些來自工具參數的規則或識別，有些只是供應商服務、資料庫或執行環境出錯。若把所有失敗都交給負責提出修改的那一方（展示裡叫 optimizer），模型可能用更多文字繞過一個原本應修正的程式缺陷。先確定哪一層出錯，才知道該由程序維護者、工具開發者或平台工程師接手。

事前準備的 eval 與生產 trace 因此各有工作。Eval 用一組任務與事先定義的判準評估行為，提供可以比較新舊版本的固定條件；生產紀錄帶來原先沒想到的要求與失敗路徑。後者需要被整理成有明確預期的案例，才能檢查下一個版本。用旅客案例分清兩個角色：一個模型提議改指令，另一個模型依保存的旅客要求替結果打分，人決定是否採用；前者展示裡叫 optimizer，後者一般叫 LLM-as-judge。我在〈[Eval、單位經濟與規模化](https://medium.com/p/d6d9623c2dc6)〉第二節提過 LLM-as-judge 的三個陷阱，其中之一是 judge 與受測模型共享盲點；展示裡 optimizer 只提出修改，由人檢視後套用；但若讓它連判準一起改，再用改過的判準驗收，就會同時決定「應該做到什麼」與「自己有沒有做到」，判準來源與角色混在一起，這是我延伸的失敗分析。兩者不同，卻都需要一個獨立的判準來源：旅客說不能放寬的條件，必須獨立於修改提案保留下來。

還有一個取樣問題。保留下來的 trace 不一定代表全部流量；若特別保留錯誤或緩慢的請求，那批材料適合找問題，不能直接拿來算整體失敗率。[23] 新提示讓這批失敗案例變好之後，仍要檢查正常案例，以及未參與調整的保留案例；可靠度篇第五節的 frozen holdout 講的正是這批不拿來練習的題目；它和前面的 golden tasks、後面的黃金資料集要分開：代表性工作拿來比較版本，人工標記資料拿來校準評分器，保留案例不交給 optimizer 調整。

### 回復舊版工作指引，仍要確認外部狀態

行為更新還要能追到版本。Logfire 的 managed variables 讓提示與設定不必重新部署就能更新，官方材料描述的模型是：版本不可變，標籤是可移動的指標，一個標籤指向一個版本。[24] 做法像這樣：production 指向第 3 版，少量試行的 canary 指向第 4 版，先把一小部分流量分給 canary，確認後再把 production 移到第 4 版。

取值的細節才是分析時的麻煩。事後要知道這一次實際使用哪一版，不能只記下會移動的標籤；一次任務可能多次取值，所以要先決定任務是固定一個版本，還是逐步保存實際用到的版本，否則同一個 trace 可能混用新舊程序，無法重現。遠端配置取不到時，程式會改用寫死的預設值；但預設值本身也是行為版本，若它保留了舊的十五分鐘寬限，配置服務出問題時就可能重新引入已修正的做法。這是本文延伸的失敗分析，不是演講報告的事故。

錄影在 13:29 保留人工檢視與套用提案，14:10 左右則說明自動產生 eval 在演講時尚未上線。[21] 有些決定仍留給人，正好使觀測、提案、驗證與採用各自有清楚位置。換回 crash 調查：改程序可能讓之後的調查更好，但不能撤回先前已寄出的通知、已修改的開關。Prompt 回復只改變後續採用的版本，外部狀態仍需另外確認。

到這裡，我們找到一種失敗並提出修改；是否改善，還要經過保留判準的驗證。下一場談的是另一種訊號：把生產對話分類、統計摩擦，它能診斷 agent 哪裡常被使用者修正，不能代替任何一筆操作的證據；它產出的紅線紀錄與校準結果，第十一節的決定會用到。

**生產回饋應讓團隊知道該改哪一層、如何驗證改善，以及哪些已發生的外部效果仍要另外處理。**

## 十、一次次任務之外，長期要觀察什麼？

PagerDuty 的 Inês Bolaños 是產品分析師，在〈From Clicks To Context: Building an Open-Source Evaluation Pipeline for AI Agents〉談的是另一種回饋：不是修一次錯誤，而是從累積的使用紀錄判斷一個 agent 該留、該訓練，還是該下線。錄影在 10 月 19 日上線，是本文最後補進的一場（[官方議程](https://agntconmcpconjapan26.sched.com/event/2QlEA/from-clicks-to-context-building-an-open-source-evaluation-pipeline-for-ai-agents-ines-bolanos-pagerduty)、[演講影片](https://www.youtube.com/watch?v=a7PuFJzgwGg)、[官方簡報](https://hosted-files.sched.co/agntconmcpconjapan26/57/From%20Clicks%20to%20Context_%20Building%20an%20Open-Source%20Evaluation%20Pipeline%20for%20AI%20Agents%20_%20Ine%CC%82s%20Bolan%CC%83os.pdf)）。[25] 它不回答單次行動的三個問題，而是提供長期的觀察訊號：一次次任務累積之後，使用者與 agent 之間的摩擦出現在哪裡。要不要續用、要不要擴權，第十一節另外談。

她的案例是 PagerDuty 內部的 SRE agent。簡報描述的是一次造成三小時 downtime 的訊息佇列消費延遲事故：log 散在各處、runbook 有好幾份、多位工程師一起處理；接上 agent 之後，它把線索接起來並很快提出修法。這是團隊自述，沒有同條件的前後比較。她沒有把這件事講成奇蹟，而是反過來問：怎麼用資料證明這種幫助是真的，而不是「agent washing」，也就是把舊技術貼上 AI 標籤。

### 先寫職位說明，再談要不要僱用

她的框架叫 H.I.R.E.，四個字母是僱用一個人時會問的四個檢查面向：人與習慣（團隊和資料準備好了嗎）、影響與意圖（替 agent 寫一份職位說明，列出職責、邊界與績效指標）、規則或推理（可預測的重複步驟交給自動化，模糊情境才需要 agent，她的比喻是「不要搭新幹線去隔壁」）、暴露與執行（最壞情況是什麼，守門的機制在哪裡）。本篇只用其中兩樣：職位說明裡的邊界，和守門的紀錄。

### 五個指標，量的是摩擦而不是點擊

她認為傳統產品指標在 agent 上會誤導：點擊數和使用次數量不出 agent 有沒有真的幫上忙。開源的 H.I.R.E. 專案定義了五個指標，每一個都對應使用者的一種反應：修正輸出、來回追問、放棄改自己做、一次就被解決，以及 agent 越界。要照算，就得知道每個指標的計算單位與分母；下表依固定版本的指標文件整理，盲點一欄是我讀文件時記下的提醒。[26]

### 讓評分器自己也被評分

這些指標的原料是對話紀錄，而對話是非結構化的文字。她建的流程分三步，用分流限制昂貴步驟的處理量；實際比例沒有公布。第一步用確定性的規則標記已知的事：從 agent 自己的程式碼知道它提供哪些控制、採取哪些動作，這一層沒有模型，少掉的是模型抽樣與版本更替造成的變動；規則仍可能分錯，所以規則也要有版本與正反案例。第二步讓便宜的模型把每則自由文字對到固定的類別清單，附上理由與信心分數；低於門檻的交給較強的模型再看一次，兩者都解不了的才進人工佇列。第三步先稽核被標成「其他」的那堆，再用分群方法找出反覆出現的新主題，候選成為新類別或新功能。

Inês Bolaños／PagerDuty，簡報第 25 頁：三步驟流程的回饋迴圈，以及「evaluate the evaluator」。來源：官方簡報。


這張圖有兩句話是我最想帶回來的。第一句是回饋迴圈：第二步發現「已知類別卻沒被觸發」，就把它寫成第一步的規則，確定性的覆蓋率因此上升。第二句是「evaluate the evaluator」：每一層模型都要對一組人工標記的資料打分，這組資料一般叫黃金資料集。做法像這樣：先由人把一批對話逐則判定，例如這一則 agent 建議了未授權的動作、那一則只是語氣不當；再讓分類模型對同一批對話分類，比對兩者的差異；信心門檻就是在這批資料上挑的，挑到一個把錯誤壓到可接受位置的值，而不是用猜的。這是框架的要求；本文沒有取得那個 SRE agent 的校準結果。我會另外要求三件事：挑門檻用的資料和最後報告準確率的資料要分開；漏判越權與誤判正常行為要分開列；高信心卻錯的分類不會進入升級路徑，要對高信心樣本做人工抽查。門檻調高，先增加的是交給較強模型的量，強模型解不了的才進人工佇列，未知類別暴增時兩者都會成為瓶頸，所以升級比例、人工處理量與等待時間要分列。這和我在〈Eval、單位經濟與規模化〉第二節提的人工抽查校準 judge，以及《綠燈不是驗收》對「agent 自己寫的檢查不能當驗收」的堅持相關，但新增的責任不同：分類器誤判會直接改變五個指標，進而影響產品決策，所以分類器的版本、人工標記的分歧與漏判／誤判率，要和指標一起進報告。

這套方法也有邊界。五個指標是為對話型 agent 設計的，放棄率還需要產品端的點擊資料才算得準；演講與簡報沒有公布那個 SRE agent 自己的分數；門檻也還沒有跨團隊的實證。但它把「使用者和 agent 之間哪裡在摩擦」從一句感覺變成一組可以每週算、每月比的數字，而且要求算分的工具自己先被檢查。

**摩擦指標幫團隊找到問題在哪裡；要決定續用，仍要合併任務正確性、事故影響、人工投入與總成本。**

## 十一、我會帶回團隊的：三個決定，和一張會議用的表

現在把假設的 crash 調查走完一次，每個決定都回答允許、發生、完成三題；三個決定屬於同一個調查，驗收對象與依據卻各不相同。Agent 已交出受影響版本、相關堆疊、開關變動時間，以及一份草稿修補；第十節的兩樣東西也帶進來：被擋下的嘗試有紀錄，評分器經過校準才算數。這份報告比最初的猜測有價值，因為同事可以回頭查它的來源；但是否要暫緩 rollout、接受修補或採用新調查程序，仍是三個各有理由的決定。下面是我會採用的導入方式，尚未在生產環境實測，也不是 AAIF 制定的驗收標準。

**第一個時刻，是在影響持續發生時決定怎麼止血。** 值班人員先確認受影響範圍、停止擴大 rollout 的代價，以及操作能否恢復。若現有證據支持暫緩，就明確核准這個對象與這次動作。這不需要假裝已經找出根因。執行後還要確認開關的實際狀態；若請求逾時，就保留結果未知、先查遠端紀錄，不能把「呼叫沒成功回來」寫成「沒有變更」。讀 crash、提出草稿與變更開關，應在一開始就分開授權，agent 才能繼續整理證據，值班人員也能及時止血，不必在「完全自動」和「什麼都不交出去」之間二選一。

**第二個時刻，是工程師決定這份修補值得接受到哪裡。** 重現測試在原版本因同一個 crash 失敗，修改後通過，而且相關回歸檢查沒有退步，這些證據才支持進一步 review。若現有測試原本就會通過，草稿裡最需要補的就是重現條件。接受 PR 之後，發布負責人還要安排部署與觀察：若暫緩 rollout 已讓新版流量減少，整體 crash 數下降並不能證明修補有效，應回到相同的問題分群比較。重現測試支持一個可解釋的修正，上線觀察則檢查這個解釋能否涵蓋真實環境。

**第三個時刻，是維護者決定這次經驗是否值得寫回共用程序。** 例如這次發現調查漏看了弱網路條件，就可以提案修改 skill。採用之前，我會直接沿用《同一份規格，跑十次》規格篇第八節的規格修改卡來填：這次改動預期改善什麼（補上弱網路條件的檢查）、哪些要求保持不變（先請值班人員確認的授權要求）、反例（正常網路下的回歸）、人工負擔（維護者審核與案例整理）、撤回條件（保留案例退步或越權嘗試增加），而且照那張卡的比較承諾，固定模型、工具、預算、停止條件，重複執行並記錄人工投入。那張卡原本處理的是一個團隊自己文件的修改；放到 skill 上，新增的問題是遠端分發的內容與執行期的版本怎麼被保存，這正是第五節的內容指紋與完整清單要回答的。變異篇第十、十一節也提醒：比較的名額買不到人工接手的成本，而資料不足時要有「仍未定」的出口。

把三個決定排成一張表，就是我想帶進週一會議的東西。每一列分開寫允許的依據、發生的紀錄與完成的判準；紀錄只是欄位，判準才會改變決定。全部是設計範例，欄位與負責角色要換成自己團隊的：

用一個最容易出錯的情況走一次這張表：agent 送出暫緩 rollout 的請求，逾時沒有回應，但遠端其實已經改了。第一列的紀錄裡要有委託人（值班工程師）、對象（哪個開關、哪個環境）、核准範圍（只准暫緩，不准關閉）、這次操作的識別，以及遠端回查後拿到的開關版本。「證據不足時」那一欄此時生效：本地只能寫「結果未知」，接著查遠端狀態與操作識別，確認那次變更是不是這筆請求造成的；查不到就交人工核對，不重送寫入；交給誰、多久內要接手、事故仍在擴大時往哪裡升級，依團隊的事故政策填進表裡。等待期間 agent 可以繼續唯讀調查，有疑義的寫入先凍結，「未知」不能變成沒有負責人的終點。第二列與第三列不受這筆逾時影響：修補的驗證仍看重現與回歸，程序更新仍看跨案例的得失。三個決定屬於同一個調查，各有驗收對象與依據；開關狀態會影響重現條件，調查結果會影響程序更新，所以紀錄要互相引用，判準卻不能互相代替。週一還可以拿一筆歷史 crash 實填一次，再用三個設計案例驗表：一筆未授權的關閉請求，應在允許那一欄被擋下；一次寫入成功但回覆遺失，應停在發生那一欄等回查；一次操作成功但事故沒有改善，應在完成那一欄判為未完成。三者得到不同的答案，表才算有用。

這三個時刻累積一季之後的續用與擴權，判準在延伸閱讀，本篇只留兩句：第十節的摩擦指標與紅線紀錄是它們的輸入，不是結論；擴權要分開「擴大給更多團隊用」與「開放某一項寫入操作」，營運篇第五節把前者放在 G2、後者放在個別審核與 G3，可靠度篇第五節替 G2 補了可靠度條件，兩件事不能用同一個閘門指。正文真正要算進去的是人工接手的成本：止血依據當下影響與可恢復性，修補依據重現和回歸，程序更新依據跨案例的得失，三者都要記下同事為了重新核對花了多少時間。把它們分清楚，團隊才看得出 agent 省下的是資料蒐集、重現環境準備還是修補時間，也才看得出它有沒有把成本藏進同事的重新核對裡。

回頭看 8 月那張邀請，我原本想知道的是，做 agent 的人已經走到哪裡。現在比較能說清楚帶回來的是什麼。午休貼文寫的是「governance 跟 agent logic 分離」，當天介面上我看到的只是一個 Blocked；回台北重查之後，才分清被限流的是哪一次請求、寫入的是模擬紀錄、晚間保存版和午休跑的是不是同一個版本。分離治理仍然必要，但它只回答了「允許」；效果與完成要另外確認，這就是三個問題分開問的理由。以那個假設的 crash 調查收尾，目前能說清楚的狀態是：開關已暫緩是遠端回查確認的目標狀態，還沒確認的是操作歸因，那筆逾時的請求是不是造成它的那一筆。這些工作之所以重要，是因為 agent 一旦真的能做事，錯誤就會留下需要有人接手的狀態。

我在《綠燈不是驗收》追問的是，一份通過檢查的程式改動，離可以放心交付還差什麼。東京的材料把這個問題往外推了一層：當一次任務跨過模型、工具、憑證與外部服務，接手者需要的證據也分散在那些地方。只把最後答案寫得更完整，仍可能讓他花很多時間重新確認究竟做過什麼。對正在處理事故的同事來說，一份坦白寫出「已確認影響範圍，尚未重現原因；草稿在這裡，開關的操作結果待查」的報告，比一句自信的完成更有幫助。他可以先處理使用者持續受影響的部分，再補上修補缺少的證據。

開源貢獻也從這裡開始：把結果未知的最小案例，或 skill 更新後漏掉的要求，帶著新舊內容與失敗案例回報給維護者，AAIF 的共同專案就多了一份真實使用中的模糊處。[27] Ola 在演講後段談到 interest group、working group 與提案過程。[9]

所以我會從一個經常發生、範圍明確的調查開始。讓 agent 交出同事真的接得下去的材料，觀察哪段工作變快、哪段仍要重新確認，再決定是否開放更多行動。下一篇要處理的，就是這份材料離開原來的 agent、交到另一個 agent 或另一個人手上時，哪些東西會一起過去，哪些必須重新查。那張邀請因此延續到了會議之外：把自己的觀察整理成可以被質疑與重用的內容，讓沒有到場的人能拿它檢查手邊的系統。
