# Agent 記住的經驗，下一次還能相信嗎？

> **TL;DR** — Agent 記得上次怎麼做，確實能省下重新說明與調查的時間。但「上次測試通過」一旦被整理成「這個系統可以升級」，原本的環境、版本與沒做完的事，就可能在下一次任務裡消失。本文只問一件事：一項經驗被換了環境、發現漏驗或正式更正之後，下一個 agent 還會不會沿用原結論？先分清一輪工作裡要讀的內容和要留給下次的經驗，再沿著東京的三場材料往下走：怎麼找回正確的對象、記憶被整理之後怎麼修正、結論怎麼接回可查核的觀察。我的判斷是：保存來源與適用條件、讓更正真的進入下一次檢索，以及讓系統承認仍需查證，缺任何一項，記憶就會替接手者作出沒有根據的決定。

## 一、照片留下了片刻，整理才把前後接起來

整理東京行的相簿時，先讓我停下來的是 9 月 10 日在會場拍下的一張投影片：研究系統提出主張，驗證者查核，論文只能從已驗證的主張產生。我把照片對回官方簡報第 40 頁，也順手讀了 Agent Memory 專案的記憶整理程式。程式裡，同一句事實再次被抽出，就會更新時間與計數。兩份材料放在一起，帶出一個值得追問的差別：一則記憶看起來更新了，支持它的證據卻未必增加。這個差別改變了我後面願意相信的範圍。

前兩篇先談 agent 怎麼使用工具，再談工作交給另一個 agent 時，接手者如何確認授權、進度與完成。這裡的 agent，是收到「評估能不能升級」這類任務後，自己決定先查哪些部署、再讀哪份相容性文件，並透過工具採取行動的系統。本篇再往後追一段，而且只問一件事：一項經驗被換了環境、發現漏驗或正式更正之後，下一個 agent 還會不會沿用原結論？

## 二、先分清這一輪要讀的，和要留給下次的

先用一位剛接手專案的同事來想。他桌上攤開的是這次要用的東西：今天的工單、翻到的幾頁 wiki、剛查到的結果，這是這次的工作集；櫃子裡供往後取用的紀錄，包括舊工單與整本 wiki，是外部儲存。舊工單可以成為下次的經驗，wiki 的某一頁也會進到這次的工作集；問題不在內容類型，而在從櫃子取進桌上時，怎麼確認它仍適用，以及桌上的臨時決定什麼時候該、什麼時候不該寫回櫃子。Agent 的記憶問題就是這件事。

桌上攤開的那些東西，對模型來說就是 context：每次被呼叫時能讀的輸入，有容量限制；同一個任務裡模型會被呼叫很多次，每次的 context 都要重新組裝。輸入量用 token 計算，模型把文字切成小單位計數，和字數不完全相同。容量帶來兩種限制：整份 log 佔的輸入空間遠大於一句摘要，舊的工具輸出會佔掉這次需要的位置；輸入愈長，模型找出並使用相關資訊的表現也可能下降，像「報表尚未驗收」明明還在輸入裡，回答卻漏用了它，Anthropic 去年 9 月的工程文章把後者稱為「context rot」，把 context 當成一種會耗盡的資源。文章建議的對策有三種。第一種先用例子說：一長串健康檢查的輸出（健康檢查是確認服務仍能回應的簡短請求，沒有證明報表真的產出），整理成「檢查通過，但報表尚未驗收」這樣的結果，保留架構決定、尚未解決的 bug 與實作細節，丟掉重複的工具輸出，這叫 compaction。第二種讓 agent 定期把筆記寫到 context 之外的檔案，需要時再讀回來。第三種只保留檔案路徑這類輕量的識別，真的需要時才取回內容。[1] 東京的 Agent Memory 場次用同一個區分開場：context 是每次呼叫組裝起來的注意力，記憶是跨工作階段的儲存；記憶只有在正確的部分回到 context 時才有用。[2]

這個區分讓本篇的問題變得具體。沿用第二篇的假設情境：平台團隊要評估 Kubernetes 從 1.30 升到 1.31。Kubernetes 協調應用程式在一組機器上運作，這組環境稱為叢集。假設團隊先在測試叢集完成一次演練，留下「升級成功」的摘要；過了一段時間，另一個 agent 被請去評估正式叢集，搜到了這份經驗。它可以少查哪些資料，又有哪些事情仍得重新確認？這是用來推導設計的例子，不是我的實際升級紀錄。

上次的結果至少還有三個條件：測的是哪個叢集、用了哪一版計畫，以及當時確認了哪些應用行為。正式環境可能使用不同的外掛，也執行著不同的服務與背景工作；由 Kubernetes 管理的這些程式，統稱工作負載。若摘要只剩下「可以升級」，省掉的正是下一個決策需要的資訊。反過來，如果把所有原始紀錄不加選擇地交給模型，接手者又得重新分辨重點與例外。

## 三、找回相似的紀錄，還需要知道它屬於誰

Neo4j 的 Stephen Chin 在〈CrabRAG: Why Automated Assistants Need Graph Memory, Not More Tokens〉用一隻反覆忘記事情的螃蟹助理介紹記憶問題。這場從檔案與相似度搜尋走向圖形資料，討論助理如何保留人物、物件與行動之間的關係（[官方議程](https://agntconmcpconjapan26.sched.com/event/2WZJf/crabrag-why-automated-assistants-need-graph-memory-not-more-tokens-stephen-chin-neo4j)、[官方簡報](https://hosted-files.sched.co/agntconmcpconjapan26/ea/CrabRAG__Graph_Memory_for_AI_Assistants_v0.6%20%28AGNTCon%20Japan%29.pdf)）。[3] 這一場回答第一件事：搜到的經驗，怎麼知道它屬於誰。

那隻螃蟹的毛病很容易懂：每次醒來都失憶，只記得硬碟上的檔案；第一百次對最好的朋友說「幸會」。他的診斷是，日誌記得「他們談過」，卻忘了誰對誰、為什麼，也就是關係。簡報第 6、8、9 頁描述他那套 OpenClaw 設定的做法：記憶是一疊像 README 那樣的純文字筆記（Markdown 檔），每次 session 開始全部重讀一次，所以 token 帳單很可觀。他的口號是「不要讀更多，要記得更好」。

### 相似性把材料找出來，關係把問題接起來

如果我問「上次升級遇到什麼問題」，用關鍵字找筆記很合理；但同一件事可能用不同說法記錄，問「升版失敗」要找回寫著「版本更新後無法啟動」的紀錄，關鍵字就對不上。向量搜尋處理的是這個需求：把文字表示成一組數字，搜尋時比較問題與筆記的表示是否接近。先取回資料，再讓模型參考這些資料回答，通常稱為檢索增強生成（RAG）。

簡報第 22 到 25 頁用三個小故事說明向量的限制：螃蟹想要一顆蘋果，相似度回傳了最像的東西，卻是另一種「Apple」；食物在兩步之外，單靠一次向量近鄰搜尋只給最近的東西，不給通往它的路徑；十個貝殼都是 99% 相似，但「我的」那一個靠的不是長相，而是「螃蟹擁有這個貝殼」這條關係。他的總結是「相似不等於相關，最近不等於正確」。[3]

Chin 用圖形資料處理這類關係。人、服務、叢集或計畫是節點，節點之間有具名的連線，例如「部署於」「依賴」或「使用此計畫驗證」。GraphRAG 把這類關係納入取回資料的過程；它是一種取回方法，不等於一定要另外買一套圖形資料庫。第 28 頁的例子是從助理找到朋友，再找到朋友喜歡的蛤蜊，最後找到蛤蜊出現的北礁；問題跨越幾段關係，查詢就沿著這幾段關係前進。

把升級案例的材料攤開來看。假設演練紀錄寫著：測試叢集的服務 A 透過儲存外掛 B 第 2 版寫出每晚的報表，升到 1.31 後，服務 A 的健康檢查回覆正常；健康檢查是確認程式仍能回應的簡短請求，沒有走到寫報表那一步。另一份正式叢集的盤點，也記著服務 A 使用 B 第 2 版；還有一份相容性文件，列出 B 第 2 版支援 1.31 所需的設定。

如果問題只是「正式叢集盤點記的是哪一版外掛」，明確的環境與版本欄位就夠用。把環境限定為正式叢集，就不會拿測試演練回答目前部署；查相容性文件時，再以外掛版本與目標版本篩選。這些已知欄位可以先排除錯誤對象，一張資料表或一份有版本的設定檔就足以處理。

接著問「服務 A 是否已找到相符的外掛相容性依據」，才需要把幾份材料接起來：先從正式叢集找到服務 A 實際使用的外掛，再找涵蓋同一外掛版本與設定的文件。文件中寫了 1.31，只完成其中一段比對；服務是否真的使用那個外掛、設定是否落在文件範圍內，還需要各自的來源。圖形資料能把這些對應保留下來，讓之後的查詢沿同一組關係繼續。

### 沿著路徑找答案，也沿著路徑找錯誤

在剛才的材料中，agent 可以列出「正式叢集 → 服務 A → B 第 2 版 → 對應 1.31 的相容性文件」。平台工程師接著查目前設定，卻發現正式叢集已改用 C 第 3 版，先前的盤點沒有更新。需要修正的是服務與外掛的那段關係；B 第 2 版的文件仍可能正確，卻已不能回答這次正式環境的問題。

更新後，這條查詢應停在「C 第 3 版與 1.31 的相容性資料待查」，並指出要補哪份文件與設定。這表示現有材料不足以確認相容性，尚不能推論 C 不相容；測試叢集先前使用 B 的演練，也仍是一次有效的歷史觀察。改掉一段關係，改變的是哪些材料可以支持眼前的判斷。

第 29 頁把可追查的路徑視為說明與稽核的基礎：答案本身就是解釋，走過的路徑就是引用，錯的時候可以追到是哪一條邊帶錯了路。這個例子讓我比較能理解它的實際用途：把一段看似合理的回答，拆成有來源、能逐段檢查的對應。但要真的完成這種查核，每段關係都需要回到建立它的依據。假如兩份摘要都抄自同一則錯誤筆記，畫出兩條路徑也沒有增加新的觀察。實作上，我會讓系統保留來源紀錄及取得時間，並區分「工具觀察到的關係」與「模型依文字推論的關係」，接手者才看得出下一步是直接查設定，還是先確認推論。

### 把時間與適用範圍放進關係裡

這也說明關係為什麼需要時間。正式叢集曾經使用 B 第 2 版，今天改用 C 第 3 版，兩個紀錄各自描述不同時期。若只把舊連線覆寫掉，歷史調查會失去線索；若全部當成目前有效，查詢又會同時得到互相衝突的答案。我會把「當時觀察到」與「目前仍有效」分開處理：每筆關係分開記錄觀察或有效的期間，和系統收錄它的時間，今天補登的舊部署紀錄仍屬於舊環境，較晚取得不代表較接近目前狀態；再由目前設定支持新的關係。針對今天的任務，查詢只用符合目標與有效期間的資料支持結論，歷史資料只能作為歷史依據；尚未確認是否改變的關係，結果應帶著待查的狀態。這是從簡報延伸的設計建議，不是 CrabRAG 已公布的完整資料規格。

選擇資料結構時，我會先看查詢是否反覆用到這些關係。只有服務 A 這組範圍固定的資料時，用明確識別碼連接資料表，再配合文字搜尋，就能走完剛才的比對。當團隊經常反過來問「B 的相容性文件改了，哪些服務的升級評估需要重看」，又要跨多個叢集、服務與版本追查，持續維護關係的價值才會增加。圖形表示並不免除維護：團隊仍須決定什麼算同一個服務、誰負責更新部署關係，以及查不到目前資料時如何回報。我的選擇條件是比較成本：同一批問題下，用既有資料表與識別碼處理，查詢要寫多複雜、關係更新要改幾處、查不到時要花多少人工核對；這些加起來超過圖形儲存的建置與維護成本，才值得換；而且換了儲存不會自動取得目前的部署，關係更新的延遲與人工補查都要算進去。圖形還有一個限制：查詢路徑只能解釋已記錄的關係，不能證明沒有漏掉關係，盤點不完整時，答案必須交代涵蓋範圍。

對象找對了，整理後的敘述仍可能把觀察寫成更大的結論。下一場談記憶被整理之後，更正要走到哪裡。

**圖形記憶最有用的地方，是讓經驗連回明確的對象與可追查的關係，並讓接手者知道哪一段仍需更新或查證。**

## 四、記憶會被整理，也就需要被修正

Rohit Ghumare 在〈Architecture Behind the Most Viral Agent Memory Open Source Project〉從「新工作階段忘記昨天的決定」開場，介紹 Agent Memory 如何擷取事件、整理記憶與取回資料。簡報也列出 Vinuja Khatode，並直接展示記憶分類、搜尋與生命週期的程式碼（[官方議程](https://agntconmcpconjapan26.sched.com/event/2QlDp/architecture-behind-the-most-viral-agent-memory-open-source-project-rohit-ghumare-devrel-as-service)、[官方簡報](https://hosted-files.sched.co/agntconmcpconjapan26/fe/agentmemory-agntcon-mcpcon-opening.pptx)、[專案程式庫](https://github.com/rohitg00/agentmemory)）。[2] 這一場回答第二件事：記憶被整理之後，後來的更正要走到哪裡。

簡報第 3 頁的開場很貼近日常：同一個 repo，新開一個工作階段，請 agent「繼續昨天的身分驗證重構」。它可以檢視程式，卻答不出昨天決定了什麼、否決了哪個方案、還有什麼沒做完。「程式在那裡，連續性不在。」

昨天的決定要在今天回來，先要以合適的記憶類型保存、讓搜尋找得到；整理成事實之後，錯了還要改得掉。〈先分清要保存的經驗，以及這一輪要讀的內容〉用升級例子對照四種記憶，再看 BM25、向量搜尋與 RRF 的排序，為什麼決定不了哪一份判定仍有效；〈反覆出現的說法，還需要新的查核〉讀 Agent Memory 的整理程式，看計數、時間與信心值為什麼不代表新的證據；〈更新與遺忘，要讓下一次檢索真的不同〉談取代與刪除怎麼走到搜尋入口，以及相似度清理為什麼不等於矛盾判定。已熟悉記憶分類與混合搜尋的讀者，可以從整理程式那一小節讀起。

### 反覆出現的說法，還需要新的查核

搜尋只能找既有紀錄；但摘要如何被升格成事實，決定了被找到的究竟是什麼。在啟用整理流程、設定了模型供應商的配置裡，系統累積至少五份工作摘要後，會由模型從中抽出事實，讓未來不用重讀每個過程。這一步很有吸引力，因為「我上次怎麼查到的」終於可以整理成「這個專案有哪些已知條件」。問題在於，整理過程同樣可能遺失限定範圍，或把前一次推論當成這一次的觀察。摘要省下讀取成本，也丟掉細節：如果「報表驗過」和「報表沒驗」都被壓成同一句「驗收通過」，下游光靠摘要就恢復不了這個差別。事實可以壓縮，必要的限定條件必須留下，或者保留能取回它們的來源入口；省下的是幾行文字，之後補驗、追問與撤回的查核成本全都加回來。

簡報第 15 頁展示的實作很具體：新抽出的事實若與既有文字相同，只忽略大小寫，就增加名為 `accessCount` 的計數（在這個分支裡它是再次抽取的次數，不是被查核的次數）、更新時間，並讓 `confidence`（抽取模型自報的信心，不是正確機率，也不是人工查核的結果）取既有值與新值中較高者；即使沒有新的觀察，重新處理同一批摘要也會刷新這些欄位。更直接的問題在對象：同一句文字不等於同一項事實，「服務 A 可以升到 1.31」在測試叢集與正式叢集是兩件事，合併前必須確認主體與適用範圍；這版程式有沒有其他外層保護，本文沒有追查。我核對了對應的[固定版本程式碼](https://github.com/rohitg00/agentmemory/blob/70517d2bdf302a0aed11ca470151ee854e74c678/src/functions/consolidation-pipeline.ts)。這個欄位是負責抽取的模型自己給出的信心值，沒有另一個外部查核者，也不是對外部事實重新量測得到的正確率；簡報自己也寫，這個比對是「不分大小寫的文字相等」。程式裡還有一處更直接的限制：新事實的來源欄位填入的是這一批近期摘要的全部工作階段識別；同一句事實再次出現時，這個分支也不補入新的來源關聯。[5] 列出來源場次，不等於知道哪一段觀察支持哪一個事實；要讓後面「沿引用關係更正」有起點，就得保存逐項的支持關係。這些還是不同的資料路徑；semantic、memories 與 observations 是這個專案三個不同的儲存集合，和前面四種記憶分類不是同一套名字：整理程式抽出的事實存在 semantic 集合，下一段的自動遺忘處理的是 memories 集合，混合搜尋從 observations 與 memories 取回。本文核對的是各自欄位的語意，沒有追到它們在檢索結果裡的下游影響，結論只到「欄位不能代表新增證據」。最值得追的是撤回路徑：自動遺忘把舊紀錄標成不是最新，但已保存的混合搜尋程式在補充結果時沒有直接檢查這個欄位；外層有沒有補上保護，本文判定不了，這正是導入時要先驗的缺口。

假設「這個系統可以升級」最初來自一次範圍過大的摘要，後面幾個工作階段又引用它。當整理程序再次抽出同一句話，計數會增加，時間也會變新。這裡的計數更新來自再次抽取，不一定代表某人實際讀過，更沒有要求重新查詢正式叢集。真正支持結論的可能仍只有最早那次測試演練；把這些欄位當成獨立查核的次數與日期，就會高估這份記憶的根據。這正是開場那張照片帶出的差別：一則記憶看起來更新了，證據卻沒有增加。

這個差別會影響記憶該如何呈現。我希望接手的人能分辨最近被讀取的時間、最近被修改的時間，以及最近取得外部證據的時間。常用的經驗可以提高檢索優先順序；要擴大它適用的環境，則應新增對應環境的證據。同樣地，三種搜尋方法都找回同一則筆記，表示這則筆記與查詢有多種關聯，它仍可能只有一個來源。RRF 讓資料更容易被找到，真實性則要回到產生這份資料的觀察與方法。

### 更新與遺忘，要讓下一次檢索真的不同

第 28 頁把記憶的後續處理整理成強化、取代、衰減與遺忘：再次被看到或取回就加強；新版本取代舊版本；久未使用就降低權重；到期或低價值就刪除。它也提醒，來源連結與版本歷史幫助檢視更新，刪除與舊快照則需要另外的保存規則。

Agent Memory 簡報第 28 頁：記憶可以被強化、由新版本取代、降低權重或刪除；來源與版本歷史也需要自己的保存規則。來源：官方 PPTX 的完整頁面轉圖。


例如，正式叢集的服務 A 已從 B 第 2 版改用 C 第 3 版。只在資料庫新增另一句「現在改用 C」，下次搜尋仍可能同時找回 B 與 C；若檢索另以使用次數加權，舊紀錄還可能排在前面，不過已保存的混合搜尋程式用的是名次、權重與多路一致的加分，沒有直接用使用次數，這是假設的風險，不是程式觀察。更新流程需要讓舊內容退出「目前有效」的候選集合，同時保留必要的歷史關聯；為了回溯而取回舊紀錄時，也要帶著已被取代的狀態。

更新時還有一條捷徑值得看，它也說明使用頻率與建立時間都不能裁決來源衝突：清理程式只比較共用同一個概念標籤的候選，把內容按空白切詞、丟掉兩個字元以下的詞，詞集合的相似度超過 0.9 時，把建立時間較早的那一則標成不是最新。[5] 這不是語意上的矛盾判定：兩則各有十幾個詞的英文筆記，新的那則只多了一個環境名稱，集合相似度就會過線；把一個詞換成另一個詞，要更長的句子才會過線；而新多或換掉的那個詞不一定帶著新的證據，可能只是重貼舊內容。反過來，中文句子沒有空白，整句會被當成一個詞，完全相同的句子相似度是 1，不同的句子接近 0，它不能有效辨識不同中文句子的近似與矛盾；而且它只比較最新候選中的前 1,000 筆。簡報描述的是生命週期，這版程式用的是捷徑，我建議的更正規則是第三種：先保留差異，交給能補資料的人或系統，不憑出現次數或建立時間選邊。

刪除也要走到檢索入口。先建立問題：正文已經刪了，搜尋目錄還留著舊字，先前匯出的副本也還在。搜尋目錄就是索引，為了快速找到內容另外維護的一份資料結構；簡報第 29 頁與對應的[到期清理程式](https://github.com/rohitg00/agentmemory/blob/70517d2bdf302a0aed11ca470151ee854e74c678/src/functions/auto-forget.ts)，同時處理記憶資料與搜尋索引。[5] 如果只刪主紀錄，索引、已產生的摘要或匯出的舊快照仍可能保留內容。團隊要先決定哪些副本需要刪除、哪些歷史只能由特定角色查閱，再檢查每個入口是否符合這個決定。

也不宜把「很久沒有用」直接當成「已經不重要」；可靠度篇第二節替每條規則記 owner 與到期日，把到期當成重新檢視的提醒而不是刪除的理由，放到自動整理的記憶上，新增的是這條人工檢視責任要怎麼落到記憶與它的副本。低頻的事故教訓可能只在下一次異常時才有價值；一次性的維護核准則即使常被引用，也有明確的任務範圍與時效。舊記憶裡的「已核准」只作歷史紀錄，不能成為本次操作的權限，這是第二篇的結論放到記憶層。

回到那則「這個系統可以升級」的假設記憶。計數、時間、信心值與來源欄位，記下的都是它被整理的經過；這句話當初能不能從一次測試演練寫出來，這些欄位都不會告訴我們。

**記憶的整理應讓下一次工作少走冤枉路，同時保留更正的入口，讓使用次數、資料新舊與外部查核各自承擔清楚的角色。**

## 五、把記憶中的結論，接回可以查核的主張

NexaScience／RIKEN 的 Wataru Kumagai 在〈Towards Trustworthy Autonomous Research〉把問題放到自動化研究：當系統能搜尋文獻、提出假設、執行實驗並寫出論文，如何確認最後的研究主張真的有依據？他提出在研究過程中查核主張的設計，並介紹開源專案 AIRAS（[官方議程](https://agntconmcpconjapan26.sched.com/event/2RqMK/towards-trustworthy-autonomous-research-wataru-kumagai-nexascienceriken)、[官方簡報](https://hosted-files.sched.co/agntconmcpconjapan26/63/AGNT-Con_2026_v7.pdf)、[專案程式庫](https://github.com/airas-org/airas)）。[6] 這一場回答第三件事：一句被記住的結論，到底看到了什麼。

這場看似離記憶較遠，其實接住了前一節尚未回答的事：來源與版本都留下來之後，要用什麼方式決定一個說法值得沿用？研究的產出會成為別人的知識來源，agent 的工作摘要也會進入下一輪的 context。兩者都需要避免在整理過程中，讓尚待驗證的說法逐漸取得「已知事實」的地位。

這一節沿著一個主張從提出、被撤回，一路走到更正傳進下一份摘要。〈在結果出現前，先決定怎樣才算有支持〉看簡報為什麼要先定驗證方式、再產生主張，並把它放回「升級成功」該怎麼定義；〈觀察沒有改變，結論仍可能需要撤回〉用研究系統、資料庫與 verifier 的分工，走一遍那則升級記憶漏驗報表、被撤回的經過；〈讓更正沿引用關係，傳到下一份摘要〉把更正填成三筆紀錄，定義「更正完成」的最小契約，也處理撤回與重建摘要交錯時，舊結論會不會復活。

### 在結果出現前，先決定怎樣才算有支持

簡報第 23、24 頁以「我們的方法在每個 benchmark 都超越對照方法」為例，指出審閱者還需要確認比較是否公平、結果是否可重現，以及是否只呈現有利的結果。Benchmark 是以事先設計的資料與任務比較方法表現；若兩種方法取得的資料或資源不同，表面的分數差距就可能包含這些條件造成的影響。

第 35 頁接著把查核方式移到研究開始之前。簡報把事後選擇驗證方式，與事前定義驗證方式作對比：他主張先決定怎麼驗證，再產生可驗證的主張。否則等結果出來才選擇指標與解釋，容易讓每一種結果都找到一個看似成功的說法。預先定義能限制事後改口，也可能漏掉有價值的新發現。我的做法是：原主張照原標準判定；新發現另立主張與驗證，不回改原紀錄。判準改版有成本：哪些舊判定可以用原觀察重評、哪些因為缺少必要的量測必須重新執行，要先分清，版本都保存才會變成維護決策。

Wataru Kumagai／NexaScience、RIKEN，簡報第 35 頁：在產生結果之前，先決定如何驗證主張。來源：官方簡報。


升級演練同樣需要這個順序。「升級成功」究竟指節點顯示目標版本、服務重新啟動，還是團隊要求的業務操作也完成了？若事前只要求版本達標，記憶就應保留這個範圍；若要支持正式環境的採用決定，服務負責人還需要定義哪些行為不能受影響。這裡判對錯的依據，就是服務負責人那份驗收清單：版本達標、健康檢查、每晚報表三項；我在《同一份規格，跑十次》的契約篇把這種依據叫 oracle。那篇還指出第三個盲點：產出者與檢查者可能共享同一個誤解，所以驗收器要先用已知的正反案例驗過。記憶整理應把結論與它的 oracle 一併保留：記憶不只保存「通過」，也保存依哪版要求、由哪版驗收器判定通過。事先定義要求也不是禁止後續學習：演練途中發現原本沒想到的相容性問題，當然值得新增檢查；關鍵是保留變更前的要求、為什麼改，以及哪一次結果使用新要求。

### 觀察沒有改變，結論仍可能需要撤回

第 36 到 40 頁把架構分成研究系統、研究資料庫與 verifier：研究系統提出主張及材料，資料庫保留紀錄，verifier 是依約定規則、拿指定材料查核主張的那一方，查完留下判定。三條原則是：每個主張都說明它主張什麼、怎麼驗證；每個主張都在研究系統之外驗證，研究系統不能影響 verifier；每篇論文只能從資料庫裡已驗證的主張產生。放到團隊實作，我還會要求產出者不能改 verifier 的規則與結果，而且規則與權限由誰維護要指定，否則它只是多放一個 agent。

把這個分工帶回那則「升級成功」的假設記憶。原始執行紀錄留下兩項觀察：測試叢集的節點版本已到 1.31，服務 A 的健康檢查回覆正常。整理者卻寫成「服務 A 在 1.31 的必要功能均已通過驗收」，後來的計畫又將它濃縮為「服務 A 可以升到 1.31」。每次濃縮都讓文字更短，也讓原本有限的觀察承擔了更大的結論。

稍後，服務負責人對照事前的驗收清單與演練設定，發現清單還要求每晚的報表工作完成，並把產出寫到指定位置。這種按時間啟動的背景工作，在演練期間設為暫停，所以沒有取得那次執行的報表結果。健康檢查仍可能正常，因為它只確認服務能回應，沒有走過產生與儲存報表的流程。這和《綠燈不是驗收》[測試篇](https://medium.com/p/b01055139451)第七節記錄的實例是同一種驗收缺口：測試全綠，replay 卻從未執行。那篇有實作輸出可對照；本篇新增的問題是，發現漏驗之後，錯誤的成功摘要怎麼退出下一輪依據，而這部分目前只有靜態核對與測試設計，至少還缺一份更正前後的儲存、工具回傳、context 與回答的對照。

這時應撤回「必要功能均已通過」的判定，改成「測試叢集已到 1.31，服務 A 健康檢查通過；報表工作尚未驗收」。節點版本與健康檢查的原始觀察仍然成立，原報表要求也沒有改變；改變的是我們知道當時少驗了什麼。這份更正尚未證明報表工作與 1.31 不相容，後續需要的是補驗，並依結果重新判定。平台工程師保留執行紀錄與當時設定，服務負責人指出漏掉的必要行為，再由負責驗收的人核對更正。提出成功摘要的 agent 可以協助整理材料，卻不能自行把報表從要求裡刪掉。

### 讓更正沿引用關係，傳到下一份摘要

在我核對的 AIRAS [固定版本說明](https://github.com/airas-org/airas/blob/e1c37b5600acb4d717111b7a5789a2144a184959/README.md)裡，這個方向具體落在實驗前提交的主張、只增加新紀錄的研究檔案，以及從執行結果填入論文的數字。README 描述的流程還有兩道自動檢查：一道核對研究紀錄，一道核對論文裡的數字是否來自已驗證的主張；它們放在持續整合（CI）裡，主分支則設成受保護分支，指定的檢查沒過，變更就進不去。README 描述的是分開查核紀錄與論文數值的設計；本文沒有驗證實際部署中誰能改檢查、誰有例外權限、有沒有繞過路徑，而且 README 自己也列出 benchmark hacking、測試資料洩漏進開發流程與設計偏離仍可能通過閘門。數值可追溯、判定符合既定標準、研究方法有效，是三件事。[7]

我會借用這種主張、紀錄與查核的分工來設計記憶更正。用剛才的報表案例填三筆紀錄，全部是假設資料；要求版本自始就是含每晚報表的 v3，錯的是判定，不是要求：

驗收程式若是漏檢，另記驗收器的版本；真正新增報表要求的情況是另一個案例，留到本節最後。一眼要看出的是：觀察保留，錯判撤回，衍生摘要失效。還要分清兩種權限：任何拿得出證據的人都可以暫停採用一個可疑的舊結論，但讓新結論成為有效判定的是服務負責人；verifier 分離之後，瓶頸可能轉到更正核准的佇列，所以暫停採用要有人隨時能做，正式核准才排隊。只修改原紀錄的文字，無法自動修好已被複製到其他地方的結論。

「更正完成」也要定義，否則這套設計只驗得了順序正常的更正。最小契約是：更正指向固定的判定識別；資料服務每次查詢都核對目前有效的版本；衍生摘要完成重建前不得作為有效依據，而不是只靠一個「待更新」標記，期待每個搜尋入口都看得懂它；更正生效有一個可觀察的時點。還有一個會讓舊結論復活的順序：程序甲拿 J-17 開始重建 P-9，程序乙完成撤回，程序甲稍後才把依據 J-17 的摘要寫回去。每次查詢核對版本，不等於寫回時也核對依據；就算發布前再查一次，查完到寫入之間仍可能有人撤回。所以依據版本的核對與摘要的發布要綁成同一次不可分割的提交，版本不符就拒絕寫入，中斷後的重試也不得恢復已撤回的狀態。更正生效的承諾也要寫明：生效時點之後的新查詢不得再取得舊結論；已經載入舊 context、稍後才輸出的回答，則要帶著它依據的判定版本，讓事後能認出來。主紀錄已撤回、索引尚未更新的那段時間，攔住舊摘要的責任在資料服務的查詢與寫入這一層，不在模型。

因此，下一次問起這場演練時，取回流程至少應帶回目前的更正、可追查的原始觀察，以及尚缺報表驗收的說明。舊摘要如果一併出現，也應連到更正，讓接手者能理解為什麼前一次說成功、現在卻要補驗。前一節討論的更新與索引在這裡有了明確目的：讓同一個問題得到符合目前證據範圍的回答。這套記憶維護方式是本文從 AIRAS 分工延伸的設計。

資料能一路對回來源之後，還有方法本身要審閱。AIRAS 的 roadmap 明確列出仍在處理的問題：實驗程式偏離設計、利用評測方式取得高分，以及讓本應只用於測試的資料提前進入方法開發。[7] 數字可以忠實來自一次執行，那次執行仍可能問錯問題。回到報表案例，若團隊原先的要求只寫「健康檢查正常」，自動核對可以確認紀錄符合這條要求，卻無從自行知道報表也應納入驗收。前面的案例是漏做既定檢查，這裡則是檢查設計本身不完整；把兩種更正分清楚，才知道下一步該補執行，還是先重寫判準。

三筆紀錄是假設資料，更正契約也還只是設計。它們有沒有用，要等一個沒參與更正的 agent，在新的工作階段裡問起這場演練，才看得出來。

**記憶中的結論被修正時，仍成立的觀察、撤回的理由與尚缺的驗證，都應一起進入下一次取回的材料。**

## 六、我會怎麼驗收下一次的記憶

三場材料讀到這裡，我想驗收的已經不是「重開之後還記不記得」。更有用的問題是：**當經驗適用、過期或被更正時，下一個 agent 的判斷會不會跟著改變，而且能說明依據？**

我會先把驗收限在唯讀評估：指定一個模擬叢集，要求 agent 說明是否已有足夠資料提出升級建議、哪些項目待查，以及引用了什麼證據。這一階段沒有變更叢集的工具權限。平台工程師準備可查詢的版本、外掛與工作負載資料，服務負責人先定義評估要求，再由另一位驗收者核對結果；我在《綠燈不是驗收》[Review 篇](https://medium.com/p/ccbf0cbe2691)第一節寫過產出超過審閱能力時要重新分配誰讀什麼；沿用這個原則，本篇新增的分工是：平台工程師核對觀察，服務負責人核准撤回，記憶系統的維護者負責取回流程，對應〈[組織篇](https://medium.com/p/9d9353ef7f3a)〉第二節平台與 domain team 的分工。以下是測試設計，尚未執行，也不是生產環境的操作手冊。

驗收依先後分成三個小節。〈先確認記憶省下的是重複調查，不是必要查核〉比較有無記憶的正常對照，再把同一份成功摘要改成另一個測試叢集留下的，並說明每次試行為什麼要還原同一份記憶快照；〈更正有沒有走到回答，要一層一層查〉把前一節的更正案例放進來，連同撤回與寫回的交錯，說明失敗時該從儲存、搜尋、context 還是解讀去找，再用一張表整理七種情況下接手者該有的行為，並把刪除與權限分開測；〈哪些結果支持擴大使用記憶〉談怎麼避免獎勵一律拒絕、每個案例要交出哪些紀錄、驗收卡怎麼填，以及題目何時失去評估用途，最後是從診斷 pilot 到擴大使用的三段出口。

### 先確認記憶省下的是重複調查，不是必要查核

先做一組有用的正常對照。同一個任務與目前環境，一次不提供歷史記憶，一次提供對象正確、來源可查、而且仍適用的演練紀錄。驗收者事先依評估要求列出哪些條件可以沿用、哪些仍要查詢，作為兩次結果的共同判準。兩次都應取得足夠的目前證據；有記憶的版本可以利用既有查核經過，較快找到需要查的相容性條件。記錄搜尋與工具查詢次數，以及負責人需要補問的事項，才知道省下的是重複調查，還是跳過了必要查核。

接著保留同一份成功摘要，只把它所屬的環境改成另一個測試叢集。目前任務仍然指向正式叢集，外部資料也維持一致。預期結果是把舊經驗用來提出檢查方向，再查明本次環境；不能直接把別處成功當成本次已完成的相容性確認。

每次試行都還原到同一份測試起始資料，連搜尋目錄也一起還原，也就是固定記憶快照與索引版本：固定目前環境與資料權限，並明訂這次允不允許自動寫入。測取回時固定寫入結果；測更新流程時才開放對應的寫入。新工作階段不等於新的記憶狀態，前一次查詢若增加了計數、留下摘要或觸發整理，後一次就不再只差指定的更正，失敗與改善都難歸因。

### 更正有沒有走到回答，要一層一層查

更正案例就沿用前一節的演練紀錄。先存入節點版本與健康檢查結果、誤寫成「必要功能均已通過」的判定，以及引用它的升級計畫摘要；接著提供原驗收清單與報表排程暫停的設定，依正常流程加入更正。更新前後都分別開兩個新工作階段，一個問「服務 A 上次的 1.31 演練驗收了哪些必要功能？」另一個問「先前的升級成功，是否已包含每晚報表的驗收？」驗收者事先保留預期結果，被測 agent 則從正常的查詢入口取得材料，這樣才能觀察更正是否找得到，而不是在同一段對話裡直接告訴它新答案。另外安排一次交錯：在撤回完成前先啟動一個重建 P-9 的程序，撤回完成後讓它寫回，檢查寫回有沒有被擋下。

更新後，取回的內容應包含範圍較小的有效判定，以及能追到原始觀察、報表要求與暫停設定的來源。舊判定或計畫摘要若仍被取回，必須看得出已撤回或待更新。合理的回答應說明版本與健康檢查已確認、報表尚未驗收，請服務負責人補齊報表執行及產出的結果；不能再說必要功能全數通過，也不能改稱報表已知不相容。驗收者再把更正後的儲存紀錄、工具回傳、實際載入模型的內容，以及最終回答排在一起，失敗才有可定位的地方：

- 儲存紀錄仍把舊判定列為有效，或沒有標出受影響的計畫摘要，先修正更新流程與引用關係。
- 儲存狀態正確，搜尋卻只送回舊摘要，檢查索引與取回規則；工具已送回更正，工作輸入卻省略了它，則檢查 context 的組裝與摘要步驟。
- 更正與來源已進入工作輸入，回答仍說全部驗收通過，問題才落到如何解讀證據與產生結論。

### 哪些結果支持擴大使用記憶

這些測試也要避免獎勵一律拒絕。材料完整且符合要求時，agent 應能提出有來源的評估；缺資料時，則保留未知並把待查事項交代清楚。我會分開統計兩種結果：充分資料下是否完成應有的工作，以及不足資料下是否錯誤下結論。再看必要資訊有沒有被找回、舊結論是否仍被沿用，以及人的查核時間是否減少，不把它們壓成一個「記憶準確率」。每個案例交出去的是一筆紀錄：案例、預期判斷、儲存狀態、工具回傳、實際載入的 context、最終回答、人工查核時間、失敗的負責人；摘要重建與關係維護的成本另計，少查幾次工具不必然省時。最小任務的驗收卡可以直接填出來：

若要比較不同記憶方案，固定任務、模型、可用工具與目前環境，先只改記憶材料或取回方式；有隨機性的執行則重複多次並保留個別結果。這延續〈[綠燈不是驗收](https://medium.com/p/582f24223eea)〉的問題：檢查取得了哪些證據，這些證據又支持團隊交出多少工作？

題目什麼時候失去評估用途，是另外兩條界線。第一條從《同一份規格，跑十次》的變異篇帶過來：這批驗收題目一旦用來調整記憶系統，就不能再當成沒看過答案的保留題；那篇第八節分了三種重查：改了量尺就檢查 grader，改了產物就檢查新候選，改了方法就檢查交付方法；本篇新增一種，用既有觀察重評舊判定，因為記憶裡的判定可以在不重跑任務的情況下被撤回。第二條是 Anthropic 的 eval 文章說的飽和：一組全過的題目只能擋回歸，提供不了改善的訊號，但這只限於已經全過的成功指標，查核時間與成本仍然看得出差異。[8] 兩條界線不是同一件事。驗收裡若有用模型打分的步驟，沿用第一篇 PagerDuty 對評分器校準的要求；本篇再把三種材料分開：沒有拿來調整系統的題目（保留題，例如一組新的叢集盤點問答）、人工已判好的回答（用來校準評分器）、agent 可查的部署與演練紀錄（證據材料）。本篇專屬的校準對照至少兩條：「尚未驗收」不能判成「不相容」；「有更正連結」不能判成「舊結論已退出有效候選」。

這些情境是診斷用的 pilot，能找出缺陷，不能估計真實工作裡的錯誤率與收益。出口因此分三段：更正仍抵達不了回答，記憶就停在協助找資料與整理待查事項，衝突判讀交給負責人；診斷案例通過後，進入保留人工核准的小範圍 trial，範圍限於這一類升級評估，每次採用由服務負責人核准，更正抵達不了回答就停止，負責人是記憶系統的維護者，並記錄實際的接手與維護成本；取得代表性工作中的收益與維護證據後，才討論擴大。這是《同一份規格，跑十次》總論第十節的採用邊界放到記憶上。

到這裡，驗收設計能指出更正停在哪一層。但這是一整套測試，團隊可以先從哪裡開始？

## 七、讓經驗留下來，也讓下一個人有理由修正它

這次核對改變了我願意相信的範圍。會場照片上，論文只能從已驗證的主張產生；後來讀到的記憶程式裡，同一句話卻可以因為再次被整理而變得更新、更常出現。所以我會先挑一項團隊常重複調查的小任務，把最近一次經驗連回原始觀察與驗收要求，再安排一次有更正的接手。接手後要改變的決定只有一個：舊的成功摘要不能再當放行依據；報表補驗與正式環境的相容性確認列為放行的前置條件，排程與剩餘風險由權責人決定。還缺的實測證據也要說清楚：一份更正前後的儲存、工具回傳、context 與回答對照，本文只有靜態核對與測試設計。

這篇文章本身也應接受同樣的檢查。本文的程式觀察對應固定版本，延伸案例則等待實際驗收；未來若來源或結果改變，引用它的敘述也需要一起調整。我希望下一個讀者拿到這些材料時，能看見哪些判斷仍有根據、哪些已被更正，以及自己可以從哪裡繼續查。讓更正後的經驗抵達下一個人，這趟東京行帶回來的材料，才接得上下一段工作。
